# 指标经验：设计与评测协议（草案）

状态：仅设计，尚未实现，未运行任何实验。本协议在实现和运行前固定；运行后修改须注明日期与原因。

修订记录：

- 2026-09-29：增加“维护方式对照”。原因：审稿式质疑指出，“守护”一节描述的流程（依赖表变化后重查该口径的全部条件，通过后刷新依赖版本）就是“标脏 + 首次使用时重验”，把它与“写入即删除”比较只能说明保留定义比删除定义好。现在把它作为定义级对照组，另设条件级维护，并区分短暂待验证、正式撤销与重新提炼。

## 要检验的问题

> 从成功轨迹提炼的指标口径，在跨 Agent 复用后，能否依靠显式依赖、版本检查和受限修复，降低已建模 ETL 变化造成的静默错误。

拆成三个互不混合的子问题：

1. **探索成本**：所有组都已知口径时，指标经验能省多少 LLM 轮数、token 和数据库开销。
2. **口径传递**：已确认的口径能否传给没有接触过该指标的 Agent 和未见任务。
3. **失效管理**：数据变化后，过期经验是否被阻断，有效经验是否被误撤销。

本协议不支持以下结论：指标口径优于 SQL 模板（没有模板对照组）；一般 SQL 推理能力提升；其他方案做不到同样的事。

## 数据结构

经验库新增 `Content::Metric`，`Status` 新增 `Candidate`。`Candidate` 和 `Revoked` 在查找时都按未命中处理，不对外提供。

```rust
pub struct Metric {
    pub name: String,
    pub aliases: Vec<String>,
    pub definition: String,                 // 口径的自然语言说明
    pub fact: String,
    pub measure: String,                    // 聚合表达式，只能引用 fact 与 joins 涉及表的列
    pub grain: Vec<String>,                 // fact 上“一行一条业务记录”的键
    pub time: Option<TimeSpec>,
    pub joins: Vec<JoinRef>,
    pub filters: BTreeMap<String, String>,  // 仅口径必需条件，不含题目参数
    pub empty: EmptyRule,                   // 无输入行时：Null / Zero / 未约定
    pub caveats: Vec<String>,
    pub examples: Vec<Example>,             // 题面与 SQL，不含结果值
    pub basis: Basis,                       // 口径依据
}

pub struct TimeSpec {
    pub role: String,      // 时间角色，如“销售日”“退货日”
    pub fact_col: String,
    pub dim: String,
    pub dim_col: String,
    pub grain: String,     // day / month / year
}

pub struct JoinRef {
    pub key: String,                        // 经验库中关联条目的 key
    pub left: String,                       // 多侧
    pub right: String,                      // 一侧
    pub on: On,
    pub filters: BTreeMap<String, String>,
    pub cardinality: String,
    pub loss_ratio: f64,
    pub revision: u32,                      // 引用时关联条目的修订号
}

pub enum Basis {
    ExplicitQuestion { task: String },      // 学习题面明确给出定义
    Glossary { source: String },            // 已有业务定义
    Confirmed { by: String },               // 业务方确认
    None,
}
```

验证证据单独保存，不随 `find_metric` 返回：来源任务、判题结果、轨迹发生时的表版本、结构化结果值、各门槛的通过记录。

约束：

- `filters` 不得包含时间维度表的列，也不得包含题目参数里的字面量。年月、排名个数属于查询，不属于口径。
- `time` 必须写明时间角色和粒度。只写两列相等不够。
- `JoinRef` 记录方向、基数、过滤和丢行比例。关联能执行不等于不放大聚合。
- `empty` 由口径依据决定。PostgreSQL 的 `SUM` 在无输入行时返回 `NULL`，依据未说明时记为未约定，不默认当作零。

## 成功的认定

以下三件事分开记录，只有第三件可以作为晋升依据：

| 事实 | 来源 | 能否作为依据 |
|---|---|---|
| Agent 声明完成 | `final_answer` | 否 |
| SQL 执行成功 | `run_sql` 返回 | 否 |
| 任务被判定成功 | 独立判题 | 是 |

实验中，独立判题指学习集的参考 SQL 经只读直连在同一数据快照上执行，按结构化结果比较。**留出题的参考答案不得进入提炼、晋升或修复。**

实验之外没有这个判题器。本版本不解决这个问题：没有独立判定的轨迹只能停在 `Candidate`。

## 记录

中间层按任务记录计算链：每次 `run_sql` 的 SQL、当时的表版本、结构化结果、是否被拦下。`final_answer` 增加两个可选字段：

- `used`：参与最终答案的 SQL 序号。
- `derivation`：后处理的算术表达式，引用 `r1..rn`（第 n 条 SQL 结果的首个单元格），只允许加减乘除和括号。

不强制客户端用一条 SQL 作答。验证器按 `derivation` 重算，结果与答案不一致或无法解析的轨迹不晋升。不晋升的比例单独报告。

## 提炼

由 adapter 侧 LLM 离线执行，不在请求路径上。

- 输入：处理后的题面、计算链中的 SQL 与 `derivation`、被拦下的记录、元数据（列、注释、已验证关联、粒度条目）。
- 不输入：业务行、结果值。
- 输出：符合上述结构的 JSON。格式错误可重试，重试次数固定。所有尝试的 token 与耗时计入提炼成本。

## 晋升门槛

全部为确定性检查，不调用 LLM。任一项不通过即停在 `Candidate`，原因记入证据。

| 编号 | 检查 | 说明 |
|---|---|---|
| G1 | 有口径依据 | `basis` 不为 `None` |
| G2 | 来源任务判定成功 | 见“成功的认定” |
| G3 | 静态检查 | 表列存在；`measure` 只引用允许的列；关联属于已验证路径且方向、基数、过滤一致；`filters` 包含必需的粒度过滤且满足上述约束 |
| G4 | 粒度 | `KeyUnique(fact, grain, 过滤)` 在当前快照上通过 |
| G5 | SQL 审查 | 示例 SQL 通过 `review_sql` |
| G6 | 示例复现 | 当前表版本与轨迹发生时相同；示例 SQL 的结构化结果与判定成功的答案相等 |
| G7 | 字段复现 | 由 `fact`、`measure`、`time`、`joins`、`filters` 编译出的规范 SQL，按来源题参数执行，结果与 G6 相等 |

G7 检查的是其他 Agent 实际读到的字段，而不只是示例 SQL。提炼器漏掉过滤或把参数写进口径时，G7 应当失败。

表版本已变化时 G6 无法判断，候选保持 `Candidate`，不算失败。

多个 Agent 得出相同口径只记作佐证，不改变状态。两个 Agent 一致作为门槛留到后续消融。

## 提供

新增工具 `find_metric(query, tables?)`，按名称和别名的子串以及涉及的表匹配。不用向量检索，不调用 LLM。

- 返回：key、修订号、依赖的表版本、口径字段、注意事项、示例（不含结果值）。
- 同一别名对应多个口径时全部返回并标明有歧义。
- 没有匹配时明确返回没有。
- 发布和检索两端都按 `role.allows` 检查全部依赖表。

新增工具 `ask_clarification`，供 Agent 在口径不明时请求澄清。

## 执行端检查

`run_sql` 增加可选参数 `metrics: [{key, revision}]`。执行前核对：条目为 `Valid`、修订号相同、守卫在当前版本下通过。不满足则拒绝并说明原因。原有 `review_sql` 照常执行。

限制：只覆盖声明了引用的 SQL。Agent 使用了经验却不声明时，只有 `review_sql` 能拦。声明率单独报告。

## 守护

指标条目的查找规则与现有条目不同：

1. 对每个 `JoinRef` 查找对应关联条目。这会触发现有的惰性重验证。重验证后必须仍存在相同 `on` 的路径且过滤一致，否则指标失效。
2. 执行粒度守卫 `KeyUnique(fact, grain, filters[fact])`。
3. 涉及表的结构指纹不变。
4. 只有 DML 计数或批次号变化且以上全部通过时，条目保持 `Valid` 并刷新依赖版本。
5. 任一项失败则撤销并通知使用者，再进入受限修复。

第 1 条是必需的：现有 `deps` 只记录表版本，关联条目的撤销和修订不会传到引用它的条目。第 4 条也是必需的：现有规则对没有守卫的条目是“依赖一变就作废”，直接套用会把正常新增数据当成失效。

（2026-09-29）以上是定义级重验：任一依赖表有写入就重查该口径的全部条件。它现在是对照组之一，条件级维护及其他对照见“维护方式对照”。

## 受限修复

- 只处理两种情况：事实表粒度守卫失败且 `repair_grain` 找到过滤条件；引用的关联经重验证后只新增了过滤（该过滤同样来自 `repair_grain`）。其他失败保持不可用。
- 修复后的示例改为由口径字段编译的规范 SQL，原示例不再使用。
- `repair_grain` 是启发式搜索：在低基数列里找一个取值，使过滤后键唯一且不丢键。它不是业务规则，结果可能不符合业务口径。
- 修复产生新的 `Candidate`，修订号加一。不在原条目上修改后直接恢复有效。
- 新候选当场重新走 G3、G4、G5。快照已变，G6 和 G7 不适用，改用 G8。全部通过后恢复有效，触发守护的这次 `find_metric` 或 `run_sql` 就拿到新修订。
- **G8 回归**：规范 SQL 按学习题参数在当前快照上执行，与学习题判题查询在当前快照上的结果比较。判题查询随来源轨迹提交，只用于 G8。
- G8 无法执行或不通过时，条目保持不可用。
- 修复与回归在请求路径上，其耗时计入触发它的任务。
- G8 依赖学习题判题查询，实验之外没有对应物；实际部署需要业务方确认，本原型不实现。

粒度过滤写入经验库后，`review_sql` 会拦下读该表却不带过滤的查询。逐键查看的查询不会重复计算，放行：没有聚合，或只有一层 SELECT 且 GROUP BY 含全部粒度键（如检查哪些键有重复行）。

## 维护方式对照（2026-09-29 增补）

### 要回答的问题

不是“保留定义是否比删除定义好”，而是：在“标脏 + 首次使用时重验”已经不漏报、不误撤销的前提下，条件级维护是否在**重验范围、跨定义复用、并发合并、可用性**上有额外收益；收益有多大、何时消失。

### 状态

| 状态 | 含义 | 对外 | 代价记在 |
|---|---|---|---|
| 有效 | 依赖版本与当前一致 | 提供 | — |
| 短暂待验证 | 依赖版本已变、尚未重查。不存为状态，由版本比较得出 | 首次使用时先重查，再决定是否提供 | 首次使用的等待 |
| 正式撤销 | 某个条件在当前版本上不成立，或逐写入撤销 | 不提供，通知使用者 | 维护 |
| 修复候选 | 受限修复得到新修订，回归前 | 不提供 | 维护（请求路径上） |
| 需重新提炼 | 没有可执行条件，或不在修复范围 | 不提供，直到新轨迹经判题并晋升 | LLM、判题与晋升，单列 |

报告按状态给出次数、持续时间与成本，不只比较状态名。

### 维护方式

`MiddleConfig.metric_maint`（`Maint`）与 `cond_reuse`：

| 方式 | 何时维护 | 重查哪些条件 | 同一版本的条件结论 | 失败后 |
|---|---|---|---|---|
| `off` | 不维护 | — | — | 继续用；执行端也不核对引用 |
| `schema` | 首次使用 | 只比结构指纹 | — | 结构变化才撤销 |
| `revoke` | 首次使用（`metricbench` 在写入通知后立即扫） | 不查，有写入即撤销 | — | 需重新提炼 |
| `definition` | 首次使用 | 该定义的全部条件；关联与时间关联经验的守卫强制重跑 | 不复用 | 撤销 → 受限修复 → 回归 |
| `condition`，`cond_reuse = false` | 首次使用 | 只查读到了变化表的条件；关联经验修订号变化、路径消失或过滤不再覆盖时按待验证处理 | 不复用 | 同上 |
| `condition`，`cond_reuse = true` | 首次使用 | 同上 | 复用：同一条件，或被已通过的更弱条件蕴含（同表同过滤、键列更少的键唯一性）；关联守卫与修复回归的 G4 也复用；同表同键的粒度修复复用已找到的过滤 | 同上 |

各方式相同的部分：条件集合（从口径字段推出：粒度、每个关联、时间关联）、受限修复与回归（G3/G4/G5/G8）、晋升门槛、同一定义同一依赖版本的维护在途合并、相同检查 SQL 的在途合并。定义级对照组因此是最强的“标脏 + 首用重验”：它同样不删除、不重新学习、并发时不重复修复。

逐写入撤销组要能恢复：`metricbench` 的 `metric-global-revoke` 在写入通知后撤销，再由 A 用带口径题面在新快照上重新学习、提炼、晋升（任务记为 `*-relearn`，成本单列，不计入答案统计）。`maint-bench` 不调用 LLM，用重新提交同一口径代替重新提炼，只计数据库成本；重新提交之前的使用记为不可用。

### 实验

两部分：

1. `metricbench` 端到端：`metric-global`（条件级，`cond_reuse`）、`metric-global-def`、`metric-global-schema`、`metric-global-revoke`，其余设置相同。看正确率、过期使用、token，以及第 6 节维护表。
2. `maint-bench` 维护专项，不调用 LLM：
   - 口径：19 个，按族共享条件。门店销售 6 个（粒度 store_sales、时间关联 store_sales⋈date_dim）、门店退货 5 个（按退货日）、门店退货比率 3 个（门店销售的条件外加 store_sales⋈store_returns）、目录渠道 5 个。各组以相同口径、相同判题查询走 G3/G4/G5/G7，不经提炼。
   - 变化序列：门店销售追加 → 门店退货追加 → 目录销售追加（均为正常）→ v2（破坏性，只改数据）。
   - 使用：每次变化后 N 个 Agent 各按随机顺序把全部口径用一次，走执行端引用检查同一条守护路径。`staggered` 依次到达，`burst` 同时开始。
   - 组：`revoke`、`schema`、`definition`、`condition-scope`（条件级、不复用）、`condition`。`definition` 与 `condition-scope` 之差是重验范围，`condition-scope` 与 `condition` 之差是跨定义复用。

指标（每次变化）：

- 维护次数，按结果分：刷新 / 撤销后修复 / 撤销未恢复 / 需重新提炼；合并的并发维护。
- 条件处理计数：跳过、复用（含蕴含）、执行、强制重跑、交给关联经验。
- 维护的数据库查询数与耗时，按类别（守卫与关联检查、指标检查、修复）。
- 可用性：等待维护的使用次数、等待总时长、延迟 p95 与最大值；不可用的使用次数；逐写入撤销组的重新提炼次数与成本。
- 正确性：过期使用（返回为有效但规范 SQL 答错探测题）、误撤销（变化前的修订在变化后仍然正确却被撤销）。

### 读代码得到的预测（尚未运行）

`staggered` 下第一个 Agent 做完全部维护，之后的 Agent 直接命中。下表是维护中对事实表的条件检查次数，不含修复搜索与回归；假定门店销售与退货的关联验证为 1:1（2026-09-29 的记录如此），因此其守卫同时读两张表。

| 变化 | definition | condition-scope | condition |
|---|---|---|---|
| 门店销售追加（9 个口径待验证） | store_sales 12、store_returns 3 | store_sales 10 | store_sales 1 |
| 门店退货追加（8 个） | store_returns 8、store_sales 6 | store_returns 6 | store_returns 1 |
| 目录销售追加（5 个） | catalog_sales 5 | catalog_sales 5 | catalog_sales 1 |

- 重验范围的收益集中在“写入只触及定义的部分条件”时：门店退货追加时，比率口径不必重扫门店销售（6 次 1M 行检查）。门店销售追加与目录追加时范围几乎省不了什么，因为写入的就是口径的主表。
- 跨定义复用的收益随“共享同一条件的定义数”增长：同族 k 个定义，定义级查 k 次，条件级查 1 次。
- v2：定义级与 condition-scope 每个退货口径各做一次粒度修复搜索，每个比率口径在回归 G4 各重扫一次门店销售；条件级复用修复得到的过滤与门店销售的粒度结论。
- `burst` 下定义级的相同检查可能同时在途而被合并，与条件级的差距会缩小；差距主要来自已完成结论的复用，所以应主要出现在 `staggered`。
- 三种重验方式的过期使用与误撤销应当相同（均为 0）；只看结构在 v2 后产生过期使用；逐写入撤销在每次正常追加后都产生误撤销与不可用。

### 收益消失的情形（要在结果中报告）

- 每个条件只被一个定义使用。
- 写入触及定义的全部条件（例如单表口径的事实表追加）且没有其他定义共享这些条件。
- 同时到达、且定义级的相同检查恰好同时在途。
- 如果定义级方案也按“检查 + 所读表的版本”缓存检查结论，它就拿回大部分范围与复用收益——那已经就是条件级维护。论文的主张因此落在“定义被分解为可规范化、可共享的条件”以及条件经共享对象的传播上，不落在缓存本身。

### 结论的写法

- 只有 `condition` 相对 `definition` 的差异可以作为条件级维护的证据。
- 相对 `revoke` 的差异只说明保留并重验比删除后重新提炼好；相对 `schema` 的差异说明需要数据级检查。
- 已知限制：条件从口径字段推出，不是独立存储对象；覆盖条件不检查；检查仍是全表扫描（增量检查未实现）；检查与执行不在同一快照上。

## 两类验证

| 验证 | 检查对象 | 预期 |
|---|---|---|
| 示例复现、字段复现、回归（G6–G8） | 固定快照或学习题 | 与该快照上的预期输出相等 |
| 守卫与执行端检查 | 当前表、关联、粒度约束 | 约束成立；业务数值可以变化 |

## 数据流与范围

- 提炼器和共享消费者：处理后的题面、SQL 结构、元数据、必要反馈。
- 验证器：结果值、快照、比较证据。
- “全局”指同一授权边界内跨 Agent 共享，不是跨客户、跨权限共享。

本版本不实现 SQL 常量脱敏和多租户隔离。实验数据是合成的 TPC-DS，这两项只作为边界声明。

## 实验

### 题目

按“指标 × 题型 × 参数”成族。题型三种：单期汇总、跨期差值、按维度排名。每道题有两种题面：

| 题面 | 内容 | 回答的问题 |
|---|---|---|
| 带口径 | 业务定义写在题面里，所有组相同 | 探索成本 |
| 不带口径 | 只有业务名称 | 口径传递 |

两种题面分开报告，不合并。带口径题面下，指标经验组不得获得对照组没有的关键口径。

### 划分

| 集合 | 用途 | 参考答案的使用 |
|---|---|---|
| 学习 | Agent A 完成，题面带口径 | 可用于判题、门槛和回归 |
| 参数留出 | 同题型换参数 | 只用于最终评分 |
| 题型留出 | 学习阶段未出现的题型 | 只用于最终评分 |

参数留出和题型留出分开报告，不合并成一个复用正确率。

### 对照组

| 组 | 工具 | 指标经验可见范围 |
|---|---|---|
| 直连 | 基础三个工具 | 无 |
| 现有中间层 | 加 `join_path`、`check_join` 和审查 | 无 |
| 指标经验，本 Agent | 同上，加 `find_metric` | 仅自己产生的 |
| 指标经验，全局 | 同上，加 `find_metric` | 全部 |

后两组只有可见范围不同。指标结构、提炼器、门槛、检索预算和守卫都相同。主场景：Agent A 完成学习，未接触该指标的 Agent B 做留出题。

（2026-09-29）维护方式对照另设三组，与“指标经验，全局”只差维护方式：`metric-global-def`（定义级重验）、`metric-global-schema`（只看结构）、`metric-global-revoke`（写入后撤销，A 重新学习与提炼）。见“维护方式对照”。

### 结果分类

每个任务的结果为正确、错误或请求澄清三类之一。不带口径且没有任何可用定义的题目，请求澄清单独计数，不计为失败，也不计为正确。

### 数据变化

| 类型 | 做法 | 预期 |
|---|---|---|
| 正常更新 | 追加新的事实行 | 答案可变；条目不应被撤销 |
| 已建模的破坏性更新 | 现有 `apply_v2`，退货表混入状态行 | 阻断，受限修复 |
| 未建模的语义变化 | 无显式信号、守卫未覆盖 | 作为漏检边界报告 |

### 守卫消融

只开关指标条目的守护和执行端引用检查。现有的关联守卫和 `review_sql` 在两组中保持一致。

读代码得到的预测，尚未运行验证：

- 指标的 SQL 包含受保护的关联时（如退货率），关闭指标守护后，`review_sql` 仍会触发关联重验证并拦下缺少过滤的 SQL。两组最终正确率可能相同，差异体现在被拦下次数和 LLM 轮数上。
- 指标只涉及单张事实表时（如按退货日期的退货金额），`grain:` 条目只在关联验证中产生。此前没有任务触发过相关关联的重验证时，`review_sql` 不会拦，差异可能体现在正确率上。
- 因此结果依赖任务顺序。顺序必须固定并记录，两类指标分开报告。

### 指标

- 正确率、请求澄清率、LLM 轮数、工具调用数、输入与输出 token、墙钟。
- 数据库：查询数、累计耗时。数据库收益依据最终 SQL 的 `EXPLAIN (ANALYZE, BUFFERS)` 判断，事后由管理连接执行，不从 SQL 条数推定。
- 经验：检索命中率、采用率、引用声明率。
- 错误经验通过门槛的比例；轨迹未晋升的比例及原因。
- 过期经验分三级计数：被检索、被提交引用、最终被执行。
- 有效经验被误撤销的比例；修复成功率；修复后的错误率。
- 提炼、重验证、修复的成本单列，并报告随复用次数的摊销结果。离开请求路径只表示不增加当次等待，不表示总成本消失。

### 不正确口径的判定

每个阶段开始时，把已晋升口径（含撤销、修复的）按所属指标的全部留出题编译成规范 SQL，与判题器比较，答错任一题即记为不正确。这只用于统计过期使用和误撤销，不进入提炼、晋升或修复。

## 实现与运行

| 文件 | 内容 |
|---|---|
| `src/metric.rs` | 题型、规范 SQL 编译、计算链求值、静态检查、提炼器 |
| `src/middle/metrics.rs` | 门槛 G1–G8、find_metric、守护、执行端检查、受限修复与当场回归 |
| `src/metricbench.rs` | 合成数据、题目与判题器、分组、审计、报告 |
| `src/maintbench.rs` | 维护方式对照：口径族、变化序列、并发使用、过期与误撤销判定、报告（不调用 LLM） |

数据：门店销售 N 行（默认 100 万），2000–2002 年，含 `ss_ext_sales_price`、`ss_net_paid`、`ss_net_paid_inc_tax` 等易混的金额列；目录销售 N/2 行。四个指标：门店营业额（单表）、门店退货金额（单表，受 v2 影响）、门店退货率（关联，受 v2 影响）、目录渠道营业额（不受影响）。每个指标 2 道学习题、1 道参数留出、2 道题型留出（跨期差值、按月排名）。

```bash
cargo run --release --locked -- --pool 16 metric-bench --agent openai --extractor openai
# 缩小范围试跑：
cargo run --release --locked -- metric-bench --rows 100000 --modes middle,metric-global --phrasings defined --metrics M2
```

默认 5 组 × 2 种题面，约 300 次查询 Agent 运行加 16 次提炼，费用取决于模型。结果写入 `results/metric-*/`，每个组一个 `cell-*.json`，汇总为 `report.md`。

维护方式对照：

```bash
# 不调用 LLM：5 组 × 2 种到达方式，每组约 19 次准入加 4 次变化
cargo run --release --locked -- --pool 16 maint-bench --agents 8
# 端到端（调用 LLM），只报指标名题面：
cargo run --release --locked -- --pool 16 metric-bench --agent openai --extractor openai \
  --modes metric-global,metric-global-def,metric-global-schema,metric-global-revoke --phrasings named --metrics M1,M2,M3
```

结果分别写入 `results/maint-*/` 与 `results/metric-*/`。

## 不做

- 通用 SQL 模板系统。
- 把多个 Agent 的一致意见作为晋升依据。
- 向量检索、持久化、淘汰。

## 已知限制

- `sqlscan` 基于正则，依赖列名全局唯一。已报告的误拦截和误放行会影响 G5 和执行端审查。
- 学习集判题器与数据和任务生成器同源，不是外部专家确认的业务金标准。
- 表版本依赖异步上报的 `pg_stat` 计数，并有 200 毫秒的缓存窗口。正常更新的实验步骤必须像 `apply_v2` 一样强制刷新并等待。
- 指标数量少，题目成族生成。结果是描述性的，不作显著性声明。
- LLM 调用有随机性，温度、模型版本和重试次数须记录。
