# 2026-09-29 实验笔记

数据见 `exp/`，协议见 `docs/metric-experience-protocol.md`。所有结果都是单次运行，只作描述。

## 1. 2×2 消融（脚本 Agent，`exp/2026-09-29-ablation-2x2`）

24 个并发脚本 Agent，每 Agent 48 个任务，4 轮，1M 行，不涉及 LLM。

- 跨 Agent 共享使测量 DB 成本平均降 50.3%（各轮 48.1–51.9%），P95 从 114 ms 降到 27 ms，吞吐从 1589 升到 2795 请求/秒。
- 内置反馈排序没有收益（C−A −1.3%，D−B −5.5%），交互项在正负之间波动。
- 并发合并：8 个 Agent 同时执行相同汇总，关闭 singleflight 时执行 8 次，开启后 1 次、合并 7 次。
- 守护：ETL 增加 98,604 条状态行后，关闭守护得到 7,379,280（正确 5,919,963.6，错 24.7%）；开启守护时关联经验被撤销、粒度修复找到 `sr_status = '完成'`，未过滤 SQL 被拦下，修正后结果正确。

## 2. 指标经验试跑（M2，带口径，`exp/2026-09-29-metric-trial-M2`）

100k 行；普通中间层 vs 共享口径；学习由 A 完成，留出由 B 完成。

- 正确率两组都是 6/6，带口径题面区分不了两组。
- 效率只在 v2 后明显：3 题输入 token 203.5k vs 49.5k，耗时 209 s vs 42 s。普通中间层每题各自重新发现状态行语义，用了三种不同去重写法（状态过滤、整行 DISTINCT、DISTINCT ON）；其中整行 DISTINCT 只因“申请”行金额与原行相同才碰巧正确。
- 守护在 v2 后第一次查找时撤销口径，受限修复加上 `sr_status = '完成'`，维护回归通过后后两题使用 r1，均正确。v2 结束时审计：r0 答错全部 3 题，r1 全对。

暴露并已修复的两个问题：

1. v2 后第一题拿不到修复口径：修复要等任务结束后的离线维护才恢复有效。改为修复后当场回归（G3/G4/G5/G8），通过即在本次请求返回新修订。G8 的期望值由学习题判题查询在当前快照上重算，判题查询随来源轨迹提交。
2. 粒度修复写入经验库后，`review_sql` 拦下了查看重复行的诊断查询。改为放行逐键查看的查询：没有聚合，或只有一层 SELECT 且 GROUP BY 含全部粒度键。

## 3. 只报指标名：直连 vs 共享口径（M1、M3，1M 行）

原计划跑 M1、M3 全组（约 180 题，估计 4 小时）。直连组跑完后发现带口径题面下直连组已经 15/15，继续跑带口径题面信息量低、成本高，于是停止，改为只跑共享组的只报指标名题面，先看效果。

### 正确率

| 阶段 | 直连 | 共享口径 |
|---|---|---|
| 留出 | 3/6 | 6/6 |
| 正常新增后 | 2/6 | 6/6 |
| ETL v2 后 | 0/3 | 3/3 |
| 合计 | 5/15 | 15/15 |

直连组（带口径题面）为 15/15。

直连组的错误全部是口径选择，不是 SQL 写错：

- M1 两题用了 `ss_ext_sales_price`（口径是 `ss_net_paid`），一题 20 轮没给出答案。同一个 Agent 在 M1-P1 用了 `ss_net_paid`、在 M1-T1 用了 `ss_ext_sales_price`，同一指标前后不一致。
- M3 用了数量比，或退货金额 ÷ 销售价；且按退货日期统计，而口径是把退货按小票号和商品对应回当期销售行。答 39.80 / 19.90 / 21.86，标准 23.81 / 11.90 / 11.90。
- 排名题（哪个月最高）口径错也可能排名相同，所以 v2 前直连组只对了排名题。

共享组 B 在 15 题中每题都查到并声明了口径。共享的 M3 口径：分子 `SUM(sr_return_amt)`，分母 `SUM(ss_net_paid)`，事实表 store_sales，销售日，按小票号+商品左连接 store_returns。

### 成本（15 题；共享组另含 4 道学习题与提炼）

| | 直连 | 共享口径 |
|---|---|---|
| 输入 token | 3.30M | 0.41M |
| 输出 token | 582k | 140k |
| 耗时 | 3,001 s | 951 s |
| 平均轮数 / 工具调用 | 11.9 / 21 | 4.5 / 6.9 |

学习与提炼共约 157k 输入 token、362 s，少于直连组两三道难题的花费。提炼 token 按 15 次命中分摊，每次约 1,573。

共享组 M3-T2（留出）有一条 Agent 自己的探索 SQL 跑满 300 s 数据库超时，最终仍答对；去掉这条，15 题耗时 268 s。

### 数据变化

- 正常新增：M1、M3 的依赖版本都变了，查找时重查通过，保持有效，没有误撤销。首次重查分别多花约 5.9 s、2.7 s 数据库时间（全表 KeyUnique）。
- ETL v2：第一次查找发现 store_sales⋈store_returns 的已验证路径现在要求 `sr_status = '完成'`，撤销；受限修复采用该过滤，G8 回归通过，同一请求就拿到 r1（修复 1 生效）。3 道 v2 题全部用 r1 且答对。这一请求数据库时间 9.2 s、墙钟 68 s，后两题 21 s、11 s。
- 修复 2（诊断查询放行）这次没有诊断查询，未得到验证。

### 新发现的问题（未修）

1. 规范编译重复加日期关联：第二条 M1 提炼把 date_dim 关联也写进了 `joins`，编译再加一次时间关联，报“表名 date_dim 被指定多次”，G7 失败。应在静态检查时去掉与时间关联重复的 join。
2. 计算链检查太严：M3 第一道学习题的 `derivation` 在算式后写了说明（`r1（按…）`），G2 判为不合法。应只取开头的算式并与答案核对。
3. 声明引用时省略了 `metric:` 前缀（写成 `门店退货率`），执行端判为不存在，重试后成功，多一轮。应接受不带前缀的 key。
4. 数据库超时 300 s 过长，一条坏 SQL 耗 5 分钟。应降到 30–60 s，各组一致。

问题 1、2 使 4 次提炼只晋升了 2 次；两次失败都不是口径错误。

## 4. 能说明什么、不能说明什么

- 能说明：一个 Agent 知道的口径能准确传给其他 Agent，并在正常新增和已建模的破坏性更新后保持正确。
- 不能说明：系统能自己发现正确口径。共享组的口径来自带口径的学习题（口径依据为题面）。
- 直连组没有中间层工具，这次对比混合了“中间层工具”和“口径共享”两个因素；应补跑普通中间层组（只报指标名）。直连组的错误都是口径选择，关联和粒度工具不提供口径，所以预计主要收益来自共享，但这是推断。
- 单次运行、15 题、一个模型；判题器与数据、题目同源。

## 6. 评审意见：标脏不等于删除（同日追加）

质疑：合理的保守方案是“依赖表变化 → 相关定义标为待验证 → 首次使用时重查约束 → 通过后继续使用”，不必删除经验、重新调用 LLM。本文守护的流程正是如此（查找时发现版本变化，重查该定义依赖的每项条件，通过后刷新依赖版本）。

对照记录确认：第 3 节“正常新增：没有误撤销”“v2 后同一请求内修复为 r1”，定义级重验同样做得到；这些数字不能说明条件级维护的价值，只说明保留比删除好。摘要里“逐写入失效必然抹掉复用收益”撤回，见 `docs/paper/abstract.md`“论断修正”。

记录里能看到的一处真实差别：正常新增后 M3-P1 的维护里，`KeyUnique(store_sales, 小票号+商品)` 执行了两次——一次作为 1:1 关联的守卫（1374 ms），一次作为口径自己的粒度条件（1293 ms）。M1 的粒度键是“日期 + 小票号 + 商品”，被前者蕴含。条件结论复用与蕴含能省掉这类重复，定义级不能。
