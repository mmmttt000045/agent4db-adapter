# 2026-09-29 实验笔记

数据见 `exp/`，协议见 `docs/metric-experience-protocol.md`。所有结果都是单次运行，只作描述。

## 1. 2×2 消融（脚本 Agent，`exp/2026-09-29-ablation-2x2`）

24 个并发脚本 Agent，每 Agent 48 个任务，4 轮，1M 行，不涉及 LLM。

- 跨 Agent 共享使测量 DB 成本平均降 50.3%（各轮 48.1–51.9%），P95 从 114 ms 降到 27 ms，吞吐从 1589 升到 2795 请求/秒。
- 内置反馈排序没有收益（C−A −1.3%，D−B −5.5%），交互项在正负之间波动。
- 并发合并：8 个 Agent 同时执行相同汇总，关闭 singleflight 时执行 8 次，开启后 1 次、合并 7 次。
- 守护：ETL 增加 98,604 条状态行后，关闭守护得到 7,379,280（正确 5,919,963.6，错 24.7%）；开启守护时关联经验被撤销、粒度修复找到 `sr_status = '完成'`，未过滤 SQL 被拦下，修正后结果正确。

## 2. 指标经验试跑（M2，带口径，`exp/2026-09-29-metric-trial-M2`）

100k 行；普通中间层 vs 共享口径；学习由 A 完成，留出由 B 完成。

- 正确率两组都是 6/6，带口径题面区分不了两组。
- 效率只在 v2 后明显：3 题输入 token 203.5k vs 49.5k，耗时 209 s vs 42 s。普通中间层每题各自重新发现状态行语义，用了三种不同去重写法（状态过滤、整行 DISTINCT、DISTINCT ON）；其中整行 DISTINCT 只因“申请”行金额与原行相同才碰巧正确。
- 守护在 v2 后第一次查找时撤销口径，受限修复加上 `sr_status = '完成'`，维护回归通过后后两题使用 r1，均正确。v2 结束时审计：r0 答错全部 3 题，r1 全对。

暴露并已修复的两个问题：

1. v2 后第一题拿不到修复口径：修复要等任务结束后的离线维护才恢复有效。改为修复后当场回归（G3/G4/G5/G8），通过即在本次请求返回新修订。G8 的期望值由学习题判题查询在当前快照上重算，判题查询随来源轨迹提交。
2. 粒度修复写入经验库后，`review_sql` 拦下了查看重复行的诊断查询。改为放行逐键查看的查询：没有聚合，或只有一层 SELECT 且 GROUP BY 含全部粒度键。

## 3. 只报指标名：直连 vs 共享口径（M1、M3，1M 行）

原计划跑 M1、M3 全组（约 180 题，估计 4 小时）。直连组跑完后发现带口径题面下直连组已经 15/15，继续跑带口径题面信息量低、成本高，于是停止，改为只跑共享组的只报指标名题面，先看效果。

### 正确率

| 阶段 | 直连 | 共享口径 |
|---|---|---|
| 留出 | 3/6 | 6/6 |
| 正常新增后 | 2/6 | 6/6 |
| ETL v2 后 | 0/3 | 3/3 |
| 合计 | 5/15 | 15/15 |

直连组（带口径题面）为 15/15。

直连组的错误全部是口径选择，不是 SQL 写错：

- M1 两题用了 `ss_ext_sales_price`（口径是 `ss_net_paid`），一题 20 轮没给出答案。同一个 Agent 在 M1-P1 用了 `ss_net_paid`、在 M1-T1 用了 `ss_ext_sales_price`，同一指标前后不一致。
- M3 用了数量比，或退货金额 ÷ 销售价；且按退货日期统计，而口径是把退货按小票号和商品对应回当期销售行。答 39.80 / 19.90 / 21.86，标准 23.81 / 11.90 / 11.90。

共享组 B 在 15 题中每题都查到并声明了口径。共享的 M3 口径：分子 `SUM(sr_return_amt)`，分母 `SUM(ss_net_paid)`，事实表 store_sales，销售日，按小票号+商品左连接 store_returns。

### 新发现的问题（未修）

1. 规范编译重复加日期关联：第二条 M1 提炼把 date_dim 关联也写进了 `joins`，编译再加一次时间关联，报“表名 date_dim 被指定多次”，G7 失败。应在静态检查时去掉与时间关联重复的 join。
2. 计算链检查太严：M3 第一道学习题的 `derivation` 在算式后写了说明（`r1（按…）`），G2 判为不合法。应只取开头的算式并与答案核对。
3. 声明引用时省略了 `metric:` 前缀（写成 `门店退货率`），执行端判为不存在，重试后成功，多一轮。应接受不带前缀的 key。
4. 数据库超时 300 s 过长，一条坏 SQL 耗 5 分钟。应降到 30–60 s，各组一致。

问题 1、2 使 4 次提炼只晋升了 2 次；两次失败都不是口径错误。

（同日修复，已在 noctis 编译并通过单元测试，未经 LLM 实验验证）1：G3 去掉与时间关联相同的 join（`src/middle/metrics.rs` 的 `static_gate`）。2：计算链只取开头的算式，说明文字忽略（`metric::leading_expr`）。3：`run_sql` 的 `metrics` 引用缺 `metric:` 前缀时自动补上。4：`metric-bench` 的 Agent 连接池超时默认 60 s（`--sql-timeout-secs`，含中间层检查；行数很大时调高），其他连接仍为 300 s。

## 4. 能说明什么、不能说明什么

- 能说明：一个 Agent 知道的口径能准确传给其他 Agent，并在正常新增和已建模的破坏性更新后保持正确。
- 不能说明：系统能自己发现正确口径。共享组的口径来自带口径的学习题（口径依据为题面）。
- 直连组没有中间层工具，这次对比混合了“中间层工具”和“口径共享”两个因素；应补跑普通中间层组（只报指标名）。直连组的错误都是口径选择，关联和粒度工具不提供口径，所以预计主要收益来自共享，但这是推断。
- 单次运行、15 题、一个模型；判题器与数据、题目同源。

## 6. 评审意见：标脏不等于删除（同日追加）

质疑：合理的保守方案是“依赖表变化 → 相关定义标为待验证 → 首次使用时重查约束 → 通过后继续使用”，不必删除经验、重新调用 LLM。本文守护的流程正是如此（查找时发现版本变化，重查该定义依赖的每项条件，通过后刷新依赖版本）。

对照记录确认：第 3 节“正常新增：没有误撤销”“v2 后同一请求内修复为 r1”，定义级重验同样做得到；这些数字不能说明条件级维护的价值，只说明保留比删除好。摘要里“逐写入失效必然抹掉复用收益”撤回，见 `docs/paper/abstract.md`“论断修正”。

记录里能看到的一处真实差别：正常新增后 M3-P1 的维护里，`KeyUnique(store_sales, 小票号+商品)` 执行了两次——一次作为 1:1 关联的守卫（1374 ms），一次作为口径自己的粒度条件（1293 ms）。M1 的粒度键是“日期 + 小票号 + 商品”，被前者蕴含。条件结论复用与蕴含能省掉这类重复，定义级不能。

代码调整（未编译、未运行）：

- `Maint`：off / schema / revoke / definition / condition；`cond_reuse` 控制同一版本的条件结论复用（守卫、粒度条件、回归 G4、粒度修复）与键唯一性的蕴含。默认关闭，其他实验不受影响。
- 口径维护按（定义, 依赖版本）在途合并，修掉了并发时重复撤销与修复的问题（定义级对照组也享有）。
- `metricbench` 新增 `metric-global-def`、`metric-global-schema`、`metric-global-revoke`（写入后撤销，A 重新学习与提炼，记为 `*-relearn`）；报告新增第 6 节维护表。
- 新增 `maint-bench`（不调用 LLM）：19 个共享条件的口径、三类正常追加与 v2、`staggered` / `burst` 两种到达方式、`condition-scope` 消融。

下一步：先跑 `maint-bench`（便宜、确定），看 `condition` 相对 `definition` 的差距是否主要来自复用、`burst` 下是否缩小；再决定端到端 `metricbench` 跑哪几组。

### 正确性

- 定义级、只缩小范围、条件级：所有 k、两种到达方式下过期使用 0、误撤销 0；v2 都撤销并修复（k = 6 时 8 个退货相关口径），没有修复失败。
- 只看结构：v2 后受影响口径的每次使用都是过期使用（16 / 32 / 56 / 64）。
- 逐写入撤销：每次正常追加都误撤销（5 / 10 / 18 / 22），恢复前的使用不可用（56 / 112 / 200 / 240）。

### 解读

1. 错峰时，定义级的 DB 时间随口径数近似线性增长（48.7 → 180.7 s），条件级基本不变（19–25 s）：每个条件每个数据版本只查一次。这支持摘要里“收益随共享度增长”的说法，方向与协议的预测一致。
2. 收益主要来自跨定义复用，不是重验范围：只缩小范围只到定义级的 0.80–0.94。与协议预测一致（写入多落在口径的主事实表上，范围省不了多少）。
3. 同时到达时收益小得多（0.48–0.74），且不单调（k = 2 时条件级 0.74，高于只缩小范围的 0.71）：定义级的相同检查同时在途，也被合并了；已完成结论的复用在同时到达时用处小。与协议预测一致。
4. k = 1 不等于没有共享：门店营业额与门店退货率共享门店销售的粒度条件，退货率的关联守卫里也是同一个键唯一性检查。所以 k = 1 时条件级仍有 0.39。写论文时共享度要按“共享同一条件的口径数”定义，而不是按族内个数。
5. 新发现：同时到达时，v2 修复期间到达的使用返回不可用（k = 6：定义级 14 次、只缩小范围 10 次、条件级 22 次，v2 共 152 次使用；错峰时都是 0）。口径已撤销、修复还没完成时，新到达的使用不会等修复，而是直接拿到撤销状态。安全（没有过期使用），但损失可用性。条件级更多，是因为它的检查很快结束、更多使用落在修复窗口里，而不是合并进在途检查（合并的维护 5 次 vs 定义级 10 次）。可改为：修复进行中的口径，新使用等待修复结果。

### 局限

- 单次运行；各共享度内组的执行顺序固定（revoke、schema、definition、condition-scope、condition），条件级总在最后，缓存可能更热。1M 行全部在内存中，影响应当不大，但要用 `--repeats 5` 让每种方式轮到每个位置后再下结论。
- 合成数据，只有一种破坏性变化（v2）；变化类型负载尚未实现。
- DB 时间是中间层全部查询（维护之外只有版本读取），不含 Agent 自己的 SQL。

### 解读

1. 共享口径能把一个 Agent 学到的口径准确传给没见过这些指标的 Agent：条件级 21/21，普通中间层 11/21；输入 token 少约 8 倍，轮数 12.2 → 4.9。
2. 只改数据的破坏性变化确实会让只看结构的做法用上过期口径并答错（M2 三题，答案翻倍）；数据级维护（条件级、定义级、写入即撤销）都避免了。
3. 条件级与定义级正确性相同；维护 DB 时间 22.4 s 对 52.9 s（0.42）。只有 3 个指标、共享少，差距小于 `maint-bench`。
4. 写入即撤销正确，但每次写入都要调 LLM 重新学习，还会误撤销仍然有效的口径。

### 局限

- 单次运行、一个模型、合成数据、判题器与数据同源；每组 21 道计分题。
- 提炼仍会因表别名被 G3 拒绝（30 次提炼中 4 次），靠另一道学习题补上；无守护组两题都被拒，M3 没学到。可在提炼提示里要求不用表别名。
- 直连组仍是 9-29 的旧数据（300 秒超时、只有 M1、M3），只作参考。

## 9. 维护方式对照反序复验（`exp/2026-09-30-maint-share-rev`）

与第 7 节相同设置，只把维护方式的执行顺序反过来（`--policies condition,condition-scope,definition,schema,revoke`），条件级在每个共享度内最先跑。

| k | 错峰：条件级 / 定义级（正序 → 反序） | 同时：条件级 / 定义级（正序 → 反序） |
|---|---|---|
| 1 | 0.39 → 0.36 | 0.64 → 0.73 |
| 2 | 0.23 → 0.20 | 0.74 → 0.77 |
| 4 | 0.15 → 0.16 | 0.59 → 0.59 |
| 6 | 0.13 → 0.13 | 0.48 → 0.41 |

- 错峰结论不受执行顺序影响：条件级在最先跑时同样只需定义级的 13–36%。第 7 节“条件级总在最后、缓存更热”的疑虑可以排除。
- 同时到达两轮差别较大（k = 1 为 0.64 与 0.73），并发调度的随机性更大；方向一致：条件级更省，但远不如错峰。
- 只缩小范围：错峰 0.73–0.85，与正序（0.80–0.94）同一量级，收益主要来自跨定义复用。
- 正确性：三种重验的过期使用与误撤销仍全为 0。同时到达的修复窗口不可用再次出现（k = 6 条件级 21 次、定义级 10 次；k = 4 为 16 与 12）。
