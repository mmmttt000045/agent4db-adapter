# 多业务域研究评测协议

本协议区分已实现的自建实验、公开查询结构适配和未来的真实生产评测。结果不称为官方 TPC、Spider 或生产轨迹成绩。

## 实验问题与对照

1. B−A：跨 agent 共享能否减少重复探索与校验？
2. C−A、D−B：带回放门槛的统计反馈能否改善检查顺序，且不再出现负收益？
3. M−B、M−D：Mock 的全局检查排序经门槛筛选后是否优于固定或统计策略？Mock 不代表真实大模型。
4. D−B−C+A：数据库成本交互项。负值才表示超出简单相加的节约。
5. 关闭结果缓存后重跑：收益是否仍然存在？不同数据规模或 agent 数量的两份报告不直接相减。

|组|共享|检查排序|
|---|---|---|
|A|每个 agent 独立|固定|
|B|全局|固定|
|C|每个 agent 独立|统计反馈，回放门槛通过前保持默认顺序|
|D|全局|统计反馈，回放门槛通过前保持默认顺序|
|M|全局|Mock 管理器在训练后和漂移后提议；按 improvement 门槛应用，漂移后先做退化监测|

五组的连接池、singleflight、结果缓存开关、审计候选种子和逻辑任务保持一致。singleflight 在主实验关闭。每轮换一个运行位置；五轮才平衡五组的位置。每轮种子变化，组内输入和调度分配相同。并发完成顺序仍由操作系统决定。

## 反馈闭环

2026-09-28 的实测中，反馈组相对固定顺序出现 −9% 到 −11% 的成本退化（64 agent）。旧实现有三处结构性问题：统计只按检查种类汇总，不区分表与方向；代价按行数线性外推，没有计入复用；自适应顺序在没有证据时也会直接生效。另外，旧实现只在键唯一性最先失败时尝试粒度修复，重排可能改变验证结论。它们各自对退化贡献多少，需要结合当次运行的检查轨迹才能归因。现实现的处理如下：

- **语义不变**：抽样扇出或行数守恒失败都蕴含右侧键不唯一。其他检查先失败、且右表尚未尝试修复时，补查键唯一性（常可复用）来决定是否修复，反例说明也优先取键唯一性的结果。验证结论与默认顺序一致，顺序只影响代价。
- **上下文与摊销**：失败概率按“检查种类 + 表 / 表对方向”统计，并向该种类整体收缩（先验强度 4）；代价优先用该上下文的实测均值；执行一次、被复用 h 次的检查按 1/(1+h) 摊销；当前已缓存的检查视为零代价。
- **回放证据**：失败后是否审计只取决于候选签名与种子，与顺序和结果无关，因此被审计的失败候选是回放其他顺序的无偏样本。对每个样本计算候选顺序与默认顺序 `KeyUnique → RowConservation → SampleFanout` 的代价：累加到第一个失败为止，若需要则加上补查键唯一性的代价，审计开销不计入。配对差给出正态近似 95% 区间，至少 8 个样本，窗口保留最近 2000 个。
- **采纳与退回**：C/D 只有区间整体低于 0 时才采用自适应顺序，证据每增加 4 条重新判断，优势消失即退回默认顺序。M 的建议按 `improvement` 门槛应用；每次管理周期先只用应用之后的新样本做退化监测，区间整体高于 0 即自动回滚。

限制：回放在同一窗口内既用于统计也用于评估，属于样本内估计；摊销代价是对跨候选复用价值的近似，不模拟顺序改变后缓存状态的连锁变化；报告的“反馈闭环”一节给出各组的采纳状态与证据数量，但不能代替组间成本比较。

## 数据和任务

- retail、billing、delivery 三个同构业务域，各有 fact、detail、entity、label、history，共 15 张业务表。域名用于任务区分；没有把三个同构 schema 宣称为三套独立真实业务。
- 每域 N 个事实、3N 个明细、N−floor(N/5) 个完成状态、4096 个实体、512 个标签。三域合计 `3 × (4N + N − floor(N/5) + 4608)` 行。
- 报告的 GiB 是装载后 PostgreSQL 测得的表及索引大小，不是下载大小，不是 `rows` 换算的估计值；后续更新产生的膨胀另当别论。
- 16 种结构：区间聚合、分组 HAVING、维度关联、条件聚合、CTE 预聚合、窗口排名、相关 EXISTS、反连接、UNION ALL、外连接缺失、嵌套聚合、窗口 LAG、状态粒度、NULL、GROUPING SETS、多对多错误陷阱。
- 16 × 3 = 48 个领域查询族。`variants` 扩大参数实例数量，**不会增加独立结构数量**。每轮每阶段实例数为 `48 × variants`，任务数再乘 repeats。
- 每个脚本任务执行画像探索与 SQL；这是预编排的两步任务，不是模型自主规划。agent 并发数与数据库池大小分开记录。
- 查询的事实范围通常限于 256 行，以控制本机运行时间；关联检查和画像可能访问全表。因此该评测不是大范围分析扫描的吞吐基准。

## 留出和学习时序

训练仅使用 retail 中三个有效关联和四个简单查询族，参数范围为前 100 行。测试事实范围从第 101 行开始；delivery 标记 domain_holdout，其余高阶结构标记 structure_holdout，简单结构标记 parameter_holdout。这是优先级标签，billing 也未参与训练，不能据标签推断其参与过训练。

反馈在测试流中继续更新，不读取标准答案。结果衡量在线运行全过程，不能称作冻结策略上的独立测试。第一次出现的任务和后续重复任务可通过 task、repeat、agent 与知识来源追溯。下一步更严格的研究应使用不同拓扑的 schema，并单独冻结策略测试。

## 参考答案与错误统计

每个合法实例有候选 SQL 和等价参考 SQL，先由只读直连 PostgreSQL 比较完整、排序后的结果，包括 NULL、重复行和行数，再由 adapter 执行候选。部分参考式使用生成规则，例如状态金额和 LAG 的端点差。这个 oracle 独立于 adapter，但与数据和任务生成器同源，不等于经外部专家验证的业务金标准。

报告完整保存失败，区分错误放行、错误拦截与执行错误。错误 SQL 被拒绝才算正确，数据库执行错误不算成功拦截。不能把“更快地拒绝合法 SQL”解释为性能提升。

另有语义边界专项：合法多对多 `COUNT(DISTINCT ...)`，以及包含正确状态文本但被 `OR` 放宽的错误过滤。专项放在主要计时后，不混入主矩阵成本。它们用于暴露轻量 SQL 审查的能力边界；报告中失败不意味着实验工具运行失败。

## 漂移与成本

稳定阶段后，向 history 中约四分之一的完成记录添加 pending 行，并将 fact 中每八行的一行金额乘三。批次日志与显式版本失效通知提供确定的变更边界。然后关联检查发现并修复粒度，再执行变化后的同一任务集。

恢复时间包含通知后检查和错误聚合验证，不代表自动发现延迟。恢复过程逐 agent、逐域执行，逻辑调用一致，共享组可以复用先前恢复结果。

成本同时提供训练、稳定阶段、恢复、变化后阶段和全程计量。全程 DB 成本含目录读取、探查、检查、守护、修复和执行，**不含数据构建、预热、参考答案生成和外部 ETL 注入**，这些属于评测装置。SQL 耗时之和不等于墙钟，且不包含连接池等待；任务延迟包含等待。`total_wall_seconds` 在当前实现也经过 ETL 注入，因此不能作为纯 adapter 延迟使用。

五轮配对 bootstrap 区间只是小样本描述，不作显著性保证。不能把同一轮里的数千个相关任务当作数千次独立实验。性能比较必须同时检查正确性、负收益、运行顺序、内存缓存与连接池限制。

## 复现

```powershell
# 主实验：使用 release 构建，24 agent，五轮，768 实例/阶段
./tools/research.ps1 -Rows 1000000 -Agents 24 -Variants 16 -Rounds 5

# 配对缓存敏感性：必须保持两次数据与 agent 参数相同
./tools/research.ps1 -Rows 100000 -Agents 64 -Variants 4 -Rounds 5
./tools/research.ps1 -Rows 100000 -Agents 64 -Variants 4 -Rounds 5 -NoResultCache

# 带来源的结构适配及语义边界专项
./tools/research.ps1 -Rows 10000 -Agents 8 -Variants 2 -Rounds 5 -Corpus data/research_public_adaptations.json

# 容量校验：按实际输出大小判断是否达到目标，不作为策略消融结果
./tools/research.ps1 -Rows 8000000 -CapacityOnly
```

需要 `.env` 中专用 `AGENTDB_URL` 的 CREATEDB 权限。实验只创建和删除唯一命名的 `agentdb_research_*` 数据库。正常完成和可处理错误都会清理；强制终止进程可能留下数据库，不能把没有报告当作成功。

如果 PostgreSQL 位于 WSL，长实验期间保持一个 WSL 会话运行。仅从 Windows 连接数据库不一定阻止 WSL 空闲退出；日志中的 `received fast shutdown request` / `57P01` 表示数据库关闭，应先恢复环境再补跑，不计为 adapter 的语义错误。

报告保存在忽略版本控制的 `results/research-*/`。`corpus-*.json` 保存 SQL、参考答案与 oracle 成本；`round-*.json` 保存全部事件和证据；`report.md/json` 汇总结果。每轮输出立即写盘，失败时保留已完成轮次和 `failure.json`。

应用中断后可用相同参数加 `-Resume results/research-<编号>` 恢复。工具核对 manifest 配置、已保存单元的种子与控制变量、缓存语料中的候选 SQL，只补跑缺失单元。完成单元不会重写。重新创建隔离数据，使用保存的参考答案，并另存补跑构建指纹；新单元含 execution_epoch。中断前的遗留数据库需要确认无活动后单独清理，工具不会按前缀批量删除数据库。跨中断或不同构建的报告必须披露这一事实，不能宣称完全连续的实验。

`manifest.json` 保存配置、运行位置是否平衡及编译时源代码的 FNV-1a 指纹（只用于标识，不是密码学签名）。`--capacity-only` 只生成数据并核对 18 个范围查询，输出 `capacity-queries.json`，不生成消融组或性能收益结论。

可选图表：安装 Python 的 matplotlib 后，执行 `python tools/plot-research.py results/research-<编号>/report.json`，生成 PNG 和 SVG。图中原始圆点为每轮成本，区间以轮次而不是请求为重采样单位。容量校验报告不适用此绘图脚本。
