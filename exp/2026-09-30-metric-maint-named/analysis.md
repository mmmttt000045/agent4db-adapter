# 指标口径维护实验汇报（2026-09-29 至 09-30）

实验机 noctis；原始数据与存档见文末附录。所有结果都是单次运行（实验一正序、反序各一轮）、单模型、合成数据上的描述性结果，不作显著性声明。

## 摘要

两组实验都支持论文的主线：共享口径让没见过指标的 Agent 答对全部 21 道计分题；不改表结构的数据变化确实会让只看结构的做法答错；条件级维护在错峰到达时只需定义级重验 13%–38% 的数据库时间。

研究问题：数据库上多个 Agent 共享 LLM 学到的指标口径时，数据变化（尤其是不改表结构的变化）会不会让口径悄悄失效，怎样以最小代价维护。做了两组实验：

- 实验一：不调用 LLM 的维护方式对照与共享度扫描（`maint-bench`），40 组 × 正序、反序两轮 = 80 组。
- 实验二：用 DeepSeek 的端到端实验（`metric-bench`），6 组 × 每组 27 题。

主要结论：

- **共享口径有效**：条件级组 21/21，没有共享口径的普通中间层 11/21；输入 token 4.30M → 0.52M，每题轮数 12.2 → 4.9。
- **问题确实存在**：v2 不改表结构，只看结构的做法把过期口径交给 Agent，M2 的 3 道 v2 题答案全部翻倍；条件级、定义级、写入即撤销都答对。
- **条件级比最强对照省**：错峰到达时 DB 时间降到定义级的 13%–38%，k = 6 时等待 180 s → 23 s，共享越多越省；同时到达时只降到 45%–76%。收益来自跨口径复用结论，只缩小重验范围仅省 6%–27%。端到端只有 3 个指标，为 22.4 s 对 52.9 s。
- **写入即撤销正确但贵**：每次正常新增都误撤销，端到端额外重新学习 8 题、约 57 万 token、904 s。
- **待解决**：同时到达时，修复进行中到达的使用被直接拒绝（k = 6 两轮共 43 / 304 次）；提炼仍有 4 / 30 次因表别名被拦。

## 1. 系统与实验环境

被测系统是一个 Rust 中间层，位于多个 LLM 数据 Agent 与 PostgreSQL 之间，负责共享并维护 Agent 学到的指标口径。口径由一个 Agent 在判题成功的学习任务中得到，离线提炼后经 G1–G7 门槛发布；其他 Agent 用 `find_metric` 查到口径，自己写 SQL，并在 `run_sql` 里声明所用口径的修订号，执行端核对该修订仍然有效。

每条口径依赖几条可执行的数据条件：事实表在粒度键上唯一（带口径过滤）、关联不放大（多重性与必需过滤）、时间关联正确。条件绑定表版本（结构指纹、DML 计数、ETL 批次）。数据变化后怎样处理这些条件，就是本次对比的“维护方式”：

| 维护方式 | 数据变化后 | 查哪些条件 | 条件不成立时 |
| --- | --- | --- | --- |
| 无守护（off） | 不检查 | 不查 | 继续使用 |
| 只看结构（schema） | 首次使用时比结构指纹 | 不查数据 | 结构变了才撤销 |
| 写入即撤销（revoke） | 依赖表有写入就撤销 | 不查 | 需重新学习与提炼 |
| 定义级重验（definition） | 标为待验证，首次使用时重查 | 该口径的全部条件，关联守卫强制重跑 | 撤销 → 受限修复 → 回归 |
| 只缩小范围（condition-scope） | 同上 | 只查读到变化表的条件，不复用结论 | 同上 |
| 条件级重验（condition，本文） | 同上 | 同上，且同一数据版本的条件结论跨口径、跨 Agent、跨修复复用 | 同上 |

后三种的条件、受限修复、回归门槛与在途合并完全相同，只差重查的范围与结论复用；定义级是最强的对照。

| 项目 | 设置 |
| --- | --- |
| 机器 | noctis：48 核 Hygon、98 GiB 内存 |
| 数据库 | PostgreSQL 18.6，关闭 WAL 与 fsync；每次实验新建隔离库，结束后删除 |
| 数据 | 合成零售数据（TPC-DS 列名）：门店销售 100 万行、门店退货约 39.6 万行、目录销售 50 万行，2000–2002 年 |
| 模型 | DeepSeek V4.1 Flash（`deepseek-flash`，max 思考）；查询 Agent 与提炼器相同 |
| 代码 | `5e82e37`，另加计算链与 G3 表名前缀两处修复（未提交，见第 6 节） |
| 指标 | M1 门店营业额（单表）、M2 门店退货金额（单表，受 v2 影响）、M3 门店退货率（关联门店退货，受 v2 影响） |

数据变化有两类：

- **正常新增**：补录 2002 年 9 月的门店销售、门店退货与目录销售，结构与粒度不变。
- **破坏性变化 v2**：表结构不变，给 2001-10-01 起的门店退货追加一条“申请”状态行（170,816 条），使退货表在（小票号, 商品）上不再唯一，旧口径会重复计数。正确口径需要加 `sr_status = '完成'`。

## 2. 实验一：维护方式对照与共享度扫描（设计）

实验一回答：条件级维护相对定义级重验，在数据库时间和 Agent 等待上多省多少，收益在什么条件下消失。它不调用 LLM，各组用完全相同的口径、数据变化和使用序列，结果可复现。

怎么做：

1. **口径**：19 条，分 4 个族——门店销售 6 条、门店退货 5 条、门店退货比率 3 条、目录渠道 5 条。同族口径共享同一批条件（事实表粒度、时间关联），比率族另外共享门店销售⋈门店退货的关联。口径直接提交并走 G3、G4、G5、G7 门槛，不经 LLM 提炼，排除提炼的随机性。
2. **共享度 k**：每族只取前 k 条，k = 1 / 2 / 4 / 6 对应 4 / 8 / 15 / 19 条口径。k 越小，共享同一条件的口径越少。
3. **数据变化**：门店销售追加 → 门店退货追加 → 目录销售追加（均为正常新增）→ v2（只改数据的破坏性变化）。
4. **使用**：每次变化后，8 个 Agent 各按自己的随机顺序把全部口径用一次，走与执行端引用检查相同的守护路径。两种到达方式：错峰（前一个 Agent 用完，下一个才开始）与同时（8 个同时开始）。
5. **分组**：5 种维护方式 × 4 种共享度 × 2 种到达方式 = 40 组，1M 行。正序跑一轮（每个共享度内条件级最后跑），再反序跑一轮（条件级最先跑），抵消执行顺序与缓存冷热的影响。

| 度量 | 含义 |
| --- | --- |
| DB 时间 | 中间层在四次变化后全部使用期间的数据库耗时合计（维护之外只有版本读取） |
| 条件检查次数 | 访问数据库的条件检查，含在途合并与定义级强制重跑的关联守卫 |
| 等待 | 一次使用执行了维护、或合并进别人的维护时，它的耗时计入等待 |
| 过期使用 | 返回为有效的修订，其规范 SQL 在当前快照上答错探测题（2002 年 9 月） |
| 误撤销 | 变化前的修订在变化后仍然正确，却被撤销 |
| 不可用使用 | 返回撤销或候选状态，这次使用拿不到口径 |

命令：`maint-bench --agents 8 --share 1,2,4,6`；反序加 `--policies condition,condition-scope,definition,schema,revoke`。

## 3. 实验一结果

错峰到达时，条件级维护的数据库时间只有定义级的 13%–38%，共享同一条件的口径越多省得越多；同时到达时只降到 45%–76%。正序与反序两轮结论一致，三种重验方式在全部 80 组里都没有过期使用和误撤销。

### 3.3 要点

- **收益来自跨口径复用**：只缩小重验范围、不复用结论时，错峰下仍是定义级的 73%–94%（各轮）。几次写入都落在口径的主事实表上，范围省不了多少。访问数据库的条件检查：定义级 15 / 30 / 53 / 63 次，条件级错峰时只有 3–4 次、同时到达 4 / 8 / 12 / 13 次。
- **同时到达时差距变小**：定义级里相同的检查同时发生，也被合并执行了；已完成结论的复用此时用处小。两轮的波动也更大（k = 1 时 64% 与 73%）。
- **执行顺序无关**：条件级在正序里最后跑、在反序里最先跑，错峰下的比值相差不超过 4 个百分点，缓存冷热的影响可以排除。
- **正确性**：只看结构在 v2 后把受影响口径的每次使用都给成过期版本（每轮 16 / 32 / 56 / 64 次）；写入即撤销每次正常新增都误撤销（每轮 5 / 10 / 18 / 22 次），恢复前 56–240 次使用拿不到口径。
- **可用性代价**：同时到达时，修复进行中到达的使用直接拿到“已撤销”。条件级检查结束得快，更多使用落进修复窗口，k = 4、6 时比定义级更多（43 对 24）。这是安全的（没有过期使用），但应该改成让这些使用等修复结果。

## 4. 实验二：端到端 LLM 实验（设计）

实验二用真实模型回答：一个 Agent 学到的口径能否准确传给别的 Agent，并在正常新增与 v2 之后保持正确；以及各种维护方式在正确率、过期使用和成本上的差别。

每组 27 道题，分四个阶段顺序进行：

| 阶段 | 谁做 | 题目 | 题面 |
| --- | --- | --- | --- |
| 学习 | Agent A | M1–M3 各 2 道单期汇总 | 带口径（业务定义写在题面里），判题成功后离线提炼口径 |
| 留出 | Agent B | M1–M3 各 3 道：换参数的单期汇总、跨期差值、按月排名 | 只报指标名 |
| 正常新增后 | Agent B | M1、M3 各 3 道（补录 2002-09 门店销售 27,095 行） | 只报指标名 |
| v2 后 | Agent B | M2、M3 各 3 道（追加“申请”行 170,816 条） | 只报指标名 |

B 从未接触过这些指标，题面也不给定义，所以它答对只有两条路：自己猜对口径，或从共享口径里查到。计分的是后三个阶段的 21 道题。

| 组 | 工具 | 维护方式 |
| --- | --- | --- |
| 直连（早先一次，只有 M1、M3） | 基础三个工具 | 无共享 |
| 普通中间层 | 加 `join_path`、`check_join` 与 SQL 审查 | 无共享口径 |
| 条件级 | 再加 `find_metric` 与声明引用 | 条件级重验 |
| 定义级 | 同上 | 定义级重验 |
| 只看结构 | 同上 | 只比结构指纹 |
| 写入即撤销 | 同上 | 写入后撤销，A 在新快照上重新学习与提炼，成本单列 |
| 无守护 | 同上 | 不维护，执行端也不核对引用 |

其他设置：每题最多 20 轮；Agent 的单条 SQL 超时 60 秒；判题用手写参考 SQL 在同一快照上执行，按题目要求的精度比较。普通中间层组来自计算链修复前的一轮（9-29 22:06）；它不做提炼，修复改动的只是计算链的写法说明，不影响答题。直连组用的是 300 秒超时，只作参考。

命令：`metric-bench --metrics M1,M2,M3 --phrasings named --modes metric-global,metric-global-def,metric-global-schema,metric-global-revoke,metric-global-noguard`（普通中间层另加 `middle`）。

## 5. 实验二结果

有共享口径且做数据级维护的三组（条件级、定义级、写入即撤销）把 21 道计分题全部答对；没有共享口径的普通中间层只答对 11 道；只看结构与无守护在 v2 后答错，M2 的答案正好是标准答案的两倍。

### 5.1 正确率

| 组 | 留出（9 题） | 正常新增后（6 题） | v2 后（6 题） | 合计 |
| --- | --- | --- | --- | --- |
| 普通中间层（无共享口径） | 5 | 2（另 1 题请求澄清） | 4 | 11/21 |
| 条件级（本文） | 9 | 6 | 6 | **21/21** |
| 定义级重验 | 9 | 6 | 6 | **21/21** |
| 写入即撤销 | 9 | 6 | 6 | **21/21** |
| 只看结构 | 9 | 6 | 3 | 18/21 |
| 无守护 | 7 | 4 | 1 | 12/21 |

无守护组的 9 个错误里，只有 v2 后 M2 的 3 题是缺守护造成的。另外 6 个来自 M3 没学到口径：它的两道 M3 学习题提炼时都用了表别名 `sr.`，被 G3 正确拒绝（规范 SQL 里没有这个别名）。早先一次直连组（只有 M1、M3，300 秒超时）答对 5/15。

### 5.2 代价

| 组 | 21 题输入 token | 21 题输出 token | 每题轮数 | 21 题耗时 s | 数据变化后的维护 DB s | 额外代价 |
| --- | --- | --- | --- | --- | --- | --- |
| 普通中间层 | 4.30M | 0.66M | 12.2 | 3306 | — | — |
| 条件级 | 0.52M | 0.12M | 4.9 | 587 | 22.4 | — |
| 定义级 | 0.49M | 0.13M | 4.9 | 613 | 52.9 | — |
| 写入即撤销 | 0.33M | 0.07M | 4.5 | 299 | 0 | 重新学习 8 题，约 57 万 token（含提炼）、904 s；误撤销 2 次 |
| 只看结构 | 0.43M | 0.07M | 4.8 | 331 | 0 | 6 次执行引用过期口径的 SQL，3 题答错 |
| 无守护 | 1.84M | 0.34M | 8.1 | 1576 | 0 | M3 未学到，多出的 token 多来自自行探索 M3 |

共享口径相对普通中间层：输入 token 少约 8 倍（4.30M → 0.52M），每题轮数 12.2 → 4.9，耗时少约 5.6 倍。各共享组另有相同性质的学习成本：A 做 6 道学习题约 11–31 万输入 token，提炼 4.3–5.2 万 token。

### 5.3 维护与过期使用

- **条件级与定义级**：v2 后都撤销 3 条口径并当场修复，6 道 v2 题全部用修复后的口径答对，没有执行过引用过期口径的 SQL。维护 DB 时间条件级 22.4 s（正常新增 5.5 s + v2 16.9 s）、定义级 52.9 s（19.0 s + 33.9 s），约 0.42；请求路径上的守卫与维护 DB 17.6 s 对 51.0 s。这里只有 3 个指标、共享少，差距小于实验一。
- **只看结构**：v2 不改表结构，所以不撤销；6 次检索、声明并执行了过期口径。M2 的 3 题全错，答案是标准答案的两倍（“申请”行被重复计数，例如 6,588,699.86 对 3,294,349.93）。M3 答对，是因为门店销售⋈门店退货的关联有自己的守卫，v2 后要求补上状态过滤；单表口径没有这层兜底。
- **写入即撤销**：正常新增后误撤销 2 条，v2 后撤销 2 条，靠 A 重新学习 8 题恢复（7 题晋升）。本实验里重新学习在 B 答题前完成，所以正确率不受影响；代价是每次写入都要调用 LLM，且恢复前口径不可用。
- **无守护**：v2 后 4 次执行了引用过期口径的 SQL，M2 的 3 题全错，错法与只看结构相同。
- **口径学习**：5 组共 30 次提炼，26 次晋升或佐证，4 次卡在 G3，原因都是聚合表达式用了表别名；审计下没有错误口径晋升。M2、M3 的两道学习题常提炼出结构不同的两条口径，B 查找时会看到两条并被标为有歧义，这次没有影响答题。

## 6. 过程中发现的问题与修复

实验过程中找到 8 个问题，7 个已修。最影响结果的是两个让 M3 学不到口径的门槛问题：计算链只读首个单元格，以及静态检查不认带表名前缀的列。为此共享组作废重跑了两次，正式结果来自 9-30 00:54 开始的一轮。

## 7. 结论、局限与下一步

论文的三个核心论断现在各有一组数据支撑，但都是单次、单模型、合成数据的结果，投稿前要扩大规模并重复。

### 7.1 结论

1. **问题存在**：不改表结构的数据变化会让共享口径悄悄失效。只看结构在两个实验里都把过期口径交给了 Agent，端到端里 M2 的答案翻倍。单表口径最危险，带关联的口径有关联守卫兜底。
2. **条件级维护正确**：在已建模的变化上，过期使用与误撤销在全部组里都是 0，v2 后当场修复，修复后的口径审计全对。这一点与定义级重验相同，不是区别。
3. **条件级维护更省，且收益随共享度增长**：错峰到达时是定义级的 13%–38%，同时到达时 45%–76%。论文里这条主张应以实验一为主；端到端只有 3 个指标，差距小（0.42），作辅证。共享少或同时到达时收益变小，要如实写进论文。

### 7.2 局限

- 每个设置只跑一次（实验一正序、反序各一轮），只用了一个模型；合成数据，判题器与数据同源；端到端每组 21 道计分题。
- 破坏性变化只有 v2 一种。
- 直连组仍是 9-29 的旧数据（300 秒超时、只有 M1、M3）。
- 摘要里“在执行快照上核对”尚未实现，现在是先检查、后执行。
- 本轮的计算链与 G3 两处修复、实验存档与笔记还没有提交到仓库。

### 7.3 下一步

- [ ] 修复窗口：修复进行中的口径让新使用等待修复结果，再跑一次同时到达
- [ ] 提炼提示要求聚合表达式不用表别名
- [ ] 变化类型负载：迟到数据、ETL 重复加载、软删除、维度键复用、改列名
- [ ] 每组重复 3 次以上，加一个官方接口的第二模型
- [ ] 实现快照绑定执行（同一 REPEATABLE READ 事务），或从摘要删去
- [ ] AgentSM 式共享轨迹检索基线与人工语义层上界
- [ ] 用当前设置重跑直连组（M1–M3）
- [ ] 指标扩到十几个，换更接近真实的 schema
