# 通用验证缓存基线与 TPC-DS 自然共享率（2026-10-02）

针对外部评审的两个质疑：(1) 条件级维护的节省是否只是普通验证缓存就能拿到的；(2) 条件共享是否只是本文构造负载的产物。

## TPC-DS 自然共享率

- 来源：TPC-DS 官方查询模板 query1–query99（gregrahn/tpcds-kit 的 `query_templates/` 与 `tools/tpcds.sql`，2026-10-02 下载；模板受 TPC 许可约束，不进仓库）。
- 命令：`python3 tools/tpcds-sharing.py --templates <dir> --schema tpcds.sql --json tpcds-sharing.json`
- 口径见脚本文件头：每个 SELECT 块对某事实表的聚合算一个定义；条件为事实表主键粒度、事实→维表连接多重性、日期角色、事实↔事实连接；身份为（类型、表、键列）。
- 结果（`tpcds-sharing.json`）：99 个模板全部解析，82 个含定义；175 个定义、559 个条件实例、65 个不同条件，每个不同条件平均被 8.6 个实例引用（本文受控负载为 41/7 = 5.9）；49 个条件被至少两个定义共享，97.1% 的实例落在共享条件上。更新 store_sales 时 99 个定义受影响，定义级要做 304 次检查，读到该表的不同条件只有 12 个。
- 解读：共享是独立指标目录的自然性质，不是构造出来的；但按版本缓存的通用缓存同样只需检查不同条件，这一结果不区分 MAVRA 与通用缓存。

## 通用验证缓存基线

- 实现：`MiddleConfig::sql_cache`（`definition-cache` 策略）：定义级重验，维护路径上每条验证 SQL 按规范化 SQL + 读到的表的版本缓存结果，不知道条件类型、不做蕴含，在途合并与其余各组相同（提交 35eddd6）。零共享对照：`--families store,returns,catalog --share 1`（cb097b9）。
- 冒烟（2 万行，`smoke-cache-20k-report.md`）：相对定义级的 DB 时间，错峰时通用缓存 0.15、条件级 0.12、仅范围 0.69；同时到达时通用缓存 0.44、条件级 0.44。两者都是零过期使用、零误撤销。
- 正式运行（1M 行共享度扫描、1M 行零共享、4M 行 k=6）在 noctis `results/motiv-20261001/cb-*`，E1 结束后自动开始。

## 受限修复的语义歧义（反例）

- 场景 `mirror`（`src/scenario.rs`）：2002 年小票号尾数为 3 的退货金额更正减 1；另写入整份退货备份副本（`sr_source = 'backup'`），被更正的行在副本里仍是旧金额。`sr_source = 'primary'`（对）与 `'backup'`（错）都能使每个键恰好一行且不丢键。
- 命令：`AGENTDB_TEST_URL=... cargo test --release -- --ignored postgres_repair_ambiguity --nocapture`（20 万行；报告 `repair-ambiguity-report.json`）。
- 结果：
  - 受限修复的搜索先选中了错误的 `'backup'`（两个候选都通过“每键一行、不丢键”的判定，取决于分组结果的顺序）。
  - 来源列在变化时才新增：中间层目录未刷新，G3 以“不是已知列”拒绝该过滤——这是偶然的拦截，不是语义判断。
  - 来源列在学习前就存在（排除上一条）时，结果取决于 G8 的参照：
    - 参照未预见来源列（学习时的参照 SQL 在当前数据上重算，会把副本一起算进去）：两个候选都不通过 G8，定义保持撤销（安全但不可用）。
    - 参照已预见来源列（与本文基准中预先写入 `sr_status`、`ss_is_current` 的判题 SQL 相同）：两个候选都通过 G8，MAVRA 发布了错误的 `sr_source = 'backup'` 修订，2002 年的新问题答错。
    - 用学习时存档的答案作参照：两个候选同样都通过。
- 含义：结构判定加学习期回归不能区分语义相反的过滤；基准中状态流水与版本化更正的修复成功，依赖判题 SQL 预先知道这些列。论文需要如实写明这一边界，并把修复的语义安全作为未解决的问题或新的设计目标。
