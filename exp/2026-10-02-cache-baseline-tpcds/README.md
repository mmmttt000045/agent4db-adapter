# 通用验证缓存基线与 TPC-DS 自然共享率（2026-10-02）

针对外部评审的两个质疑：(1) 条件级维护的节省是否只是普通验证缓存就能拿到的；(2) 条件共享是否只是本文构造负载的产物。

## TPC-DS 自然共享率

- 来源：TPC-DS 官方查询模板 query1–query99（gregrahn/tpcds-kit 的 `query_templates/` 与 `tools/tpcds.sql`，2026-10-02 下载；模板受 TPC 许可约束，不进仓库）。
- 命令：`python3 tools/tpcds-sharing.py --templates <dir> --schema tpcds.sql --json tpcds-sharing.json`
- 口径见脚本文件头：每个 SELECT 块对某事实表的聚合算一个定义；条件为事实表主键粒度、事实→维表连接多重性、日期角色、事实↔事实连接；身份为（类型、表、键列）。
- 结果（`tpcds-sharing.json`）：99 个模板全部解析，82 个含定义；175 个定义、559 个条件实例、65 个不同条件，每个不同条件平均被 8.6 个实例引用（本文受控负载为 41/7 = 5.9）；49 个条件被至少两个定义共享，97.1% 的实例落在共享条件上。更新 store_sales 时 99 个定义受影响，定义级要做 304 次检查，读到该表的不同条件只有 12 个。
- 解读：共享是独立指标目录的自然性质，不是构造出来的；但按版本缓存的通用缓存同样只需检查不同条件，这一结果不区分 MAVRA 与通用缓存。

## 通用验证缓存基线

- 实现：`MiddleConfig::sql_cache`（`definition-cache` 策略）：定义级重验，维护路径上每条验证 SQL 按规范化 SQL + 读到的表的版本缓存结果，不知道条件类型、不做蕴含，在途合并与其余各组相同（提交 35eddd6）。零共享对照：`--families store,returns,catalog --share 1`（cb097b9）。
- 冒烟（2 万行，`smoke-cache-20k-report.md`）：相对定义级的 DB 时间，错峰时通用缓存 0.15、条件级 0.12、仅范围 0.69；同时到达时通用缓存 0.44、条件级 0.44。两者都是零过期使用、零误撤销。
- 正式运行（1M 行共享度扫描、1M 行零共享、4M 行 k=6）在 noctis `results/motiv-20261001/cb-*`，E1 结束后自动开始。

## 受限修复的语义歧义（反例）

- 场景 `mirror`（`src/scenario.rs`）：2002 年小票号尾数为 3 的退货金额更正减 1；另写入整份退货备份副本（`sr_source = 'backup'`），被更正的行在副本里仍是旧金额。`sr_source = 'primary'`（对）与 `'backup'`（错）都能使每个键恰好一行且不丢键。
- 命令：`AGENTDB_TEST_URL=... cargo test --release -- --ignored postgres_repair_ambiguity --nocapture`（20 万行；报告 `repair-ambiguity-report.json`）。
- 结果：
  - 受限修复的搜索先选中了错误的 `'backup'`（两个候选都通过“每键一行、不丢键”的判定，取决于分组结果的顺序）。
  - 来源列在变化时才新增：中间层目录未刷新，G3 以“不是已知列”拒绝该过滤——这是偶然的拦截，不是语义判断。
  - 来源列在学习前就存在（排除上一条）时，结果取决于 G8 的参照：
    - 参照未预见来源列（学习时的参照 SQL 在当前数据上重算，会把副本一起算进去）：两个候选都不通过 G8，定义保持撤销（安全但不可用）。
    - 参照已预见来源列（与本文基准中预先写入 `sr_status`、`ss_is_current` 的判题 SQL 相同）：两个候选都通过 G8，MAVRA 发布了错误的 `sr_source = 'backup'` 修订，2002 年的新问题答错。
    - 用学习时存档的答案作参照：两个候选同样都通过。
- 含义：结构判定加学习期回归不能区分语义相反的过滤；基准中状态流水与版本化更正的修复成功，依赖判题 SQL 预先知道这些列。论文需要如实写明这一边界，并把修复的语义安全作为未解决的问题或新的设计目标。

## 声明的修订是否被遵循（不调用 LLM，读已有场景记录）

- 问题：执行端检查只能保证“声明的修订仍有效”，不能保证智能体的 SQL 真的按该修订写（评审第 2 点的后半）。
- 命令：`python3 tools/declared-use.py results/scen-20260930 --json declared-use.json`（noctis；条件级与定义级共 15 组、1,289 条留出与变化阶段记录）。
- 口径：用各阶段开始与结束时的审计（同一 (键, 修订) 的规范 SQL 在该阶段数据上逐题比对标准答案）判定定义是否答对，再与记录的回答比较。
- 结果（`declared-use.json`）：
  - 声明了本指标定义的 902 条：follow 823（定义对、回答对）、deviate 11（定义对、回答错）、override 3、stale 65。
  - 声明了有效且正确的修订、回答仍然错的比例为 11/834 = 1.3%：智能体基本按声明的定义作答，但这不是机制保证。
  - stale 65 条中 57 条来自 `unit`（没有任何条件覆盖金额单位变化，已知边界）；其余 8 条（dupload 3、latekey 4、revision 1）多为声明的修订在执行端被拒绝后没有答案。
  - **331/1,289 = 26% 的回答没有声明任何定义**，执行端检查对它们不起作用；保证的适用范围只覆盖声明了修订、且按规范编译路径作答的使用。

## 配对回放：固定指标库，只换维护方式（不调用 LLM）

- 问题：场景评测里条件级与定义级各自学习，正确率差异（宏平均 74% 对 77%，GLM-5.3 Flash 54% 对 65%）混合了学习随机性与维护方式（评审第 4 点的“机制层配对回放”）。
- 实现：`replay-bench` 子命令（`src/replaybench.rs`）。取 `results/scen-20260930` 中 15 个条件级与定义级组学到的指标库（97 条已晋升定义，每库 3–8 条；GLM-5.3 Flash 的条件级组只晋升了 3 条，定义级组 4–8 条），每个库在每种维护方式下各建一个中间层实例，用同一份数据、同一个变化、同一批留出题；答案一律用当时提供的修订的规范 SQL 计算。G8 参照两种：judge = 学习题判题 SQL（本文基准的做法）；example = 智能体学习时自己写的 SQL（部署中可得的参照），只对会修复的条件级与定义级区分。
- 命令：`agentdb-mid --pool 8 replay-bench --libs results/scen-20260930 --rows 200000`（11 个变化，含 mirror；场景评测本身是 1M 行，结果类别与规模无关，耗时与规模有关）；统计 `python3 tools/replay-stats.py report.json`。
- 文件：`replay-report.md`（总表）、`replay-stats.json`（题次级、定义级、按变化、按模型、配对差异与整群自助区间、维护 DB 时间）、`replay-outcomes.json.gz`（逐题结果）。
- 结果：
  - **条件级与定义级在同一库上逐题结果 100% 相同**（judge 参照 1,530 题次、example 参照 1,470 题次，零不一致）。场景评测中两组的正确率差来自学到的库不同，不是维护方式。
  - **通用验证缓存（定义级 + 按版本缓存验证 SQL）逐题结果也与条件级 100% 相同**；维护 DB 时间：条件级 583 秒，通用缓存 613 秒（1.05×），定义级 1,058 秒（1.82×）。通用缓存在重复装载上更快（149 对 277 秒：它也缓存修复搜索的查询），在无需处理的变化上略慢。
  - 提供但答错只出现在 `unit`（101 题次，没有条件覆盖金额单位）；只看结构的方式提供但答错 746 题次；逐写入撤销不重新学习时 0 题答对。
  - **G8 参照决定修复能否成功**：同一批 1,470 题次上，judge 参照答对 933，example 参照答对 780（−10.4 个百分点，按库整群自助 95% 区间 [−11.8, −9.4]）；差别全部是 judge 下修复成功、example 下修复被 G8 拒绝而不可用（130 + 23），没有一题因此答错。分变化：版本化更正 174 → 69 题答对，维表拉链 63 → 9，状态流水不受影响（105 → 99 为准入差异），备份副本在两种参照下都不可用。
  - “不必要的不可用”（judge 下定义级 15 例）几乎都是 M3（退货率）在重复装载、迟到键与备份副本下被撤销：比率的分子分母同步膨胀，答案碰巧仍对，但粒度条件确实被破坏，撤销是保守而非错误。

## 快照绑定执行与并发写入（不调用 LLM）

- 问题（评审第 2 点）：验证在快照 S₁ 上成立，写入随后提交，业务 SQL 在 S₂ 上执行，此时修订号检查仍然通过。原实现的版本源是 `pg_stat` 的 DML 计数（不随事务提交、异步上报）加 ETL 批次登记，验证与执行也不在同一快照。
- 实现（默认关闭，`MiddleConfig::snapshot_exec`）：
  - 事务性版本：`catalog::install_tx_versions` 建 `mavra_versions` 表，被依赖的表上装语句级触发器，在写入事务内把表版本加一，随写入一起提交。
  - 同快照执行（`run_bound`）：声明了指标修订的 `run_sql` 开一个可重复读只读事务，先读事务性版本，逐条核对所引用修订的条件（各关联一侧键唯一、时间维度键唯一、覆盖、粒度），再在同一快照里执行业务 SQL；任一条件不成立即拒绝。
  - 结论复用：条件结论按“条件 + 读到的表的事务性版本”记录；同版本的快照看到的这些表的数据相同，所以结论可直接复用，并发的同一检查只执行一次。维护时的检查前后各读一次事务性版本，两次相同（其间没有写入提交）才记录，供之后同版本的快照使用，避免写入后维护与快照各查一遍。
- 实验：`postgres_snapshot_binding`（`src/integration_tests.rs`；20 万行；M1 门店营业额；违反条件的写入为 2002-06 至 09 的门店销售整批重复一次）。判定：探针在同一语句里同时算答案与该月销售行的重复键数，重复键数 > 0 即“答案算在违反所引用修订粒度条件的数据上”（violation）。
- 命令：`AGENTDB_TEST_URL=... AGENTDB_SCENARIO_ROWS=200000 AGENTDB_SNAP_TRIALS=10 cargo test --release -- --ignored postgres_snapshot_binding --nocapture`；汇总 `python3 tools/snapshot-stats.py report.json`。
- 文件：`snapshot-binding-report.json`、`snapshot-binding-stats.json`（最终版，v3）；`snapshot-binding-v1-*`为第一版（判定探针扫全表、相同查询在途合并，随机并发里两种模式都没有出现违规，见下）。
- 结果（v3）：
  - 确定性交错（各 10 次）：核对通过后、执行前提交写入——预检查 10/10 violation，快照绑定 0/10（在写入前的快照上作答）；写入刚提交、未通知就调用——预检查 7/10 violation（3 次统计计数已上报被拦下），快照绑定 10/10 拒绝；写入提交并通知后调用——两种都 10/10 拒绝。
  - 随机并发（4 个读者，每次间隔 10 ms，3 秒窗口，写者随机时刻写入，每组 20 次试验）：

    | 写者协议 | 读者查询 | 预检查 violation / 作答 | 出现违规的试验 | 快照绑定 violation / 作答 |
    |---|---|---|---|---|
    | 提交后不通知 | 相同 | 141 / 3,077（4.6%） | 19/20 | 0 / 2,767 |
    | 提交后不通知 | 不同月份 | 120 / 3,128（3.8%） | 19/20 | 0 / 2,849 |
    | 提交后立即通知 | 相同 | 8 / 2,848（0.28%） | 2/20 | 0 / 2,818 |
    | 提交后立即通知 | 不同月份 | 2 / 2,934（0.07%） | 1/20 | 0 / 2,863 |

    预检查的违规在不通知时出现在提交后 0–157 ms（版本缓存与统计上报的滞后窗口），在通知时来自提交前 0.4–4 ms 已通过核对、提交后才开始执行的调用。快照绑定四组合计 0 / 11,297（每组 Wilson 95% 上界 ≤ 0.14%）。
  - 读者代价：随机并发下两种模式吞吐与延迟相同（p50 约 28 ms，p95 37–62 ms）；单读者无写入时 p50 6.9 对 5.1 ms（多两次往返：开启事务与读版本），写入后第一次调用 1,095 对 1,188 ms（维护时的结论被快照复用）。
  - 写者代价（有无触发器，三轮中位数）：顺序单行语句吞吐 0.78×，8 个连接并发单行语句 0.62×（同表的版本行成为热点），每条 1 万行的批量语句 1.02×。分析型负载以批量 ETL 为主时代价可忽略；高并发小事务写入需要分片计数或按事务合并的版本号（未实现）。
  - 版本计数分片（之后新增，默认 16 片，`catalog::install_tx_versions`）：每表的计数分成 16 行，按写入后端的进程号选行，版本取各行之和（PostgreSQL 中后取的快照看到的已提交事务集合包含先取的，和相同即看到的写入相同）。`snapshot-binding-shards-*`（只跑写者开销与交错；与配对回放等并行，绝对吞吐有噪声，三轮中位数）：

    | 写者 | 每表一行 | 16 片 |
    |---|---|---|
    | 32 个连接并发单行语句 | 0.36× | 0.97× |
    | 8 个连接并发单行语句 | 0.65× | 0.81× |
    | 顺序单行语句 | 0.72× | 0.70× |
    | 每条 1 万行的批量语句 | 1.03× | 1.05× |

    分片消除了版本行热点；剩下的是每条写语句多一次插入或更新的固定代价（顺序单行约 0.7×）。分片后交错实验结果与上面相同（预检查 10/10 与 7/10 违规，快照绑定 0）。
  - 第一版的教训：相同查询会合并到在途执行、判定探针本身很慢时，竞争窗口被掩盖（v1 两种模式都是 0 违规）；v2 起改为按月判定、读者问不同月份；v2 中快照模式的 p95 尾部来自并发的同一检查各自重跑，v3 合并后消失。

### 修复候选唯一性（针对上面的反例，2026-10-02 新增，默认打开）

- 实现：`MiddleConfig::repair_unique`（默认 true）。粒度修复不再取搜索到的第一个过滤，而是列出全部能恢复“每键一行、不丢键”的过滤；不止一个时，结构判定分不出哪个在业务上是对的，不自动修复，定义保持不可用，修复事件写明全部候选。关闭时为早期行为。
- 本文已有的修复场景不受影响：状态流水中“申请”、版本化更正中旧版本、维表拉链中历史行都只覆盖部分键，过不了“不丢键”，候选唯一；只有完整的备份副本会出现两个都通过的候选。
- 结果（`repair-ambiguity-unique-report.json`，来源列学习前已存在的变体）：

  | G8 参照 | 唯一性要求 | M2 / M3 | 修复事件 |
  |---|---|---|---|
  | 未预见来源列 | 关 | 不可用 | 选中 `backup`，G8 拒绝 |
  | 未预见来源列 | 开 | 不可用 | 候选不唯一（`backup`、`primary`），不修复 |
  | 已预见来源列 | 关 | **发布 `backup`，新问题 4 题答错 2 题** | 选中 `backup`，G8 通过 |
  | 已预见来源列 | 开 | 不可用 | 候选不唯一，不修复 |

- 配对回放复核（`replay-unique-report.md`；条件级、两种参照，同 15 个库、11 个变化）：与关闭时逐题对比 3,000 题次，**结果类别零变化**——唯一性要求不影响已有修复的可用性。维护 DB 时间 701.5 对 582.8 秒（约 +20%），来自修复搜索要检查全部候选列而不是找到第一个就停（两次都与 E1 16M 并行，有噪声）。
- 含义：错误修复的来源是“搜索取第一个”，而不是 G8 本身；要求候选唯一后，反例在两种参照下都退化为安全的不可用。修复的边界可以写成：结构上唯一的过滤才自动修复，多个候选交给业务确认。
