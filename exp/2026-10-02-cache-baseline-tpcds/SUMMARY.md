# 回应外部评审的实验：阶段小结（2026-10-02 凌晨，持续更新）

## 已有结论

1. **通用验证缓存基本拿到了条件级维护的全部数据库节省**（冒烟，2 万行；1M / 4M 正式结果见下）。定义级 + 按“规范化 SQL + 读到的表的版本”缓存验证结果，错峰时为定义级的 15%（条件级 12%），同时到达时 44%（条件级 44%）；两者都是零过期使用、零误撤销。受控实验中条件蕴含从未触发（80 行 `implied` 全为 0），收益来自依赖范围跳过和完全相同条件的复用，这两项通用缓存都能做到。
   → “条件级复用更省数据库时间”不能单独作为主贡献；它可以作为“维护对象选对了之后，用标准的版本缓存即可高效实现”的工程结论。
2. **条件共享是独立指标目录的自然性质**：TPC-DS 官方 99 个查询模板导出 175 个定义、559 个条件实例、65 个不同条件（每个条件平均 8.6 个实例；本文受控负载为 5.9）。更新 store_sales 时定义级要做 304 次检查，读到它的不同条件只有 12 个。
   → 共享不是构造出来的，但这个结果同样不区分 MAVRA 与通用缓存。
3. **受限修复不能保证语义正确（新反例）**。备份副本场景中 `sr_source = 'primary'`（对）与 `'backup'`（错）都使每个键恰好一行且不丢键，修复搜索先选中了错误的 `backup`。
   - 参照 SQL 未预见来源列（真实部署中学习时的参照就是这样）：G8 把两个候选都拒绝，定义只能撤销（安全但不可用）。
   - 参照 SQL 已预见来源列（本文基准里判题 SQL 预先写了 `sr_status`、`ss_is_current`）：两个候选都通过 G8，**MAVRA 发布了错误修订，新问题答错**。
   → 论文中“状态流水与版本化更正的修复成功”依赖判题 SQL 预先知道这些列，属于评估效度问题，必须写明；修复的语义安全是未解决的问题。
4. **数据规模（E1）**：维护代价随事实表行数线性增长（1M → 4M 约 ×4），条件级相对定义级的比例不变（错峰 13%，同时 43%）。16M 进行中。

## 进行中

## 对主线的含义（待正式结果确认）

- 节省数据库工作量的部分，通用缓存可以替代；MAVRA 的独特部分只能落在：从学习得到的定义推出该检查什么（有效性模型）、何时允许使用（撤销与执行端约束，含快照绑定）、以及修复的边界。
- 修复部分需要降级表述：现有修复在参照能分辨时可用，参照分辨不了时要么拒绝一切修复、要么放过语义错误的修复。
