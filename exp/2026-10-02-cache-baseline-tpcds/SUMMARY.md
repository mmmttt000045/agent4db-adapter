# 回应外部评审的实验：阶段小结（2026-10-02，持续更新）

细节、命令与文件见同目录 `README.md`。以下都不调用 LLM。

## 已有结论

1. **通用验证缓存拿到了条件级维护的全部节省，答案也完全相同。**
   - 配对回放（15 个模型学到的指标库、11 个变化、约 1,500 题次）：条件级、定义级、通用缓存（定义级 + 按“规范化 SQL + 表版本”缓存验证结果）三者逐题结果 100% 相同；维护 DB 时间 583 / 1,058 / 613 秒（通用缓存为条件级的 1.05×）。
   - 受控冒烟（2 万行）同样：相对定义级，错峰时通用缓存 0.15、条件级 0.12，同时到达时都是 0.44；条件蕴含从未触发（80 行 `implied` 全为 0）。正式的共享度扫描与零共享对照在跑（见“进行中”）。
   → “条件级维护更省”不能作为主贡献，只能作为“维护对象选对之后，用标准的版本缓存即可高效实现”的工程结论。
2. **场景评测里条件级与定义级的正确率差不是维护方式造成的。** 配对回放中两者在同一库上逐题相同；差异来自各自学到的库（例如 GLM-5.3 Flash 的条件级组只晋升了 3 条定义，定义级组 4–8 条）。论文里两组的正确率对比要改成配对回放，或明确它反映的是学习的随机性。
3. **条件共享是独立指标目录的自然性质**：TPC-DS 官方 99 个模板导出 175 个定义、65 个不同条件，每个条件平均 8.6 个实例（本文受控负载 5.9）；更新 store_sales 时定义级要做 304 次检查，不同条件只有 12 个。但这一结果同样不区分 MAVRA 与通用缓存。
4. **快照绑定执行已实现并验证（默认关闭）**：事务性版本（写入事务内的触发器）+ 在同一可重复读快照里核对条件并执行。
   - 核对与执行之间提交写入：原预检查 10/10 次在违反条件的数据上作答，快照绑定 0/10。
   - 随机并发 4 组合计：快照绑定 0 / 11,297 次作答违规；原预检查在写入不通知时 3.8–4.6% 的作答违规（20 次试验中 19 次出现），即使写入后立即通知也有 0.07–0.28%（检查与执行之间的竞争）。
   - 代价：读者吞吐与延迟不变（p50 约 28 ms）；写者每条语句多一次版本计数更新，顺序单行语句约 0.7×，批量语句约 1.03×。版本计数改为 16 片后，32 个并发写者从 0.36×（同一版本行成为热点）恢复到 0.97×。
   → 这是通用缓存不提供、MAVRA 可以独立主张的部分：**定义有效性证据与执行快照的绑定**。
5. **受限修复的成败取决于 G8 参照，且参照分辨不了时可能发布错误修复。**
   - 配对回放：参照用本文基准的判题 SQL（预先写入了 `sr_status`、`ss_is_current`、`i_is_current`）时答对 933 / 1,470；改用智能体学习时自己写的 SQL（部署中真正可得的参照）时答对 780（−10.4 个百分点，95% 区间 [−11.8, −9.4]）。差别全部是修复被拒绝而不可用（版本化更正 174 → 69 题答对，维表拉链 63 → 9），没有一题因此答错。
   - 反例（备份副本）：两个语义相反的过滤都恢复粒度且不丢键；参照未预见来源列时两者都被拒绝，参照预见了来源列时发布了错误的那个，新问题答错。
   - **修复候选唯一性（新增，默认打开）**：错误修复的直接原因是搜索取第一个通过的过滤。改为列出全部候选、不止一个就不自动修复后，反例在两种参照下都变成安全的不可用；本文已有的修复场景候选都唯一（“申请”、旧版本、历史行只覆盖部分键），不受影响（配对回放复核：3,000 题次结果零变化，修复搜索的 DB 时间约 +20%）。
   → 论文中“状态流水与版本化更正修复成功”依赖判题 SQL 预先知道这些列，必须写明；修复的边界写成“结构上唯一的过滤才自动修复，且须通过 G8；参照分辨不了或候选不唯一时拒绝”，语义正确性仍取决于参照，不作保证。
6. **同时到达时的不可用来自修复期间拒绝请求，已修正。** 让修复进行中到达的使用等待那次维护（`wait_repair`，默认打开）后，20 万行、k=6、同时到达 3 轮：定义级不可用 30 → 0，条件级 63 → 0，等待时长、数据库代价、过期使用与误撤销都不变。评审指出的“条件级不可用更多”（43/304 对 24/304）由此消除。
7. **保证的适用范围**：已有场景记录中，声明了有效且正确修订的回答仍然答错的只有 11/834（1.3%），但 26% 的回答根本没有声明定义，执行端检查对它们不起作用。保证只覆盖“声明了修订、按规范编译路径作答”的使用。
8. **数据规模（E1，已完成）**：维护代价随事实表行数线性增长，条件级相对定义级的比例不随规模变化。错峰：定义级 184.9 / 762.6 / 2,992.7 秒，条件级 23.3 / 98.8 / 360.5 秒（1M / 4M / 16M，比例 0.126 / 0.130 / 0.120）；同时到达比例 0.417 / 0.433 / 0.390。三种规模都是零过期使用、零误撤销（`e1-scaling-stats.json`；旧二进制，没有等待修复，同时到达的不可用为条件级 26 / 27 / 32、定义级 14 / 10 / 14；16M 与快照、回放实验部分时段并行）。
9. **金额单位变化**仍是唯一“提供但答错”的来源（配对回放 101 题次），属于已知边界：没有任何结构条件覆盖业务单位。

## 对论文主线的建议

- 主线收敛为：**学习得到的共享指标定义，其有效性证据如何随数据库变化被维护，并在使用时得到保证。**
- 独特贡献落在三处：(a) 从学到的定义推出该检查什么（有效性模型：粒度、连接多重性、时间角色、覆盖）；(b) 何时允许使用——撤销、执行端修订检查，以及新实现的快照绑定（第 4 条，有并发实验支撑）；(c) 修复的边界——给出 G8 参照何时足够、何时会拒绝、何时会错放（第 5 条）。
- 效率部分降级：条件级维护与“定义级 + 版本缓存”等价（第 1 条），写成实现选择与代价分析，不作为贡献。
- 评估改为两层：机制层用配对回放（第 1、2、5 条），端到端层报告多次独立运行的正确率、拒绝率与成本。
