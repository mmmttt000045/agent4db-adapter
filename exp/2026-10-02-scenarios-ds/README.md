# 场景主实验（DeepSeek V4.1 Flash，2026-10-02 起）

按用户要求，设计定下之前只用订阅模型 `cline-pass/deepseek-v4.1-flash`（新的 ClinePass 账号，密钥只在 noctis `.env`）；设计确定后主实验再补其他模型。

## 设计

- 二进制：noctis `target/release`，源码 `cd3e02e` 起未变（修复候选唯一性 `repair_unique`、等待进行中的修复 `wait_repair` 默认打开；绑定快照执行默认关闭——场景中更新在阶段之间施加，没有并发写入）。
- 方法 7 种：不共享 `middle`、轨迹检索 `traj-global`（新增，AgentSM 式匹配基线）、无守护、只看结构、写入即撤销（重新学习）、定义级、条件级（MAVRA）。
- 变化 11 种：原 10 种 + 备份副本 `mirror`（修复歧义反例）。
- 每种方法 3 次独立重复（每次重新学习）；方法顺序按重复轮换；100 万行；题面只给指标名（named）。
- 6 个进程并行（ClinePass 并发上限），相邻启动间隔 60 秒：`queue-scen-ds.sh`。
- 输出：noctis `results/scen-20261002/dsv41flash-r{1,2,3}-{a,b}/`。

## 轨迹检索基线冒烟（20 万行，1 次，变化 status 与 mirror）

- 10 道学习题全部入库（判题成功且计算链可复核），留出与变化阶段每题平均检索约 1 次。
- 留出题 15/15 答对：数据不变时，按题面检索成功轨迹与共享定义一样有效。
- 状态流水下退货金额 3 题全错（沿用不带状态过滤的旧 SQL，金额翻倍）；备份副本下 6 题错 2 题。
- 输出：noctis `results/scen-20261002/smoke-traj/`。

## 分析方案（2026-10-02 10:50 写定，早于看到任何结果；之后不改）

1. **计分题**：留出题与 11 种变化下重问的题；学习题与写入即撤销的重新学习题不计分。
2. **失败的归类**（对所有方法同一规则）：
   - 服务端失败（HTTP 错误、用量上限、限流、网络中断等，记录的 error 来自请求本身）不计分；学习阶段出现服务端失败的组整组重跑（同一方法、同一重复编号），原组保留在原始结果中但不进统计，重跑次数如实报告。
   - 模型自身造成的失败（工具调用格式错误、输出了原始工具调用标记、答案无法解析、请求澄清、答错）按答错计分，不排除、不重跑。学习阶段的这类失败只意味着该组少学到一个定义，组保留。
   - 每个 error 记录先按其错误信息归类，再适用上述规则；无法判定来源的按服务端失败处理并在报告中单列。
3. **主要指标**：各方法正确率（每种变化等权，留出单列）、过期使用题数、不可用（撤销后无替代修订）、每题轮数与输入 token、维护数据库时间。
4. **不确定性**：95% 区间按组（方法 × 重复）整群自助法，而不是按题重抽样。
5. **预先声明的比较**：(a) 已建模的破坏性变化下 MAVRA 与轨迹检索、定义级的差别；(b) 全部情形下 MAVRA 与不共享的差别；(c) 留出题上 MAVRA 与轨迹检索预期相当（冒烟中轨迹检索 15/15）。
6. **全部报告**：不在看到结果后删除方法、变化或组；区间重叠时写“无可分辨差别”；某方法在某变化下优于 MAVRA 时如实写入并解释。

## 运行记录

- 10:15 启动 6 组。至 11:50 共 9 道题记为 error，全部 0 轮。读出的错误信息为服务端失败：Cline 网关把上游（Vercel）的限流包成 HTTP 500 返回——“this team's limit of 100000000 input tokens per minute (per region) was reached. Retry after 57s”。客户端把 500 当服务端错误只重试 3 次（共约 14 秒），短于要求的 57 秒，于是放弃。
- 按预先写定的规则：这些题不计分；学习阶段出现这类失败的组（r2-b 的条件级、r3-a 的写入即撤销各 1 组）整组重跑。
- 12:02 修复客户端（提交 `Treat upstream rate limits wrapped in HTTP 500 as 429`）：正文含 rate limit exceeded 的 5xx 按限流处理，按正文中的 Retry after 秒数等待，最多 8 次。只改服务端失败的重试，对所有方法相同。
- 12:05 起 `supervise-scen-ds.sh` 在每组完成当前单元后停止旧进程、清理其临时库、用新二进制以剩余方法重启该组；已完成的单元全部保留，刚开始的单元作废重来。
- 12:57 六组都已切换到新二进制，切换后各组再无 error。清理了被停止进程留下的 6 个临时库（`supervise-scen-ds.sh` 中的清理语句因经 ssh 单引号写入丢了引号而没生效，改为手工清理；存档的脚本保持原样）。
- 13:05 已完成各组的 error 全部为服务端失败（按错误信息归类）。规则补充（只依据失败类型，未看任何正确率）：写入即撤销的“重新学习”也属学习阶段。据此整组重跑 3 组：r2-b 条件级（学习失败）、r3-a 写入即撤销（学习与重新学习失败）、r1-b 写入即撤销（重新学习失败）。由 `rerun-scen-ds.sh` 在有空位时启动，被替换的原组记在 `results/scen-20261002/replaced.txt`，统计时排除。计分阶段的服务端失败只排除该题。
- 19:43 全部完成：21 次有效运行（7 种方法 × 3 次），3 次被替换的原运行排除；计分题 2,010 道，服务端失败 6 道不计分。

## 分析方案增补（2026-10-03，写于启动增补运行之前；之后不改）

增补两种方法，各 3 次独立重复，其余（模型、数据规模、题目、变化、并发、失败归类、整群自助法）与主实验完全相同，输出到同一目录（`queue-ablate-ds.sh`）：

- `metric-global-exref`：条件级维护（MAVRA），但修复回归 G8 的参照改为提炼出的示例 SQL（G6 已核实它复现智能体自己的答案），而不是基准作者手写、预先带有状态与版本过滤的判题 SQL。回答审稿人的问题：主实验里修复成功依赖部署中拿不到的参照（配对回放第 7.4 节：换参照后 1,470 题少答对 10.4 个百分点），端到端还剩多少优势。
- `traj-verify`：轨迹检索基线加一句系统提示，把 MAVRA 维护的四类条件直接告诉智能体，要求它在复用检索到的 SQL 之前自己核对（键唯一、关联不放大、日期能关联），不成立就补过滤。回答“让智能体自己验证是否就够了”。

预先声明的比较（都在已建模的破坏性变化上，按运行整群自助法 95% 区间）：

- (d1) `metric-global-exref` − `traj-global`：用部署可得的参照时 MAVRA 相对轨迹检索还剩多少优势；预期为正但小于主实验的 +16。
- (d2) `metric-global-exref` − `metric-global`：参照的代价；预期为负，差别全部表现为不可用而不是答错（配对回放的结论）。
- (e1) `traj-verify` − `traj-global`：自验证提示的收益；(e2) `metric-global` − `traj-verify`：MAVRA 相对自验证基线的剩余优势；(e3) 同上但在全部情形上。

报告规则同主方案第 6 条：全部报告，区间重叠时写“无可分辨差别”，某方法在某变化下优于 MAVRA 时如实写入并解释。
