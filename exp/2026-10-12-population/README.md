# 群体评测：共享记忆 vs 单智能体记忆（2026-10-12 起）

10-12 用户把论文主线改为“跨智能体共享记忆省下大量时间与 token”，对照现有的单智能体记忆工作；并选定补这个实验（完整版）。
已有实验都是“一个内置学习智能体先学、使用者再用”，没有“每个智能体只用自己的记忆”的对照，也没有代价随智能体数量变化的曲线。

## 设计（写于看到任何结果之前）

- `metric-bench --population`（提交 7ab15d5 起）：16 个智能体 U1..U16 依次到来（同时在场 1 个），每个智能体按顺序答 7 道题，
  从题集 v2 的 35 道题（5 个指标 × 2 道学习题 + 5 道计分题）中不放回抽样、顺序随机；学习题给出业务定义，其余题只给指标名。
  第 r 次重复用种子 r 抽题，四组抽到的题相同（配对）。
- 记忆从空开始，只从“给出业务定义、答案与参考答案一致”的会话学习（与主实验的学习前提相同）：
  - MAVRA（`metric-global-snap`）：会话没有声明使用已有定义时，提炼并经发布前检查发布到共享记忆，所有智能体可用；
  - 单智能体记忆（`metric-private`）：同样的学习、检查与维护，但定义只属于学到它的智能体（`Scope::Agent`）；
  - 示例检索（`traj-global`）：保存这次会话（同一道学习题只保存一次），所有智能体按题面检索；
  - 无记忆（`middle`）：同样的工具，没有跨会话状态。
- 之后施加“更正保留旧行”（revision：2001 年起小票号尾数为 7 的销售，旧金额保留为 ss_is_current = 0 的行），
  同一批 16 个智能体回来，各答 4 道读到 store_sales 的题（种子 r + 1000）。单智能体记忆组里每个智能体各自维护自己的定义。
- 100 万行合成零售数据，模型为 happycoding 网关 deepseek-v4.1-flash（智能体与提炼器），20 轮，60 秒 SQL 超时，5 次独立重复。
- 同时修改（7ab15d5）：`find_metric` 在同一任务里对已完整返回过的定义只给键与版本；只有失效条目匹配时提示直接探索。
  原因：主实验中定义失效后，MAVRA 使用者每题调用 find_metric 14–25 次，每次都拿到整段定义，每题 6.8–7.1 万 token。
  这项修改对四组都生效（只有指标组用 find_metric）。

## 分析方案（写于看到任何结果之前）

1. 每题代价：token = 智能体会话的输入 + 输出 token，若这次会话触发了学习，再加提炼的 token（学习代价记在触发它的会话上）；
   时间 = 智能体会话从第一次调用到最终答案的秒数（用户等待的时间）。学习在答完之后进行，其秒数（提炼与发布前检查）单列为后台工作。
2. 主要指标：v1 阶段前 N 个智能体（N = 1, 2, 4, 8, 16）的累计 token 与时间、正确率；后 8 个智能体的每题代价；
   更正之后的正确率、每题代价、过期使用（声明使用了在该快照上审计为答错的定义）与维护数据库时间。
3. 预先声明的比较：MAVRA 与无记忆、单智能体记忆、示例检索在 16 个智能体累计 token 与时间上的差别；更正之后 MAVRA 与示例检索的正确率。
4. 服务端失败不计分、不计代价；学习阶段出现服务端失败的组照常保留（群体评测没有单独的学习阶段）。每次重复的值都报告，给出 5 次的范围。
5. 全部报告：不删除组或重复。

## 第二版设计（10-12 晚；在看到上述部分结果与 TPC-DS 试跑之后修改，原因如下）

查出三处问题，都使各组差距被低估：

1. 无记忆组并非无记忆。中间层的表结构知识（表描述、关联路径、守卫依据）与查询结果缓存默认全局共享（`MiddleConfig.scope = Global`），
   `middle` 组后到的智能体直接拿到前人探出的关联与结果；`metric-private` 也一样只私有了定义。
   改为：无记忆 = 新组 `middle-alone`（表结构知识与结果缓存只在一道题内有效）；单智能体记忆 = `metric-private`，定义与表结构知识都只属于该智能体
   （提交 df9f89c）。示例检索与 MAVRA 不变（全局共享）。
2. 提示让记忆组照样探索。基础提示要求“先弄清表结构与关联方式”，记忆工具只说“可以作为参考”，MAVRA 智能体找到已验证的口径后仍列表、看表。
   两种记忆的提示改为同一句：找到与题目相符的口径 / 解题过程时，直接据此写 SQL，不必再查看表结构（提交 aac6549）。
3. 场景太小。合成数据只有几张表、100 万行，探索 5–6 步即可。改用 TPC-DS SF1（24 张表，store_sales 288 万行，模板库 `tpcds_sf1`），
   5 个指标取自由 TPC-DS 查询模板导出的定义库（`tpcds-defs.json`，提交 4bd0b45；带维度过滤与关联：1 号品类经理、登记顾客、
   员工数 200–295 的门店、关联得上门店的退货、TPC-DS 年度汇总口径）。更正（revision）施加在 store_sales 上。

TPC-DS 试跑（`results/pilot-pop-tpcds`，1 次，8 个智能体 × 7 题，无回访，第 3 个智能体起每题均值）：

| 组 | 步数 | 秒 | 数据库秒 |
|---|---|---|---|
| 无记忆（middle-alone） | 7.0 | 32.0 | 2.49 |
| 示例检索 | 3.4 | 5.4 | 0.37 |
| MAVRA | 3.1 | 4.8 | 0.20 |

旧设置下（`results/pilot-pop-tpcds-old`）同样的题：middle 4.8 步 14.5 秒，MAVRA（旧提示）4.2 步 9.7 秒。

其余设计与分析方案不变（16 个智能体 × 7 题，更正后各回答 4 道，5 次独立重复，同一抽题配对）。
数据库换成 TPC-DS 后，每组复制一份 2.4 GB 的模板库（MAVRA 与单智能体记忆另复制一份学习时快照库），noctis 剩余约 35 GB，
因此同时运行 5 组。SQL 超时 120 秒（同 TPC-H 端到端）。

- 正式：`queue-pop-tpcds.sh` → noctis `results/pop-tpcds-20261012/r{1..5}-<mode>/`；
  统计 `tools/population-stats.py --runs results/pop-tpcds-20261012`。
