## 结论（第一轮试跑，10-21 下午）

**P2 门槛没过，正式实验暂不启动，等你决定。** 截点 2–5 的 12 个会话里，MAVRA 的 token 是无记忆组的 0.361 倍（门槛 ≤ 1/3），user-badge 测试 AUC 低 0.018（容差 0.01）。同时 LLM 调用少 79%（45 对 215），工具调用少 78%（95 对 439）。

- **在有目标的会话里，省 token 的效果很明显。** 11 个有目标的会话：MAVRA 46.8 万 token，无记忆 282.8 万，比值 0.166；其中 9 个只用 2 次 LLM 调用就达到目标。超标全部来自截点 5 的 user-engagement：两组都没有目标（上一期方案在本期审计为泄漏），MAVRA 一直探索到上限，用了 64.7 万 token。
- **user-badge 的质量差距从截点 1 就有，之后被复用固定下来。** MAVRA 截点 1 的会话还没有记忆可用，和无记忆组条件相同，它的方案测试 AUC 0.827，无记忆组 0.844。之后 MAVRA 每期复用这个方案、一验证就达标；无记忆组每期重新探索，每期都有机会找到更好的方案。
- **MAVRA 的智能体时间被网关停顿拉长。** 4,614 s 对 5,868 s，其中 1,519 s 是 5 次会话首个请求的 300 s 超时（框架复用了空闲几分钟的连接，已修）。去掉后为 3,095 s，快 1.9 倍。
- **两个框架问题已修**：网关连接空闲 30 s 后重建；新写的队列脚本与 Python 标准库重名，已改名。泄漏审计只抽 500 个种子，会漏掉少量泄漏，是否加大由你决定。

**需要你决定的事**（详见“正式实验的选项”一节）：

1. 停止规则和质量比较怎么处理 user-badge 这类“复用即达标、不再改进”的情况。
2. 泄漏审计的种子数。
3. APC 的小模型，或不做 APC。
4. 用哪几个库、跑几次，以及正式实验前是否先在 rel-trial、rel-amazon 上做小规模试跑。

## 试跑的实验设计

试跑只用 rel-stack 一个库、1 次运行，比较无记忆与 MAVRA 两组；完整方案见 `exp/2026-10-20-relbench/README.md`。

| 项目 | 设置 |
| --- | --- |
| 基准 | RelBench v1 rel-stack（7 张表），任务 user-engagement、user-badge、post-votes，窗口 91 天 |
| 截点 | 5 个：test_k = 2020-01-03、2020-04-03、2020-07-03、2020-10-02、2021-01-01；截点 5 即官方划分，标签与官方 parquet 逐行一致 |
| 数据变化 | 截点之间把新一期的行真实追加进库 |
| 智能体 | 每个任务一个智能体，每个截点开一个全新会话，共 15 个会话 |
| 模型 | river 网关 DeepSeek-V4.1-Flash，思考强度 high |
| 工具 | list_tables、describe_table、join_path、check_join、run_sql、validate_features、submit；MAVRA 另有 find_program、find_features、compose_features |
| 学习器 | 固定 LightGBM 4.6，训练种子抽 5 万行；参照 = 只用实体表自身的列 |
| 预算 | 每会话 ≤ 40 次 LLM 调用、≤ 8 次验证，连续 2 次不提升即停 |
| 停止规则 | 从截点 2 起，验证分数达到目标即停；目标 = 本组上一期的最终特征 SQL 在本期数据上重新拟合的验证分数 |
| 泄漏审计 | 每次验证都做：在最晚训练种子时刻取 500 个种子，用“只含该时刻以前行”的视图重算特征并比较；泄漏的验证不计分，泄漏的提交被拒 |
| MAVRA | 共享按实体、相对种子时间窗口的特征定义和任务方案（含整份通过审计的 SQL）；会话后提炼定义，经字段、粒度、重现（2,000 个种子）及不泄漏四项检查才发布 |
| 并行 | 无记忆组同一截点 3 个会话并行；MAVRA 一个接一个（后一个能用上前一个发布的内容） |

门槛（事先写定）：P1 无记忆组五条；P2 从截点 2 起 MAVRA 的 token ≤ 无记忆的 1/3，测试分数不劣（分类 AUC 容差 0.01，回归 MAE 容差 2%）；P3 每个基线的行为与原文一致。

## 试跑期间的设计修订

试跑期间共修订 8 次：1 次在 P1，7 次在 P2。P2 的每次修订都停掉当时的运行（移到 `results/relbench-pilot/aborted/`，不计），再用同一抽签从头重跑；其中前 3 次在看到任何节省数据之前。

| 时间 | 修订 | 原因 | 决定 |
| --- | --- | --- | --- |
| 10-21 13:30 | 目标改为“上一期模型在本期重新拟合的验证分数”；MAVRA 的任务方案另存整份通过审计的 SQL | 按“上一期最好分数”作目标时，新一期数据更难就两组都达不到、探索到上限，节省被数据难度掩盖 | 用户 |
| 10-21 09:50 | 每次验证都做泄漏审计，泄漏的验证不计分，泄漏的提交被拒 | 无记忆组 user-badge 截点 3 用泄漏特征得到验证 AUC 0.987，立即“达标” | 框架修订，对所有组相同 |
| 10-21 01:40 | 从截点 2 起“达到目标即停” | post-votes 截点 2 第 2 次调用就已不差于上一期，原规则仍探索到 40 次调用、106 万 token | 用户 |
| 10-20 23:30 | 定义覆盖面：EXTRACT 的 FROM 不当子查询；白名单加 exp、sign、mod、trunc；实体可带 anchor（关联实体的特征） | 学习时大部分特征被拒，方案只剩 3 条定义 | 实现修订，不涉及得分 |
| 10-20 22:15 | MAVRA 提示写明用法：先查方案与定义，先验证返回的 SQL，需要改进时再探索 | 原提示只写“Using them is optional”，智能体照旧自己探索；各基线原文都给出记忆的用法 | 实现修订 |
| 10-20 22:00 | find_features 直接返回编译好的 SQL；定义可用 seed_time 与常用标量函数 | 智能体拿到定义却不编译；“距上次……多少天”一类特征写不成定义 | 实现修订 |
| 10-20 21:30 | 学习条件改为“提交优于参照”，泄漏列不进提炼器 | 原先要求整份提交审计 clean，会少学约四分之一的会话；每条定义仍要过重现与不泄漏检查 | 实现修订 |
| 10-20 20:38 | 特征查询加 LIMIT 种子数 + 1；每次运行限 24 GB 内存 | 一个放大百万倍的查询把框架进程撑到 58.7 GB，noctis 交换约两小时 | 框架修订 |

## P1：无记忆组五条门槛全部通过

rel-stack 上的无记忆智能体确实在做一份数据工作，而且重复很多：第 2 个及以后的会话里，97% 的看结构调用在更早的会话中出现过。

| 门槛 | 要求 | 结果 |
| --- | --- | --- |
| (a) 正常结束 | ≥ 13/15 | 15/15 |
| (b) 每会话 LLM 调用中位数 | ≥ 15 | 16 |
| (c) 看结构 + 探查占工具调用 | ≥ 30% | 86% |
| (d) 验证分数优于参照 | ≥ 2/3 | 15/15 |
| (e) 看结构调用在更早会话出现过 | ≥ 50% | 97% |

代价：每会话 token 中位数 19.6 万（15 个会话合计 416 万），会话时间中位数 412 s。当时还没有验证时的泄漏审计，15 个提交中有 4 个泄漏：没有共享的、经过检查的定义时，智能体自己写的特征常常泄漏。

各组的目标取自本组上一期的方案，所以两组的目标值不同。MAVRA 复用上一期方案时，验证分数就是目标本身。截点 1 三个 MAVRA 会话的先后顺序是 user-badge、user-engagement、post-votes；user-badge 排在第一个，没有任何记忆可用。

## 时间花在哪里

MAVRA 省下的是 LLM 时间（3,555 s → 812 s），但智能体时间只快 1.3 倍：网关停顿占了 1,519 s，验证复用的方案又花了 1,999 s。

截点 2–5，每组 12 个会话，单位 s。网关停顿 = 耗时 ≥ 290 s 的调用（均为 300 s 超时后重试）。

| 构成 | 无记忆 | MAVRA |
| --- | --- | --- |
| LLM（不含停顿） | 3,555 | 812 |
| 网关停顿 | 0 | 1,519 |
| 验证 SQL 与训练 | 1,146 | 1,999 |
| 其他工具 | 1,167 | 284 |
| **智能体时间合计** | **5,868** | **4,614**（去掉停顿 3,095） |
| 目标计算（框架工作，不计入智能体时间） | 769 | 1,410 |
| MAVRA 学习（不计入智能体时间） | — | 854 |

- **网关停顿（已修）。** 5 次停顿都是 MAVRA 会话的第一次调用。MAVRA 的会话在主线程里一个接一个跑，复用同一个 HTTP 连接；会话之间要算目标、学习，连接空闲几分钟后被中途断掉，下一次请求等满 300 s 超时才重试。无记忆组每个截点换新线程、新连接，没有遇到。现在连接空闲 30 s 就重建，并逐次记录重试次数与耗时。
- **验证复用方案的 SQL 很重。** MAVRA 的 user-badge 方案来自截点 1 的会话，每次验证 170–180 s；无记忆组同任务每次 24–49 s。验证的是智能体提交的 SQL，框架不改它。
- **算目标是框架的工作，不计入智能体时间。** 它在本期数据上重算一遍上一期的 SQL，MAVRA 的方案更重，所以要 1,410 s（无记忆 769 s）。正式实验改为每个截点开始时三个任务并行算。
- **整轮用时。** 无记忆组截点 2–5 用了 72 分钟（同一截点 3 个会话并行）；MAVRA 截点 1–5 用了 222 分钟，其中截点 2–5 用了 161 分钟（会话一个接一个，含学习与算目标）。

## 两条门槛为什么没过

质量差距来自停止规则与复用的组合；token 超标来自一个没有目标的会话，以及 MAVRA 长会话里不断累积的记忆返回。

### user-badge 质量低 0.018

- **起点在截点 1。** MAVRA 的 user-badge 会话排在截点 1 的第一个，没有任何记忆，条件与无记忆组相同。两份方案验证 AUC 几乎一样（0.8624 对 0.8634），测试却差 0.017（0.8271 对 0.8442）。
- **之后的差距不只在测试上。** 这份方案在新数据上重新拟合的验证分数是 0.811–0.857，无记忆组的是 0.846–0.864。
- **机制。** 规则是“达到本组在用方案的水平即停”。MAVRA 直接复用在用方案，验证分数正好等于目标，2 次调用就停，方案从此不变。无记忆组每期重写方案，写到不差于在用方案才停，常常超过它（截点 5：目标 0.864，得到 0.877）。等于无记忆组每期多做一次搜索、只留不差的结果，质量只升不降；MAVRA 的质量停在第一份方案上。
- **1 次运行分不清两种解释。** 一是截点 1 恰好得到一份较弱的方案（3 次运行会平均掉），二是规则结构上偏向重新探索（运行再多也在）。post-votes 与 user-engagement 上没有差距，因为 MAVRA 这两份方案本来就不差。

### token 比值 0.361

- **唯一的超出是截点 5 的 user-engagement。** 两组截点 4 的方案在截点 4 审计都是 clean，到截点 5 审计都判为泄漏，所以两组都没有目标，一直探索到 8 次验证用完。
- **审计会漏。** 审计只看最晚训练种子时刻、实体编号最小的 500 个种子。MAVRA 方案泄漏的是“帖子收到的投票”一组特征（rv_*）；推测是投票时间只到日期、帖子时间到秒，“同一天先投票、后发帖”只在少数用户身上出现，抽到的 500 个种子里没有就查不出来。
- **MAVRA 的长会话更贵。** 同是 16 次调用，MAVRA 用了 64.7 万 token，无记忆 26.1 万。find_program 与 find_features 的返回共 4.6 万字符，留在对话里、每轮重复计入输入；最后一轮输入 6.2 万 token，无记忆组 3.5 万。MAVRA 的输出也更长（9.0 万对 4.8 万）。
- **截点 1 的 MAVRA 会话也更贵**（合计 100.0 万对 50.6 万，不计入门槛）：user-badge、user-engagement 两场各自一直有提升，用到 8 次验证；无记忆组同任务连续 2 次不提升就停了。这是单次运行的随机差异，与记忆无关（user-badge 排在第一个，没有记忆可用）。
