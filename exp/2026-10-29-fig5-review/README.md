### 零显式调用不等于没有编译

- `src/middle/features.rs:339` 的 `find_features` 在有定义和 seed_key 时调用 `compose_feature_sql`。
- 同文件 `:431` 的 `find_program` 同时提供原始完整任务 SQL 与定义编译 SQL。
- 同文件 `:389` 的编译入口在返回时增加定义的 `hits` 与 `consumers`，不等智能体验证或采用。因此 feature_report 的命中数也不是实际使用率。
- 这些源码与实验启动归档哈希完全一致，不能把该行为误当成运行后的新改动。

关键区别是“编译产物被生成”“智能体验证了产物”“最终有效方案采用了产物”三个阶段。当前 Fig.5 把查找、编译等合成一个记忆工具柱，未展示这条证据链。

### 唯一直接验证编译 SQL 的案例被拒绝

`results/official-20261028/mavra-rel-stack-r1/sessions/user_engagement-k1.json` 的第 3 号工具调用逐字验证 `find_features` 返回的八列编译 SQL。来源为此前 user-badge 发布的定义。验证 AUC 为 0.8733228646，但审计标记 `leak=true`，涉及：

- `user_posts_total`
- `user_days_since_first_post`
- `user_days_since_last_post`

这三项定义在 user-badge 的发布记录中 F1–F4 均通过。它们在新任务上的审计失败，说明学习样本上的发布检查不能直接作为任意目标任务的安全证据。最终方案由智能体重新写 SQL 并通过公共审计；不能把这一过程报告为编译器自动保证了跨任务安全。

当前记录能确认审计失败，不能单靠日志把根因定为某一个实现缺陷。源码中编译器只对指定事实时间列添加上界，关联/实体依赖以及源、目标审计样本不同，都应在隔离开发用例中定位。原失败与最终结果保留，不对正式结果进行针对性调参。

## 为什么当前实验偏向整份方案复用

1. `exp/2026-10-28-official/study-cell.py:43` 明确要求先验证 program_sql，再按需查定义。共享框架也优先完整方案。
2. 正式负载重复同一任务的时间截点，旧方案天然可以成为直接初始解。
3. 共同停止规则在达到上一截点方案的验证目标后限制继续尝试；该规则各方法一致，但使已经成功的旧 SQL 缺少重新组合的必要。
4. 两个开发候选的选择条件是保持验证质量并减少 token，没有检验结构化定义的独立增益。

这些选择解释了观察到的执行路径；它们不构成结构化表示的组件消融。

## Fig.5 的验证柱不能支撑什么

绿色柱统计 `validate_features`，其模型验证与时间泄漏审计由共同框架对所有方法执行。它不等于 MAVRA 的 F1–F4 发布检查，也不等于条件身份共享、消费快照绑定或更新维护。调用次数本身没有给出检查覆盖、通过率、误拒绝率或错误放行率。内部记忆模块的模型工作也不在该图中，不能拿该图推导所有模块的总成本。
