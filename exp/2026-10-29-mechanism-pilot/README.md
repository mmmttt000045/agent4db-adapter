# 三幅机制图：小规模预实验与受控补充

本批响应 2026-10-29 的请求：图 A 落实公平对照并试跑；图 B、C 先用归档数据作预览，再按发现补实验。所有图沿用 `tools/figures/mplstyle.py` 与论文 preamble 的方法配色，使用衬线字体、黑色坐标框、空心标记及可黑白区分的纹理。

## 图 A：程序访问 × 定义访问

四组为无记忆、仅完整 SQL、仅定义、完整 SQL + 定义。固定 user-badge k1 的源程序，重新审计并提炼一次；12 条候选中 7 条通过准入。两种目标是同一实体的 user-engagement k1，以及同任务后续截点 user-badge k2。每组一个重复，共八个单元。预算、数据抽样、目标审计和基础工具配置相同；记忆工具可选，不强制先用某条路径。源记忆冻结，目标结果不写回。

这是开发预实验。每格至多 12 次规划调用、3 次验证；训练抽样 10,000，验证抽样 2,000，时间审计最多 5,000 个训练种子。测试文件仅读取实体键与时间列，不读取、评分测试标签。具体边界见 `protocol.json`。不能从一格一次推导统计显著性，也不能把验证集 AUC 当作测试集非劣性。

源程序历史探索成本单列，按每个记忆组的两个目标分摊；新提炼成本只分配给定义与组合组。在线 token、含源成本的 token、合法方案覆盖、验证质量及实际 SQL 采纳分别统计。跨任务无记忆组没有有效方案时，其配对质量阈值为空，不将失败设为 AUC=0 或据此宣称质量提升。

### 预实验中的接口修复

首轮六个记忆单元在调用工具前遇到适配错误：共享 harness 要求 `names()` 方法，新适配器却暴露为集合。两个无记忆单元正常完成，其结果全部保留。修复后只补跑六个中断单元，保留故障代码、逐单元错误、原始费用账本与部分会话，不以更好结果替换已完成单元。

同时覆盖通用工具入口中的 SQL 执行方法，避免触发 AgentSM 的额外模型修复；该额外行为在首轮记忆单元中尚未执行。修复版与原版只涉及实验适配层，冻结的源程序、七条定义、样本、目标和预算均不更换。

原源中间层退出后，使用相同 Rust `metric::compose_features` 从已冻结的定义生成全部 127 个非空子集；要求全量编译 SQL 与原冻结 SQL 完全相等。补跑据此返回相同编译结果，无重新提炼、目标反馈筛选或模型调用。验证代码在 `system_tests.rs` 的 `mechanism_compile_frozen_source`。

运行结果见 `pilot-summary.json`；可读表格与图预览生成在 `output/mechanism-pilot-20261029/`。适配边界、实际 dispatch 协议、禁用隐藏模型修复及下阶段字段绑定共 11 个测试通过。

### 已完成的八格结果

| 目标 | 无记忆 | 仅完整 SQL | 仅定义 | SQL + 定义 |
| --- | ---: | ---: | ---: | ---: |
| user-engagement k1，跨任务 | 无有效方案 | 0.8469 | 0.8366 | 无有效方案 |
| user-badge k2，同任务后续截点 | 0.7852 | 0.8176 | 0.7962 | 0.7943 |

表中是验证 AUC。六个最终方案通过目标时间审计；另外两格用完规划预算，没有最终 SQL 或验证分数。所有成本仍保留。六个记忆组均检索了某种记忆，但没有一格调用 `compose_features`；同任务组合组只检索了定义。因此本图反映“开放两种记忆入口”这一策略的行为，尚不支持组合器带来独立增益的结论。

同任务组合组在线 token 为 75,890，低于无记忆的 103,255；计入两次目标使用分摊的源成本后为 201,880，高于无记忆。该区别保留在堆叠成本图中。新的 API 调用共 92 次，含故障消耗的保守计价上界为 1.2333 元，不是已结算账单金额。

### 正式图 A 的准入问题

- 小预算下，无记忆跨任务单元用尽 12 次调用仍无验证结果；缺乏完整配对质量证据。正式预算需要对所有组统一校准，不能只给表现差的某组加次数。
- 源任务与跨任务目标的种子字段名不同。预实验保留源 SQL 原样，让智能体自行适配；不得把直接执行时的字段错误解释为时间泄漏或记忆失效。`seed_adapter.py` 提供下一协议中对程序和编译 SQL 完全相同的字段绑定，`preflight_seed_bindings.py` 在独立数据库中审计绑定后的 SQL，不调用模型，也不覆盖预实验结果。
- 原程序含更多特征，只有七条被提炼为定义。本轮测的是可用记忆入口的组合策略，不能将差异全部归于表示形式。正式表示消融还须增加同一组特征内容的程序投影对照，并在源数据上证明对应列一致。
- 检索了定义、调用了编译器、原样验证编译 SQL、最终采用编译 SQL 是四件不同的事。`analyze_pilot.py` 保存精确匹配证据；改写来源需要另行审阅，不能把“无原样匹配”写成“从未参考定义”。
- 已确认探查 HTTP 时限为 180 秒，而冻结 Rust 连接池的数据库时限为 300 秒。客户端超时后的查询会继续到服务端时限；本轮不据此做干净延迟对比，正式批次需要统一服务端截止与取消机制。执行检查确认长查询在服务端时限结束，没有人为删掉不利结果。

下阶段的具体准入条件保存在 `formal-a-next.json`。在内容量对照、字段绑定、完整配对支持和查询时限尚未校准前，不把扩大付费运行称为正式机制证据。

字段绑定预检已经完成：相同包装应用于两种源 SQL，在 user-engagement k1 的 760 个最新训练种子、user-badge k2 的 751 个最新训练种子上，四次审计均为 clean、差异单元格为 0。这里的 5,000 是审计上限，实际最新时间片只有上述种子数；这不是全体样本的安全证明。结果在 `results/mechanism-pilot-20261029/seed-binding-preflight.json`，不覆盖原预实验的字段错误或任何最终方案。

## 图 B：固定定义数量的共享扫描

归档预览来自 `exp/2026-10-02-cache-baseline-tpcds/`。原扫描的定义数与共享程度同时变化，各配置只有一次运行；零重叠和 4M 行/8、32 智能体属于独立测量批次。图上明确这些边界，不补造误差棒。

按预览结果追加 `systems-protocol.json` 中的固定数量对照：16 个定义、每个事实表 100,000 行、8 个智能体、共享因子 1/2/4/8，比较全定义重查、SQL/版本缓存与 MAVRA；交错和同时到达各三轮，共 72 格。各格均存在并预热同样 16 对事实/日期表，保持每格请求数、准入门槛、版本失效方式与在途合并一致。共享度仅通过定义到表对的映射改变，度量为不同常数单位换算。

此补充识别完全相同条件的复用，不证明蕴含复用、真实业务泛化或优于强 SQL 缓存。活跃表集合随共享而缩小这一局限保留。三个随机顺序运行块仅用于展示运行离散度；不将 128 次请求当成 128 个独立重复。原始逐条件事件与所有请求状态都保留。

### 三轮受控结果

72 格均完成，9,216 次请求全部返回 valid。以下是各格相对于同一运行块、相同共享因子及到达方式的全量重查之耗时比，再取三轮中位数：

| 共享因子 | MAVRA 交错到达 | SQL 缓存交错到达 | MAVRA 同时到达 | SQL 缓存同时到达 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 103.48% | 107.64% | 99.96% | 101.56% |
| 2 | 58.63% | 63.06% | 55.28% | 54.91% |
| 4 | 37.16% | 37.66% | 41.40% | 41.38% |
| 8 | 21.91% | 30.40% | 34.00% | 35.28% |

交错到达时，全量重查的验证 SQL 数保持 48；MAVRA 随共享因子增加为 48、24、12、6。SQL/版本缓存也基本取得这一复用效果。在同时到达的情况下，全量重查同样使用公共的在途合并机制，因此其查询数随共享上升而下降（中位数 48、47、33、24），不能把它当作完全没有请求合并的弱基线。共享因子为 1 时，未观察到可靠优势。

第三轮“共享因子 1、SQL 缓存、交错到达”出现额外一轮维护：16 个定义各刷新两次，实际验证 SQL 为 96 次，相对耗时为 199.36%。该格保留在中位数、全范围误差棒和原始数据中，没有删去或替换。版本实现使用结构、ETL 批次和异步 DML 计数；异步计数后到是一个可能原因，但本轮没有保存逐次版本序列，不能据此确定根因。后续严谨复测应记录版本序列，并对所有方法使用同一稳定版本协议。

该图支持“相同检查被共享时，重复验证明显减少”；当前数据不能证明 MAVRA 在这一场景稳定优于 SQL/版本缓存，更不能支持语义蕴含复用的结论。图中的误差棒是三轮最小值到最大值，不是置信区间。

## 图 C：消除版本来源混淆

归档预览分别显示并发有效返回/违规/拒绝、读延迟和写吞吐。旧 precheck 与 snapshot-bound 不仅快照绑定不同，版本来源也不同；读、写、并发实验不是同一到达率下的端到端测量。图上标明这一点。

新增对照使用同一事务性版本表、同一守卫与条件缓存、同一 `run_bound` 路径；测试开关只让 precheck 在执行前释放核验快照。双向 barrier 精确安排“检查通过后，另一连接提交，再执行”，包含良性写入、破坏粒度的写入，以及调用前已提交的破坏性写入。两种模式每种情况五次，共 30 次受控调用。

首次启动在准入检查处发现测试夹具缺少 `ss_is_current`，尚未产生受控测量。补上原有 `scenario::setup` 标准初始化后重启未完成的系统批次；该错误报告与退出状态单独保留。

这是因果机制验证，人工等待不进入性能图，次数不作为自然工作负载的违规率。由查询同一语句中的独立重复键探针判断条件是否成立，保留拒绝与错误。生产构建行为不变，新增开关均为 `cfg(test)`，只存在于隔离实验副本。

30 次受控调用已完成，无调用错误：良性写入后两种模式各 5 次有效返回；检查后提交破坏性写入时，precheck 的 5 次返回均违反查询条件，snapshot-bound 的 5 次均读取条件成立的同一快照；调用前已经破坏条件时，两种模式均拒绝 5 次。新图 C 上半部分使用这一公平对照。下半部分仍是归档的读延迟（两个运行中位数的均值）和写吞吐（三个运行的中位数）；旧读延迟同时改变版本来源，不能把它解释为只改变快照绑定的性能代价。
