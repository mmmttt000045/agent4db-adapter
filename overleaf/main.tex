\begin{abstract}
\bi{LLM data agents learn what business metrics mean by exploring a database. Sharing the learned metric definitions across agents makes answers more accurate and consistent, but it turns each definition into long-lived state over a changing database. A definition's SQL is correct only while data properties that the SQL does not state still hold: a filtered key identifies one business record, joins do not fan out, and dates assign facts to the intended period. Data-only updates break these properties without any schema change; the shared query keeps running and silently returns wrong aggregates. We present \system, a middleware that maintains the validity of shared metric definitions and enforces it where they are used. \system\ derives typed executable conditions from each learned definition, keys their verdicts by dependency versions, and admits a query that declares a definition only if the definition's conditions hold on the snapshot on which the query runs. It repairs a broken definition only with a filter that is the unique structural fix and passes regression, and otherwise withdraws the definition. Replaying \RpLibs\ definition libraries learned by three LLMs under \RpChanges\ data changes, maintained definitions never serve a wrong answer under the modeled changes, whereas schema-only maintenance serves \RpSchemaWrongModeled. Under concurrent writers, checking before execution answers on condition-violating data in up to \SnPreUnannMax\% of uses; snapshot-bound execution does so in none of \SnSnapAnswered\ uses at the same reader latency. Repair is safe but depends on its reference: with the agent's own learning query as reference, \RpRefDiff\ points of answers become unavailable instead of repaired, and none becomes wrong. Maintenance follows the distinct conditions an update touches and costs \CbStagCondSix--\CbStagCacheSix\% of definition-level revalidation, whether verdicts are keyed by typed conditions or by check SQL in a generic version-keyed cache. End to end, maintained sharing raises agent accuracy from \ScenAccNoShare\% to \ScenAccCond\%.}
{大语言模型数据智能体通过探索数据库学到业务指标的含义。在智能体之间共享学到的指标定义，能让答案更准确、口径更一致，但也使每个定义成为变化数据库上的长期状态。定义的 SQL 只在一些 SQL 本身没有写明的数据性质成立时才正确：过滤后的键对应一条业务记录，连接不放大行数，日期把事实归入预期的期间。纯数据更新可以在不改任何表结构的情况下破坏这些性质；共享查询照常执行，却静默返回错误的汇总值。本文提出 \system，一个维护共享指标定义的有效性、并在使用处强制这种有效性的中间层。\system\ 从每个学到的定义推出类型化的可执行条件，按依赖版本索引条件结论；声明使用某个定义的查询，只有在该定义的条件于查询执行所在的快照上成立时才被放行。它只用“结构上唯一、且通过回归测试”的过滤修复失效定义，否则撤下该定义。把 3 个大模型学到的 \RpLibs\ 个定义库在 \RpChanges\ 种数据变化下回放：在已建模的变化下，维护后的定义从不给出错误答案，而只看结构的维护给出了 \RpSchemaWrongModeled\ 个错误答案。存在并发写入时，执行前检查会让最多 \SnPreUnannMax\% 的使用在违反条件的数据上作答；绑定快照的执行在 \SnSnapAnswered\ 次使用中一次也没有，读者延迟不变。修复是安全的，但取决于其参照：以智能体自己的学习查询为参照时，有 \RpRefDiff\ 个百分点的答案变为不可用而不是被修复，没有一个变为错误。维护工作沿更新触及的不同条件展开，耗时为定义级重验证的 \CbStagCondSix--\CbStagCacheSix\%，无论结论按类型化条件还是按检查 SQL 在通用版本缓存中索引。端到端实验中，维护后的共享把智能体正确率从 \ScenAccNoShare\% 提高到 \ScenAccCond\%。}
\end{abstract}

\section{\bt{Introduction}{引言}}
\label{sec:introduction}
\bi{LLM-based data agents are an emerging and rapidly growing class of data-system clients~\cite{luo2026dataagents}, expected to become the dominant workload of data systems~\cite{liu2026agents}. To answer a question such as ``What was the store return amount in September 2002?'', an agent lists tables, inspects columns and values, validates candidate joins, and composes SQL over many turns. The hard part is rarely SQL syntax; it is business semantics. Enterprise warehouses name columns in terminology that only domain experts understand~\cite{floratou2024nl2sql}, and an o1-preview agent solves only 21.3\% of real enterprise text-to-SQL workflows~\cite{lei2025spider2}. Business knowledge closes much of the gap: attaching expert-annotated external-knowledge evidence raises GPT-4's execution accuracy on the BIRD test set from 34.9\% to 54.9\%~\cite{li2023bird}, and answering enterprise insurance questions over a knowledge graph that captures business semantics raises GPT-4's accuracy from 16.7\% to 54.2\%~\cite{sequeda2024kg}.}
{基于大语言模型的数据智能体是一类新兴且快速增长的数据系统使用者~\cite{luo2026dataagents}，并被预期成为数据系统的主要负载~\cite{liu2026agents}。为回答“2002 年 9 月门店退货金额是多少”这样的问题，智能体需要多轮列出表、查看列和取值、验证候选连接并编写 SQL。难点很少在 SQL 语法，而在业务语义。企业数仓的列名使用只有领域专家才懂的术语~\cite{floratou2024nl2sql}；在真实企业 Text-to-SQL 工作流上，基于 o1-preview 的智能体只能完成 21.3\%~\cite{lei2025spider2}。业务知识能弥补很大一部分差距：在 BIRD 测试集上附加专家标注的外部知识证据，使 GPT-4 的执行正确率从 34.9\% 提高到 54.9\%~\cite{li2023bird}；在刻画业务语义的知识图谱上回答企业保险问题，使 GPT-4 的正确率从 16.7\% 提高到 54.2\%~\cite{sequeda2024kg}。}

\bi{Metric definitions carry much of this semantics. A definition fixes which fact rows to aggregate, which records count as one business event, and how measurements relate across tables; data warehouses have long required such definitions to be conformed across uses~\cite{kimball2013toolkit}. Agents need not rely on hand-written definitions: systems derive domain knowledge, including the calculation logic of derived columns, from script histories and lineage~\cite{weng2025datalab}, organize prior trajectories as reusable semantic memory~\cite{biswal2026agentsm}, and distill reusable workflows and insights from experience~\cite{wang2025awm,zhao2024expel}. Sharing a learned definition amortizes exploration that agents otherwise repeat. In our traces, fresh agent sessions spend two thirds of their database calls on lookups and re-derive facts that earlier sessions already obtained. Most of these are schema facts, but 38\% of the SQL probes also re-derive an earlier session's fact, and none repeats an earlier probe's SQL text, so a result cache keyed by query text captures none of this reuse (Section~\ref{sec:workload-characterization}). Sharing also keeps answers consistent: one agent's verified meaning of ``return amount'' becomes every agent's, and in our end-to-end study it raises accuracy from \ScenAccNoShare\% to \ScenAccCond\%.}
{指标定义承载了其中大部分语义。一个定义规定聚合哪些事实行、哪些记录算作一次业务事件，以及度量如何跨表关联；数据仓库长期要求这类定义在各处保持一致（conformed）~\cite{kimball2013toolkit}。智能体不必依赖人工编写的定义：已有系统从脚本历史和血缘中推导领域知识（包括派生列的计算逻辑）~\cite{weng2025datalab}，把既往轨迹组织成可复用的语义记忆~\cite{biswal2026agentsm}，并从经验中提炼可复用的工作流和洞见~\cite{wang2025awm,zhao2024expel}。共享学到的定义能摊薄智能体原本要重复的探索。在我们的轨迹中，全新智能体会话把三分之二的数据库调用用于查找，并重新获取此前会话已经得到的事实。其中大部分是表结构事实，但也有 38\% 的 SQL 探查重新获取了此前会话的事实，而且没有一条与此前探查的 SQL 文本相同，因此按查询文本索引的结果缓存捕获不到这类复用（第~\ref{sec:workload-characterization} 节）。共享还能保持答案一致：一个智能体验证过的“退货金额”含义成为所有智能体的含义；在我们的端到端实验中，它把正确率从 \ScenAccNoShare\% 提高到 \ScenAccCond\%。}

\bi{Sharing, however, turns a learned definition into long-lived state over a changing database. Liu et al.\ propose that data systems keep a persistent agentic memory store for grounding agents, and caution that if the store drifts from the data, ``the stale information may lead a new probe to make a mistake''~\cite{liu2026agents}; a tutorial on data agents lists adapting to changing data among their open problems~\cite{luo2026dataagents}, and a tutorial on agentic memory notes that memory stores accumulate redundant, outdated, or conflicting information~\cite{li2026agenticmemory}. For metric definitions the risk is specific. A definition's SQL is correct only while certain data properties hold: the filtered key identifies one business record, joins do not fan out, and dates join through the intended role. The first two are instances of the summarizability conditions that govern correct aggregation~\cite{lenz1997summarizability,mazon2009summarizability}; the third fixes which date relation assigns a fact to a period. The SQL text does not state them and the schema does not enforce them. Dimensional modeling treats them as design contracts: the declared grain is ``a binding contract'', ``different grains must not be mixed in the same fact table'', and a date dimension can play several roles in one fact table~\cite{kimball2013toolkit}. Yet routine warehouse operations change the data behind these contracts: type-2 dimensions add a row for each changed member, late-arriving facts and reloads append rows, and a status history appended to a transaction table mixes two grains~\cite{kimball2013toolkit}. Like the soft constraints exploited by query optimizers~\cite{godfrey2001soft}, the conditions hold on the current data and can be broken by the next load.}
{然而，共享使学到的定义成为变化数据库上的长期状态。Liu 等提出数据系统应保存持久的智能体记忆库，为智能体提供依据，并提醒若记忆库与数据不一致，“过期信息可能导致新的探查出错”~\cite{liu2026agents}；关于数据智能体的教程把适应不断变化的数据列为开放问题~\cite{luo2026dataagents}，关于智能体记忆的教程也指出记忆库会积累冗余、过时或相互冲突的信息~\cite{li2026agenticmemory}。对指标定义而言，这一风险有具体形态。定义的 SQL 只在某些数据性质成立时才正确：过滤后的键对应一条业务记录，连接不放大行数，日期按预期角色关联。前两项是决定汇总正确性的可汇总性条件的具体实例~\cite{lenz1997summarizability,mazon2009summarizability}，第三项规定由哪种日期关系把事实归入某个期间。SQL 文本不写明它们，表结构也不强制它们。维度建模把它们当作设计契约：声明的粒度是“具有约束力的契约”，“同一事实表中不得混合不同粒度”，一个日期维度可以在同一事实表中扮演多个角色~\cite{kimball2013toolkit}。然而数仓的日常操作会改变这些契约背后的数据：第 2 类缓慢变化维为每个变化的成员追加一行，迟到事实与重新装载追加行，在交易表中追加状态流水则混入了第二种粒度~\cite{kimball2013toolkit}。与查询优化器利用的软约束一样~\cite{godfrey2001soft}，这些条件在当前数据上成立，却可能被下一次装载破坏。}

\bi{Consider a returns table that stores one completed row per return. An ETL change starts to append an application-state row for each new return. No table or column changes, and the shared definition \code{SUM(sr\_return\_amt)} still executes. It now counts many returns twice: in our experiment a single-period query returns 6,588,699.86 instead of 3,294,349.93. Nothing fails loudly. Such failures are familiar from data pipelines: upstream feeds change in unexpected ways and downstream applications break silently~\cite{song2021autovalidate}, and a seemingly innocuous upstream change can produce data that ``looks perfectly fine'' to its consumer~\cite{breck2019validation}. Agents rarely catch such breaks on their own: in our traces, only 16\% of sessions check key uniqueness, and every wrong answer came from SQL that ran without error (Section~\ref{sec:workload-characterization}).}
{例如，退货表对每笔退货保存一条完成记录。一次 ETL 改动开始为每笔新退货追加一条申请状态记录。表和列都没有变化，共享定义 \code{SUM(sr\_return\_amt)} 照常执行，却把许多退货计算了两次：在我们的实验中，一个单期查询返回 6,588,699.86，正确值是 3,294,349.93。整个过程没有任何报错。这类失效在数据管道中并不陌生：上游数据源以意想不到的方式变化，下游应用随之静默出错~\cite{song2021autovalidate}；一次看似无害的上游改动，产出的数据在使用方看来可能“完全正常”~\cite{breck2019validation}。智能体自己很少能发现这类破坏：在我们的轨迹中，只有 16\% 的会话检查键唯一性，而所有错误答案都来自执行成功、没有报错的 SQL（第~\ref{sec:workload-characterization} 节）。}

\bi{Keeping shared definitions correct requires answers to three questions that existing mechanisms address only in part. \emph{What must be checked?} The properties a definition relies on are stated neither in its SQL nor in the schema, so schema-evolution support~\cite{curino2008prism,zhang2025evoschema} misses data-only breaks, and data-validation systems~\cite{schelter2018deequ,breck2019validation} check declared constraints without knowing which learned definition depends on which property. \emph{When may a definition be used?} A check that passed describes one snapshot; a write can commit between the check and the query that relies on it, and cheap version signals such as DML statistics are neither transactional nor immediate. In our experiments, checking before execution lets queries answer on condition-violating data in up to \SnPreUnannMax\% of uses under concurrent writers. \emph{What happens when a definition breaks?} Revoking it on every write discards valid knowledge after benign appends, while repairing it is risky: a filter can restore one row per business key yet select the wrong population, and whether a regression test notices depends on what its reference already knows.}
{要保持共享定义正确，需要回答三个问题，现有机制只回答了其中一部分。\emph{该检查什么？}定义依赖的性质既不写在 SQL 里，也不写在表结构里，因此模式演化支持~\cite{curino2008prism,zhang2025evoschema}会漏掉纯数据破坏；数据验证系统~\cite{schelter2018deequ,breck2019validation}检查声明的约束，却不知道哪个学到的定义依赖哪条性质。\emph{何时可以使用定义？}一次通过的检查只描述一个快照；写入可能在检查与依赖它的查询之间提交，而 DML 统计这类廉价的版本信号既不随事务提交，也不即时可见。在我们的实验中，存在并发写入时，执行前检查会让最多 \SnPreUnannMax\% 的使用在违反条件的数据上作答。\emph{定义失效后怎么办？}每次写入都撤销会在正常追加后丢掉有效知识；修复则有风险：一个过滤可以恢复每个业务键一行，却选中了错误的总体，回归测试能否发现，取决于其参照事先知道什么。}

\bi{Our approach treats the validity evidence of a learned definition as first-class, versioned state, and binds every use of a definition to evidence that holds on the use's own snapshot. Conditions are derived from the definition's structured implementation: filtered key uniqueness for its grain, multiplicity for each join, and the role and coverage of its date join. A verdict is indexed by the condition's identity and the versions of the tables it reads, so it serves every definition and agent that needs the same condition until one of those tables changes. A query that declares a definition revision runs in a repeatable-read snapshot on which the revision's conditions hold, reusing verdicts whose transactional versions match the snapshot and checking the rest inside it. Repair publishes a replacement only when it is the unique structural fix and passes regression; otherwise the definition is withdrawn. This organization also makes maintenance cheap, because work follows the distinct conditions that an update touches rather than the definitions that depend on them. We find, however, that a generic version-keyed cache of check queries recovers nearly the same savings. We therefore treat efficiency as a property that explicit, versioned conditions make easy to obtain, and locate our contribution in what is checked and when a check's result may be relied on.}
{我们的做法是把学到的定义的有效性证据作为一等的、版本化的状态，并把每一次使用绑定到在该次使用自身快照上成立的证据。条件从定义的结构化实现中推出：粒度对应过滤后键唯一性，每个连接对应多重性，日期连接对应角色与覆盖。条件结论按条件身份及其读取表的版本索引，因此在这些表变化之前，它服务于所有需要同一条件的定义和智能体。声明使用某个定义修订的查询，在一个该修订条件成立的可重复读快照中执行：事务性版本与快照一致的结论直接复用，其余条件在快照内检查。只有当替代修订是结构上唯一的修复且通过回归测试时才发布，否则撤下定义。这种组织方式也使维护代价低廉，因为工作沿更新触及的不同条件展开，而不是沿依赖它们的定义展开。但我们发现，一个按版本索引检查查询的通用缓存几乎能拿到同样的节省。因此我们把效率视为显式、版本化的条件使之易于获得的性质，而把贡献落在“检查什么”以及“检查结果何时可以依赖”上。}

\bi{We present \system\ (\textbf{M}etric-\textbf{A}ware \textbf{V}alidation and \textbf{R}euse for \textbf{A}gents), a middleware between data agents and PostgreSQL that implements this lifecycle. \emph{Admission} extracts structured definitions from judged-successful trajectories and replays their canonical SQL. \emph{Maintenance} rechecks conditions whose dependencies changed, reuses verdicts across definitions and agents, revokes failed revisions, and repairs them under the uniqueness and regression rules; requests that arrive during a repair wait for its outcome. \emph{Execution} checks declared revisions and, in snapshot-bound mode, validates and executes each declaring query on one snapshot, using transactional table versions maintained by statement-level triggers. Because maintenance operates on structured definitions, it applies equally to definitions declared in a semantic layer, which at least one commercial metric layer does not validate at runtime~\cite{databricks2026metricviews}.}
{本文提出 \system（Metric-Aware Validation and Reuse for Agents，面向智能体的指标感知验证与复用），一个位于数据智能体与 PostgreSQL 之间、实现上述生命周期的中间层。\emph{准入}从判题成功的轨迹中提炼结构化定义，并重放其规范 SQL。\emph{维护}重查依赖发生变化的条件，跨定义和智能体复用结论，撤销失效修订，并在唯一性与回归规则下修复；修复进行中到达的请求等待其结果。\emph{执行}核对声明的修订，并在绑定快照模式下，借助语句级触发器维护的事务性表版本，在同一快照上验证并执行每条声明了修订的查询。由于维护作用于结构化定义，它同样适用于在语义层中声明的定义，而至少有一个商用指标层不在运行时验证这类声明~\cite{databricks2026metricviews}。}

\bi{We evaluate \system\ in two layers. At the mechanism layer we fix what agents learned and vary only maintenance: we replay \RpLibs\ definition libraries learned by three LLMs under \RpChanges\ data changes, run concurrent writers against declaring queries, and measure maintenance cost against definition-level revalidation and a generic version-keyed cache from one to 16 million rows. Maintained definitions serve no wrong answer under the modeled changes, whereas schema-only maintenance serves \RpSchemaWrongModeled; condition-level and definition-level maintenance give identical answers on all paired questions. Snapshot-bound execution eliminates answers on condition-violating data (none in \SnSnapAnswered\ uses, versus \SnPreUnannMin--\SnPreUnannMax\% under unannounced writes when checking before execution) without changing reader latency. Repair succeeds when its reference distinguishes the business populations and otherwise withdraws the definition; a counterexample shows that, without the uniqueness rule, an indistinguishable backup copy yields a wrong published repair. End to end, agents on three LLMs face ten data changes: maintained sharing raises accuracy from \ScenAccNoShare\% to \ScenAccCond\%, and the boundary of the approach is visible, since duplicate loads and re-keyed dates are detected but cannot be repaired by filters, and a unit change that no condition models goes unnoticed.}
{我们从两个层面评估 \system。在机制层，固定智能体学到的内容，只改变维护方式：把 3 个大模型学到的 \RpLibs\ 个定义库在 \RpChanges\ 种数据变化下回放，让并发写入与声明了修订的查询同时运行，并在 100 万到 1600 万行数据上把维护代价与定义级重验证及通用版本缓存比较。在已建模的变化下，维护后的定义不给出错误答案，只看结构的维护给出 \RpSchemaWrongModeled\ 个；条件级与定义级维护在全部配对题目上答案完全相同。绑定快照的执行消除了在违反条件的数据上作答（\SnSnapAnswered\ 次使用中为零，执行前检查在不通知的写入下为 \SnPreUnannMin--\SnPreUnannMax\%），且不改变读者延迟。参照能区分业务总体时修复成功，否则撤下定义；一个反例表明，没有唯一性规则时，无法区分的备份副本会导致发布错误的修复。端到端实验中，基于 3 个大模型的智能体面对 10 种数据变化：维护后的共享把正确率从 \ScenAccNoShare\% 提高到 \ScenAccCond\%，方法的边界也清楚可见：重复装载与日期键改写能被检测但无法用过滤修复，没有任何条件刻画的单位变化则不会被发现。}

\section{\bt{Background and Motivation}{背景与动机}}
\label{sec:background}
\subsection{\bt{Application and agent workloads}{应用与智能体工作负载}}
\label{sec:workload-characterization}
\bi{In a parameterized application, query templates and database knowledge reside in code: applications invoke the same queries with different parameters, so millions of queries reduce to thousands of templates~\cite{ma2018querybot}. A fresh data-agent session must acquire that knowledge through schema lookups, data probes, and checks before it can write the query that answers its question. To quantify the difference, we compare two workloads (Table~\ref{tab:workload-characterization}). The application side is Redset~\cite{vanrenen2024redset}, the query metadata of 200 provisioned and 200 serverless Amazon Redshift clusters over three months: 441 million queries, analyzed as complete per-cluster streams. Its template identifier is a feature fingerprint, which the dataset documents as a proxy for query-likeness that overestimates repetition; the dataset is a biased sample of clusters, not a representative view of the fleet~\cite{redset2024dataset}. The agent side consists of 100 fresh DeepSeek V4.1 Flash sessions, each answering one of the 25 questions of Section~\ref{sec:evaluation} with only table listing, table description, and SQL tools, three sessions at a time on one database and with no shared state. SQL templates are libpg\_query fingerprints, which ignore constants and formatting.\footnote{\url{https://github.com/pganalyze/libpg_query}} A rule-based classifier, checked on a random sample of calls, labels each call as a schema lookup, data probe, validation, abandoned attempt, final answer, or failure. A lookup's \emph{fact} is its purpose together with the tables and columns it reads, so differently written SQL that probes the same columns counts as the same fact.}
{在参数化应用中，查询模板和数据库知识保存在代码里：应用以不同参数反复调用相同的查询，数百万条查询可归并为数千个模板~\cite{ma2018querybot}。全新的数据智能体会话则必须先通过结构查找、数据探查和检查获得这些知识，才能写出回答问题的查询。为量化这一差别，我们对照两类负载（表~\ref{tab:workload-characterization}）。应用侧采用 Redset~\cite{vanrenen2024redset}，即 Amazon Redshift 中 200 个预置集群和 200 个无服务器集群三个月的查询元数据，共 4.41 亿条查询，按每个集群的完整查询流分析。其模板标识是一种特征指纹，数据集文档说明它是查询相似性的近似、会高估重复程度；数据集是有偏的集群样本，不代表整个集群群体~\cite{redset2024dataset}。智能体侧是 100 个全新的 DeepSeek V4.1 Flash 会话，每个会话回答第~\ref{sec:evaluation} 节 25 道题中的一道，只有列出表、描述表和执行 SQL 三种工具；三个会话同时访问同一数据库，会话之间不共享状态。SQL 模板使用忽略常量与格式的 libpg\_query 指纹。基于规则的分类器（在随机抽样的调用上人工核对）把每次调用标为结构查找、数据探查、验证、放弃的尝试、最终答案或失败。查找所获得的\emph{事实}由其目的及读取的表和列确定，因此写法不同、但探查相同列的 SQL 算作同一事实。}

\bi{The two workloads repeat different things. Applications repeat queries: long-lived principals issue the same templates, which prepared statements and result caches serve well (34\% of Redset's read queries are answered from Redshift's result cache); Redshift's own analysis finds that in half of the clusters, 80\% of queries are exact repetitions~\cite{vanrenen2024redset}. Agents repeat knowledge. Their SQL changes from session to session, and correct answers to the same question use different templates. Most repeated lookups are schema facts that a metadata cache could serve; the SQL probes that test business properties repeat less often, and never verbatim, so a cache keyed by query text serves none of them. Two further observations shape the design. Answers are wrong without any failure: 31 of the 32 wrong answers occur when a question names a metric without defining it, exactly where a shared definition helps. And validation is rare: only 16\% of sessions check key uniqueness, the kind of validity condition that \system\ maintains on their behalf. A shared definition removes rediscovery and supplies business meaning, but a reused fact remains correct only while the data it was derived from does not change in the wrong way.}
{两类负载重复的东西不同。应用重复的是查询：长期存在的用户主体发出相同模板，预编译语句和结果缓存能很好地服务它们（Redset 中 34\% 的读查询由 Redshift 的结果缓存直接回答）；Redshift 自身的分析发现，在一半集群中 80\% 的查询是完全相同的重复~\cite{vanrenen2024redset}。智能体重复的是知识。它们的 SQL 在会话之间不断变化，同一道题的正确答案也使用不同模板。重复的查找大部分是表结构事实，元数据缓存可以服务它们；检验业务性质的 SQL 探查重复得少一些，且从不逐字重复，因此按查询文本索引的缓存一条也服务不了。另有两点观察决定了后文的设计。答案在没有任何报错的情况下出错：32 个错误答案中有 31 个出现在题目只给出指标名而不给定义时，这正是共享定义能帮上忙的地方。验证很少见：只有 16\% 的会话检查键唯一性，而这正是 \system\ 代为维护的那类有效性条件。共享定义消除了重复获取并提供业务含义，但被复用的事实只有在其来源数据没有发生错误变化时才保持正确。}

\subsection{\bt{Data agents and metric definitions}{数据智能体与指标定义}}
\bi{A data agent interacts with the database through tools: it lists tables, describes columns, validates joins, and runs SQL, and it submits an answer together with the queries that produced it. A metric definition packages what the agent had to discover. Our running example is store return amount: its definition records the fact table (\code{store\_returns}), the measure (the amount of completed returns), the grain (ticket and item identify one return), the time role (return date), persistent filters, and the convention for empty input. Initially, every return has one completed row, so no status filter is needed. Question parameters such as the month are not part of the definition. A return-rate definition additionally joins sales to returns on the same business key and uses sale date to assign the sale to a period; it can share the returns-grain condition with the return-amount definition.}
{数据智能体通过工具与数据库交互：列出表、查看列、验证连接、执行 SQL，并在提交答案时附上产生答案的查询。指标定义把智能体需要摸索出来的内容打包保存。本文以门店退货金额为贯穿例子：其定义记录事实表（\code{store\_returns}）、度量（已完成退货的金额）、粒度（小票号与商品确定一笔退货）、时间角色（退货日）、持久过滤，以及无输入行时的约定。最初每笔退货只有一条完成记录，因此无需状态过滤。月份等题目参数不属于定义。退货率定义还按同一业务键连接销售与退货，并用销售日把销售归入某个期间；它可以与退货金额定义共享退货粒度条件。}

\bi{Definitions come from two sources. Semantic layers let engineers declare measures, keys, and relationships by hand; the declarations document intent but are not necessarily checked against the data at query time. The documentation of one commercial metric layer, for instance, states that a declared join property ``is not validated at runtime'' and that measures return incorrect results if the join fans out~\cite{databricks2026metricviews}. Increasingly, such knowledge is also derived from script and query histories~\cite{weng2025datalab} or reused from agent trajectories~\cite{biswal2026agentsm}. Learned definitions reach many agents quickly, but their assumptions are recorded, at best, only implicitly in the exploration that produced them.}
{定义有两个来源。语义层让工程师手工声明度量、键和关系；这些声明记录了意图，但查询时不一定在数据上检查。例如，某商用指标层的文档写明，声明的连接性质“不在运行时验证”，一旦连接放大行数，度量就会返回错误结果~\cite{databricks2026metricviews}。越来越多的此类知识则从脚本与查询历史中推导~\cite{weng2025datalab}，或从智能体轨迹中复用~\cite{biswal2026agentsm}。学到的定义能迅速传到许多智能体，但其前提假设至多只隐含在产生它的探索过程中。}

\subsection{\bt{How updates break a correct definition}{更新如何破坏正确的定义}}
\bi{Continue the return-amount example. An ETL update adds an application-state row for each new return while retaining the completed row. The shared SQL, \code{SUM(sr\_return\_amt)}, still runs, but the ticket-and-item key is no longer unique and the aggregate counts some returns twice. Revalidation discovers this broken grain. Adding a completed-status filter is a repair candidate: it restores one row per return while retaining the business keys. The filter must also preserve the stated business meaning and pass regression against learning evidence. The return-rate definition needs the same filtered uniqueness to avoid join fan-out, so one verdict can justify both definitions. And while the update is being loaded, a query that relies on the old verdict must not read the half-changed data as if the grain still held.}
{继续退货金额的例子。一次 ETL 更新在保留完成记录的同时，为新退货追加申请状态行。共享 SQL \code{SUM(sr\_return\_amt)} 仍能执行，但小票号与商品键不再唯一，聚合把部分退货计算了两次。重验证发现粒度被破坏。添加完成状态过滤是一个修复候选：它保留业务键，并恢复每笔退货一条记录。该过滤还必须保留声明的业务含义，并通过学习证据的回归测试。退货率定义也需要同一个过滤后唯一性条件来避免连接放大，因此一个验证结论可以支撑两个定义。而在更新装载期间，依赖旧结论的查询不能把已经变化的数据当作粒度仍然成立来读取。}

\bi{An aggregate is summarizable only if the grouped records are disjoint and complete and the measure is compatible with the aggregation~\cite{lenz1997summarizability}; violations can make analysis tools return wrong results~\cite{mazon2009summarizability}. For a learned definition, disjointness becomes two executable requirements, filtered key uniqueness and bounded join multiplicity, and completeness becomes coverage requirements on business keys and periods. A third requirement, the time role, fixes which date relation assigns a fact to a period. Data-only updates break each of them in practice: status-history rows or duplicate loads violate grain, reused dimension keys make a many-to-one join fan out, and late or re-keyed rows shift a fact to another period or to none. Schema-based invalidation observes none of these changes. When such conditions are checked on data instances rather than guaranteed by the schema, a check holds only for the current data and any change requires a new check~\cite{lenz1997summarizability}. Each requirement can be checked with a SQL probe over a few tables: a grouped count that finds a duplicated key under the filter, or a comparison of row counts before and after a join. Data profiling discovers such unique column combinations while noting that they are valid only for a specific instance~\cite{abedjan2015profiling}, and data-validation systems run such checks declaratively over growing datasets~\cite{schelter2018deequ,breck2019validation}. What is missing for agents is the link between a learned definition and the checks that justify it, so that the checks run when the definition's data changes and their outcome governs whether, and on which data, agents may use the definition.}
{只有当被分组的记录互不相交且完备、度量与聚合方式相容时，汇总才是可汇总的~\cite{lenz1997summarizability}；违反这些条件可能使分析工具给出错误结果~\cite{mazon2009summarizability}。对学到的定义而言，不相交性对应两项可执行要求，即过滤后键唯一性和有界的连接多重性；完备性对应业务键与期间上的覆盖要求。第三项要求是时间角色，它规定由哪种日期关系把事实归入某个期间。纯数据更新在实践中会分别破坏它们：状态流水行或重复装载破坏粒度，被复用的维度键使多对一连接放大行数，迟到或重新赋键的记录把事实移到另一个期间或归不到任何期间。按表结构失效观察不到其中任何一种变化。当这些条件在数据实例上检查、而不由表结构保证时，检查结果只对当前数据成立，任何变化都需要重新检查~\cite{lenz1997summarizability}。每项要求都能用读取少数几张表的 SQL 探查来检查：用分组计数找出过滤后重复的键，或比较连接前后的行数。数据画像能够发现这类唯一列组合，同时指出它们只对某一数据实例成立~\cite{abedjan2015profiling}；数据验证系统能在不断增长的数据集上声明式地执行这类检查~\cite{schelter2018deequ,breck2019validation}。智能体场景中缺少的是把学到的定义与支撑它的检查联系起来：定义所依赖的数据一变，检查就执行，其结果决定智能体能否使用该定义、以及在哪些数据上使用。}

\label{sec:alternatives}
\bi{Table~\ref{tab:ladder} compares maintenance strategies along the three questions of Section~\ref{sec:introduction}. Schema-only maintenance never notices a data-only break. Revoke-on-write never serves a stale definition but discards valid ones after every benign append and depends on LLM relearning. Definition-level lazy revalidation, adapted from lazy view maintenance~\cite{zhou2007lazy}, rechecks all conditions of an affected definition on its next use, and a version-keyed cache of its check queries removes checks repeated across definitions. \section{\bt{System Overview}{系统概览}}
\label{sec:overview}
\bi{\system\ sits between agents and PostgreSQL (Figure~\ref{fig:architecture}). It exposes tool-style HTTP endpoints for listing and describing tables, finding and checking join paths, looking up metric definitions (\code{find\_metric}), and running SQL (\code{run\_sql}). Agents submit final answers with the query references and arithmetic that produced them, so the middleware records a calculation chain for every task. An in-memory store keeps versioned definitions, join paths, grain entries, verdicts, and evidence. Version detection reads table fingerprints, DML statistics, and an ETL batch log; in snapshot-bound mode, statement-level triggers additionally maintain transactional table versions (Section~\ref{sec:snapshot}). The middleware comprises about 6,600 lines of Rust, plus 4,200 lines of benchmark harnesses, with 40 unit and integration tests.}

\section{\bt{Metric Definitions and Validity Conditions}{指标定义与有效性条件}}
\label{sec:model}
\subsection{\bt{Definitions and evidence}{定义与证据}}
\bi{A definition revision is $m^r=(B,I,C,E,r)$, where $B$ is its business meaning, $I$ its structured implementation, $C$ its set of executable conditions, $E$ its supporting evidence, and $r$ its revision number. The implementation records the fact table, aggregate expression, grain, time role, join references, persistent filters, and empty-input convention. Canonical SQL is compiled from $I$ for any question parameters, giving agents a common representation of the calculation. Evidence includes the source task, the explicit basis of the business meaning, tool results, an independent task-success judgment, the judged learning query, and the table versions at learning time. Admission requires this judgment together with the executable gates in Section~\ref{sec:maintenance}.}
{定义修订记为 $m^r=(B,I,C,E,r)$，其中 $B$ 为业务含义，$I$ 为结构化实现，$C$ 为可执行条件集，$E$ 为支撑证据，$r$ 为修订号。实现记录事实表、聚合表达式、粒度、时间角色、连接引用、持久过滤和空输入约定。对任意题目参数，规范 SQL 都由 $I$ 编译得到，为智能体提供统一的计算表示。证据包括来源任务、业务含义的显式依据、工具结果、独立的任务成功判定、经过判题的学习查询以及学习时的表版本。准入同时要求这一判定和第~\ref{sec:maintenance} 节的可执行门槛。}

\subsection{\bt{Validity conditions}{有效性条件}}
\bi{A condition $c$ is a predicate over the tables $\operatorname{dep}(c)$ with a check query $Q_c$ that returns a violation witness or nothing. Its identity $\operatorname{id}(c)$ consists of its type, tables, key set, join direction, filters, and null policy. \system\ derives four kinds of conditions from the implementation:}
{条件 $c$ 是依赖表集合 $\operatorname{dep}(c)$ 上的谓词，附带一个检查查询 $Q_c$，返回违例证据或空。其身份 $\operatorname{id}(c)$ 由类型、表、键集合、连接方向、过滤和空值规则组成。\system\ 从定义的实现中推导四类条件：}
\begin{description}
\item[\bt{Filtered key uniqueness}{过滤后键唯一性}]
\bi{$\operatorname{KeyUnique}(T,K,\varphi)$: no two rows of $\sigma_\varphi(T)$ agree on $K$. It is derived from the grain and the fact table's persistent filters.}
{$\operatorname{KeyUnique}(T,K,\varphi)$：$\sigma_\varphi(T)$ 中没有两行在 $K$ 上取值相同。由粒度和事实表上的持久过滤推出。}
\item[\bt{Join multiplicity}{连接多重性}]
\bi{For a join reference $L\to R$ on keys $K$ with filters, each $L$ row matches at most the permitted number of $R$ rows; it is checked through uniqueness of $K$ on the filtered one side.}
{对按键 $K$、带过滤的连接引用 $L\to R$，每条 $L$ 记录匹配的 $R$ 记录数不超过允许值；通过过滤后一侧在 $K$ 上的唯一性检查。}
\item[\bt{Time role}{时间角色}]
\bi{The fact's date key joins the date dimension many-to-one through the declared role.}
{事实表的日期键按声明的角色与日期维度多对一关联。}
\item[\bt{Coverage}{覆盖}]
\bi{The fraction of fact rows that fail to join the date dimension stays within the fraction recorded at admission, so that facts are not silently dropped from every period.}
{关联不上日期维度的事实行比例不超过准入时记录的比例，使事实不会被静默地排除在所有期间之外。}
\end{description}

\subsection{\bt{Versions, verdicts, and reuse}{版本、结论与复用}}
\bi{The version $V(T)$ of a table identifies the state of $T$ that a check read. \system\ supports two sources. The default combines the schema fingerprint, DML counters, and the ETL batch identifier; it is cheap but neither transactional nor immediate, because PostgreSQL reports DML statistics asynchronously after commit. \emph{Transactional versions} are maintained by a statement-level trigger that increments a per-table counter inside every writing transaction; the counter is sharded by backend process so that concurrent writers do not contend on one row, and the version is the sum of the shards. A verdict is the outcome of $Q_c$ at the versions it read and is indexed by}
{表的版本 $V(T)$ 标识检查读到的 $T$ 的状态。\system\ 支持两种版本来源。默认来源组合结构指纹、DML 计数和 ETL 批次号，代价很低，但既不随事务提交也不即时可见，因为 PostgreSQL 在提交后异步上报 DML 统计。\emph{事务性版本}由语句级触发器维护：每个写事务内把对应表的计数加一；计数按后端进程分片，使并发写入者不争同一行，版本取各分片之和。结论是 $Q_c$ 在其所读版本上的执行结果，以如下键索引：}
\[
\bigl(\operatorname{id}(c),\,V(\operatorname{dep}(c))\bigr).
\]
\bi{A verdict serves every definition that requires the same condition at the same dependency versions. Identity is semantic rather than textual: the order of key columns and the formatting of filters do not change it, so a grain condition and a join guard that state the same key in different orders share one verdict. \system\ also supports a key implication (with identical filters and null semantics, uniqueness on $K$ implies uniqueness on each superset of $K$), which did not apply in our workloads.}
{一个结论服务于所有在相同依赖版本上需要同一条件的定义。条件身份按语义而非文本确定：键列顺序与过滤的书写格式不影响身份，因此以不同顺序写出同一键的粒度条件与连接守卫共享一个结论。\system\ 还支持一条键蕴含规则（过滤与空值语义相同时，键 $K$ 上的唯一性蕴含其每个超集上的唯一性），在我们的负载中没有用上。}

\subsection{\bt{States and the execution contract}{状态与执行契约}}
\bi{A revision is \emph{valid} when its conditions hold at the current versions of their dependencies. A dependency-version change makes it \emph{pending}, a state derived by version comparison that triggers revalidation. Revalidation either refreshes the evidence or \emph{revokes} the revision when a required condition fails. Repair produces a new \emph{candidate} revision, which becomes valid after passing the gates in Section~\ref{sec:maintenance}. For a query $q$ that declares $m^r$ and executes on snapshot $s$, the execution contract is}
{当修订的全部条件在其依赖的当前版本上成立时，修订是\emph{有效}的。依赖版本变化使其进入\emph{待验证}状态；这一状态由版本比较得出，并触发重验证。重验证要么刷新证据，要么在必需条件失败时\emph{撤销}修订。修复产生新的\emph{候选}修订，通过第~\ref{sec:maintenance} 节的门槛后变为有效。对声明使用 $m^r$、在快照 $s$ 上执行的查询 $q$，执行契约为}
\begin{equation}
\begin{split}
\operatorname{Admit}(q,m^r,s)\Longrightarrow {}& \operatorname{Available}(m^r,s)\\
&{}\land\bigwedge_{c\in C(m^r)}c(D_s),
\end{split}
\end{equation}
\bi{where $D_s$ is the database at snapshot $s$. Revision checks alone enforce availability but establish the conditions on the snapshot of the most recent maintenance; snapshot-bound execution (Section~\ref{sec:snapshot}) establishes them on $s$ itself.}
{其中 $D_s$ 为快照 $s$ 上的数据库。单靠修订核对只能保证可用性，条件则是在最近一次维护所在的快照上成立；绑定快照的执行（第~\ref{sec:snapshot} 节）使条件在 $s$ 本身上成立。}

\section{\bt{Admission, Maintenance, and Bounded Repair}{准入、维护与有界修复}}
\label{sec:maintenance}
\subsection{\bt{Admission from successful trajectories}{从成功轨迹准入}}
\bi{Candidates are extracted only from tasks with explicit business evidence and a successful judgment. The extractor sees the question, the SQL and derivation of the calculation chain, rejected queries, and metadata, but no business rows or result values. Deterministic gates then check the candidate: G1 business basis, G2 judged success, G3 static well-formedness (columns exist, the measure uses only permitted columns, joins follow validated paths, and required grain filters are present without question literals), G4 grain on the current snapshot, G5 SQL review, G6 replay of the example SQL, and G7 replay of the canonical SQL compiled from the fields. G7 checks what other agents will actually read, so a candidate that omits a filter or hard-codes a parameter fails it. Learning questions supply admission evidence; held-out questions only measure transfer.}
{只从具备显式业务依据且判题成功的任务中提炼候选。提炼器能看到题面、计算链中的 SQL 与算式、被拦下的查询以及元数据，但看不到业务行和结果值。随后由确定性门槛检查候选：G1 业务依据，G2 判题成功，G3 静态合法性（列存在、度量只用允许的列、连接沿已验证路径、包含必需的粒度过滤且不含题目字面量），G4 当前快照上的粒度，G5 SQL 审查，G6 示例 SQL 重放，G7 由字段编译的规范 SQL 重放。G7 检查的是其他智能体实际会读到的内容，因此遗漏过滤或把参数写死的候选会失败。学习题提供准入证据，留出题只用于测量迁移。}

\subsection{\bt{Selective revalidation and reuse}{选择性重验证与复用}}
\bi{On use, maintenance compares the recorded versions of each condition's dependencies with the current versions. Conditions over unchanged tables keep their evidence. For each remaining condition, \system\ looks up a completed verdict for the same identity at the current versions; otherwise it runs $Q_c$, and concurrent requests for the same check share that execution. Join references are checked through the shared join entries, so a revised or vanished join path also makes the definition pending. The definition-level baseline uses the same conditions, repair, regression, and in-flight merging but rechecks the entire condition set of the definition and forces join guards to rerun.}
{使用时，维护过程把每个条件所依赖表的记录版本与当前版本比较。未变化表上的条件保留原有证据。对其余条件，\system\ 查找同一身份在当前版本上的已完成结论；否则执行 $Q_c$，对同一检查的并发请求共享这次执行。连接引用通过共享的连接条目检查，因此连接路径被修订或消失时，定义同样变为待验证。定义级基线使用相同的条件、修复、回归和在途合并，但重查定义的全部条件，并强制重跑连接守卫。}

\subsection{\bt{Revocation and bounded repair}{撤销与有界修复}}
\bi{A failed condition revokes the revision and records the reason. Repair is restricted to two cases: a failed fact-table grain, for which it searches equality filters on low-cardinality columns, and a revised join path, whose new filters it adopts. A grain filter must keep exactly one row per business key without losing keys; this coverage requirement rejects, for instance, an application-state filter that restores uniqueness by dropping returns that never had such a row. \system\ further requires the fix to be \emph{unique}: it enumerates every passing filter and repairs only if exactly one exists. Two complete copies of the data, such as a primary table and an appended backup, each satisfy the structural tests, and nothing structural tells which copy holds the business truth; without this rule, the first filter found would be published (Section~\ref{sec:repair-eval}). A unique fix must then pass G3--G5 and G8, which compiles the replacement for the learning question and compares it on current data with the judged learning query. G8 is only as discriminating as that reference: if the change leaves the learning period untouched, every fix that restores the grain passes; if it touches that period, a reference that ignores the distinguishing column rejects even the correct fix. Repair searches over the same table and key are shared across definitions. A failed repair leaves the definition unavailable until new evidence is learned.}
{条件失败会撤销修订并记录原因。修复只处理两种情况：事实表粒度失效时，搜索低基数列上的等值过滤；连接路径被修订时，采用新路径的过滤。粒度过滤必须使每个业务键恰好保留一行且不丢键；这一覆盖要求会排除诸如申请状态过滤这样的候选，它恢复了唯一性，却丢掉了从未有过申请状态行的退货。\system\ 进一步要求修复是\emph{唯一}的：列出全部通过检查的过滤，只有恰好一个时才修复。主表与追加的备份副本这样的两份完整数据，各自都能通过结构检查，而结构上无从判断哪一份承载了业务事实；没有这条规则，搜索到的第一个过滤就会被发布（第~\ref{sec:repair-eval} 节）。唯一的修复还要通过 G3--G5 与 G8：G8 把替代修订按学习题编译，在当前数据上与经过判题的学习查询比较。G8 的分辨力取决于这一参照：若变化没有触及学习期，任何恢复粒度的修复都会通过；若触及了学习期，不涉及区分列的参照连正确的修复也会拒绝。同一张表、同一个键上的修复搜索在定义之间共享。修复失败的定义保持不可用，直到学到新的证据。}

\bi{The request that triggers maintenance performs the repair and receives the replacement revision. Other requests that arrive while the repair runs observe a revoked revision; instead of rejecting them, \system\ lets them join the in-flight maintenance and read its outcome, so a successful repair serves them as well.}
{触发维护的请求执行修复并获得替代修订。修复期间到达的其他请求看到的是已撤销的修订；\system\ 不拒绝它们，而是让它们加入进行中的维护并读取其结果，因此修复成功时它们同样得到服务。}

\section{\bt{Use-Time Enforcement}{使用时的强制保证}}
\label{sec:execution}
\subsection{\bt{Revision checks}{修订核对}}
\bi{Agents declare the metric keys and revisions used by a query; the middleware checks those references at execution and rejects absent, revoked, inaccessible, or superseded revisions. SQL review checks the supported grain and join requirements. Explicit rechecking at use makes a definition's maintained state actionable, and revocation notices reach agents on their next tool response. Canonical compilation supplies the calculation encoded by the recorded fields.}
{智能体声明查询所用的指标键和修订号，中间层在执行时核对这些引用，拒绝不存在、已撤销、不可访问或已被替代的修订。SQL 审查检查支持的粒度与连接要求。使用时的显式重查使定义的维护状态直接约束执行，撤销通知通过智能体下一次工具响应传达。规范编译提供记录字段所表达的计算。}

\subsection{\bt{Snapshot-bound execution}{绑定快照的执行}}
\label{sec:snapshot}
\bi{Revision checks ensure that a declared revision was valid when it was last maintained, not that its conditions hold on the data the query reads. Between the two, a writer may commit, and the default version source may not yet show the write. Snapshot-bound execution closes this gap. For a \code{run\_sql} call that declares revisions, \system\ (1) opens a repeatable-read, read-only transaction and reads the transactional versions; (2) collects the conditions of the declared revisions; (3) for each condition, looks up a verdict at its identity and the snapshot's versions of its tables, and otherwise runs $Q_c$ inside the transaction; (4) rejects the call if any condition fails, which also hands the definition to regular maintenance; and (5) otherwise executes the business SQL in the same transaction.}
{修订核对只能保证声明的修订在最近一次维护时有效，不能保证其条件在查询读取的数据上成立。两者之间可能有写入提交，而默认版本来源可能还没反映这次写入。绑定快照的执行填补了这一空隙。对声明了修订的 \code{run\_sql} 调用，\system\（1）开启一个可重复读的只读事务并读取事务性版本；（2）收集所声明修订的条件；（3）对每个条件，按其身份及快照中其依赖表的版本查找结论，没有就在该事务内执行 $Q_c$；（4）任一条件不成立即拒绝调用，并把定义交给常规维护；（5）否则在同一事务中执行业务 SQL。}

\bi{Reuse in step~(3) is sound because PostgreSQL snapshots are nested: a snapshot taken later sees every committed transaction that an earlier one saw. Every write to a table increments its transactional version inside the writing transaction, so two snapshots that read equal versions of a table see the same committed writes to it, and a verdict computed on one holds on the other. Verdicts computed by maintenance outside a snapshot qualify only if the versions read immediately before and after the check are equal, so that no write committed while the check ran. Concurrent identical checks at the same versions run once and are shared. The cost is a counter update per writing statement, which Section~\ref{sec:enforce-eval} measures.}
{第（3）步的复用是可靠的，因为 PostgreSQL 的快照是嵌套的：后取的快照能看到先取快照看到的每个已提交事务。对一张表的每次写入都在写事务内增加其事务性版本，因此读到该表相同版本的两个快照看到的对它的已提交写入完全相同，在一个快照上算出的结论在另一个快照上同样成立。维护在快照之外算出的结论，只有在检查前后各读一次的版本相同、即检查期间没有写入提交时，才可用于快照。相同版本上的相同检查并发到达时只执行一次并共享结果。代价是每条写语句多一次计数更新，第~\ref{sec:enforce-eval} 节测量这一代价。}

\subsection{\bt{Scope of the guarantee}{保证的范围}}
\bi{The guarantee covers declared uses: a query that declares a revision runs only on data on which the revision's conditions hold. It does not make undeclared SQL follow a definition, and it does not certify that an agent's own SQL matches the canonical calculation; SQL review checks the supported grain and join requirements, and canonical compilation supplies the calculation for agents that use it. Section~\ref{sec:scenarios} reports how often agents declare definitions and follow them.}
{这一保证覆盖声明了修订的使用：声明某个修订的查询只在该修订条件成立的数据上执行。它不能使未声明的 SQL 遵循定义，也不能证明智能体自己写的 SQL 与规范计算一致；SQL 审查检查支持的粒度与连接要求，规范编译为使用它的智能体提供计算。第~\ref{sec:scenarios} 节报告智能体声明并遵循定义的频率。}

\section{\bt{Evaluation}{实验评估}}
\label{sec:evaluation}
\subsection{\bt{Questions and setup}{研究问题与实验设置}}
\bi{The evaluation answers five questions. (Q1) Do maintained definitions stay correct under data-only changes, independently of what agents learned? (Q2) Does use-time enforcement hold under concurrent writes, and at what cost? (Q3) When does repair restore a broken definition, and when must it withdraw it? (Q4) What does maintenance cost, and which part of the savings requires typed conditions? (Q5) What do maintained definitions do for LLM agents end to end? Q1--Q4 are answered at the mechanism layer, where definitions are fixed and only maintenance varies; Q5 runs complete agents. The machine has 48 Hygon cores and 98\,GiB RAM. PostgreSQL 18.6 runs in disposable isolated databases with WAL and fsync disabled. The synthetic retail fixture uses TPC-DS-style column names; with one million store-sales rows it contains about 396,000 returns and 500,000 catalog-sales rows, and the other studies scale it to the sizes in Table~\ref{tab:experiments}. Table~\ref{tab:baselines} lists the compared methods.}
{评估回答五个问题。（Q1）维护后的定义能否在纯数据变化下保持正确，且不受智能体学到什么的影响？（Q2）存在并发写入时，使用时的强制保证是否成立，代价如何？（Q3）修复何时能恢复失效定义，何时必须撤下定义？（Q4）维护代价如何，节省中哪一部分需要类型化条件？（Q5）维护后的定义在端到端上对大模型智能体有何作用？Q1--Q4 在机制层回答：定义固定，只改变维护方式；Q5 运行完整的智能体。实验机有 48 核 Hygon 和 98\,GiB 内存。PostgreSQL 18.6 在可丢弃的隔离库中运行，关闭 WAL 与 fsync。合成零售数据采用 TPC-DS 风格列名；100 万行门店销售对应约 39.6 万行退货和 50 万行目录销售，其他实验按表~\ref{tab:experiments} 的规模缩放。表~\ref{tab:baselines} 列出被比较的方法。}

\subsection{\bt{Validity under data changes}{数据变化下的有效性}}
\label{sec:validity}
\bi{\emph{Paired replay (Q1).} The scenario runs of Section~\ref{sec:scenarios} leave each cell with the library its agents learned: \RpLibs\ libraries of 3--8 promoted definitions, \RpDefs\ in all, from three LLMs. We replay every library under every method on the same data. Each method gets its own middleware instance, admitted with the library's definitions and learning evidence; each of the \RpChanges\ changes (the ten scenarios of Table~\ref{tab:scenarios} plus a backup-copy change, Section~\ref{sec:repair-eval}) is applied from the same initial snapshot; and the scored questions of every affected definition are answered with the canonical SQL of whatever revision the method serves. This isolates maintenance from learning and from agent behavior. A question is \emph{correct}, \emph{served wrong} (the served revision answers incorrectly), or \emph{unavailable}; unavailability is \emph{needed} if the unmaintained definition would also have answered incorrectly.}
{\emph{配对回放（Q1）。}第~\ref{sec:scenarios} 节的场景实验在每组结束时留下该组智能体学到的定义库：\RpLibs\ 个库，各含 3--8 个已晋升定义，共 \RpDefs\ 个，来自 3 个大模型。我们在同一份数据上用每种方法回放每个库。每种方法各有一个中间层实例，以该库的定义和学习证据准入；\RpChanges\ 种变化（表~\ref{tab:scenarios} 的 10 个场景，外加一个备份副本变化，见第~\ref{sec:repair-eval} 节）都从同一初始快照施加；每个受影响定义的计分题，用该方法当时提供的修订的规范 SQL 作答。这把维护与学习、与智能体行为隔离开。每道题的结果为\emph{答对}、\emph{提供但答错}（提供的修订答错）或\emph{不可用}；若未经维护的定义同样会答错，则称该不可用为\emph{必要的}。}

\subsection{\bt{Enforcement under concurrent writes}{并发写入下的强制保证}}
\label{sec:enforce-eval}
\bi{\emph{Setup (Q2).} We compare checking before execution (\emph{pre-check}, the default) with snapshot-bound execution for store revenue at 200,000 rows. The violating write reloads four months of sales, duplicating their keys. Each probe query returns the canonical answer for one month together with the number of duplicated keys in that month, computed in the same statement and therefore on the same snapshot; an answer is a \emph{violation} if that count is positive, i.e., it was computed on data that violates the declared revision's grain condition.}
{\emph{设置（Q2）。}我们在 20 万行数据上比较执行前检查（\emph{预检查}，默认方式）与绑定快照的执行，指标为门店营业额。违反条件的写入把四个月的销售重新装载一次，使其键重复。每条探针查询返回某个月的规范答案，同时在同一条语句、因而在同一快照上算出该月重复键的个数；该数大于零即为\emph{违规}，即答案是在违反所声明修订粒度条件的数据上算出的。}

\bi{\emph{Deterministic interleavings.} When the write commits after the check and before execution, pre-check answers on violating data in \SnPausePre\ of \SnTrials\ trials and snapshot-bound execution in none, answering from the pre-write snapshot. When the write commits just before an unannounced call, pre-check still answers on violating data in \SnBeforePre\ trials because its version source has not yet observed the write; snapshot-bound execution rejects all \SnBeforeSnapRej. When the write is announced and its statistics are visible, both reject.}
{\emph{确定性交错。}写入在检查之后、执行之前提交时，预检查在 \SnTrials\ 次中有 \SnPausePre\ 次在违规数据上作答，绑定快照的执行一次也没有，它在写入前的快照上作答。写入刚提交、未经通知就调用时，预检查仍有 \SnBeforePre\ 次违规，因为其版本来源尚未观察到这次写入；绑定快照的执行 \SnBeforeSnapRej\ 次全部拒绝。写入经过通知、统计已经可见时，两者都拒绝。}

\subsection{\bt{Repair and its boundary}{修复及其边界}}
\label{sec:repair-eval}
\bi{\emph{The reference decides (Q3).} The last row of Table~\ref{tab:replay} repeats \system\ with a second G8 reference: instead of the benchmark's judged learning query, which was written knowing the status, version, and current-flag columns, it uses the SQL the agent wrote for the learning question, the reference a deployment would actually have. Over the same \RpPairN\ questions, correct answers fall from \RpPairJudge\ to \RpPairEx, \RpRefDiff\ points (95\% cluster-bootstrap interval \RpRefLo--\RpRefHi). Every lost answer becomes unavailable and none becomes wrong. Repairs of versioned corrections now succeed for \RpRevisionEx\ instead of \RpRevisionJudge\ of \RpRevisionN\ questions, and those of dimension history for \RpDimhistEx\ instead of \RpDimhistJudge\ of \RpDimhistN, because these changes touch the learning period and the agent's own query ignores the column that separates the versions; status-history repairs are unaffected (\RpStatusEx\ of \RpStatusN) because that change leaves the learning period intact. The successful status and versioning repairs reported in Section~\ref{sec:scenarios} therefore rely on references that anticipate those columns.}
{\emph{参照决定成败（Q3）。}表~\ref{tab:replay} 最后一行用另一种 G8 参照重复 \system：不用基准中经过判题的学习查询（它在编写时已知道状态、版本和当前标志列），而用智能体为学习题写下的 SQL，这才是部署中真正可得的参照。在同一批 \RpPairN\ 道题上，答对数从 \RpPairJudge\ 降到 \RpPairEx，下降 \RpRefDiff\ 个百分点（按库整群自助法 95\% 区间 \RpRefLo--\RpRefHi）。丢失的答案全部变为不可用，没有一个变为错误。版本化更正的修复现在只在 \RpRevisionN\ 道题中的 \RpRevisionEx\ 道上成功（原为 \RpRevisionJudge\ 道），维表拉链只在 \RpDimhistN\ 道中的 \RpDimhistEx\ 道上成功（原为 \RpDimhistJudge\ 道），因为这两种变化触及学习期，而智能体自己的查询不涉及区分版本的列；状态流水的修复不受影响（\RpStatusN\ 道中 \RpStatusEx\ 道），因为该变化没有触及学习期。因此，第~\ref{sec:scenarios} 节报告的状态流水与版本化更正修复的成功，依赖于预先知道这些列的参照。}

\bi{\emph{Ambiguous fixes.} The backup-copy change corrects some 2002 return amounts and appends a full backup copy of the returns table, marked by a source column, that keeps the old amounts. Filters on the primary source and on the backup source each restore one row per return without losing returns. Without the uniqueness rule, repair takes the first filter it finds, the backup. A reference that ignores the source column rejects it, but a reference that already filters on the primary source accepts it, and \system\ then publishes a revision that answers two of four new questions wrongly for both return metrics. With the uniqueness rule, repair finds both filters and withdraws the definitions under either reference. Rerunning the replay of \system\ with the rule changes none of the 3,000 paired outcomes, because the status, versioning, and dimension-history fixes are unique.}
{\emph{有歧义的修复。}备份副本变化更正了部分 2002 年的退货金额，并追加一整份退货表的备份副本（以来源列标记），副本保留旧金额。按主数据来源过滤和按备份来源过滤，都能使每笔退货恰好一行且不丢退货。没有唯一性规则时，修复取搜索到的第一个过滤，即备份。不涉及来源列的参照会拒绝它，但预先按主数据来源过滤的参照会接受它，于是 \system\ 发布的修订在两个退货指标的 4 道新题中都答错 2 道。有了唯一性规则，修复会找到两个过滤，在任一参照下都撤下定义。打开该规则后重新回放 \system，3,000 道配对题的结果没有任何变化，因为状态流水、版本化更正与维表拉链的修复都是唯一的。}

\bi{\emph{Availability during repair.} If requests that arrive while a repair runs are rejected, simultaneous arrivals (eight agents, 19 definitions, three runs at 200,000 rows) make \WrDefOff\ of \WrUses\ uses unavailable under definition-level and \WrCondOff\ under condition-level maintenance; condition-level maintenance suffers more because shared verdicts revoke many definitions at once. Letting such requests wait for the in-flight repair removes all of them, at the same total waiting time and database work.}
{\emph{修复期间的可用性。}若拒绝修复进行中到达的请求，在同时到达下（8 个智能体、19 个定义、20 万行、3 轮），定义级维护的 \WrUses\ 次使用中有 \WrDefOff\ 次不可用，条件级维护为 \WrCondOff\ 次；条件级更多，是因为共享结论使许多定义同时被撤销。让这些请求等待进行中的修复后，不可用全部消失，总等待时间与数据库工作量不变。}

{图~\ref{fig:cost} 表明，节省来自结论复用而不是缩小检查范围，而且结论复用不需要类型化条件。错峰到达时，定义级的耗时随定义数增长（\CbStagDefOne\ 到 \CbStagDefSix\ 秒），\system\ 与通用缓存则分别保持在 \CbCondStagMin--\CbCondStagMax\ 与 \CbCacheStagMin--\CbCacheStagMax\ 秒；19 个定义时二者分别只需定义级的 \CbStagCondSix\% 与 \CbStagCacheSix\%，仅范围维护需要 83--94\%。唯一明显的差距出现在共享最少时（\CbStagCondOne\% 对 \CbStagCacheOne\%）：退货比率的粒度条件与连接守卫刚刚以另一种键列顺序检查过的条件是同一个，\system\ 的语义身份能识别这一点，按 SQL 文本索引的缓存则不能。同时到达时，在途合并已为各方法去掉了大量重复工作，通用缓存与 \system\ 需要定义级的 50--84\%。三个定义互不共享条件时，各方法的耗时都在定义级的 \CbZeroMin--\CbZeroMax\%：节省只来自共享，跟踪条件也没有可见的额外开销。所有配置都是零过期使用、零误撤销、零不可用。}

\bi{\emph{Scale and concurrency.} The ratios persist with data size and agent count. With 4 million rows, \system\ and the cache need \CbFourStagCond\% and \CbFourStagCache\% of definition-level time under staggered arrivals; with 32 agents, \CbAgentsStagCond\% and \CbAgentsStagCache\%, whereas simultaneous requests from 32 agents leave little to save beyond in-flight merging (\CbAgentsBurstCond\% and \CbAgentsBurstCache\%). From 1 to 16 million rows, definition-level time under staggered arrivals grows from \EoneDefOne\ to \EoneDefSixteen\,s and condition-level time from \EoneCondOne\ to \EoneCondSixteen\,s, a constant ratio of \EoneRatioSixteen--\EoneRatioFour\%.}
{\emph{规模与并发。}这些比例在数据量与智能体数增加后保持不变。400 万行时，错峰到达下 \system\ 与通用缓存分别需要定义级的 \CbFourStagCond\% 与 \CbFourStagCache\%；32 个智能体时为 \CbAgentsStagCond\% 与 \CbAgentsStagCache\%，而 32 个智能体同时到达时，除在途合并外已没有多少可省（\CbAgentsBurstCond\% 与 \CbAgentsBurstCache\%）。从 100 万到 1600 万行，错峰到达下定义级耗时从 \EoneDefOne\ 秒增长到 \EoneDefSixteen\ 秒，条件级从 \EoneCondOne\ 秒增长到 \EoneCondSixteen\ 秒，比例稳定在 \EoneRatioSixteen--\EoneRatioFour\%。}

Table~\ref{tab:scenarios} groups the ten scenarios by the condition they target; the unit change is a control that no condition models. These runs predate snapshot-bound execution, the uniqueness rule, and waiting for repairs, and their updates are applied between phases.}
{\emph{实验流程（Q5）。}5 个指标为门店营业额、门店退货金额、门店退货率、目录渠道营业额和电子品类门店营业额，各有 2 道学习题和 3 道计分题（新期间、跨期差值和按月排名）。智能体 A 在给出显式业务定义的学习题上作答，提炼器把判题成功的轨迹转成候选，经准入后发布。从未接触过这些指标的智能体 B 只拿到指标名，先在未变化的数据上回答计分题，再在每个数据变化场景下各答一次。每个场景都从相同的初始快照和共享知识库出发，施加一次更新，只重问读到被更新表的指标，结束后回滚。标准答案反映更新的业务效果，在施加重复行、状态行或旧版本等表示变化之前计算，因此智能体必须过滤掉这些行才能答对。表~\ref{tab:scenarios} 按目标条件对 10 个场景分组，其中单位变化是任何条件都没有刻画的对照。这些运行早于绑定快照执行、唯一性规则与修复等待的实现，更新在阶段之间施加。}

In both cases maintenance is safe but the definition becomes unavailable. The unit change violates no condition: \ScenUnitStaleTasks\ of \ScenUnitTasks\ condition-level tasks use the unchanged definition, and every method that shares definitions inherits the error. {\emph{模型的边界。}重复装载破坏销售粒度并被撤销（\ScenRevokedDupload\ 次撤销），但任何过滤都无法区分完全相同的行，修复失败，正确率降到不共享的水平（\ScenAccCondDupload\% 对 \ScenAccNoShareDupload\%）。日期键改写破坏日期连接的覆盖，同样被撤销且没有修复候选（\ScenAccCondLatekey\% 对 \ScenAccNoShareLatekey\%）。这两种情形下维护是安全的，但定义变得不可用。单位变化不违反任何条件：条件级的 \ScenUnitTasks\ 道题中有 \ScenUnitStaleTasks\ 道使用了未变化的定义，所有共享定义的方法都继承了这一错误。有效性条件刻画粒度、多重性与覆盖，而不刻画取值的含义。}

\section{\bt{Related Work}{相关工作}}
\label{sec:related}
\paragraph{\bt{Data agents and business semantics}{数据智能体与业务语义}}
\bi{Agent-first data systems identify redundant agent requests and propose a persistent agentic memory that must track changes to data and metadata~\cite{liu2026agents}; tutorials survey data agents, including their difficulty with changing data~\cite{luo2026dataagents}, and the management of agentic memory~\cite{li2026agenticmemory}. Text-to-SQL benchmarks and practitioner studies show that realistic enterprise schemas, their terminology, and their documentation remain hard for current systems~\cite{lei2025spider2,floratou2024nl2sql}, and that external knowledge and explicit business semantics raise accuracy~\cite{li2023bird,huo2026birdinteract,sequeda2024kg}. Business-intelligence platforms maintain term definitions~\cite{jiang2025siriusbi} or generate calculation logic from script history and lineage~\cite{weng2025datalab}; AgentSM organizes trajectories as structured semantic memory and leaves the consistency of shared memory to future work~\cite{biswal2026agentsm}. \system\ addresses that consistency for metric definitions: executable conditions connect a definition's recorded meaning and implementation to current database state, and their verdicts decide whether and on which snapshot the definition may be used. Schema and data-model robustness studies~\cite{zhang2025evoschema,furst2025datamodel} address complementary schema and data-model variation; our evaluation isolates data-only breakage under a fixed schema.}
{面向智能体的数据系统指出智能体请求高度重复，并提出必须跟踪数据与元数据变化的持久智能体记忆~\cite{liu2026agents}；教程综述了数据智能体（包括其难以适应变化数据的问题）~\cite{luo2026dataagents}和智能体记忆的管理~\cite{li2026agenticmemory}。Text-to-SQL 基准与实践研究表明，真实企业表结构及其术语和文档对现有系统仍然困难~\cite{lei2025spider2,floratou2024nl2sql}，外部知识与显式业务语义能够提高正确率~\cite{li2023bird,huo2026birdinteract,sequeda2024kg}。商业智能平台维护术语定义~\cite{jiang2025siriusbi}，或从脚本历史和血缘中生成计算逻辑~\cite{weng2025datalab}；AgentSM 把轨迹组织为结构化语义记忆，并把共享记忆的一致性留作未来工作~\cite{biswal2026agentsm}。\system\ 针对指标定义解决这种一致性：可执行条件把定义记录的含义与实现联系到当前数据库状态，其结论决定定义能否使用、在哪个快照上使用。表结构与数据模型鲁棒性研究~\cite{zhang2025evoschema,furst2025datamodel}处理互补的表结构与数据模型差异；本文评估单独考察固定表结构下的纯数据破坏。}

\paragraph{\bt{Agent memory and experience reuse}{智能体记忆与经验复用}}
\bi{Agent memory systems induce workflows from successful trajectories~\cite{wang2025awm}, distill insights or strategies from experience~\cite{zhao2024expel,ouyang2026reasoningbank}, evolve context playbooks~\cite{zhang2026ace}, link and update notes~\cite{xu2025amem}, manage long-term facts~\cite{chhikara2025mem0,packer2023memgpt}, cache plan templates~\cite{zhang2025apc}, and store and reuse past solutions~\cite{guo2024dsagent}. These representations organize knowledge across tasks and conversations. \system\ represents shared metric knowledge together with typed database conditions and versioned evidence; condition outcomes govern admission and every later use, and a failed condition leads to a bounded, regression-tested repair or to withdrawal.}
{智能体记忆系统从成功轨迹中归纳工作流~\cite{wang2025awm}，从经验中提炼洞见或策略~\cite{zhao2024expel,ouyang2026reasoningbank}，演化上下文手册~\cite{zhang2026ace}，链接并更新笔记~\cite{xu2025amem}，管理长期事实~\cite{chhikara2025mem0,packer2023memgpt}，缓存计划模板~\cite{zhang2025apc}，并保存和复用既往方案~\cite{guo2024dsagent}。这些表示在任务与对话之间组织知识。\system\ 把共享指标知识与类型化数据库条件、版本化证据一起表示；条件结论决定准入与之后的每一次使用，条件失败则导致有界的、经过回归测试的修复或撤下定义。}

\paragraph{\bt{Metric layers and summarizability}{指标层与可汇总性}}
\bi{Dimensional modeling conforms dimensions and facts across business processes~\cite{kimball2013toolkit}, and measures in SQL attach aggregation semantics to tables so that joins do not double count~\cite{hyde2024measures}. Summarizability research identifies disjointness, completeness, and type compatibility as necessary conditions for correct aggregation~\cite{lenz1997summarizability}, surveys how complex multidimensional structures violate them~\cite{mazon2009summarizability}, and proposes summary constraints analogous to integrity constraints~\cite{horner2004additivity}. Commercial metric layers declare keys and join properties, and at least one documents that a declared join property is not validated at runtime~\cite{databricks2026metricviews}. \system\ turns these conditions into executable checks attached to learned definitions and enforces them where the definitions are used.}
{维度建模要求在各业务过程间使用一致的维度和事实~\cite{kimball2013toolkit}；SQL 中的度量把聚合语义附着在表上，使连接不再重复计数~\cite{hyde2024measures}。可汇总性研究指出，不相交、完备和类型相容是正确汇总的必要条件~\cite{lenz1997summarizability}，综述了复杂多维结构违反这些条件的方式~\cite{mazon2009summarizability}，并提出类似完整性约束的汇总约束~\cite{horner2004additivity}。商用指标层声明键与连接性质，至少有一家在文档中写明声明的连接性质不在运行时验证~\cite{databricks2026metricviews}。\system\ 把这些条件变成附着在学到的定义上的可执行检查，并在定义被使用处强制它们。}

\paragraph{\bt{Constraints, profiling, and data validation}{约束、数据画像与数据验证}}
\bi{Integrity checking specializes verification to updates that can violate a constraint~\cite{nicolas1982integrity,ceri1990constraint}, and derived-relation maintenance can first identify irrelevant updates~\cite{blakeley1989irrelevant}. Soft constraints hold on current data without being enforced and support optimization while valid~\cite{godfrey2001soft}; CORDS discovers approximate dependencies from samples~\cite{ilyas2004cords}. Profiling discovers and maintains unique column combinations and dependencies~\cite{abedjan2015profiling,abedjan2014swan,schirmer2019dynfd}. Data-validation systems check declarative constraints on growing data and share their scans~\cite{schelter2018deequ}, and infer constraints~\cite{breck2019validation,song2021autovalidate} or acceptable batch profiles~\cite{redyuk2021dynamic} from past data. \system\ derives its conditions from learned definitions rather than from declarations or profiles, and couples their verdicts to which definitions agents may use and on which snapshot.}
{完整性检查按可能违反约束的更新执行验证~\cite{nicolas1982integrity,ceri1990constraint}，派生关系维护可以先识别无关更新~\cite{blakeley1989irrelevant}。软约束在当前数据上成立但不被强制，并在有效时支持优化~\cite{godfrey2001soft}；CORDS 从样本中发现近似依赖~\cite{ilyas2004cords}。数据画像发现并维护唯一列组合与依赖~\cite{abedjan2015profiling,abedjan2014swan,schirmer2019dynfd}。数据验证系统在增长的数据上检查声明式约束并共享扫描~\cite{schelter2018deequ}，从历史数据中推断约束~\cite{breck2019validation,song2021autovalidate}或可接受的批次画像~\cite{redyuk2021dynamic}。\system\ 的条件由学到的定义推出，而不是来自声明或画像，并把条件结论与智能体能使用哪些定义、在哪个快照上使用联系起来。}

\paragraph{\bt{View maintenance, shared work, and caching}{视图维护、共享计算与缓存}}
\bi{Materialized-view maintenance~\cite{gupta1995maintenance,blakeley1986efficiently} can defer work off the update path~\cite{colby1996deferred} or until a view is referenced~\cite{zhou2007lazy}; our definition-level baseline applies this lazy strategy. Multiple-query optimization and shared execution evaluate common work once~\cite{sellis1988mqo,harizopoulos2005qpipe,giannikis2012shareddb}, and recycling reuses intermediate results and invalidates those affected by updates~\cite{ivanova2010recycling}. Cache designs use semantic descriptions~\cite{dar1996semantic}, update-driven invalidation~\cite{garrod2008ferdinand}, input-dependent keys~\cite{gunda2010nectar}, and leases that merge concurrent misses~\cite{nishtala2013memcache}; TxCache keeps cached results transactionally consistent with the database through validity intervals~\cite{ports2010txcache}. Build systems track dependency hashes~\cite{mokhov2018build}, and demand-driven incremental computation recomputes requested dependencies~\cite{hammer2014adapton}. Our cost results confirm that these techniques suffice to make maintenance cheap once conditions are explicit: a version-keyed cache of check queries captures nearly all of \system's savings. \system's snapshot-bound execution applies TxCache's principle to validity verdicts; what \system\ adds is the derivation of the checks from learned definitions and the use of their verdicts to govern which definitions agents may use.}
{物化视图维护~\cite{gupta1995maintenance,blakeley1986efficiently}可以把工作移出更新路径~\cite{colby1996deferred}，或推迟到视图被引用时~\cite{zhou2007lazy}；本文定义级基线采用这一懒维护策略。多查询优化与共享执行对公共工作只计算一次~\cite{sellis1988mqo,harizopoulos2005qpipe,giannikis2012shareddb}，中间结果回收复用中间结果，并使受更新影响的结果失效~\cite{ivanova2010recycling}。缓存设计使用语义描述~\cite{dar1996semantic}、更新驱动失效~\cite{garrod2008ferdinand}、依赖输入的键~\cite{gunda2010nectar}及合并并发未命中的租约~\cite{nishtala2013memcache}；TxCache 用有效区间使缓存结果与数据库保持事务一致~\cite{ports2010txcache}。构建系统跟踪依赖哈希~\cite{mokhov2018build}，按需增量计算重算被请求的依赖~\cite{hammer2014adapton}。我们的代价结果证实，一旦条件显式化，这些技术就足以使维护代价低廉：按版本缓存检查查询，几乎能拿到 \system\ 的全部节省。\system\ 的绑定快照执行把 TxCache 的原则用于有效性结论；\system\ 增加的是从学到的定义推出检查，并用检查结论决定智能体可以使用哪些定义。}

\section{\bt{Discussion and Limitations}{讨论与局限}}
\label{sec:limitations}
\paragraph{\bt{Guarantee scope}{保证的范围}}
\bi{\system\ guarantees that a declared use runs on data that satisfies the revision's modeled conditions. Business evidence supplies the meaning; conditions cover grain, multiplicity, time role, and coverage, not the meaning of values, so a unit change goes unnoticed. Undeclared use is outside the guarantee, and in our traces a quarter of answers declared nothing; routing canonical SQL through the middleware, or recognizing a definition in undeclared SQL, would extend it.}
{\system\ 保证声明了修订的使用在满足该修订已建模条件的数据上执行。业务证据提供含义；条件覆盖粒度、多重性、时间角色与覆盖，不覆盖取值的含义，因此单位变化不会被发现。未声明的使用不在保证之内，在我们的轨迹中有四分之一的答案什么也没声明；让规范 SQL 经由中间层执行，或在未声明的 SQL 中识别定义，可以扩大保证范围。}
\paragraph{\bt{Repair semantics}{修复的语义}}
\bi{Repair restores structure, not meaning. The uniqueness rule prevents publishing one of several structurally equivalent fixes, and regression catches a wrong fix only if its reference distinguishes the alternatives. Our benchmark references were written knowing the distinguishing columns; with the agent's own learning query, more repairs are refused. An ambiguous or unverifiable repair should go to a human with its candidates, and repairs that deduplicate rows or remap keys would extend the operators to duplicate loads and re-keyed dates.}
{修复恢复的是结构，而不是含义。唯一性规则防止在多个结构上等价的修复中发布其中一个；只有当参照能区分各个备选时，回归测试才能发现错误的修复。本文基准的参照在编写时已知道区分列；以智能体自己的学习查询为参照时，更多修复被拒绝。有歧义或无法验证的修复应带着候选交给人确认；能去重或重映射键的修复算子可以把范围扩展到重复装载与日期键改写。}
\paragraph{\bt{Cost of enforcement}{强制保证的代价}}
\bi{Snapshot-bound execution adds a counter update to every writing statement; sharding removes contention among concurrent writers, but single-row statements still run at about 0.7$\times$ throughput, which suits analytical tables loaded in batches better than high-rate transactional writes. Long-running write transactions do not block readers, which keep using the last committed versions.}
{绑定快照的执行为每条写语句增加一次计数更新；分片消除了并发写者之间的争用，但单行语句的吞吐仍约为 0.7 倍，因此更适合批量装载的分析型表，而非高频事务写入。长时间运行的写事务不会阻塞读者，读者继续使用最近一次已提交的版本。}
\paragraph{\bt{Generalization}{泛化}}
\bi{The mechanism experiments fix what agents learned and vary maintenance, but they share one synthetic schema with the scenarios, and the replay runs at 200,000 rows while the scenarios use one million; outcome classes do not depend on data size, whereas timings do. The TPC-DS analysis establishes natural condition sharing in an independently written workload, not the behavior of updates on it. Provider usage caps left the planned three end-to-end repetitions incomplete, and the scenario runs predate the uniqueness rule, waiting for repairs, and snapshot-bound execution. We have implemented a matched trajectory-retrieval baseline that receives the same learning history; its end-to-end evaluation, independent repetitions, and a second schema with real update histories are the next steps. With WAL and fsync disabled, the reported timings characterize this configuration.}
{机制层实验固定了智能体学到的内容、只改变维护方式，但与场景实验共用一个合成表结构；回放使用 20 万行，场景使用 100 万行，结果类别与数据规模无关，耗时则相关。TPC-DS 分析证明了独立编写的负载中存在自然的条件共享，但没有考察其上的更新。服务商用量上限使计划的 3 次端到端重复没有完成，而且场景运行早于唯一性规则、修复等待与绑定快照执行。我们已经实现了获得相同学习历史的匹配轨迹检索基线；它的端到端评估、独立重复以及具有真实更新历史的第二个表结构是下一步工作。关闭 WAL 与 fsync 时的耗时只刻画这一实验配置。}

\section{\bt{Conclusion}{结论}}
\bi{Data agents repeat knowledge rather than queries, and sharing the metric definitions they learn makes them more accurate and consistent. Shared definitions, however, are long-lived state over a changing database, and their SQL stays correct only while unstated data properties hold. \system\ makes those properties explicit as executable conditions derived from each definition, keeps their verdicts by dependency version, binds every declared use to verdicts that hold on the query's own snapshot, and repairs a broken definition only with a unique fix that passes regression, withdrawing it otherwise. On libraries learned by three LLMs, maintained definitions serve no wrong answer under the modeled changes, snapshot-bound execution removes answers on condition-violating data under concurrent writers, and repair fails safe when its reference cannot tell populations apart. Maintenance itself is cheap once conditions are explicit, whether by typed verdicts or a generic version-keyed cache. Changes to the meaning of values, undeclared uses, and repairs that need human judgment mark the next steps.}
{数据智能体重复的是知识而非查询，共享它们学到的指标定义能让答案更准确、口径更一致。但共享定义是变化数据库上的长期状态，其 SQL 只在一些未写明的数据性质成立时才保持正确。\system\ 把这些性质显式化为从每个定义推出的可执行条件，按依赖版本维护条件结论，把每次声明了修订的使用绑定到在查询自身快照上成立的结论，并只用通过回归测试的唯一修复来修复失效定义，否则撤下定义。在 3 个大模型学到的定义库上，维护后的定义在已建模的变化下不给出错误答案，绑定快照的执行在并发写入下消除了在违反条件的数据上作答，参照无法区分总体时修复会安全地失败。一旦条件显式化，维护本身的代价很低，无论用类型化结论还是通用的版本缓存。取值含义的变化、未声明的使用以及需要人工判断的修复，是下一步的方向。}
