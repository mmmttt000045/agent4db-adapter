\section{\bt{Introduction}{引言}}
\label{sec:introduction}
\bi{A data agent learns what a business metric means by exploring the database: it lists tables, inspects values, validates candidate joins, and settles on SQL over many turns. What it learns has two parts. The business meaning of ``return amount'' does not change, but the SQL that implements it is correct only because, on the snapshot the agent explored, a ticket--item key identifies one completed return, the joins do not fan out, and the return date assigns each return to its period; the SQL states none of this and the schema enforces none of it. Sharing such a definition across agents raises the accuracy of the agents that reuse it, and it also hands the implementation to agents that never saw its evidence. When an ETL change later appends an application-state row for each new return, no table or column changes and the shared \code{SUM(sr\_return\_amt)} still executes; it now counts many returns twice, returning 6,588,699.86 for one period where the correct value is 3,294,349.93. The agent that learned the definition is gone, the agents that reuse it have no ground truth, and a successful execution tells them nothing. The database therefore has to carry the validity of what agents learned about it.}
{数据智能体通过探索数据库学到业务指标的含义：多轮列出表、查看取值、验证候选连接，最后确定 SQL。它学到的东西有两部分。“退货金额”的业务含义不会变，但实现它的 SQL 之所以正确，只是因为在智能体探索的那个快照上，小票--商品键对应一笔已完成的退货，连接不放大行数，退货日期把每笔退货归入其期间；这些性质 SQL 一条也没写明，表结构一条也不强制。在智能体之间共享这样的定义能提高复用它的智能体的正确率，同时也把这一实现交给了从未见过其证据的智能体。之后一次 ETL 改动开始为每笔新退货追加一条申请状态记录：表和列都没有变，共享的 \code{SUM(sr\_return\_amt)} 照常执行，却把许多退货计算了两次，某个期间返回 6,588,699.86，而正确值是 3,294,349.93。学到这个定义的智能体已经结束，复用它的智能体没有基准真值，一次成功的执行什么也说明不了。因此数据库必须替智能体记住它们学到的东西为什么成立。}

\bi{Agents cannot do without the business knowledge that shared definitions carry, and systems increasingly keep it for them. Enterprise warehouses name columns in terminology that only domain experts understand~\cite{floratou2024nl2sql}, an o1-preview agent solves only 21.3\% of real enterprise text-to-SQL workflows~\cite{lei2025spider2}, and supplying business knowledge closes much of the gap: expert-annotated evidence raises GPT-4's execution accuracy on BIRD from 34.9\% to 54.9\%~\cite{li2023bird}, and a knowledge graph of business semantics raises it on enterprise insurance questions from 16.7\% to 54.2\%~\cite{sequeda2024kg}. Metric definitions carry much of this knowledge: which fact rows to aggregate, which records count as one business event, and how measurements relate across tables, the definitions that warehouses require to be conformed across uses~\cite{kimball2013toolkit}. Re-exploration does not recover them, because the business meaning is not in the data, and it is not free: in our end-to-end study, agents without shared definitions answer \ScenAccNoShare\% of questions correctly and agents with them \DsNoguardAll\%, in \ScenHoldTurnsCondModelA\ instead of \ScenHoldTurnsNoShareModelA\ turns per held-out question. Accordingly, systems now derive such knowledge from script histories and lineage~\cite{weng2025datalab} and from prior agent trajectories~\cite{biswal2026agentsm}, and metric layers let engineers declare it by hand~\cite{databricks2026metricviews}. Shared definitions are thus long-lived state over a changing database, and Liu et al.\ caution that a memory store that drifts from the data ``may lead a new probe to make a mistake''~\cite{liu2026agents}.}
{智能体离不开共享定义所承载的业务知识，而系统正越来越多地替它们保存这些知识。企业数仓的列名使用只有领域专家才懂的术语~\cite{floratou2024nl2sql}；在真实企业 Text-to-SQL 工作流上，基于 o1-preview 的智能体只能完成 21.3\%~\cite{lei2025spider2}；补上业务知识能弥补很大一部分差距：专家标注的证据使 GPT-4 在 BIRD 上的执行正确率从 34.9\% 提高到 54.9\%~\cite{li2023bird}，刻画业务语义的知识图谱使其在企业保险问题上的正确率从 16.7\% 提高到 54.2\%~\cite{sequeda2024kg}。指标定义承载了其中大部分知识：聚合哪些事实行、哪些记录算作一次业务事件、度量如何跨表关联，也就是数据仓库要求在各处保持一致的那些定义~\cite{kimball2013toolkit}。重新探索找不回它们，因为业务含义不在数据里，而且探索本身有代价：在我们的端到端实验中，没有共享定义的智能体答对 \ScenAccNoShare\%，有共享定义的答对 \DsNoguardAll\%，每道留出题的轮数从 \ScenHoldTurnsNoShareModelA\ 降至 \ScenHoldTurnsCondModelA{}。因此，已有系统从脚本历史和血缘~\cite{weng2025datalab}以及既往智能体轨迹~\cite{biswal2026agentsm}中推导这类知识，指标层则让工程师手工声明它~\cite{databricks2026metricviews}。共享定义由此成为变化数据库上的长期状态，Liu 等提醒，与数据不一致的记忆库“可能导致新的探查出错”~\cite{liu2026agents}。}

\bi{Warehouses have always depended on these properties, but three things change when the consumer is an agent, and today's safeguards do not cover them. First, the premise moves from design to observation. Dimensional modeling declares the grain as ``a binding contract''~\cite{kimball2013toolkit}, validation pipelines test declared constraints~\cite{schelter2018deequ,breck2019validation}, and schema-evolution tools track structure~\cite{curino2008prism,zhang2025evoschema}; an agent instead checks a property once, on the current data, and records it nowhere but its trajectory. The properties correspond to the summarizability conditions for correct aggregation~\cite{lenz1997summarizability,mazon2009summarizability} and, like the soft constraints that optimizers exploit~\cite{godfrey2001soft}, hold on the current data only: type-2 dimensions add a row per changed member, late-arriving facts and reloads append rows, and status-change rows appended to a transaction table mix two grains, which dimensional modeling rules out~\cite{kimball2013toolkit}. None of these changes the schema, and even a hand-declared join property in a commercial metric layer ``is not validated at runtime''~\cite{databricks2026metricviews}. Second, producers and consumers are decoupled. A query in an application has an owner who is told when a feed changes; a definition in shared memory outlives the session that learned it and is served to fresh sessions as authoritative, so one stale observation propagates to every agent: under the covered breaking changes in our study, sharing without validation serves a stale definition in \DsNoguardStaleModeled\ tasks and schema-change invalidation in \DsSchemaStaleModeled. Third, the consumer cannot see the break. Upstream changes can produce data that ``looks perfectly fine'' to the consumer~\cite{breck2019validation} and break downstream applications silently~\cite{song2021autovalidate}; in our traces only 16\% of sessions check key uniqueness, and every wrong answer came from SQL that ran without error (Section~\ref{sec:workload-characterization}). Telling agents to verify the properties themselves lifts accuracy under breaking changes only from \DsTrajModeled\% to \DsTrajVerifyModeled\%, against \DsCondModeled\% when the system maintains them.}
{数据仓库一直依赖这些性质，但当使用者变成智能体时，有三件事发生了变化，而现有的保障手段没有覆盖它们。其一，前提从设计变成了观测。维度建模把声明的粒度当作“具有约束力的契约”~\cite{kimball2013toolkit}，验证管道测试声明的约束~\cite{schelter2018deequ,breck2019validation}，模式演化工具跟踪表结构~\cite{curino2008prism,zhang2025evoschema}；智能体则是在当前数据上把一条性质查一次，除了轨迹之外没有任何地方记下它。这些性质对应于决定汇总正确性的可汇总性条件~\cite{lenz1997summarizability,mazon2009summarizability}，并且与查询优化器利用的软约束一样~\cite{godfrey2001soft}，只在当前数据上成立：第 2 类缓慢变化维为每个变化的成员追加一行，迟到事实与重新装载追加行，在交易表中追加状态变更行则混入了第二种粒度，而这是维度建模明确禁止的~\cite{kimball2013toolkit}。这些变化都不改表结构，而即使是商用指标层中人工声明的连接性质，也“不在运行时验证”~\cite{databricks2026metricviews}。其二，生产者与消费者脱钩。应用中的查询有作者，数据源变化时会有人通知作者；共享记忆中的定义在学到它的会话结束后继续存在，并作为权威提供给全新的会话，于是一次过期的观测会传播到每个智能体：在我们实验中条件覆盖的破坏性变化下，共享但不验证在 \DsNoguardStaleModeled\ 道任务中提供了过期定义，按模式变更失效在 \DsSchemaStaleModeled\ 道中如此。其三，消费者看不出破坏。上游变化产出的数据在使用者看来可以“完全正常”~\cite{breck2019validation}，却让下游应用静默出错~\cite{song2021autovalidate}；在我们的轨迹中，只有 16\% 的会话检查键唯一性，所有错误答案都来自执行成功、没有报错的 SQL（第~\ref{sec:workload-characterization} 节）。让智能体自己核对这些性质，只把破坏性变化下的正确率从 \DsTrajModeled\% 提高到 \DsTrajVerifyModeled\%，而由系统维护时为 \DsCondModeled\%。}

\bi{Keeping shared definitions correct therefore requires answers to three questions that existing mechanisms answer only in part. \emph{What must be checked?} The properties a definition relies on are stated neither in its SQL nor in the schema, so schema-change invalidation misses data-only breaks (it serves \RpSchemaWrongModeled\ wrong answers in our replay), and data-validation systems~\cite{schelter2018deequ,breck2019validation} test declared constraints per table without knowing which learned definition depends on which property or how to restore it. \emph{When may a definition be used?} A check that passed describes one snapshot; a write can commit between the check and the query that relies on it, and cheap version signals such as DML statistics are neither transactional nor immediate: check-then-execute lets queries answer on condition-violating data in up to \SnPreUnannMax\% of uses under concurrent writers. \emph{What happens when a definition breaks?} Invalidating it on every write discards valid knowledge after benign appends and sends agents back to exploring, while repairing it is risky: a filter can restore one row per business key yet select the wrong population, and a regression test can compare only with the SQL the agent wrote before the change.}
{因此，要保持共享定义正确，需要回答三个问题，现有机制只回答了其中一部分。\emph{该检查什么？}定义依赖的性质既不写在 SQL 里，也不写在表结构里，因此按模式变更失效会漏掉纯数据破坏（在我们的回放中给出 \RpSchemaWrongModeled\ 个错误答案）；数据验证系统~\cite{schelter2018deequ,breck2019validation}按表测试声明的约束，却不知道哪个学到的定义依赖哪条性质，也不知道如何恢复它。\emph{何时可以使用定义？}一次通过的检查只描述一个快照；写入可能在检查与依赖它的查询之间提交，而 DML 统计这类廉价的版本信号既不随事务提交，也不即时可见：存在并发写入时，先检查后执行会让最多 \SnPreUnannMax\% 的使用在违反条件的数据上作答。\emph{定义失效后怎么办？}每次写入都使定义失效，会在正常追加后丢掉有效知识，把智能体赶回探索；修复则有风险：一个过滤可以恢复每个业务键一行，却选中了错误的总体，而回归测试只能拿变化前智能体写的 SQL 作比较。}

\bi{\system\ (\textbf{M}etric-\textbf{A}ware \textbf{V}alidation and \textbf{R}euse for \textbf{A}gents) answers these questions by recording the evidence on which a learned definition rests as first-class, versioned state, maintaining it as the data changes, and binding every declared use of the definition to evidence that holds on the use's own snapshot. \emph{What to check} follows from the definition's structured implementation: filtered key uniqueness for its grain, cardinality for each join, and the role and key completeness of its date join. These four conditions are sufficient: when they hold together with the definition's business premises, the canonical SQL counts every business event exactly once in its period, up to the omissions that the completeness condition bounds (Proposition~\ref{prop:sufficiency}), and the proof fixes which data-only updates they detect. \emph{When a definition may be used} is decided per snapshot. A check result is keyed by the condition's canonical form and the versions of the tables it reads, so it serves every definition and agent that needs the same condition until one of those tables changes; a query that declares a definition revision runs in a repeatable-read snapshot on which the revision's conditions hold, reusing check results whose transactional versions match the snapshot and checking the rest inside it (Lemma~\ref{lem:reuse}). \emph{When a definition breaks}, repair publishes a replacement only if it is the unique structural fix and passes a regression test against the agent's original SQL, and invalidates the definition otherwise (Algorithm~\ref{alg:repair}). \system\ implements this lifecycle as a middleware between data agents and PostgreSQL: \emph{admission} extracts structured definitions from judged-successful trajectories and replays their canonical SQL; \emph{maintenance} rechecks the conditions an update touches, reuses check results across definitions and agents, and invalidates or repairs failed revisions, with requests that arrive during a repair waiting for its outcome; \emph{execution} checks declared revisions and, in same-snapshot mode, validates and executes each declaring query on one snapshot, using transactional table versions maintained by statement-level triggers. Maintenance work follows the distinct conditions an update touches rather than the definitions that depend on them; a version-keyed cache of the check queries obtains the same savings, so the contribution of \system\ lies in what is checked, when a check's result may be relied on, and what happens when a check fails. Because maintenance operates on structured definitions, it applies equally to definitions declared in a semantic layer.}
{\system（\textbf{M}etric-\textbf{A}ware \textbf{V}alidation and \textbf{R}euse for \textbf{A}gents，面向智能体的指标感知验证与复用）这样回答这三个问题：把学到的定义赖以成立的证据记录为一等的、版本化的状态，随数据变化维护它，并把每一次声明了定义的使用绑定到在该次使用自身快照上成立的证据。\emph{检查什么}由定义的结构化实现决定：粒度对应过滤后键唯一性，每个连接对应连接基数，日期连接对应角色与日期键完整性。这四类条件是充分的：它们与定义的业务前提一起成立时，规范 SQL 把每个业务事件在其期间内恰好计数一次，遗漏仅限于完整性条件所约束的部分（命题~\ref{prop:sufficiency}），证明同时确定了它们能发现哪些纯数据更新。\emph{何时可以使用}按快照判定。检查结果按条件的规范形式及其读取表的版本索引，因此在这些表变化之前，它服务于所有需要同一条件的定义和智能体；声明使用某个定义修订的查询，在一个该修订条件成立的可重复读快照中执行：事务性版本与快照一致的检查结果直接复用，其余条件在快照内检查（引理~\ref{lem:reuse}）。\emph{定义失效时}，只有当替代修订是结构上唯一的修复、且通过以智能体原 SQL 为对照的回归测试时才发布，否则使定义失效（算法~\ref{alg:repair}）。\system\ 以位于数据智能体与 PostgreSQL 之间的中间件实现这一生命周期：\emph{准入}从判题成功的轨迹中提取结构化定义并重放其规范 SQL；\emph{维护}重查更新触及的条件，跨定义和智能体复用检查结果，使失败的修订失效或修复它们，修复进行中到达的请求等待其结果；\emph{执行}核对声明的修订，并在同快照模式下，借助语句级触发器维护的事务性表版本，在同一快照上验证并执行每条声明了修订的查询。维护工作沿更新触及的不同条件展开，而不是沿依赖它们的定义展开；按版本索引检查查询的缓存能得到同样的节省，因此 \system\ 的贡献在于检查什么、检查结果何时可以依赖，以及检查失败时怎么办。由于维护作用于结构化定义，它同样适用于在语义层中声明的定义。}

\bi{We evaluate \system\ at two levels. At the system level, without LLMs, we fix what agents learned and vary only maintenance. Replaying \RpLibs\ definition libraries learned by three LLMs, and a TPC-DS library derived from its 99 query templates, under \RpChanges\ data changes, maintained definitions serve no wrong answer under the covered changes, whereas schema-change invalidation serves \RpSchemaWrongModeled\ and \TrSchemaWrongModeled; condition-level and definition-level maintenance give identical answers on every question. Under concurrent writers, same-snapshot validation answers on condition-violating data in none of \SnSnapAnswered\ uses, against \SnPreUnannMin--\SnPreUnannMax\% with check-then-execute, without changing reader latency. Repair, tested against the agent's own SQL, succeeds when the change leaves the learning period untouched and otherwise invalidates the definition; a counterexample shows that without the uniqueness rule an indistinguishable backup copy yields a wrong published repair. With 19 shared definitions, maintenance costs \CbStagCondSix\% of definition-level revalidation, and the ratio holds from one to 16 million rows. End to end, DeepSeek V4.1 Flash agents face eleven data changes in three independent runs per method: sharing alone raises accuracy from \ScenAccNoShare\% to \DsNoguardAll\%, maintenance raises it to \ScenAccCond\%, and under the covered breaking changes maintained definitions answer \DsCondModeled\%, against \DsTrajModeled\% for a matched trajectory-retrieval baseline that is as accurate on unchanged data and \DsTrajVerifyModeled\% when that baseline is told to verify the same properties itself. Every covered break is detected, as Proposition~\ref{prop:sufficiency} predicts, and the unit change, which violates no condition, serves as the control. Maintained sharing also cuts each agent's work: \ScenHoldTokSaveModelA\% fewer input tokens and \ScenHoldTurnsCondModelA\ instead of \ScenHoldTurnsNoShareModelA\ turns per held-out task, and in \SlSessions\ fixed-library sessions tasks complete in \SlCondMean\ instead of \SlNoneMean\,s.}
{我们从两个层面评估 \system。在系统层（不调用大模型），固定智能体学到的内容，只改变维护方式。把 3 个大模型学到的 \RpLibs\ 个定义库，以及从 TPC-DS 的 99 个查询模板导出的定义库，在 \RpChanges\ 种数据变化下回放：在条件覆盖的变化下，维护后的定义不给出错误答案，按模式变更失效分别给出 \RpSchemaWrongModeled\ 和 \TrSchemaWrongModeled\ 个；条件级与定义级维护在全部题目上答案完全相同。存在并发写入时，同快照验证在 \SnSnapAnswered\ 次使用中没有一次在违反条件的数据上作答，先检查后执行则为 \SnPreUnannMin--\SnPreUnannMax\%，读者延迟不变。修复以智能体自己的 SQL 作回归测试，变化不触及学习期时成功，否则使定义失效；一个反例表明，没有唯一性规则时，无法区分的备份副本会导致发布错误的修复。19 个定义共享条件时，维护耗时为定义级重验证的 \CbStagCondSix\%，这一比例从 100 万行到 1600 万行保持不变。端到端实验中，基于 DeepSeek V4.1 Flash 的智能体面对 11 种数据变化，每种方法独立运行 3 次：仅共享本身把正确率从 \ScenAccNoShare\% 提高到 \DsNoguardAll\%，维护进一步提高到 \ScenAccCond\%；在条件覆盖的破坏性变化下，维护后的定义答对 \DsCondModeled\%，而数据不变时同样准确的匹配轨迹检索基线为 \DsTrajModeled\%，让该基线自己核对同样的性质后为 \DsTrajVerifyModeled\%。每一种条件覆盖的破坏都被检测到，正如命题~\ref{prop:sufficiency} 所预言；不违反任何条件的单位变化则作为对照。维护后的共享还减少每个智能体的工作：留出题上输入 token 少 \ScenHoldTokSaveModelA\%，每题轮数从 \ScenHoldTurnsNoShareModelA\ 降至 \ScenHoldTurnsCondModelA{}；在 \SlSessions\ 个固定库会话中，任务完成时间从 \SlNoneMean\ 秒降至 \SlCondMean\ 秒。}

\bi{This paper makes the following contributions:}
{本文的贡献如下：}
\begin{itemize}
\item \bi{We formulate shared metric definitions as maintainable knowledge whose implementation depends on four kinds of typed, executable validity conditions, and prove that, under the definition's business premises, the conditions suffice for the canonical SQL to count every business event exactly once in its period, up to omissions bounded by the completeness condition; the proof fixes which data-only updates the conditions detect (Section~\ref{sec:model}).}
{我们把共享指标定义建模为可维护的知识，其实现依赖四类类型化、可执行的有效性条件，并证明在定义的业务前提下，这些条件足以让规范 SQL 把每个业务事件在其期间内恰好计数一次，遗漏仅限于完整性条件所约束的部分；证明同时确定了条件能发现哪些纯数据更新（第~\ref{sec:model} 节）。}
\item \bi{We bind every declared use of a shared definition to validity evidence that holds on the query's own snapshot: check results keyed by the condition's canonical form and dependency versions, invalidation and version checks that govern availability, and same-snapshot validation, which applies the transactional-consistency principle of TxCache~\cite{ports2010txcache} to check results under a reuse rule we prove sound (Lemma~\ref{lem:reuse}; Sections~\ref{sec:maintenance} and~\ref{sec:execution}).}
{我们把每一次声明了修订的共享定义使用，绑定到在查询自身快照上成立的有效性证据：检查结果按条件的规范形式与依赖版本索引，失效与版本校验决定可用性，同快照验证把 TxCache~\cite{ports2010txcache} 的事务一致性原则用于检查结果，其复用规则经我们证明是可靠的（引理~\ref{lem:reuse}；第~\ref{sec:maintenance} 和~\ref{sec:execution} 节）。}
\item \bi{We give a bounded repair algorithm (Algorithm~\ref{alg:repair}) that publishes a replacement only if it is the unique structural fix and passes regression, characterize when regression against the agent's own SQL suffices, and show that without the uniqueness rule an ambiguous fix is wrongly published (Sections~\ref{sec:maintenance} and~\ref{sec:repair-eval}).}
{我们给出有界修复算法（算法~\ref{alg:repair}）：只有当替代修订是结构上唯一的修复并通过回归测试时才发布；刻画以智能体自己的 SQL 作回归测试何时足够，并证明没有唯一性规则时有歧义的修复会被错误发布（第~\ref{sec:maintenance} 和~\ref{sec:repair-eval} 节）。}
\item \bi{We implement \system\ and evaluate it at the system level, with replays of learned libraries and of a TPC-DS library, concurrent writers, and cost against a check-result cache up to 16 million rows, and end to end against a matched trajectory-retrieval baseline under eleven data changes, measuring accuracy together with each agent's turns, tokens, and completion time. A characterization of data-agent workloads against 441 million queries from 400 Amazon Redshift clusters motivates the design: agents rediscover database knowledge that no query cache captures, rarely check validity properties themselves, and fail silently (Sections~\ref{sec:background} and~\ref{sec:evaluation}).}
