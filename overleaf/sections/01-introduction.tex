\section{\bt{Introduction}{引言}}
\label{sec:introduction}
\bi{LLM-based data agents are an emerging and rapidly growing class of data-system clients~\cite{luo2026dataagents}, expected to become the dominant workload of data systems~\cite{liu2026agents}. To answer a question such as ``What was the store return amount in September 2002?'', an agent lists tables, inspects columns and values, validates candidate joins, and composes SQL over many turns. The hard part is rarely SQL syntax; it is business semantics. Enterprise warehouses name columns in terminology that only domain experts understand~\cite{floratou2024nl2sql}, and an o1-preview agent solves only 21.3\% of real enterprise text-to-SQL workflows~\cite{lei2025spider2}. Business knowledge closes much of the gap: attaching expert-annotated external-knowledge evidence raises GPT-4's execution accuracy on the BIRD test set from 34.9\% to 54.9\%~\cite{li2023bird}, and answering enterprise insurance questions over a knowledge graph that captures business semantics raises GPT-4's accuracy from 16.7\% to 54.2\%~\cite{sequeda2024kg}.}
{基于大语言模型的数据智能体是一类新兴且快速增长的数据系统使用者~\cite{luo2026dataagents}，并被预期成为数据系统的主要负载~\cite{liu2026agents}。为回答“2002 年 9 月门店退货金额是多少”这样的问题，智能体需要多轮列出表、查看列和取值、验证候选连接并编写 SQL。难点很少在 SQL 语法，而在业务语义。企业数仓的列名使用只有领域专家才懂的术语~\cite{floratou2024nl2sql}；在真实企业 Text-to-SQL 工作流上，基于 o1-preview 的智能体只能完成 21.3\%~\cite{lei2025spider2}。业务知识能弥补很大一部分差距：在 BIRD 测试集上附加专家标注的外部知识证据，使 GPT-4 的执行正确率从 34.9\% 提高到 54.9\%~\cite{li2023bird}；在刻画业务语义的知识图谱上回答企业保险问题，使 GPT-4 的正确率从 16.7\% 提高到 54.2\%~\cite{sequeda2024kg}。}

\bi{Metric definitions carry much of this semantics. A definition fixes which fact rows to aggregate, which records count as one business event, and how measurements relate across tables; data warehouses have long required such definitions to be conformed across uses~\cite{kimball2013toolkit}. Agents need not rely on hand-written definitions: systems derive domain knowledge, including the calculation logic of derived columns, from script histories and lineage~\cite{weng2025datalab}, organize prior trajectories as reusable semantic memory~\cite{biswal2026agentsm}, and distill reusable workflows and insights from experience~\cite{wang2025awm,zhao2024expel}. Sharing a learned definition amortizes exploration that agents otherwise repeat. In our traces, fresh agent sessions spend two thirds of their database calls on lookups and re-derive facts that earlier sessions already obtained. Most of these are schema facts, but 38\% of the SQL probes also re-derive an earlier session's fact, and none repeats an earlier probe's SQL text, so a result cache keyed by query text captures none of this reuse (Section~\ref{sec:workload-characterization}). Sharing also keeps answers consistent: one agent's verified meaning of ``return amount'' becomes every agent's, and in our end-to-end study sharing alone raises accuracy from \ScenAccNoShare\% to \DsNoguardAll\%.}
{指标定义承载了其中大部分语义。一个定义规定聚合哪些事实行、哪些记录算作一次业务事件，以及度量如何跨表关联；数据仓库长期要求这类定义在各处保持一致（conformed）~\cite{kimball2013toolkit}。智能体不必依赖人工编写的定义：已有系统从脚本历史和血缘中推导领域知识（包括派生列的计算逻辑）~\cite{weng2025datalab}，把既往轨迹组织成可复用的语义记忆~\cite{biswal2026agentsm}，并从经验中提炼可复用的工作流和洞见~\cite{wang2025awm,zhao2024expel}。共享学到的定义能摊薄智能体原本要重复的探索。在我们的轨迹中，全新智能体会话把三分之二的数据库调用用于查找，并重新获取此前会话已经得到的事实。其中大部分是表结构事实，但也有 38\% 的 SQL 探查重新获取了此前会话的事实，而且没有一条与此前探查的 SQL 文本相同，因此按查询文本索引的结果缓存捕获不到这类复用（第~\ref{sec:workload-characterization} 节）。共享还能保持答案一致：一个智能体验证过的“退货金额”含义成为所有智能体的含义；在我们的端到端实验中，仅共享本身就把正确率从 \ScenAccNoShare\% 提高到 \DsNoguardAll\%。}

\bi{Sharing, however, turns a learned definition into long-lived state over a changing database. Liu et al.\ propose that data systems keep a persistent agentic memory store for grounding agents, and caution that if the store drifts from the data, ``the stale information may lead a new probe to make a mistake''~\cite{liu2026agents}; a tutorial on data agents lists adapting to changing data among their open problems~\cite{luo2026dataagents}, and a tutorial on agentic memory notes that memory stores accumulate redundant, outdated, or conflicting information~\cite{li2026agenticmemory}. For metric definitions the risk is specific. A definition's SQL is correct only while certain data properties hold: the filtered key identifies one business record, joins do not fan out, and dates join through the intended role. The first two are instances of the summarizability conditions that govern correct aggregation~\cite{lenz1997summarizability,mazon2009summarizability}; the third fixes which date relation assigns a fact to a period. The SQL text does not state them and the schema does not enforce them. Dimensional modeling treats them as design contracts: the declared grain is ``a binding contract'', ``different grains must not be mixed in the same fact table'', and a date dimension can play several roles in one fact table~\cite{kimball2013toolkit}. Yet routine warehouse operations change the data behind these contracts: type-2 dimensions add a row for each changed member, late-arriving facts and reloads append rows, and a status history appended to a transaction table mixes two grains~\cite{kimball2013toolkit}. Like the soft constraints exploited by query optimizers~\cite{godfrey2001soft}, the conditions hold on the current data and can be broken by the next load.}
{然而，共享使学到的定义成为变化数据库上的长期状态。Liu 等提出数据系统应保存持久的智能体记忆库，为智能体提供依据，并提醒若记忆库与数据不一致，“过期信息可能导致新的探查出错”~\cite{liu2026agents}；关于数据智能体的教程把适应不断变化的数据列为开放问题~\cite{luo2026dataagents}，关于智能体记忆的教程也指出记忆库会积累冗余、过时或相互冲突的信息~\cite{li2026agenticmemory}。对指标定义而言，这一风险有具体形态。定义的 SQL 只在某些数据性质成立时才正确：过滤后的键对应一条业务记录，连接不放大行数，日期按预期角色关联。前两项是决定汇总正确性的可汇总性条件的具体实例~\cite{lenz1997summarizability,mazon2009summarizability}，第三项规定由哪种日期关系把事实归入某个期间。SQL 文本不写明它们，表结构也不强制它们。维度建模把它们当作设计契约：声明的粒度是“具有约束力的契约”，“同一事实表中不得混合不同粒度”，一个日期维度可以在同一事实表中扮演多个角色~\cite{kimball2013toolkit}。然而数仓的日常操作会改变这些契约背后的数据：第 2 类缓慢变化维为每个变化的成员追加一行，迟到事实与重新装载追加行，在交易表中追加状态流水则混入了第二种粒度~\cite{kimball2013toolkit}。与查询优化器利用的软约束一样~\cite{godfrey2001soft}，这些条件在当前数据上成立，却可能被下一次装载破坏。}

\bi{Consider a returns table that stores one completed row per return. An ETL change starts to append an application-state row for each new return. No table or column changes, and the shared definition \code{SUM(sr\_return\_amt)} still executes. It now counts many returns twice: in our experiment a single-period query returns 6,588,699.86 instead of 3,294,349.93. Nothing fails loudly. Such failures are familiar from data pipelines: upstream feeds change in unexpected ways and downstream applications break silently~\cite{song2021autovalidate}, and a seemingly innocuous upstream change can produce data that ``looks perfectly fine'' to its consumer~\cite{breck2019validation}. Agents rarely catch such breaks on their own: in our traces, only 16\% of sessions check key uniqueness, and every wrong answer came from SQL that ran without error (Section~\ref{sec:workload-characterization}).}
{例如，退货表对每笔退货保存一条完成记录。一次 ETL 改动开始为每笔新退货追加一条申请状态记录。表和列都没有变化，共享定义 \code{SUM(sr\_return\_amt)} 照常执行，却把许多退货计算了两次：在我们的实验中，一个单期查询返回 6,588,699.86，正确值是 3,294,349.93。整个过程没有任何报错。这类失效在数据管道中并不陌生：上游数据源以意想不到的方式变化，下游应用随之静默出错~\cite{song2021autovalidate}；一次看似无害的上游改动，产出的数据在使用方看来可能“完全正常”~\cite{breck2019validation}。智能体自己很少能发现这类破坏：在我们的轨迹中，只有 16\% 的会话检查键唯一性，而所有错误答案都来自执行成功、没有报错的 SQL（第~\ref{sec:workload-characterization} 节）。}

\bi{Keeping shared definitions correct requires answers to three questions that existing mechanisms address only in part. \emph{What must be checked?} The properties a definition relies on are stated neither in its SQL nor in the schema, so schema-evolution support~\cite{curino2008prism,zhang2025evoschema} misses data-only breaks, and data-validation systems~\cite{schelter2018deequ,breck2019validation} check declared constraints without knowing which learned definition depends on which property. \emph{When may a definition be used?} A check that passed describes one snapshot; a write can commit between the check and the query that relies on it, and cheap version signals such as DML statistics are neither transactional nor immediate. In our experiments, checking before execution lets queries answer on condition-violating data in up to \SnPreUnannMax\% of uses under concurrent writers. \emph{What happens when a definition breaks?} Revoking it on every write discards valid knowledge after benign appends, while repairing it is risky: a filter can restore one row per business key yet select the wrong population, and whether a regression test notices depends on what its reference already knows.}
{要保持共享定义正确，需要回答三个问题，现有机制只回答了其中一部分。\emph{该检查什么？}定义依赖的性质既不写在 SQL 里，也不写在表结构里，因此模式演化支持~\cite{curino2008prism,zhang2025evoschema}会漏掉纯数据破坏；数据验证系统~\cite{schelter2018deequ,breck2019validation}检查声明的约束，却不知道哪个学到的定义依赖哪条性质。\emph{何时可以使用定义？}一次通过的检查只描述一个快照；写入可能在检查与依赖它的查询之间提交，而 DML 统计这类廉价的版本信号既不随事务提交，也不即时可见。在我们的实验中，存在并发写入时，执行前检查会让最多 \SnPreUnannMax\% 的使用在违反条件的数据上作答。\emph{定义失效后怎么办？}每次写入都撤销会在正常追加后丢掉有效知识；修复则有风险：一个过滤可以恢复每个业务键一行，却选中了错误的总体，回归测试能否发现，取决于其参照事先知道什么。}

\bi{Our approach treats the validity evidence of a learned definition as first-class, versioned state, and binds every use of a definition to evidence that holds on the use's own snapshot. Conditions are derived from the definition's structured implementation: filtered key uniqueness for its grain, multiplicity for each join, and the role and coverage of its date join. A verdict is indexed by the condition's identity and the versions of the tables it reads, so it serves every definition and agent that needs the same condition until one of those tables changes. A query that declares a definition revision runs in a repeatable-read snapshot on which the revision's conditions hold, reusing verdicts whose transactional versions match the snapshot and checking the rest inside it. Repair publishes a replacement only when it is the unique structural fix and passes regression; otherwise the definition is withdrawn. The four conditions are sufficient: when they hold, the canonical SQL counts every business event exactly once in its period (Proposition~\ref{prop:sufficiency}), and the proposition states which data-only updates they detect. This organization also makes maintenance cheap, because work follows the distinct conditions that an update touches rather than the definitions that depend on them; the savings are a property of explicit, versioned conditions, and a version-keyed cache of the check queries obtains them as well. The contribution of \system\ lies in what is checked, when a check's result may be relied on, and what happens when a check fails.}
{我们的做法是把学到的定义的有效性证据作为一等的、版本化的状态，并把每一次使用绑定到在该次使用自身快照上成立的证据。条件从定义的结构化实现中推出：粒度对应过滤后键唯一性，每个连接对应多重性，日期连接对应角色与覆盖。条件结论按条件身份及其读取表的版本索引，因此在这些表变化之前，它服务于所有需要同一条件的定义和智能体。声明使用某个定义修订的查询，在一个该修订条件成立的可重复读快照中执行：事务性版本与快照一致的结论直接复用，其余条件在快照内检查。只有当替代修订是结构上唯一的修复且通过回归测试时才发布，否则撤下定义。这四类条件是充分的：它们成立时，规范 SQL 把每个业务事件在其期间内恰好计数一次（命题~\ref{prop:sufficiency}），命题同时说明了它们能发现哪些纯数据更新。这种组织方式也使维护代价低廉，因为工作沿更新触及的不同条件展开，而不是沿依赖它们的定义展开；这种节省是显式、版本化条件本身的性质，按版本索引检查查询的缓存同样能得到它。\system\ 的贡献在于检查什么、检查结果何时可以依赖，以及检查失败时怎么办。}

\bi{We present \system\ (\textbf{M}etric-\textbf{A}ware \textbf{V}alidation and \textbf{R}euse for \textbf{A}gents), a middleware between data agents and PostgreSQL that implements this lifecycle. \emph{Admission} extracts structured definitions from judged-successful trajectories and replays their canonical SQL. \emph{Maintenance} rechecks conditions whose dependencies changed, reuses verdicts across definitions and agents, revokes failed revisions, and repairs them under the uniqueness and regression rules; requests that arrive during a repair wait for its outcome. \emph{Execution} checks declared revisions and, in snapshot-bound mode, validates and executes each declaring query on one snapshot, using transactional table versions maintained by statement-level triggers. Because maintenance operates on structured definitions, it applies equally to definitions declared in a semantic layer, which at least one commercial metric layer does not validate at runtime~\cite{databricks2026metricviews}.}
{本文提出 \system（Metric-Aware Validation and Reuse for Agents，面向智能体的指标感知验证与复用），一个位于数据智能体与 PostgreSQL 之间、实现上述生命周期的中间层。\emph{准入}从判题成功的轨迹中提炼结构化定义，并重放其规范 SQL。\emph{维护}重查依赖发生变化的条件，跨定义和智能体复用结论，撤销失效修订，并在唯一性与回归规则下修复；修复进行中到达的请求等待其结果。\emph{执行}核对声明的修订，并在绑定快照模式下，借助语句级触发器维护的事务性表版本，在同一快照上验证并执行每条声明了修订的查询。由于维护作用于结构化定义，它同样适用于在语义层中声明的定义，而至少有一个商用指标层不在运行时验证这类声明~\cite{databricks2026metricviews}。}

\bi{We evaluate \system\ in two layers. At the mechanism layer we fix what agents learned and vary only maintenance: we replay \RpLibs\ definition libraries learned by three LLMs under \RpChanges\ data changes, run concurrent writers against declaring queries, and measure maintenance cost against definition-level revalidation and a generic version-keyed cache from one to 16 million rows. Maintained definitions serve no wrong answer under the modeled changes, whereas schema-only maintenance serves \RpSchemaWrongModeled; condition-level and definition-level maintenance give identical answers on all paired questions. Snapshot-bound execution eliminates answers on condition-violating data (none in \SnSnapAnswered\ uses, versus \SnPreUnannMin--\SnPreUnannMax\% under unannounced writes when checking before execution) without changing reader latency. Repair succeeds when its reference distinguishes the business populations and otherwise withdraws the definition; a counterexample shows that, without the uniqueness rule, an indistinguishable backup copy yields a wrong published repair. End to end, DeepSeek V4.1 Flash agents face eleven data changes in three independent runs per method: sharing alone raises accuracy from \ScenAccNoShare\% to \DsNoguardAll\%, maintenance raises it to \ScenAccCond\%, and under the modeled breaking changes maintained definitions answer \DsCondModeled\% against \DsTrajModeled\% for a matched trajectory-retrieval baseline that is as accurate on unchanged data. The evaluation also confirms the boundary that Proposition~\ref{prop:sufficiency} predicts: duplicate loads and re-keyed dates are detected but have no filter repair, and a unit change, which violates no condition, goes unnoticed.}
{我们从两个层面评估 \system。在机制层，固定智能体学到的内容，只改变维护方式：把 3 个大模型学到的 \RpLibs\ 个定义库在 \RpChanges\ 种数据变化下回放，让并发写入与声明了修订的查询同时运行，并在 100 万到 1600 万行数据上把维护代价与定义级重验证及通用版本缓存比较。在已建模的变化下，维护后的定义不给出错误答案，只看结构的维护给出 \RpSchemaWrongModeled\ 个；条件级与定义级维护在全部配对题目上答案完全相同。绑定快照的执行消除了在违反条件的数据上作答（\SnSnapAnswered\ 次使用中为零，执行前检查在不通知的写入下为 \SnPreUnannMin--\SnPreUnannMax\%），且不改变读者延迟。参照能区分业务总体时修复成功，否则撤下定义；一个反例表明，没有唯一性规则时，无法区分的备份副本会导致发布错误的修复。端到端实验中，基于 DeepSeek V4.1 Flash 的智能体面对 11 种数据变化，每种方法独立运行 3 次：仅共享本身把正确率从 \ScenAccNoShare\% 提高到 \DsNoguardAll\%，维护进一步提高到 \ScenAccCond\%；在已建模的破坏性变化下，维护后的定义答对 \DsCondModeled\%，而数据不变时同样准确的匹配轨迹检索基线为 \DsTrajModeled\%。评估同时印证了命题~\ref{prop:sufficiency} 预言的边界：重复装载与日期键改写能被检测但没有过滤形式的修复，不违反任何条件的单位变化则不会被发现。}

\bi{This paper makes the following contributions:}
{本文的贡献如下：}
\begin{itemize}
\item \bi{We formulate shared metric definitions as maintainable knowledge whose implementation depends on four kinds of typed, executable validity conditions, and prove the conditions sufficient for the canonical SQL to count every business event exactly once in its period; the proof fixes which data-only updates the conditions detect (Section~\ref{sec:model}).}
{我们把共享指标定义建模为可维护的知识，其实现依赖四类类型化、可执行的有效性条件，并证明这些条件足以保证规范 SQL 把每个业务事件在其期间内恰好计数一次；证明同时确定了条件能发现哪些纯数据更新（第~\ref{sec:model} 节）。}
\item \bi{We bind every declared use of a shared definition to validity evidence that holds on the query's own snapshot. Verdicts are keyed by condition identity and dependency versions; revocation and declared-revision checks govern availability; snapshot-bound execution applies the transactional-consistency principle of TxCache~\cite{ports2010txcache} to validity verdicts, and we prove its reuse rule sound: a verdict computed on one snapshot holds on every snapshot with equal transactional versions (Sections~\ref{sec:maintenance} and~\ref{sec:execution}).}
{我们把每一次声明了修订的共享定义使用，绑定到在查询自身快照上成立的有效性证据。结论按条件身份与依赖版本索引；撤销与声明修订核对决定可用性；绑定快照的执行把 TxCache~\cite{ports2010txcache} 的事务一致性原则用于有效性结论，我们证明其复用规则是可靠的：在一个快照上算出的结论在事务性版本相同的每个快照上都成立（第~\ref{sec:maintenance} 和~\ref{sec:execution} 节）。}
\item \bi{We give a bounded repair algorithm that publishes a replacement only if it is the unique structural fix and passes regression, characterize when the regression reference suffices, and show that without the uniqueness rule an ambiguous fix is wrongly published (Sections~\ref{sec:maintenance} and~\ref{sec:repair-eval}).}
{我们给出有界修复算法：只有当替代修订是结构上唯一的修复并通过回归测试时才发布；我们刻画回归参照何时足够，并证明没有唯一性规则时有歧义的修复会被错误发布（第~\ref{sec:maintenance} 和~\ref{sec:repair-eval} 节）。}
\item \bi{We implement \system\ and evaluate it at the mechanism layer, with a paired replay of learned libraries, concurrent writers, cost against a generic cache, natural sharing in TPC-DS, and up to 16 million rows, and end to end against a matched trajectory-retrieval baseline under eleven data changes. A characterization of data-agent workloads against 441 million queries from 400 Amazon Redshift clusters motivates the design: agents rediscover database knowledge that no query cache captures, rarely check validity properties themselves, and fail silently (Sections~\ref{sec:background} and~\ref{sec:evaluation}).}
{我们实现了 \system，并在机制层（学到的定义库的配对回放、并发写入、与通用缓存的代价对比、TPC-DS 中的自然共享、最多 1600 万行数据）和端到端层（与匹配的轨迹检索基线对比，11 种数据变化）上评估它。把数据智能体负载与 400 个 Amazon Redshift 集群的 4.41 亿条查询对照的负载刻画支撑了这一设计：智能体反复重新获取查询缓存捕获不到的数据库知识，很少自行检查有效性性质，并且静默出错（第~\ref{sec:background} 和~\ref{sec:evaluation} 节）。}
\end{itemize}
