\subsection{\bt{Application and agent workloads}{应用与智能体工作负载}}
\label{sec:workload-characterization}
\bi{In a parameterized application, query templates and database knowledge reside in code, so millions of queries reduce to thousands of templates~\cite{ma2018querybot}; a fresh data-agent session must acquire that knowledge through schema lookups, data probes, and checks. Table~\ref{tab:workload-characterization} compares two workloads. The application side is Redset~\cite{vanrenen2024redset}: 441 million queries of 400 Amazon Redshift clusters over three months, analyzed per cluster with the dataset's template fingerprint, which overestimates repetition~\cite{redset2024dataset}. The agent side is 100 fresh DeepSeek V4.1 Flash sessions, each answering one of 25 questions of Section~\ref{sec:evaluation} (the learning questions and the first three scored types) with table-listing, table-description, and SQL tools and no shared state. SQL templates are libpg\_query fingerprints;\footnote{\url{https://github.com/pganalyze/libpg_query}} a rule-based classifier, checked on a sample, labels each call, and a lookup's \emph{fact} is its purpose together with the tables and columns it reads.}
{在参数化应用中，查询模板和数据库知识保存在代码里，数百万条查询可归并为数千个模板~\cite{ma2018querybot}；全新的数据智能体会话则必须通过结构查找、数据探查和检查获得这些知识。表~\ref{tab:workload-characterization} 对照两类负载。应用侧采用 Redset~\cite{vanrenen2024redset}：400 个 Amazon Redshift 集群三个月的 4.41 亿条查询，按集群分析，模板标识采用数据集自带的特征指纹，它会高估重复程度~\cite{redset2024dataset}。智能体侧是 100 个全新的 DeepSeek V4.1 Flash 会话，每个会话回答第~\ref{sec:evaluation} 节 25 道题（学习题与前三种计分题型）中的一道，只有列出表、描述表和执行 SQL 三种工具，互不共享状态。SQL 模板使用 libpg\_query 指纹；基于规则的分类器（在抽样上人工核对）为每次调用标注类别；查找所获得的\emph{事实}由其目的及读取的表和列确定。}

\bi{Applications repeat queries, which prepared statements and result caches serve well. Agents repeat knowledge: their SQL changes from session to session, while almost every lookup repeats a fact that an earlier session obtained, and since no repeated SQL probe repeats its text, a cache keyed by query text serves none of them. Answers are wrong without any failure: 31 of the 32 wrong answers occur when a question names a metric without defining it, exactly where a shared definition helps. And only 16\% of sessions check key uniqueness, the kind of condition that \system\ maintains on their behalf.}
{应用重复的是查询，预编译语句和结果缓存能很好地服务它们。智能体重复的是知识：它们的 SQL 在会话之间不断变化，而几乎每次查找都在重复此前会话已经得到的事实；重复事实的 SQL 探查没有一条文本相同，因此按查询文本索引的缓存一条也服务不了。答案在没有任何报错的情况下出错：32 个错误答案中有 31 个出现在题目只给出指标名而不给定义时，这正是共享定义能帮上忙的地方。只有 16\% 的会话检查键唯一性，而这正是 \system\ 代为维护的那类条件。}

\subsection{\bt{How updates break a learned definition}{更新如何破坏学到的定义}}
\bi{A metric definition packages what an agent had to discover: the fact table, the measure, the grain (the key that identifies one business event), the date role, definition filters, and joins; question parameters such as the month are not part of it. An aggregate is summarizable only if the grouped records are disjoint and complete and the measure is compatible with the aggregation~\cite{lenz1997summarizability}. For a learned definition, disjointness becomes filtered key uniqueness and bounded join cardinality, completeness becomes the requirement that joins drop no facts beyond what was admitted, and the date role fixes which date relation assigns a fact to its period. Data-only updates break each of them: status-change rows, restatements, or duplicate loads violate the grain, reused dimension keys make a many-to-one join fan out, and late or reformatted date keys move facts to another period or to none, while the schema stays the same. Checked on data instances rather than guaranteed by the schema, such a condition must be rechecked after every update~\cite{mazon2009summarizability,abedjan2015profiling}, yet each is a SQL probe over a few tables. What is missing for agents is the link between a learned definition and the checks that justify it, so that the checks run when its data changes and their outcome governs whether, and on which data, agents may use it.}
{指标定义把智能体需要摸索出来的内容打包保存：事实表、度量、粒度（标识一个业务事件的键）、日期角色、定义过滤和连接；月份等题目参数不属于定义。只有当被分组的记录互不相交且完备、度量与聚合方式相容时，汇总才是可汇总的~\cite{lenz1997summarizability}。对学到的定义而言，不相交性对应过滤后键唯一性和有界的连接基数，完备性对应“连接排除的事实不超过准入时的比例”，日期角色则规定由哪种日期关系把事实归入其期间。纯数据更新会分别破坏它们：状态变更行、多版本更正或重复加载破坏粒度，被复用的维度键使多对一连接放大行数，迟到或改换格式的日期键把事实移到另一个期间或归不到任何期间，而表结构始终不变。这些条件在数据实例上检查、而不由表结构保证，每次更新后都必须重新检查~\cite{mazon2009summarizability,abedjan2015profiling}；而每一项都只是读取少数几张表的 SQL 探查。智能体场景中缺少的是把学到的定义与支撑它的检查联系起来：定义的数据一变，检查就执行，其结果决定智能体能否使用该定义、以及在哪些数据上使用。}

\subsection{\bt{What maintenance must decide}{维护需要决定什么}}
\label{sec:alternatives}
\bi{The maintenance strategies we compare (the last two groups of Table~\ref{tab:ladder}) differ in when they check and how much work they repeat, but all of them check and then execute. Their work differs because definitions share conditions: the 19 definitions of our controlled workload reference 41 condition instances but only seven distinct conditions, and treating each aggregate over a fact table in the 99 TPC-DS query templates as a definition yields \TpDefs\ definitions over \TpConds\ distinct conditions; an update of \code{store\_sales} affects \TpSalesDefs\ definitions with \TpSalesDefChecks\ condition checks but only \TpSalesConds\ distinct conditions. Any mechanism that keys check outcomes by condition and dependency version exploits this sharing, a version-keyed cache of the check queries included (Section~\ref{sec:cost}). The harder questions are whether a passed check still holds when the query runs, and what to do when it fails.}
{本文比较的各维护方式（表~\ref{tab:ladder} 的后两组）在何时检查、重复多少工作上各不相同，但都是先检查后执行。它们的工作量不同，是因为定义共享条件：受控负载的 19 个定义引用 41 个条件实例，但不同条件只有 7 个；把 99 个 TPC-DS 查询模板中每个对事实表的聚合视为一个定义，可得到 \TpDefs\ 个定义、\TpConds\ 个不同条件；更新 \code{store\_sales} 会影响 \TpSalesDefs\ 个定义、\TpSalesDefChecks\ 次条件检查，但不同条件只有 \TpSalesConds\ 个。任何按条件与依赖版本索引检查结果的机制都能利用这种共享，按版本缓存检查查询也不例外（第~\ref{sec:cost} 节）。更难的问题是：通过的检查在查询执行时是否仍然成立，以及检查失败后该怎么办。}
