\label{sec:background}
\subsection{\bt{Repeated knowledge across agent queries}{智能体查询之间的知识重复}}
\label{sec:workload-characterization}
\bi{Tasks over the same database require overlapping domain knowledge. We quantify this overlap using the released tasks of public text-to-SQL benchmarks. LiveSQLBench~\cite{livesqlbench2025}, on which BIRD-Interact builds~\cite{huo2026birdinteract}, documents each of its PostgreSQL databases in a knowledge base of calculations, domain rules, and value meanings (\ExLsKb\ entries for the \ExLsDbs\ databases of the full release), and BIRD~\cite{li2023bird} gives each question evidence that defines its terms. Since LiveSQLBench withholds which entries a task needs, we count a task as needing an entry when its question names the entry or an entry built on it; a BIRD question needs the terms that its evidence defines. By excluding implicit references and paraphrases, these lexical counts provide a conservative estimate of knowledge repetition. Sharing rates use knowledge-requiring tasks as the denominator; overlap for task $n$ is averaged over random task orders within each database.}
{同一数据库上的任务需要重叠的领域知识。我们使用公开 Text-to-SQL 基准已发布的任务量化这种重叠。LiveSQLBench~\cite{livesqlbench2025}（BIRD-Interact 即建立在它之上~\cite{huo2026birdinteract}）为它的每个 PostgreSQL 数据库编写了知识库，包括计算、领域规则与取值含义（完整版 \ExLsDbs\ 个数据库共 \ExLsKb\ 条）；BIRD~\cite{li2023bird} 为每个问题附上定义其术语的证据。由于 LiveSQLBench 不公开任务需要哪些条目，我们在问题点名某条目或点名依赖它的条目时，认为任务需要该条目；BIRD 的问题需要其证据所定义的术语。这些词汇计数排除隐含引用与不同措辞的表达，为知识重复程度提供保守估计。知识共享比例以需要知识的任务为分母；第 $n$ 个任务的知识重叠比例对各库内随机任务顺序取平均。}

\bi{Table~\ref{tab:external} shows that most tasks share knowledge with another task on their database, \ExLsSharePct\% on LiveSQLBench and \ExBdSharePct\% on BIRD. Half of the knowledge uses in LiveSQLBench (\ExLsRepeatPct\%) repeat an earlier use, and calculations, the kind of knowledge that \system\ learns, repeat as often (\ExLsCalcRepeatPct\%). Repetition grows with the number of tasks: the 10th task on a LiveSQLBench database finds \ExLsTenth\% of its required knowledge shared with earlier tasks, and the 20th \ExLsTwentieth\%; on BIRD the share still grows to \ExBdHundredth\% by the 100th question. These benchmarks contain \ExLsTasksPerDb\ to \ExBdTasksPerDb\ tasks per database on average. When tasks are answered by independent agent sessions, each session repeats this knowledge discovery.}
{表~\ref{tab:external} 表明，大多数任务与同库另一任务共用知识：LiveSQLBench 上为 \ExLsSharePct\%，BIRD 上为 \ExBdSharePct\%。LiveSQLBench 中，一半的知识使用（\ExLsRepeatPct\%）涉及此前已使用的知识，而计算类知识，即 \system\ 所学习的那类知识，重复得同样多（\ExLsCalcRepeatPct\%）。重复随任务增多而增长：LiveSQLBench 一个库上的第 10 个任务，所需知识中有 \ExLsTenth\% 与此前的任务共享，第 20 个任务为 \ExLsTwentieth\%；在 BIRD 上，到第 100 个问题这一比例仍增长到 \ExBdHundredth\%。这些基准每个库平均包含 \ExLsTasksPerDb\ 到 \ExBdTasksPerDb\ 个任务。在独立会话设置下，每个新会话都会重复发现这些知识。}

\bi{In applications, parameterized query templates and database knowledge reside in code, so millions of queries reduce to thousands of templates~\cite{ma2018querybot}; a new data-agent session must acquire that knowledge through schema lookups, data probes, and checks. To see what this costs, Table~\ref{tab:workload-characterization} compares two workloads. The application side is Redset~\cite{vanrenen2024redset}: 441 million queries of 400 Amazon Redshift clusters over three months, with read queries analyzed per cluster using the dataset's template fingerprint~\cite{redset2024dataset}. To capture session-level execution and LLM overhead not logged in the static benchmarks, the agent side traces 100 memoryless \llmmodel{} sessions over 25 analytical questions spanning five metrics (the learning questions and the first three scored forms). The sessions issue 521 database calls, including 176 SQL statements, through table-listing, table-description, and SQL tools. A \emph{lookup} inspects schemas, probes data, or performs validation; its target \emph{fact} pairs the inspection intent with the accessed tables and columns.}
{在参数化应用中，查询模板和数据库知识保存在代码里，数百万条查询可归并为数千个模板~\cite{ma2018querybot}；全新的数据智能体会话则必须通过结构查找、数据探查和检查获得这些知识。为了看清这样做的代价，表~\ref{tab:workload-characterization} 对照两类负载。应用侧采用 Redset~\cite{vanrenen2024redset}：400 个 Amazon Redshift 集群三个月的 4.41 亿条查询，读查询按集群分析，模板标识采用数据集自带的特征指纹~\cite{redset2024dataset}。为捕捉静态基准未记录的会话级执行与 LLM 开销，智能体侧追踪 100 个无记忆的 \llmmodel{} 会话，覆盖五个指标的 25 道分析题（学习题与前三种计分题型）。这些会话通过列出表、描述表和执行 SQL 三种工具，共发起 521 次数据库调用，其中 SQL 176 条。查找指结构检查、数据探查或验证；其目标\emph{事实}由检查意图及其访问的表与列确定。}

\bi{Applications repeat query templates: in Redset, 93.4\% of statements repeat an earlier template, with 6.6 templates per 100 statements. Prepared statements support template reuse, and the result cache answers 34\% of read queries. Agent queries have greater template diversity in our traces: 100 agent statements contain 76 templates, because each session writes its SQL anew from what it has just looked up. Agents instead repeat underlying knowledge discovery: on our questions, 93\% of lookups target a fact already obtained by an earlier session, yet none of the redundant SQL probes has the same text as an earlier probe, so a text-keyed query cache serves none of them.}
{应用重复的是查询模板：Redset 中 93.4\% 的语句重复已有模板，每百条语句只有 6.6 个模板。预编译语句支持模板复用，结果缓存回答了 34\% 的读查询。在我们的轨迹中，智能体查询的模板更多样：每百条智能体语句中有 76 个模板，因为每个会话都根据刚刚查到的内容重新写 SQL。智能体重复的则是底层知识发现：在我们的题目上，93\% 的查找以此前会话已获得的事实为目标，但这些重复事实的 SQL 探查没有一条与先前探查的文本相同，因此按查询文本索引的缓存无法服务这些探查。}

\bi{Even with exact or semantic result caching on the database side, caching probe results does not remove the LLM calls that formulate probes and interpret their outputs: 57\% of an agent's LLM calls issue no SQL that the answer uses, and 71\% of a session passes before that SQL starts. A cache makes a lookup cheaper for the database, but the agent still incurs the cost of an LLM call to issue the lookup and interpret its result. Liu et al.\ find the same split in the traces of an OpenAI o3-based agent: of 12.67 SQL statements per task, 3.44 explore tables and 3.56 explore columns, and expert hints such as which column holds the relevant information cut column exploration by 27.7\% and all statements by 18.1\%~\cite{liu2026agents}. Providing previously learned database knowledge lets later agents skip the corresponding exploration; \system\ shares this knowledge across agents.}
{即使数据库侧采用精确匹配或语义结果缓存，缓存探查结果仍不能消除构造探查和解释其输出的大模型调用：智能体 57\% 的大模型调用不发出答案所用的 SQL，会话 71\% 的时间都在这条 SQL 开始之前。缓存能够降低数据库执行查找的成本，但智能体仍需承担发起查找和解释结果的大模型调用开销。Liu 等人在 o3 智能体的轨迹中看到同样的分布：每个任务平均 12.67 条 SQL，其中 3.44 条查看表、3.56 条查看列；专家给出提示（例如哪一列包含相关信息）后，查看列的 SQL 减少 27.7\%，全部 SQL 减少 18.1\%~\cite{liu2026agents}。预先提供其他智能体已学到的数据库知识，使后续智能体能够省去相应的重复探索；\system\ 在智能体之间共享这些知识。}

\bi{Incorrect answers can occur without SQL execution errors. Of the 32 incorrect answers, 31 occur when a question names a metric without defining it. This concentration motivates sharing explicit metric definitions across sessions. Only 16\% of sessions check key uniqueness, the kind of condition that \system\ maintains on their behalf.}
{SQL 未报告执行错误时，答案仍可能不正确。32 个错误答案中有 31 个出现在题目只给出指标名而不给定义时。这一错误分布提示了跨会话共享明确指标定义的需求。只有 16\% 的会话检查键唯一性，而这正是 \system\ 代为维护的那类条件。}

\subsection{\bt{Amortizing exploration across agents}{跨智能体分摊探索开销}}
\label{sec:alternatives}
\bi{Sharing memory across agents amortizes the discovery of database knowledge. A private memory serves the later sessions of its owner; a database-wide memory also serves other agents whose questions use the same definitions. With $N$ agents and $k$ metrics, private copies can require up to $Nk$ discoveries, whereas under stable data one successful publication per metric can serve the population. \system\ makes these publications executable for new periods and tasks, reducing both repeated discovery and the work of translating knowledge into SQL. The population study measures this effect using shared and private copies of the same learning and validation mechanisms.}
{跨智能体共享记忆可以分摊数据库知识的发现开销。私有记忆服务其拥有者的后续会话；数据库范围的共享记忆还服务使用相同定义的其他智能体。对于 $N$ 个智能体和 $k$ 个指标，私有副本至多需要 $Nk$ 次发现；数据稳定时，每个指标一次成功发布即可服务整个群体。\system\ 将这些发布的定义编译为新期间和任务所需的查询，同时减少重复发现以及把知识转化为 SQL 的工作。群体实验使用学习和验证机制相同的共享与私有副本，测量这一效果。}

\bi{\emph{A cost model.} Let $N$ agents each ask $q$ questions about $k$ metrics. For a given cost metric, such as LLM tokens or total agent time, let $c_e$ be exploration cost per question, $c_r$ reuse cost, $c_\ell$ the one-time extraction and publication cost per definition, and $M$ the cumulative additional maintenance cost across updates. Assume each metric is asked at least once, its first question publishes a definition, and subsequent questions reuse it. The costs are $Nq\,c_e$ without memory and $k(c_e+c_\ell)+(Nq-k)c_r+M$ with sharing. Sharing saves work exactly when}
{\emph{代价模型。}设 $N$ 个智能体各就 $k$ 个指标提 $q$ 个问题。对于给定的代价指标（如 LLM token 或智能体总时间），$c_e$ 为每题探索代价，$c_r$ 为复用代价，$c_\ell$ 为每个定义的一次性提取与发布代价，$M$ 为更新带来的额外累计维护代价。假定每个指标至少被问一次，第一道题发布定义，后续问题均复用该定义。无记忆总代价为 $Nq\,c_e$，共享代价为 $k(c_e+c_\ell)+(Nq-k)c_r+M$。共享节省工作的充要条件为}
\begin{equation}
\label{eq:sharing-benefit}
(Nq-k)(c_e-c_r)>k\,c_\ell+M.
\end{equation}
\bi{Thus reuse must repay both learning and maintenance, and sharing checks can reduce $M$. With fixed $k,q$ and $M/(Nq)\to\mu$, the saving tends to $1-(c_r+\mu)/c_e$ as $N\to\infty$. For LLM token consumption, deterministic SQL-only maintenance incurs zero token overhead ($M=0$), simplifying the asymptotic limit to $1-c_r/c_e$. In the stable-data population study, $c_e$ is \PpNoneLateTokK\,k tokens and $c_r$ is \PpMavraLateTokK\,k, giving a limiting token saving of \PpMavraAsymTokSaveNone\%. At the measured reuse share \ExModelReusePct\%, with $c_\ell=\ExModelLearnTokK$\,k tokens, the model gives \ExModelTokSaveOurs\%, matching the observed saving.}
{因此，复用收益需要覆盖学习与维护开销，共享检查有助于降低 $M$。固定 $k,q$，若 $M/(Nq)\to\mu$，当 $N\to\infty$ 时节省趋近 $1-(c_r+\mu)/c_e$。对于 LLM token，纯确定性的 SQL 维护不产生 token 开销（$M=0$），因此渐近极限简化为 $1-c_r/c_e$。在数据稳定的群体实验中，$c_e$ 为 \PpNoneLateTokK\,k token，$c_r$ 为 \PpMavraLateTokK\,k，故 token 节省的极限为 \PpMavraAsymTokSaveNone\%。在实测复用比例 \ExModelReusePct\%、$c_\ell=\ExModelLearnTokK$\,k token 时，模型给出 \ExModelTokSaveOurs\%，与观测节省一致。}
