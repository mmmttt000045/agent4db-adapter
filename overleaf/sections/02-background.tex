\section{\bt{Background and Motivation}{背景与动机}}
\label{sec:background}
\subsection{\bt{Agents repeat knowledge, not queries}{智能体重复的是知识而不是查询}}
\label{sec:workload-characterization}
\bi{Tasks on one database need the same knowledge, and public text-to-SQL benchmarks show how often without any choice of ours. LiveSQLBench~\cite{livesqlbench2025}, on which BIRD-Interact builds~\cite{huo2026birdinteract}, documents each of its PostgreSQL databases in a knowledge base of calculations, domain rules, and value meanings (\ExLsKb\ entries for the \ExLsDbs\ databases of the full release), and BIRD~\cite{li2023bird} gives each question evidence that defines its terms. Since LiveSQLBench withholds which entries a task needs, we count a task as needing an entry when its question names the entry or an entry built on it; a BIRD question needs the terms that its evidence defines. Both counts miss knowledge that a task uses without naming it or that annotators phrase in different words, so they understate the repetition. Table~\ref{tab:external} shows that most tasks share knowledge with another task on their database, \ExLsSharePct\% on LiveSQLBench and \ExBdSharePct\% on BIRD. Half of LiveSQLBench's uses of knowledge (\ExLsRepeatPct\%) repeat an earlier use, and calculations, the kind of knowledge that \system\ learns, repeat as often (\ExLsCalcRepeatPct\%). Repetition grows with the number of tasks: the 10th task on a LiveSQLBench database finds \ExLsTenth\% of the knowledge it needs already needed by an earlier task, and the 20th \ExLsTwentieth\%; on BIRD the share still grows to \ExBdHundredth\% by the 100th question. The benchmarks keep their tasks diverse for coverage and hold \ExLsTasksPerDb\ to \ExBdTasksPerDb\ tasks per database on average, whereas a database that serves an organization's agents for months receives far more, so it repeats more. Every task is answered by a new agent session, which explores the knowledge again.}
{同一数据库上的任务需要同样的知识；公开的 Text-to-SQL 基准不经我们的任何选择就能说明其频繁程度。LiveSQLBench~\cite{livesqlbench2025}（BIRD-Interact 即建立在它之上~\cite{huo2026birdinteract}）为它的每个 PostgreSQL 数据库编写了知识库，包括计算、领域规则与取值含义（完整版 \ExLsDbs\ 个数据库共 \ExLsKb\ 条）；BIRD~\cite{li2023bird} 为每个问题附上定义其术语的证据。由于 LiveSQLBench 不公开任务需要哪些条目，我们在问题点名某条目或点名依赖它的条目时，认为任务需要该条目；BIRD 的问题需要其证据所定义的术语。两种计数都会漏掉任务用到却未点名的知识，以及标注者用不同措辞写出的同一知识，因此都低估了重复。表~\ref{tab:external} 表明，大多数任务与同库另一任务共用知识：LiveSQLBench 上为 \ExLsSharePct\%，BIRD 上为 \ExBdSharePct\%。LiveSQLBench 中一半的知识使用（\ExLsRepeatPct\%）重复此前的使用，而计算类知识，即 \system\ 所学习的那类知识，重复得同样多（\ExLsCalcRepeatPct\%）。重复随任务增多而增长：LiveSQLBench 一个库上的第 10 个任务，所需知识中有 \ExLsTenth\% 已被此前的任务需要过，第 20 个任务为 \ExLsTwentieth\%；在 BIRD 上，到第 100 个问题这一比例仍增长到 \ExBdHundredth\%。这些基准为了覆盖面刻意让任务多样，每个库平均只有 \ExLsTasksPerDb\ 到 \ExBdTasksPerDb\ 个任务；而为一个组织的智能体服务数月的数据库会收到多得多的任务，因此重复更多。每个任务都由一个新的智能体会话回答，它把这些知识重新探索一遍。}

\bi{In a parameterized application, query templates and database knowledge reside in code, so millions of queries reduce to thousands of templates~\cite{ma2018querybot}; a new data-agent session must acquire that knowledge through schema lookups, data probes, and checks. To see what this costs, Table~\ref{tab:workload-characterization} compares two workloads. The application side is Redset~\cite{vanrenen2024redset}: 441 million queries of 400 Amazon Redshift clusters over three months, analyzed per cluster with the dataset's template fingerprint, which overestimates repetition~\cite{redset2024dataset}. The agent side is 100 new DeepSeek V4.1 Flash sessions, each answering one of 25 questions of Section~\ref{sec:evaluation} (the learning questions and the first three scored types) with table-listing, table-description, and SQL tools and no shared state. A lookup's \emph{fact} is its purpose together with the tables and columns it reads. Our questions ask about five metrics and therefore repeat more than the benchmarks do; we use them to measure what the benchmarks do not record, the cost of a session.}
{在参数化应用中，查询模板和数据库知识保存在代码里，数百万条查询可归并为数千个模板~\cite{ma2018querybot}；全新的数据智能体会话则必须通过结构查找、数据探查和检查获得这些知识。为了看清这样做的代价，表~\ref{tab:workload-characterization} 对照两类负载。应用侧采用 Redset~\cite{vanrenen2024redset}：400 个 Amazon Redshift 集群三个月的 4.41 亿条查询，按集群分析，模板标识采用数据集自带的特征指纹，它会高估重复程度~\cite{redset2024dataset}。智能体侧是 100 个全新的 DeepSeek V4.1 Flash 会话，每个会话回答第~\ref{sec:evaluation} 节 25 道题（学习题与前三种计分题型）中的一道，只有列出表、描述表和执行 SQL 三种工具，互不共享状态。查找所获得的\emph{事实}由其目的及读取的表和列确定。我们的题目只涉及五个指标，因此比这些基准重复得更多；我们用它们测量基准没有记录的东西，即一个会话的代价。}

\bi{Applications repeat queries: in Redset, 93.4\% of the statements repeat an earlier template, 6.6 templates per 100 statements, and prepared statements and the result cache, which answers 34\% of the reads, serve them well. Agents answer the same kind of recurring questions but do not repeat queries: 100 agent statements contain 76 templates, because each session writes its SQL anew from what it has just looked up. What agents repeat is knowledge: on our questions, 93\% of the lookups repeat a fact that an earlier session obtained, yet no SQL probe that repeats a fact repeats the text of an earlier one, so a cache keyed by query text serves none of them. A cache would not remove the cost anyway, because the cost lies in the LLM calls: 57\% of an agent's LLM calls issue no SQL that the answer uses, and 71\% of a session passes before that SQL starts. A cache makes a lookup cheaper for the database, but the agent still spends the LLM call that issues the lookup and reads its result. Liu et al.\ find the same split in the traces of an o3 agent: of 12.67 SQL statements per task, 3.44 explore tables and 3.56 explore columns, and expert hints such as which column holds the relevant information cut column exploration by 27.7\% and all statements by 18.1\%~\cite{liu2026agents}. Knowledge that an agent has before it starts removes exploration; \system\ supplies it from what other agents have learned. Answers are wrong without any failure: 31 of the 32 wrong answers occur when a question names a metric without defining it, exactly where a shared definition helps. And only 16\% of sessions check key uniqueness, the kind of condition that \system\ maintains on their behalf.}
{应用重复的是查询：Redset 中 93.4\% 的语句重复已有模板，每百条语句只有 6.6 个模板，预编译语句和回答了 34\% 读查询的结果缓存能很好地服务它们。智能体回答的是同样反复出现的问题，却不重复查询：每百条智能体语句中有 76 个模板，因为每个会话都根据刚刚查到的内容重新写 SQL。智能体重复的是知识：在我们的题目上，93\% 的查找都在重复此前会话已经得到的事实，而重复事实的 SQL 探查没有一条与先前探查的文本相同，因此按查询文本索引的缓存一条也服务不了。即使有缓存也省不下这部分代价，因为代价在大模型调用上：智能体 57\% 的大模型调用不发出答案所用的 SQL，会话 71\% 的时间都在这条 SQL 开始之前。缓存能让数据库更便宜地回答一次查找，但发出这次查找、读取其结果的那次大模型调用照样要花。Liu 等人在 o3 智能体的轨迹中看到同样的分布：每个任务平均 12.67 条 SQL，其中 3.44 条查看表、3.56 条查看列；专家给出提示（例如哪一列包含相关信息）后，查看列的 SQL 减少 27.7\%，全部 SQL 减少 18.1\%~\cite{liu2026agents}。智能体开始前就掌握的知识能省掉探索；\system\ 用其他智能体学到的知识来提供它。答案在没有任何报错的情况下出错：32 个错误答案中有 31 个出现在题目只给出指标名而不给定义时，这正是共享定义能帮上忙的地方。只有 16\% 的会话检查键唯一性，而这正是 \system\ 代为维护的那类条件。}

\subsection{\bt{Per-agent memory and shared memory}{单智能体记忆与共享记忆}}
\label{sec:alternatives}
\bi{Two kinds of memory can remove this repeated exploration, and they differ in who benefits. \emph{Per-agent memory}, the design of current agent memory systems, keeps what one agent learned for that agent's later sessions: a new agent starts empty and explores every metric it is asked about, and an agent that asks about a metric once gains nothing from having learned it. \emph{Shared memory}, the design of \system, keeps what any agent learned for every agent of the database: it stores the definition behind an agent's SQL with the question's parameters removed, so that every agent can compile it for its own question. With $N$ agents asking about $k$ metrics, per-agent memory explores up to $N\cdot k$ times and shared memory $k$ times; Section~\ref{sec:population-eval} measures the difference.}
{有两类记忆可以消除这种重复探索，它们的区别在于谁受益。\emph{单智能体记忆}是现有智能体记忆系统的做法，把一个智能体学到的东西留给它自己以后的会话：新来的智能体从空开始，每遇到一个指标都要探索；只问一次某个指标的智能体，学到了也用不上。\emph{共享记忆}是 \system\ 的做法，把任何一个智能体学到的东西留给这个数据库的所有智能体：它保存智能体所写 SQL 背后去掉题目参数的定义，使每个智能体都能针对自己的问题编译它。若 $N$ 个智能体问到 $k$ 个指标，单智能体记忆最多探索 $N\cdot k$ 次，共享记忆探索 $k$ 次；第~\ref{sec:population-eval} 节测量其差别。}

\bi{\emph{A cost model.} Let $N$ agents each ask $q$ questions about $k$ metrics, let $c_e$ be the cost of answering a question by exploration and $c_r$ the cost of answering it from memory, and let $c_\ell$ be the cost of learning one definition (extraction and publication checks). Without memory the agents pay $Nq\,c_e$. Shared memory pays at most $k(c_e+c_\ell)$ for the first question about each metric and $(Nq-k)\,c_r$ for the rest, plus its upkeep once per data change, so its saving
\[ 1-\frac{k(c_e+c_\ell)+(Nq-k)\,c_r}{Nq\,c_e}\;\longrightarrow\;1-\frac{c_r}{c_e}\qquad(N\to\infty) \]
grows with every agent that arrives. Per-agent memory pays the learning up to $Nk$ times and reuses only when an agent asks about a metric it learned itself, which is rare when each agent asks a few of many questions, so its cost stays near $Nq\,c_e$. Section~\ref{sec:population-eval} measures both: on TPC-DS, $c_e$ is \PpNoneLateTokK\,k tokens and $c_r$ is \PpMavraLateTokK\,k, so the token saving approaches \PpMavraAsymTokSaveNone\%. Writing $r=(Nq-k)/Nq$ for the share of questions answered from memory, the saving is $1-(1-r)(c_e+c_\ell)/c_e-r\,c_r/c_e$. With $c_\ell=\ExModelLearnTokK$\,k tokens, the model gives \ExModelTokSaveOurs\% at the \ExModelReusePct\% of questions that \system's agents answer from memory, the saving we measure; with $r$ set to the repetition of knowledge in LiveSQLBench (Table~\ref{tab:external}), it predicts \ExModelTokSaveLs\% over the benchmark's tasks and \ExModelTokSaveLsTwentieth\% on the 20th task of a database.}
{\emph{代价模型。}设 $N$ 个智能体各就 $k$ 个指标提 $q$ 个问题，$c_e$ 为靠探索回答一道题的代价，$c_r$ 为从记忆回答一道题的代价，$c_\ell$ 为学习一个定义的代价（提取与发布前检查）。没有记忆时，智能体共付 $Nq\,c_e$。共享记忆为每个指标的第一道题至多付 $k(c_e+c_\ell)$，其余的题付 $(Nq-k)\,c_r$，再加上每次数据变化只付一次的维护，因此它的节省
\[ 1-\frac{k(c_e+c_\ell)+(Nq-k)\,c_r}{Nq\,c_e}\;\longrightarrow\;1-\frac{c_r}{c_e}\qquad(N\to\infty) \]
随每个新到的智能体增长。单智能体记忆至多要付 $Nk$ 次学习，且只在智能体问到自己学过的指标时才复用；每个智能体只从众多问题中问几个时，这很少发生，因此它的代价停留在 $Nq\,c_e$ 附近。第~\ref{sec:population-eval} 节测量了这两者：在 TPC-DS 上，$c_e$ 为 \PpNoneLateTokK\,k token，$c_r$ 为 \PpMavraLateTokK\,k，因此 token 的节省趋近 \PpMavraAsymTokSaveNone\%。记 $r=(Nq-k)/Nq$ 为从记忆作答的题目占比，节省即为 $1-(1-r)(c_e+c_\ell)/c_e-r\,c_r/c_e$。取 $c_\ell=\ExModelLearnTokK$\,k token，模型在 \system\ 的智能体从记忆作答的 \ExModelReusePct\% 处给出 \ExModelTokSaveOurs\%，与实测的节省一致；把 $r$ 取为 LiveSQLBench 中知识的重复程度（表~\ref{tab:external}），模型预测在该基准的全部任务上省 \ExModelTokSaveLs\%，在一个库的第 20 个任务上省 \ExModelTokSaveLsTwentieth\%。}

\bi{Table~\ref{tab:capabilities} places these designs next to three that data systems already offer. Query and result caches are shared but save only on a query that repeats, and they stay correct by invalidating on writes, which also discards the saving. Metric layers share definitions that engineers write by hand and do not validate at run time. Data validation tests tables, not the knowledge that depends on them. None of these designs saves for every agent, on questions no agent has asked, from knowledge learned in the agents' own sessions, while keeping the saving through data changes. \system\ does all four, and it pays the upkeep of each shared definition once for every agent.}
{表~\ref{tab:capabilities} 把这些设计与数据系统已有的三种设计放在一起比较。查询与结果缓存是共享的，但只在查询重复时省下代价，并靠写入时失效保持正确，这也一并丢掉了节省。指标层共享由工程师手写的定义，运行时并不验证。数据验证检查的是表，而不是依赖这些表的知识。这些设计没有一种能同时做到：为每个智能体省下代价，在尚无人问过的问题上省下代价，所用的知识从智能体自己的会话中学到，并在数据变化后保住这份节省。\system\ 同时做到这四点，并为所有智能体对每个共享定义只付一次维护代价。}
