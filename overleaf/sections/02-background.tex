\section{\bt{Background and Motivation}{背景与动机}}
\label{sec:background}
\subsection{\bt{Repeated knowledge across agent queries}{智能体查询之间的知识重复}}
\label{sec:workload-characterization}
\bi{Tasks over the same database require overlapping domain knowledge. We quantify this overlap using the released tasks of public text-to-SQL benchmarks. LiveSQLBench~\cite{livesqlbench2025}, on which BIRD-Interact builds~\cite{huo2026birdinteract}, documents each of its PostgreSQL databases in a knowledge base of calculations, domain rules, and value meanings (\ExLsKb\ entries for the \ExLsDbs\ databases of the full release), and BIRD~\cite{li2023bird} gives each question evidence that defines its terms. Since LiveSQLBench withholds which entries a task needs, we count a task as needing an entry when its question names the entry or an entry built on it; a BIRD question needs the terms that its evidence defines. By excluding implicit references and paraphrases, these lexical counts provide a conservative estimate of knowledge repetition. Table~\ref{tab:external} shows that most tasks share knowledge with another task on their database, \ExLsSharePct\% on LiveSQLBench and \ExBdSharePct\% on BIRD. Half of LiveSQLBench's uses of knowledge (\ExLsRepeatPct\%) repeat an earlier use, and calculations, the kind of knowledge that \system\ learns, repeat as often (\ExLsCalcRepeatPct\%). Repetition grows with the number of tasks: the 10th task on a LiveSQLBench database finds \ExLsTenth\% of the knowledge it needs already needed by an earlier task, and the 20th \ExLsTwentieth\%; on BIRD the share still grows to \ExBdHundredth\% by the 100th question. These benchmarks contain \ExLsTasksPerDb\ to \ExBdTasksPerDb\ tasks per database on average. Every task is answered by a new agent session, which explores the knowledge again.}
{同一数据库上的任务需要重叠的领域知识。我们使用公开 Text-to-SQL 基准已发布的任务量化这种重叠。LiveSQLBench~\cite{livesqlbench2025}（BIRD-Interact 即建立在它之上~\cite{huo2026birdinteract}）为它的每个 PostgreSQL 数据库编写了知识库，包括计算、领域规则与取值含义（完整版 \ExLsDbs\ 个数据库共 \ExLsKb\ 条）；BIRD~\cite{li2023bird} 为每个问题附上定义其术语的证据。由于 LiveSQLBench 不公开任务需要哪些条目，我们在问题点名某条目或点名依赖它的条目时，认为任务需要该条目；BIRD 的问题需要其证据所定义的术语。这些词汇计数排除隐含引用与不同措辞的表达，为知识重复程度提供保守估计。表~\ref{tab:external} 表明，大多数任务与同库另一任务共用知识：LiveSQLBench 上为 \ExLsSharePct\%，BIRD 上为 \ExBdSharePct\%。LiveSQLBench 中一半的知识使用（\ExLsRepeatPct\%）重复此前的使用，而计算类知识，即 \system\ 所学习的那类知识，重复得同样多（\ExLsCalcRepeatPct\%）。重复随任务增多而增长：LiveSQLBench 一个库上的第 10 个任务，所需知识中有 \ExLsTenth\% 已被此前的任务需要过，第 20 个任务为 \ExLsTwentieth\%；在 BIRD 上，到第 100 个问题这一比例仍增长到 \ExBdHundredth\%。这些基准每个库平均包含 \ExLsTasksPerDb\ 到 \ExBdTasksPerDb\ 个任务。每个任务都由一个新的智能体会话回答，它把这些知识重新探索一遍。}

\bi{In applications, parameterized query templates and database knowledge reside in code, so millions of queries reduce to thousands of templates~\cite{ma2018querybot}; a new data-agent session must acquire that knowledge through schema lookups, data probes, and checks. To see what this costs, Table~\ref{tab:workload-characterization} compares two workloads. The application side is Redset~\cite{vanrenen2024redset}: 441 million queries of 400 Amazon Redshift clusters over three months, analyzed per cluster with the dataset's template fingerprint~\cite{redset2024dataset}. To capture session-level execution and LLM overhead not logged in the static benchmarks, the agent side traces 100 memoryless \llmmodel{} sessions over 25 analytical questions spanning five metrics (Section~\ref{sec:evaluation}: the learning questions and the first three scored forms). Each session uses table-listing, table-description, and SQL tools. A lookup's \emph{fact} is its purpose together with the tables and columns it reads.}
{在参数化应用中，查询模板和数据库知识保存在代码里，数百万条查询可归并为数千个模板~\cite{ma2018querybot}；全新的数据智能体会话则必须通过结构查找、数据探查和检查获得这些知识。为了看清这样做的代价，表~\ref{tab:workload-characterization} 对照两类负载。应用侧采用 Redset~\cite{vanrenen2024redset}：400 个 Amazon Redshift 集群三个月的 4.41 亿条查询，按集群分析，模板标识采用数据集自带的特征指纹~\cite{redset2024dataset}。为捕捉静态基准未记录的会话级执行与 LLM 开销，智能体侧追踪 100 个无记忆的 \llmmodel{} 会话，覆盖五个指标的 25 道分析题（第~\ref{sec:evaluation} 节的学习题与前三种计分题型）。每个会话使用列出表、描述表和执行 SQL 三种工具。查找所获得的\emph{事实}由其目的及读取的表和列确定。}

\bi{Applications repeat queries: in Redset, 93.4\% of the statements repeat an earlier template, 6.6 templates per 100 statements, and prepared statements and the result cache, which answers 34\% of the reads, serve them well. Agent queries have greater template diversity in our traces: 100 agent statements contain 76 templates, because each session writes its SQL anew from what it has just looked up. What agents repeat is knowledge: on our questions, 93\% of the lookups repeat a fact that an earlier session obtained, yet no SQL probe that repeats a fact repeats the text of an earlier one, so a cache keyed by query text serves none of them. Even with exact or semantic result caching on the database side, caching probe results does not remove the LLM calls that formulate probes and interpret their outputs: 57\% of an agent's LLM calls issue no SQL that the answer uses, and 71\% of a session passes before that SQL starts. A cache makes a lookup cheaper for the database, but the agent still spends the LLM call that issues the lookup and reads its result. Liu et al.\ find the same split in the traces of an OpenAI o3-based agent: of 12.67 SQL statements per task, 3.44 explore tables and 3.56 explore columns, and expert hints such as which column holds the relevant information cut column exploration by 27.7\% and all statements by 18.1\%~\cite{liu2026agents}. Knowledge that an agent has before it starts removes exploration; \system\ supplies it from what other agents have learned. Incorrect answers can occur without SQL execution errors: 31 of the 32 wrong answers occur when a question names a metric without defining it, exactly where a shared definition helps. Only 16\% of sessions check key uniqueness, the kind of condition that \system\ maintains on their behalf.}
{应用重复的是查询：Redset 中 93.4\% 的语句重复已有模板，每百条语句只有 6.6 个模板，预编译语句和回答了 34\% 读查询的结果缓存能很好地服务它们。在我们的轨迹中，智能体查询的模板更多样：每百条智能体语句中有 76 个模板，因为每个会话都根据刚刚查到的内容重新写 SQL。智能体重复的是知识：在我们的题目上，93\% 的查找都在重复此前会话已经得到的事实，而重复事实的 SQL 探查没有一条与先前探查的文本相同，因此按查询文本索引的缓存一条也服务不了。即使数据库侧采用精确匹配或语义结果缓存，缓存探查结果仍不能消除构造探查和解释其输出的大模型调用：智能体 57\% 的大模型调用不发出答案所用的 SQL，会话 71\% 的时间都在这条 SQL 开始之前。缓存能让数据库更便宜地回答一次查找，但发出这次查找、读取其结果的那次大模型调用照样要花。Liu 等人在 o3 智能体的轨迹中看到同样的分布：每个任务平均 12.67 条 SQL，其中 3.44 条查看表、3.56 条查看列；专家给出提示（例如哪一列包含相关信息）后，查看列的 SQL 减少 27.7\%，全部 SQL 减少 18.1\%~\cite{liu2026agents}。智能体开始前就掌握的知识能省掉探索；\system\ 用其他智能体学到的知识来提供它。答案在没有任何报错的情况下出错：32 个错误答案中有 31 个出现在题目只给出指标名而不给定义时，这正是共享定义能帮上忙的地方。只有 16\% 的会话检查键唯一性，而这正是 \system\ 代为维护的那类条件。}

\subsection{\bt{Amortizing exploration across agents}{跨智能体分摊探索开销}}
\label{sec:alternatives}
\bi{Sharing memory across agents amortizes the discovery of database knowledge. A private memory serves the later sessions of its owner; a database-wide memory also serves other agents whose questions use the same definitions. With $N$ agents and $k$ metrics, private copies can require up to $Nk$ discoveries, whereas under stable data one successful publication per metric can serve the population. \system\ makes these publications executable for new periods and tasks, reducing both repeated discovery and the work of translating knowledge into SQL. The population study measures this effect using shared and private copies of the same learning and validation mechanisms (Section~\ref{sec:population-eval}).}
{跨智能体共享记忆可以分摊数据库知识的发现开销。私有记忆服务其拥有者的后续会话；数据库范围的共享记忆还服务使用相同定义的其他智能体。对于 $N$ 个智能体和 $k$ 个指标，私有副本至多需要 $Nk$ 次发现；数据稳定时，每个指标一次成功发布即可服务整个群体。\system\ 将这些发布的定义编译为新期间和任务所需的查询，同时减少重复发现以及把知识转化为 SQL 的工作。群体实验使用学习和验证机制相同的共享与私有副本，测量这一效果（第~\ref{sec:population-eval} 节）。}

\bi{\emph{A cost model.} Let $N$ agents each ask $q$ questions about $k$ metrics, let $c_e$ be the cost of answering a question by exploration and $c_r$ the cost of answering it from memory, and let $c_\ell$ be the cost of learning one definition (extraction and publication checks). Assume stable definitions and one successful publication per metric. Without memory the agents pay $Nq\,c_e$. Shared memory pays at most $k(c_e+c_\ell)$ for the first question about each metric and $(Nq-k)\,c_r$ for the rest, plus its upkeep once per data change, so its saving
\[ 1-\frac{k(c_e+c_\ell)+(Nq-k)\,c_r}{Nq\,c_e}\;\longrightarrow\;1-\frac{c_r}{c_e}\qquad(N\to\infty) \]
grows with every agent that arrives. Per-agent memory pays the learning up to $Nk$ times and reuses only when an agent asks about a metric it learned itself, which is rare when each agent asks a few of many questions, so its cost stays near $Nq\,c_e$. Section~\ref{sec:population-eval} measures both: on TPC-DS, $c_e$ is \PpNoneLateTokK\,k tokens and $c_r$ is \PpMavraLateTokK\,k, so the token saving approaches \PpMavraAsymTokSaveNone\%. Writing $r=(Nq-k)/Nq$ for the share of questions answered from memory, the saving is $1-(1-r)(c_e+c_\ell)/c_e-r\,c_r/c_e$. With $c_\ell=\ExModelLearnTokK$\,k tokens, the model gives \ExModelTokSaveOurs\% at the \ExModelReusePct\% of questions that \system's agents answer from memory, the saving we measure.}
{\emph{代价模型。}设 $N$ 个智能体各就 $k$ 个指标提 $q$ 个问题，$c_e$ 为靠探索回答一道题的代价，$c_r$ 为从记忆回答一道题的代价，$c_\ell$ 为学习一个定义的代价（提取与发布前检查）。假定定义稳定、每个指标一次成功发布。没有记忆时，智能体共付 $Nq\,c_e$。共享记忆为每个指标的第一道题至多付 $k(c_e+c_\ell)$，其余的题付 $(Nq-k)\,c_r$，再加上每次数据变化只付一次的维护，因此它的节省
\[ 1-\frac{k(c_e+c_\ell)+(Nq-k)\,c_r}{Nq\,c_e}\;\longrightarrow\;1-\frac{c_r}{c_e}\qquad(N\to\infty) \]
随每个新到的智能体增长。单智能体记忆至多要付 $Nk$ 次学习，且只在智能体问到自己学过的指标时才复用；每个智能体只从众多问题中问几个时，这很少发生，因此它的代价停留在 $Nq\,c_e$ 附近。第~\ref{sec:population-eval} 节测量了这两者：在 TPC-DS 上，$c_e$ 为 \PpNoneLateTokK\,k token，$c_r$ 为 \PpMavraLateTokK\,k，因此 token 的节省趋近 \PpMavraAsymTokSaveNone\%。记 $r=(Nq-k)/Nq$ 为从记忆作答的题目占比，节省即为 $1-(1-r)(c_e+c_\ell)/c_e-r\,c_r/c_e$。取 $c_\ell=\ExModelLearnTokK$\,k token，模型在 \system\ 的智能体从记忆作答的 \ExModelReusePct\% 处给出 \ExModelTokSaveOurs\%，与实测的节省一致。}
