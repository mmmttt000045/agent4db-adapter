\section{\bt{Background and Motivation}{背景与动机}}
\label{sec:background}
\subsection{\bt{Repeated discovery of database knowledge}{数据库知识的重复探索}}
\label{sec:workload-characterization}

\bi{Different questions over the same database often rely on common metric definitions, domain rules, and value meanings. We examine this overlap using the released tasks of two text-to-SQL benchmarks. LiveSQLBench~\cite{livesqlbench2025}, which underlies BIRD-Interact~\cite{huo2026birdinteract}, provides each PostgreSQL database with a knowledge base of calculations, domain rules, and value meanings; the full release contains \ExLsKb\ entries across \ExLsDbs\ databases. BIRD~\cite{li2023bird} provides question-specific evidence about calculations, domain knowledge, and the interpretation of database values.}
{同一数据库上的不同问题往往依赖共同的指标定义、领域规则和取值含义。我们使用两个 Text-to-SQL 基准已发布的任务考察这种重叠。LiveSQLBench~\cite{livesqlbench2025} 是 BIRD-Interact~\cite{huo2026birdinteract} 的基础，为每个 PostgreSQL 数据库提供包含计算、领域规则和取值含义的知识库；完整版的 \ExLsDbs\ 个数据库共有 \ExLsKb\ 条知识。BIRD~\cite{li2023bird} 则提供与问题相关的证据，说明计算方式、领域知识及数据库取值的含义。}

\bi{The public LiveSQLBench task files omit the required knowledge-entry IDs. We therefore associate a task with an entry when its question explicitly names that entry or another entry that depends on it. For BIRD, we extract the terms explicitly defined in each question's evidence. This procedure measures explicit lexical overlap and excludes implicit references and paraphrases. Sharing rates are computed over tasks with at least one identified knowledge item. For the $n$th task, we measure the fraction of its identified knowledge items that have appeared in earlier tasks, averaging over random task orders within each database.}
{LiveSQLBench 的公开任务文件未包含各任务所需的知识条目 ID。因此，当问题明确提及某个条目或依赖该条目的其他条目时，我们将该任务与这一条目关联。对于 BIRD，我们提取各问题证据中明确界定的术语。这一方法衡量显式的词汇重叠，不计入隐含引用或改述。共享比例以至少识别出一项知识的任务为分母。对于第 $n$ 个任务，我们计算其已识别知识中曾在先前任务出现的比例，并对各数据库内的随机任务顺序取平均。}

\bi{Table~\ref{tab:external} shows that, among tasks with identified knowledge items, \ExLsSharePct\% on LiveSQLBench and \ExBdSharePct\% on BIRD share at least one item with another task on the same database. On LiveSQLBench, \ExLsRepeatPct\% of identified knowledge uses repeat an earlier use; the rate is \ExLsCalcRepeatPct\% for calculation entries. The fraction of knowledge already encountered reaches \ExLsTenth\% at the 10th task and \ExLsTwentieth\% at the 20th task on LiveSQLBench, and \ExBdHundredth\% at the 100th task on BIRD. The two benchmarks contain an average of \ExLsTasksPerDb\ and \ExBdTasksPerDb\ tasks per database, respectively. These overlaps create opportunities to reuse database knowledge across agent sessions.}
{表~\ref{tab:external} 表明，在识别出知识条目的任务中，LiveSQLBench 上有 \ExLsSharePct\%、BIRD 上有 \ExBdSharePct\% 与同一数据库上的其他任务共享至少一项知识。在 LiveSQLBench 中，\ExLsRepeatPct\% 的已识别知识使用重复了先前的使用；计算类条目的这一比例为 \ExLsCalcRepeatPct\%。所需知识中此前已出现的比例，在 LiveSQLBench 的第 10 个任务达到 \ExLsTenth\%、第 20 个任务达到 \ExLsTwentieth\%，在 BIRD 的第 100 个任务达到 \ExBdHundredth\%。两个基准每个数据库分别平均包含 \ExLsTasksPerDb\ 和 \ExBdTasksPerDb\ 个任务。这些重叠为跨智能体会话复用数据库知识提供了机会。}

\bi{Applications encode database knowledge in query templates and application logic. Prior work has grouped millions of application queries into thousands of templates~\cite{ma2018querybot}. A memoryless data agent acquires task-relevant knowledge through schema inspection, data probes, and validation. To characterize the work involved, Table~\ref{tab:workload-characterization} reports an analysis of Redset and a trace study of agent sessions. Our Redset analysis covers 441 million queries from 400 Amazon Redshift instances over three months~\cite{vanrenen2024redset}. We analyze read queries within each instance using the dataset's feature fingerprint, a proxy for query similarity that can overestimate repetition~\cite{redset2024dataset}.}
{应用将数据库知识编码在查询模板和应用逻辑中。已有工作曾将数百万条应用查询归并为数千个模板~\cite{ma2018querybot}。无记忆的数据智能体通过结构检查、数据探查和验证获取任务所需的知识。为刻画这一过程的开销，表~\ref{tab:workload-characterization} 给出对 Redset 的分析及对智能体会话的轨迹研究。我们的 Redset 分析覆盖 400 个 Amazon Redshift 实例在三个月内的 4.41 亿条查询~\cite{vanrenen2024redset}。读查询按实例分析，使用数据集提供的特征指纹；该指纹是查询相似度的近似标识，可能高估重复程度~\cite{redset2024dataset}。}

\bi{The agent study traces 100 memoryless \llmmodel{} sessions over 25 analytical questions spanning five metrics. These sessions make 521 database calls through table-listing, table-description, and SQL execution tools, including 176 SQL statements. We call a schema inspection, data probe, or validation step a \emph{lookup}. We group lookups by their inspection intent and the tables and columns they access, treating each group as an \emph{inspection target}.}
{智能体研究追踪 100 个无记忆的 \llmmodel{} 会话，覆盖五个指标的 25 道分析题。这些会话通过列出表、描述表和执行 SQL 的工具，共发起 521 次数据库调用，其中包括 176 条 SQL 语句。我们将一次结构检查、数据探查或验证称为一次\emph{查找}。按照检查意图及访问的表和列对查找分组，将每组视为一个\emph{检查目标}。}

\bi{In our Redset analysis, 93.4\% of read queries have a feature fingerprint observed earlier in the same instance, with 6.6 distinct fingerprints per 100 read queries; 34\% of read queries are served by the result cache. Our agent traces contain 76 distinct SQL templates per 100 statements. However, different SQL statements can revisit the same inspection target: 93\% of lookups target information inspected in an earlier session. None of the SQL probes that revisit these targets is textually identical to an earlier probe, so an exact-text result cache would have no hits on this subset.}
{在我们的 Redset 分析中，93.4\% 的读查询使用了同一实例内此前已出现的特征指纹，每百条读查询对应 6.6 个不同指纹；34\% 的读查询由结果缓存回答。智能体轨迹中，每百条语句对应 76 个不同的 SQL 模板。然而，不同 SQL 语句仍可能访问相同的检查目标：93\% 的查找针对先前会话已经检查过的信息。重复访问这些目标的 SQL 探查均未与先前探查的文本完全相同，因此，精确匹配查询文本的结果缓存无法命中这一组探查。}

\bi{Database-side result caching can reduce the execution cost of a probe, while the agent still has to formulate the probe and interpret its result. In our traces, 57\% of LLM calls issue no SQL used in the final answer, and 71\% of session time elapses before that SQL begins execution. An independent study by Liu et al.\ also reports substantial exploration by an o3-based agent: each task generates 12.67 SQL statements on average, including 3.44 for table exploration and 3.56 for column exploration. Expert hints about relevant data reduce column exploration by 27.7\% and total statements by 18.1\%~\cite{liu2026agents}. Providing previously acquired knowledge can help subsequent sessions bypass the corresponding exploration steps.}
{数据库侧的结果缓存可以降低探查的执行代价，但智能体仍需构造探查并解释其结果。在我们的轨迹中，57\% 的大模型调用未发出最终答案使用的 SQL；在这类 SQL 开始执行之前，已消耗会话时间的 71\%。Liu 等人的独立研究也观察到基于 o3 的智能体进行了大量探索：每个任务平均生成 12.67 条 SQL，其中 3.44 条用于表探索，3.56 条用于列探索。提供有关相关数据的专家提示后，列探索减少 27.7\%，SQL 总量减少 18.1\%~\cite{liu2026agents}。向后续会话提供先前已获得的知识，有助于省去相应的探索步骤。}

\bi{The traces also motivate making metric definitions explicit. Of the 32 incorrect answers, 31 concern questions that name a metric without specifying its definition. Sharing an explicit definition gives subsequent sessions a common basis for interpreting the metric and constructing its SQL.}
{这些轨迹也体现了明确指标定义的需求。在 32 个错误答案中，31 个对应的问题只给出了指标名称而未说明其定义。共享明确的定义，可以为后续会话解释指标含义和构造 SQL 提供共同依据。}

\subsection{\bt{Sharing and maintaining database knowledge}{数据库知识的共享与维护}}
\label{sec:alternatives}

\bi{A private memory reuses knowledge across the sessions of one agent; a database-wide memory makes the same knowledge available to other agents. If each of $N$ agents independently learns each of $k$ metric definitions once, private memories require $Nk$ learning episodes. Under stable data, a shared memory can publish each definition once for all agents to reuse. Representing the learned computation as a parameterized, executable definition also allows later questions to use it with new inputs.}
{私有记忆在一个智能体的不同会话之间复用知识；数据库范围的共享记忆则使其他智能体也能使用这些知识。如果 $N$ 个智能体分别独立学习 $k$ 个指标定义各一次，私有记忆需要 $Nk$ 次学习。在数据稳定时，共享记忆可以将每个定义发布一次，供所有智能体复用。将学得的计算表示为参数化、可执行的定义，还可以让后续问题使用新的输入执行这一计算。}

\bi{\emph{Validity under updates.} A metric's meaning can remain unchanged while the data conditions required by its implementation cease to hold. For example, consider a revenue definition that joins each sale to a customer table under the assumption that each customer key identifies one row. If updates introduce multiple historical versions per customer, the same join can duplicate sales and inflate revenue even though the SQL still executes successfully. In our traces, 16\% of sessions explicitly check key uniqueness, one example of such a data condition. Sharing a definition therefore also requires recording and maintaining the conditions on which its computation depends.}
{\emph{更新后的有效性。}指标的含义可以保持不变，但实现该指标所依赖的数据条件可能不再成立。例如，一个营业额定义将每笔销售与客户表连接，并假定每个客户键只对应一行。如果更新引入同一客户的多个历史版本，相同的连接就可能复制销售记录、放大营业额，而 SQL 仍能正常执行。在我们的轨迹中，16\% 的会话显式检查键唯一性，它正是这类数据条件的一个例子。因此，共享定义也需要记录并维护其计算所依赖的条件。}

\bi{When a condition fails, continued reuse can expose multiple agents to the same error. Maintenance must identify the affected definitions, revalidate their conditions, and repair or invalidate definitions whose conditions no longer hold, while retaining unaffected knowledge. Reuse also requires validation evidence that applies to the query's execution snapshot. A check on an earlier state remains usable only when its validity for the execution snapshot is established. These requirements motivate tracking dependencies and sharing validation and maintenance across consumers.}
{当某个条件失效时，继续复用可能使多个智能体遇到同一错误。维护机制需要识别受影响的定义、重新验证其条件，并修复或停用不再满足条件的定义，同时保留未受影响的知识。复用还要求验证证据适用于查询的执行快照。只有在能够确认既有检查对执行快照仍然有效时，才能继续使用这一检查结果。这些要求促使系统跟踪依赖，并在多个使用者之间共享验证与维护工作。}

\bi{\emph{A cost model.} Consider $N$ agents, each asking $q$ questions over a shared set of $k$ metrics. Assume that each question uses one metric, every metric is requested, its first question publishes a reusable definition, and subsequent questions reuse it. For one cost measure, such as LLM tokens or cumulative processing time, let $c_e$ be the cost of answering a question through fresh exploration, $c_r$ the cost of answering it through reuse, and $c_\ell$ the additional cost of extracting, validating, and publishing a definition. Let $M$ be the cumulative additional maintenance cost across database updates. The costs are $Nq\,c_e$ without memory and $k(c_e+c_\ell)+(Nq-k)c_r+M$ with sharing. Under this model, sharing reduces total cost when}
{\emph{代价模型。}考虑 $N$ 个智能体，每个智能体针对同一组 $k$ 个指标提出 $q$ 个问题。假定每个问题使用一个指标，每个指标至少被请求一次，其首次请求发布可复用定义，后续请求复用该定义。对于一种代价度量，例如大模型 token 或累计处理时间，令 $c_e$ 为通过重新探索完成一个问题的代价，$c_r$ 为通过复用完成一个问题的代价，$c_\ell$ 为提取、验证和发布一个定义的额外代价。令 $M$ 为数据库更新引起的额外累计维护代价。无记忆时的总代价为 $Nq\,c_e$，共享时为 $k(c_e+c_\ell)+(Nq-k)c_r+M$。在这一模型下，共享降低总代价的条件为}
\begin{equation}
\label{eq:sharing-benefit}
(Nq-k)(c_e-c_r)>k\,c_\ell+M.
\end{equation}
\bi{Reuse must therefore repay both learning and maintenance. Sharing validation work and restricting maintenance to affected definitions help preserve this benefit as the database changes. All terms use the same cost measure: maintenance performed entirely through database operations can incur execution cost even when it consumes no LLM tokens.}
{因此，复用收益需要覆盖学习与维护开销。共享验证工作，并将维护限制在受影响的定义上，有助于在数据库变化时保留这一收益。所有项均采用相同的代价度量：完全通过数据库操作完成的维护，即使不消耗大模型 token，也会产生执行开销。}
