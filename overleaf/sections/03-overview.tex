\section{\bt{System Overview}{系统概览}}
\label{sec:overview}
\bi{\system\ is a shared memory layer between data agents and a SQL database, PostgreSQL in our prototype (Figure~\ref{fig:architecture}). It exposes tool-style HTTP endpoints for listing and describing tables, finding and checking join paths, looking up metric definitions (\code{find\_metric}), and running SQL (\code{run\_sql}); agents submit final answers with the query references and arithmetic that produced them, so the middleware records the provenance of every answer. The shared memory, an in-memory store, keeps versioned definitions, join paths, grain entries, check results, and evidence. Version detection reads table fingerprints, DML statistics, and an ETL batch log; in same-snapshot mode, statement-level triggers maintain transactional table versions (Section~\ref{sec:snapshot}). The middleware is about 6,600 lines of Rust with 40 unit and integration tests.}
{\system\ 是位于数据智能体与 SQL 数据库之间的共享记忆层，原型使用 PostgreSQL（图~\ref{fig:architecture}）。它通过工具式 HTTP 接口提供列出和描述表、查找与检查连接路径、查找指标定义（\code{find\_metric}）以及执行 SQL（\code{run\_sql}）等功能；智能体提交最终答案时附上产生答案的查询编号和算式，因此中间件为每个答案记录溯源。共享记忆是一个内存存储，保存版本化的定义、连接路径、粒度条目、检查结果和证据。版本检测读取表指纹、DML 统计和 ETL 批次日志；在同快照模式下，语句级触发器维护事务性表版本（第~\ref{sec:snapshot} 节）。中间件约 6,600 行 Rust 代码，含 40 个单元与集成测试。}

\bi{\emph{Who reads and who writes.} The memory separates what agents read from what \system\ keeps. Agents read a revision's business basis, fields, canonical and example SQL, caveats, and revision number; \system\ keeps the revision's conditions, their check results and dependency versions, the admission evidence, and the learning snapshot for as-of queries. No agent writes to the memory directly: a revision enters only through the admission checks, whether it comes from the learner, a repair, or an optimization, and a published revision is never edited in place. Two candidates for one metric whose structures differ are kept as separate entries; \system\ does not reconcile them. Consumers state reliance explicitly by declaring the revisions a query uses, which lets the layer enforce validity at use and tell a consumer when what it relied on has changed.}
{\emph{谁读，谁写。}记忆把智能体读到的内容与 \system\ 保管的内容分开。智能体读到修订的业务依据、字段、规范 SQL 与示例 SQL、注意事项和修订号；\system\ 保管修订的条件、条件的检查结果与依赖版本、准入证据，以及供 as-of 查询使用的学习时快照。任何智能体都不直接写记忆：修订只能经过准入检查进入，无论它来自学习、修复还是优化；已发布的修订从不原地修改。同一指标下结构不同的两个候选作为两个条目分别保存，\system\ 不去调和它们。使用者通过声明查询所用的修订来明确表示依赖，这使这一层能够在使用处执行有效性，并在使用者所依赖的内容变化时通知它。}

\bi{A definition moves through three paths. On the \emph{learning path}, \system's built-in analysis optimizer, an LLM agent, answers a question whose business meaning is stated explicitly; if an independent judge accepts the answer, an offline extractor turns the recorded answer provenance into a structured candidate, which the admission checks validate before publication. On the \emph{use path}, a user agent calls \code{find\_metric}; if any dependency version has changed, the lookup first runs condition maintenance and then returns the current valid revision with its fields and caveats. On the \emph{execution path}, the agent's \code{run\_sql} declares the metric keys and revisions it uses; the middleware rejects absent, invalidated, or superseded revisions, reviews the SQL against recorded grain and join requirements, and, in same-snapshot mode, checks the revisions' conditions and runs the query on one snapshot. After learning, an \emph{optimization} sweep rewrites published definitions and publishes the rewrites that pass its tests as new revisions (Section~\ref{sec:optimization}). Invalidations and new revisions reach agents as notices on their next tool response.}
{一个定义经过三条路径。在\emph{学习路径}上，\system\ 内置的分析优化器（一个大模型智能体）回答一道显式给出业务含义的题目；若独立判题接受其答案，离线提取器把记录的答案溯源转成结构化候选，由准入检查验证后发布。在\emph{使用路径}上，用户端智能体调用 \code{find\_metric}；若有依赖版本变化，查找先执行条件维护，再返回当前有效修订及其字段和注意事项。在\emph{执行路径}上，智能体在 \code{run\_sql} 中声明所用的指标键和修订号；中间件拒绝不存在、已失效或已被替代的修订，按记录的粒度和连接要求审查 SQL，并在同快照模式下于同一快照上核对修订条件、执行查询。学习结束后，一轮\emph{优化}改写已发布的定义，把通过其测试的改写发布为新修订（第~\ref{sec:optimization} 节）。失效与新修订通过智能体下一次工具调用的返回中的通知传达。}
