\section{\bt{System Overview}{系统概览}}
\label{sec:overview}
\bi{\system\ is a shared memory layer between data agents and a SQL database, PostgreSQL in our prototype (Figure~\ref{fig:architecture}). It exposes tool-style endpoints for listing and describing tables, finding join paths, looking up metric definitions (\code{find\_metric}), and running SQL (\code{run\_sql}); agents submit final answers with the query references and arithmetic that produced them, so the middleware records the provenance of every answer. The shared memory keeps versioned definitions, join paths, grain entries, check results, and evidence. The middleware is about 6,600 lines of Rust with 40 unit and integration tests.}
{\system\ 是位于数据智能体与 SQL 数据库之间的共享记忆层，原型使用 PostgreSQL（图~\ref{fig:architecture}）。它以工具接口的形式提供列出和描述表、查找连接路径、查找指标定义（\code{find\_metric}）以及执行 SQL（\code{run\_sql}）等功能；智能体提交最终答案时附上产生答案的查询编号和算式，因此中间件为每个答案记录溯源。共享记忆保存版本化的定义、连接路径、粒度条目、检查结果和证据。中间件约 6,600 行 Rust 代码，含 40 个单元与集成测试。}

\bi{\emph{Who reads and who writes.} Agents read a revision's business basis, fields, canonical and example SQL, caveats, and revision number; \system\ keeps its conditions, their check results and dependency versions, the admission evidence, and the learning snapshot for as-of queries. No agent writes to the memory directly: a revision enters only through the admission checks, whether it comes from the learner, a repair, or an optimization, and a published revision is never edited in place. Two candidates for one metric whose structures differ are kept as separate entries. Consumers state reliance by declaring the revisions a query uses, which lets the layer enforce validity at use and notify a consumer, on its next tool response, when what it relied on has changed.}
{\emph{谁读，谁写。}智能体读到修订的业务依据、字段、规范 SQL 与示例 SQL、注意事项和修订号；\system\ 保管修订的条件、条件的检查结果与依赖版本、准入证据，以及供 as-of 查询使用的学习时快照。任何智能体都不直接写记忆：修订只能经过准入检查进入，无论它来自学习、修复还是优化；已发布的修订从不原地修改。同一指标下结构不同的两个候选作为两个条目分别保存。使用者通过声明查询所用的修订来表示依赖，这使这一层能够在使用处执行有效性，并在使用者所依赖的内容变化时，于其下一次工具调用的返回中通知它。}

\bi{A definition moves through the three paths of Figure~\ref{fig:architecture}. On the \emph{learning path}, the analysis optimizer answers a question whose business meaning is stated explicitly, and if an independent judge accepts the answer, an offline extractor turns the recorded provenance into a candidate for admission (Section~\ref{sec:maintenance}). On the \emph{use path}, \code{find\_metric} first runs condition maintenance if a dependency version has changed and then returns the valid revision. On the \emph{execution path}, \code{run\_sql} rejects declared revisions that are absent or invalidated and runs the query on one snapshot on which their conditions hold (Section~\ref{sec:execution}).}
{一个定义经过图~\ref{fig:architecture} 的三条路径。在\emph{学习路径}上，分析优化器回答一道显式给出业务含义的题目；若独立判题接受其答案，离线提取器把记录的溯源转成候选，交给准入（第~\ref{sec:maintenance} 节）。在\emph{使用路径}上，若有依赖版本变化，\code{find\_metric} 先执行条件维护，再返回有效修订。在\emph{执行路径}上，\code{run\_sql} 拒绝不存在或已失效的声明修订，并在这些修订的条件成立的同一快照上执行查询（第~\ref{sec:execution} 节）。}
