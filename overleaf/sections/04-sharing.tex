\section{\bt{Design of \system}{\system\ 的设计}}
\label{sec:model}
\bi{Sharing saves work only if what one agent learned answers other agents' questions and stays correct for them, and only if keeping it correct costs less than what it saves. This section describes what agents share and how it is learned (Section~\ref{sec:shared-object}), when it is correct (Section~\ref{sec:sufficiency}), how \system\ maintains it once for all agents (Section~\ref{sec:maintenance}), how it guards each query (Section~\ref{sec:execution}), and how one optimization speeds up every agent (Section~\ref{sec:optimization}).}
{共享要省下工作，一个智能体学到的东西必须能回答其他智能体的问题并对它们保持正确，而且保持正确的代价必须小于它省下的。本节说明智能体共享什么、它如何学来（第~\ref{sec:shared-object} 节），它何时正确（第~\ref{sec:sufficiency} 节），\system\ 如何为所有智能体一次性地维护它（第~\ref{sec:maintenance} 节），如何守护每个查询（第~\ref{sec:execution} 节），以及一次优化如何让每个智能体都更快（第~\ref{sec:optimization} 节）。}

\subsection{\bt{What agents share and how it is learned}{智能体共享什么、如何学来}}
\label{sec:shared-object}
\bi{A definition revision is $m^r=(B,I,C,E,r)$, where $B$ is its business meaning, $I$ its structured implementation, $C$ its set of executable conditions, $E$ its learning record, and $r$ its revision number. The implementation records the fact table, aggregate expression, grain, date join, joins, and definition filters; its joins form a many-to-one tree rooted at the fact table (a star or snowflake). Question parameters such as the month are not part of it: the generated SQL is compiled from $I$ for any period, difference, or ranking, so one learning session serves questions that no agent has asked yet.}
{定义的一个版本记为 $m^r=(B,I,C,E,r)$，其中 $B$ 为业务含义，$I$ 为结构化实现，$C$ 为可执行条件集，$E$ 为学习记录，$r$ 为版本号。实现记录事实表、聚合表达式、粒度、日期连接、连接和定义过滤；连接构成以事实表为根的多对一连接树（星型或雪花型）。月份等题目参数不属于实现：生成的 SQL 由 $I$ 针对任意期间、差值或排名编译得到，因此一次学习会话可以服务尚无智能体问过的问题。}

\bi{\emph{Learning from use.} Any agent's session can teach the memory: a candidate comes from a session whose question states the business definition and whose answer matches the reference answer, which a hand-written reference query computes on the same snapshot. The extractor sees the question, the SQL and arithmetic behind the answer, rejected queries, and metadata, but no business rows or result values. Seven deterministic publication checks follow: a stated business definition; the match with the reference answer, with a recorded calculation that reproduces it from the query results; static checks (columns exist, the measure uses only permitted columns, joins follow validated paths, and required grain filters are present without question literals); key uniqueness on the current snapshot; the SQL check (no join known to fan out, no missing grain filter); replay of the example SQL; and replay of the generated SQL compiled from the fields. The last check tests what other agents will read rather than what the producer ran, so a candidate that drops a filter or hard-codes a parameter is rejected before it reaches anyone. No agent writes to the memory directly, and a published revision is never edited in place.}
{\emph{边用边学。}任何智能体的会话都可以教给记忆：候选来自题目给出业务定义、且答案与参考答案一致的会话，参考答案由人工编写的参考查询在同一快照上算出。提取器看到题目、答案背后的 SQL 与算式、被拒绝的查询以及元数据，但看不到业务数据行和结果值。随后是七项确定性的发布前检查：给出的业务定义；与参考答案一致，且记录的算式能从查询结果复现该答案；静态检查（列存在，度量只用允许的列，连接沿已验证的路径，粒度所需的过滤齐全且不含题目字面值）；当前快照上的键唯一性；SQL 检查（不含已知会放大行数的连接，不缺粒度所需的过滤）；示例 SQL 重放；由字段编译出的生成的 SQL 重放。最后一项检查的是其他智能体将要读到的内容，而不是生产者当时执行的内容，因此丢掉过滤或写死参数的候选在到达任何人之前就被拒绝。任何智能体都不直接写记忆，已发布的版本从不原地修改。}

\bi{\emph{Use.} An agent looks a metric up by name with \code{find\_metric} and receives the valid revision's business definition, fields, generated SQL, example SQL, and revision number; it runs the generated SQL with its own period and declares the revision to \code{run\_sql}. An agent looks up the memory at most three times per question, and when nothing matches it explores as it would without memory, so a metric that no one has learned yet costs no more than having no memory.}
{\emph{使用。}智能体用 \code{find\_metric} 按名称查找指标，得到有效版本的业务定义、字段、生成的 SQL、示例 SQL 与版本号；它用自己的期间执行生成的 SQL，并在 \code{run\_sql} 中声明该版本。智能体每道题最多查找三次记忆，没有匹配时就像没有记忆那样自行探索，因此尚无人学过的指标不会比没有记忆花得更多。}

\subsection{\bt{When shared knowledge is correct}{共享的知识何时正确}}
\label{sec:sufficiency}
\bi{A condition $c$ is a predicate over the tables $\operatorname{dep}(c)$ with a check query $Q_c$ that returns violating rows or nothing; its normalized form $\operatorname{id}(c)$ consists of its type, tables, keys, join direction, normalized filters, and null policy. \system\ derives four kinds from $I$. \emph{Filtered key uniqueness} $\operatorname{KeyUnique}(T,K,\varphi)$: no two rows of $\sigma_\varphi(T)$ agree on $K$, from the grain and the fact table's filters. \emph{Join cardinality}: each row of $L$ in a join $L\to R$ matches at most the permitted number of $R$ rows. \emph{Date join}: the fact's date key joins the date dimension many-to-one, or a date column supplies the date. \emph{Join completeness}: for the date join and every inner join, the fraction of fact rows that match no row stays within the fraction recorded at publication plus 0.1 percentage points.}
{条件 $c$ 是表集合 $\operatorname{dep}(c)$ 上的谓词，附带一个检查查询 $Q_c$，返回违例行或空；其规范化形式 $\operatorname{id}(c)$ 由类型、表、键、连接方向、规范化的过滤和空值规则组成。\system\ 从 $I$ 推导四类条件。\emph{过滤后键唯一性} $\operatorname{KeyUnique}(T,K,\varphi)$：$\sigma_\varphi(T)$ 中没有两行在 $K$ 上取值相同，由粒度和事实表上的过滤推出。\emph{连接基数}：连接 $L\to R$ 中每条 $L$ 记录匹配的 $R$ 记录数不超过允许值。\emph{日期连接}：事实的日期键与日期维度多对一连接，或由日期列给出日期。\emph{连接完整性}：对日期连接和每个内连接，匹配不到任何行的事实行比例不超过发布时记录的比例加 0.1 个百分点。}

\bi{For a period $p$, the generated SQL evaluates $\mathrm{AGG}(e)$ over the rows of $\sigma_\varphi(F)\bowtie R_1\bowtie\cdots\bowtie R_k$ whose date falls in $p$. The business meaning contributes two assumptions that no query can check: (B1) the metric's business events correspond one-to-one to the values of $K$ in $\sigma_\varphi(F)$, and (B2) $e$ evaluates on an event's row to that event's measurement.}
{对期间 $p$，生成的 SQL 在 $\sigma_\varphi(F)\bowtie R_1\bowtie\cdots\bowtie R_k$ 中日期落在 $p$ 内的行上计算 $\mathrm{AGG}(e)$。业务含义提供两条任何查询都无法检查的前提：（B1）指标的业务事件与 $\sigma_\varphi(F)$ 中 $K$ 的取值一一对应；（B2）在事件对应的行上，$e$ 求值得到该事件的度量值。}
\begin{proposition}[\bt{Sufficiency}{充分性}]
\label{prop:sufficiency}
\bi{If B1 and B2 hold on $D_s$ and every condition in $C(m^r)$ holds on $D_s$, then for every period $p$ the generated SQL of $m^r$ returns $\mathrm{AGG}$ over the measurements of the events whose date lies in $p$, each event contributing exactly once; the events it omits are those whose date or join key matches no row, and the completeness conditions bound their fraction.}
{若 B1、B2 在 $D_s$ 上成立，且 $C(m^r)$ 中每个条件都在 $D_s$ 上成立，则对每个期间 $p$，$m^r$ 的生成的 SQL 返回日期落在 $p$ 内的事件度量值的 $\mathrm{AGG}$，每个事件恰好贡献一次；被遗漏的只有日期键或连接键匹配不到任何行的事件，其比例受完整性条件约束。}
\end{proposition}
\begin{proof}[\bt{Proof sketch}{证明概要}]
\bi{By B1 and filtered key uniqueness, $\sigma_\varphi(F)$ holds one row per event. Join cardinality keeps every join from duplicating a row, join completeness bounds the rows that inner joins drop, and the date join gives each row at most one date and hence at most one period. Every remaining row contributes its measurement (B2) once, to the period of its date.}
{由 B1 和过滤后键唯一性，$\sigma_\varphi(F)$ 中每个事件恰有一行。连接基数保证连接不复制任何行，连接完整性约束内连接排除的行，日期连接给每行至多一个日期，因而至多一个期间。于是每个保留下来的行把其度量值（B2）恰好贡献一次，归入其日期所在的期间。}
\end{proof}
\bi{Conversely, while B1 and B2 hold, every data-only update that makes the generated SQL count an event twice or drop facts beyond the recorded fraction violates a condition. The conditions cannot see changes to the values themselves, such as a rescaled measure column, or tell apart two complete copies of the data, such as a table and an appended backup, which both satisfy the grain.}
{反过来，只要 B1、B2 成立，凡是使生成的 SQL 把一个事件计数两次、或排除超过记录比例的事实的纯数据更新，都会违反某个条件。条件看不到取值本身的变化（例如度量列整体换了量纲），也分不清两份完整的数据（例如一张表和追加进来的整份备份），二者都满足粒度。}

\subsection{\bt{Maintenance once for all agents}{为所有智能体一次性维护}}
\label{sec:maintenance}
\bi{\emph{Shared check results.} The version $V(T)$ of a table identifies the state that a check read: either the schema fingerprint, DML counters, and ETL batch identifier, or a \emph{transactional version} that a statement-level trigger increments inside every writing transaction. A check result is keyed by $\bigl(\operatorname{id}(c),V(\operatorname{dep}(c))\bigr)$, so it serves every definition and every agent that needs the same condition on the same table versions. When an agent looks up a definition, \system\ compares the versions recorded for each condition's tables with the current ones, keeps the check results of conditions over unchanged tables, looks up a completed result for each remaining condition at the current versions, and runs $Q_c$ only if none exists; concurrent requests for the same check share that one execution (request coalescing). Joins are checked through shared join entries, so a changed or vanished join path also makes the definition pending. A failed condition invalidates the revision; consumers then learn that the definition is unavailable and explore on their own, and the next successful learning session publishes it again.}
{\emph{共享的检查结果。}表的版本 $V(T)$ 标识检查读到的状态：或者组合结构指纹、DML 计数与 ETL 批次号，或者使用\emph{事务性版本}，由语句级触发器在每个写事务内递增。检查结果以 $\bigl(\operatorname{id}(c),V(\operatorname{dep}(c))\bigr)$ 为键，因此服务于所有在相同表版本上需要同一条件的定义和智能体。智能体查找定义时，\system\ 把每个条件所读各表记录下的版本与当前版本比较：未变化表上的条件保留原有检查结果；对其余条件，查找同一规范化形式在当前版本上的已完成结果，没有才执行 $Q_c$，同一检查的并发请求共享这一次执行（请求合并）。连接通过共享的连接条目检查，因此连接路径被改变或消失时，定义同样变为待验证。条件失败使版本失效；使用者随即得知定义不可用、自行探索，下一次成功的学习会话会重新发布它。}

\bi{\emph{Automatic repair.} Repair handles two cases: a failed fact-table grain, for which it searches equality filters on low-cardinality columns, and a changed join path, whose new filters it adopts. A grain filter must keep exactly one row per business key without losing keys. The fix must also be \emph{unique}: \system\ enumerates every passing filter and repairs only if exactly one exists, because two complete copies of the data, such as a primary table and an appended backup, each pass the structural tests, and nothing structural tells which holds the business truth. A unique fix must then pass the static, grain, and SQL checks and a regression test that runs the replacement and the agent's learning SQL as \emph{as-of queries} (time-travel queries) at learning time and requires equal results: the agent's SQL was verified correct only on that data, and on current data it can itself be stale, counting old versions after a restatement. Warehouses answer as-of queries through time travel; our prototype keeps a copy of the tables taken at publication. Repair searches over the same table and key are shared across definitions, requests that arrive while a repair runs join it instead of being rejected, and a failed repair leaves the definition unavailable until it is relearned.}
{\emph{自动修复。}修复只处理两种情况：事实表粒度失效时，搜索低基数列上的等值过滤；连接路径改变时，采用新路径的过滤。粒度过滤必须使每个业务键恰好保留一行且不丢键。修复还必须是\emph{唯一}的：\system\ 列出全部通过检查的过滤，只有恰好一个时才修复，因为主表与追加的备份副本这样的两份完整数据各自都能通过结构检查，结构上无从判断哪一份承载了业务事实。唯一的修复还要通过静态、粒度与 SQL 检查以及回归测试：把替代版本与智能体的学习 SQL 一起以学习时刻为基准作 \emph{as-of 查询}（时间旅行查询），要求结果相同；智能体的 SQL 只在那时的数据上被判过对，在当前数据上它本身可能已经过期，例如更正保留旧行后会把旧行也算进去。数仓用 time travel 回答 as-of 查询；我们的原型在发布时保留一份表的副本。同一张表、同一个键上的修复搜索在定义之间共享；修复期间到达的请求与进行中的修复合并而不被拒绝；修复失败的定义保持不可用，直到重新学习。}

\subsection{\bt{Checks at query execution}{执行时检查}}
\label{sec:execution}
\bi{\emph{Version checks.} Agents declare the metric keys and revisions a query uses, and \code{run\_sql} checks these references at execution. It rejects absent, inaccessible, and invalidated revisions, including those that a repair replaced, naming the failed condition; it accepts a revision replaced by an optimized revision, with a notice that names the newer revision, after checking the revision's own conditions. The SQL check rejects joins known to fan out and SQL that lacks a filter the grain now requires.}
{\emph{版本校验。}智能体声明查询所用的指标键和版本号，\code{run\_sql} 在执行时核对这些引用。它拒绝不存在、不可访问和已失效的版本（包括被修复所替代的版本），并指明失败的条件；对被优化取代的版本，它先核对该版本自身的条件，然后接受，并附上指明新版本的通知。SQL 检查拒绝已知会放大行数的连接，以及缺少粒度所需过滤的 SQL。}

\bi{\emph{Same-snapshot validation.} A version check ensures that a declared revision was valid when it was last maintained, not that its conditions hold on the data the query reads: a writer may commit in between, and the default version source may not yet show the write. Same-snapshot validation checks the conditions inside the query's own transaction. For a \code{run\_sql} call that declares revisions, \system\ (1) opens a repeatable-read, read-only transaction and reads the transactional versions; (2) collects the conditions of the declared revisions; (3) for each condition, looks up a check result at its normalized form and the snapshot's versions of its tables, and otherwise runs $Q_c$ inside the transaction; (4) rejects the call if any condition fails, which also hands the definition to maintenance; and (5) otherwise executes the business SQL in the same transaction. Reuse in step~(3) rests on the following lemma.}
{\emph{同快照验证。}版本校验只能保证声明的版本在最近一次维护时有效，不能保证其条件在查询读取的数据上成立：两者之间可能有写入提交，而默认版本来源可能还没反映这次写入。同快照验证在查询自己的事务内检查条件。对声明了版本的 \code{run\_sql} 调用，\system{}（1）开启一个可重复读的只读事务并读取事务性版本；（2）收集所声明版本的条件；（3）对每个条件，按其规范化形式及快照中其依赖表的版本查找检查结果，没有就在该事务内执行 $Q_c$；（4）任一条件不成立即拒绝调用，并把定义交给维护；（5）否则在同一事务中执行业务 SQL。第（3）步的复用依据下面的引理。}
\label{sec:snapshot}
\begin{lemma}[\bt{Check-result reuse}{检查结果复用}]
\label{lem:reuse}
\bi{Let $v_s(T)$ be the transactional version of $T$ visible in snapshot $s$. If $v_{s_1}(T)=v_{s_2}(T)$ for every $T\in\operatorname{dep}(c)$, then $c(D_{s_1})=c(D_{s_2})$.}
{设 $v_s(T)$ 为快照 $s$ 中可见的 $T$ 的事务性版本。若对每个 $T\in\operatorname{dep}(c)$ 都有 $v_{s_1}(T)=v_{s_2}(T)$，则 $c(D_{s_1})=c(D_{s_2})$。}
\end{lemma}
\begin{proof}
\bi{PostgreSQL snapshots are nested: the sets of committed transactions they see are totally ordered by inclusion, say $s_1\subseteq s_2$. A transaction that writes $T$ increments $T$'s counter inside the same transaction, so a snapshot sees the write exactly when it sees the increment, and $v_{s_2}(T)-v_{s_1}(T)$ is at least the number of transactions in $s_2\setminus s_1$ that write $T$. Equal versions leave no such transaction, so both snapshots see the same committed state of every table that $Q_c$ reads.}
{PostgreSQL 的快照是嵌套的：它们所见的已提交事务集合按包含关系全序，不妨设 $s_1\subseteq s_2$。写 $T$ 的事务在同一事务内递增 $T$ 的计数，因此一个快照看到这次写入当且仅当它看到这次递增，$v_{s_2}(T)-v_{s_1}(T)$ 不小于 $s_2\setminus s_1$ 中写 $T$ 的事务数。版本相等意味着没有这样的事务，于是两个快照看到 $Q_c$ 所读各表的同一已提交状态。}
\end{proof}
\bi{A check runs as one statement and therefore reads one snapshot $s_c$. Maintenance, which runs outside a same-snapshot transaction, reads the versions in one statement before the check and one after it; by nesting, $s_{\mathrm{before}}\subseteq s_c\subseteq s_{\mathrm{after}}$, so equal versions key the check result at those versions by the lemma, and unequal versions discard it. The lemma needs transactional versions: the default source reports DML statistics asynchronously after commit, so equal values do not imply equal states, which is the gap Section~\ref{sec:enforce-eval} measures. The guarantee covers declared uses: a query that declares a revision runs only on data on which the revision's conditions hold. It does not make undeclared SQL follow a definition.}
{一次检查作为一条语句执行，因而只读一个快照 $s_c$。维护在同快照验证的事务之外运行，它在检查前后各用一条语句读取版本；由嵌套性 $s_{\mathrm{before}}\subseteq s_c\subseteq s_{\mathrm{after}}$，版本相等时由引理可把检查结果按这些版本索引，不相等则丢弃。引理需要事务性版本：默认来源在提交后异步上报 DML 统计，取值相等并不蕴含状态相等，这正是第~\ref{sec:enforce-eval} 节测量的空隙。这一保证覆盖声明了版本的使用：声明某个版本的查询只在该版本条件成立的数据上执行；它不能使未声明的 SQL 遵循定义。}

\subsection{\bt{Optimization once for all agents}{为所有智能体一次性优化}}
\label{sec:optimization}
\bi{A published definition is correct but not necessarily cheap, and because agents copy its generated SQL, a cheaper equivalent speeds up every consumer. After learning, \system\ runs an optimization pass over the valid definitions; candidates are structured definitions, so compilation, the conditions, and Proposition~\ref{prop:sufficiency} apply to them. Two rules propose candidates: \emph{key range} replaces the period join with a range predicate on the fact table's date key, whose bounds scalar subqueries read from the date dimension, and \emph{left-join removal} drops a left join that contributes no column and no filter. Only when no rule candidate is published does an LLM propose candidates from the definition, its generated SQL and plan, and table sizes; a proposal is published only if it coincides with a rule rewrite. A candidate must pass the static, grain, and SQL checks and three tests. \emph{Assumption}: the key-range rule adds date-key contiguity, checked before adoption and maintained afterwards. \emph{Equivalence}: candidate and current revision return equal results for the learning question as of learning time and, within one repeatable-read snapshot, for the twelve months of the learning year, a quarter, a period difference, and a monthly ranking. \emph{Cost}: in the same snapshot, the paired execution times of at least eight periods, measured in alternating order, must have a 95\% confidence interval below zero and a mean saving of at least 10\%.}
{已发布的定义是正确的，但不一定是最省的；由于智能体会照抄它的生成的 SQL，一个更省的等价写法对每个使用者都有收益。学习结束后，\system\ 对有效的定义执行一轮优化；候选都是结构化定义，因此编译、条件和命题~\ref{prop:sufficiency} 都适用于它们。两条规则提出候选：\emph{日期键范围}把期间连接改为事实表日期键上的范围谓词，上下界由标量子查询从日期维度读出；\emph{去掉左连接}去掉一个既不提供列也不带过滤的左连接。只有在没有规则候选发布时，才由大模型根据定义、其生成的 SQL 与执行计划以及表的规模提出候选；提议只有与某个规则改写相同时才发布。候选必须通过静态、粒度和 SQL 检查以及三项测试。\emph{前提}：日期键范围规则新增日期键连续条件，采纳前检查，之后受维护。\emph{等价}：候选与当前版本对学习题按学习时刻返回相同结果，并在一个可重复读快照内对学习年份的 12 个月、一个季度、一次期间差值和一次按月排名返回相同结果。\emph{代价}：在同一快照中，至少 8 个期间以交替顺序测得的配对执行时间差，其 95\% 置信区间必须整体低于 0，平均节省至少 10\%。}
\begin{proposition}[\bt{Rule equivalence}{规则等价}]
\label{prop:rewrite}
\bi{Let the date dimension's key be unique on $D$. (a) If \emph{date-key contiguity} holds on $D$, i.e., the keys of every month form an integer interval that begins one above the previous month's last key, then for every period of consecutive months the generated SQL of a key-range revision returns on $D$ what that of its previous revision returns. (b) If the right side of a removed left join is unique on the join key on $D$, removing the join does not change the result.}
{设日期维度的键在 $D$ 上唯一。（a）若\emph{日期键连续性}在 $D$ 上成立，即每个月的键构成一个整数区间、且从上个月最后一个键加一开始，则对由连续月份组成的每个期间，键区间版本的生成的 SQL 在 $D$ 上返回与其前一版本相同的结果。（b）若被消除的左连接右侧在连接键上唯一，消除该连接不改变结果。}
\end{proposition}
\begin{proof}[\bt{Proof sketch}{证明概要}]
\bi{(a) By contiguity, the keys of a period's months are exactly the integer interval between the bounds, so a fact row's key lies in the interval if and only if it joins one date row of the period. (b) A left join with at most one match keeps each left row once and supplies nothing that is read.}
{（a）由连续性，一个期间各月的键恰好是边界之间的整数区间，因此事实行的键落在区间内当且仅当它连接到该期间的一行日期。（b）至多一个匹配的左连接使每个左侧行恰好保留一次，且不提供任何被读取的内容。}
\end{proof}
\bi{The assumption of (a) is a condition of the new revision; that of (b) is a condition of the previous revision that the new revision no longer needs. Wherever the maintained conditions hold, a rule revision thus agrees with its previous revision on every period, and the sampled tests check the implementation and measure the cost. Maintenance checks an added assumption last; when it alone fails, every condition shared with the previous revision has just been confirmed, and \system\ invalidates the optimized revision and makes its previous revision current again, so an optimization never trades correctness for speed.}
{（a）的前提是新版本的条件；（b）的前提是前一版本的条件，新版本不再需要它。因此，只要受维护的条件成立，规则版本就在每个期间上都与前一版本一致；抽样测试检查的是实现并测量代价。维护最后检查新增的前提；只有它不成立时，与前一版本共有的每个条件都刚刚得到确认，\system\ 使优化后的版本失效，并让前一版本重新成为当前版本，因此优化从不以正确性换取速度。}
