\section{\bt{Admission, Maintenance, and Bounded Repair}{准入、维护与有界修复}}
\label{sec:maintenance}
\subsection{\bt{Admission from successful trajectories}{从成功轨迹准入}}
\bi{Candidates are extracted only from tasks with explicit business evidence and a successful judgment. The extractor sees the question, the SQL and derivation of the answer provenance, rejected queries, and metadata, but no business rows or result values. Deterministic admission checks follow: G1 business basis, G2 the judgment that the answer is correct, G3 static well-formedness (columns exist, the measure uses only permitted columns, joins follow validated paths, and required grain filters are present without question literals), G4 grain on the current snapshot, G5 SQL review, G6 replay of the example SQL, and G7 replay of the canonical SQL compiled from the fields. G7 checks what other agents will actually read, so a candidate that omits a filter or hard-codes a parameter fails it. Learning questions supply admission evidence; held-out questions only measure transfer.}
{只从具备显式业务依据且判题成功的任务中提取候选。提取器能看到题面、答案溯源中的 SQL 与算式、被拦下的查询以及元数据，但看不到业务行和结果值。随后执行确定性的准入检查：G1 业务依据，G2 答案经判定正确，G3 静态合法性（列存在、度量只用允许的列、连接沿已验证路径、包含必需的粒度过滤且不含题目字面量），G4 当前快照上的粒度，G5 SQL 审查，G6 示例 SQL 重放，G7 由字段编译的规范 SQL 重放。G7 检查的是其他智能体实际会读到的内容，因此遗漏过滤或把参数写死的候选会失败。学习题提供准入证据，留出题只用于测量迁移。}

\subsection{\bt{Selective revalidation and reuse}{选择性重验证与复用}}
\bi{On use, maintenance compares the recorded versions of each condition's dependencies with the current versions. Conditions over unchanged tables keep their evidence. For each remaining condition, \system\ looks up a completed check result for the same canonical form at the current versions; otherwise it runs $Q_c$, and concurrent requests for the same check share that execution. Joins are checked through the shared join entries, so a revised or vanished join path also makes the definition pending. The definition-level baseline uses the same conditions, repair, regression, and request coalescing but rechecks the entire condition set of the definition and forces join cardinality checks to rerun.}
{使用时，维护过程把每个条件所依赖表的记录版本与当前版本比较。未变化表上的条件保留原有证据。对其余条件，\system\ 查找同一规范形式在当前版本上的已完成检查结果；否则执行 $Q_c$，对同一检查的并发请求共享这次执行。连接通过共享的连接条目检查，因此连接路径被修订或消失时，定义同样变为待验证。定义级基线使用相同的条件、修复、回归和请求合并，但重查定义的全部条件，并强制重跑连接基数检查。}

\subsection{\bt{Invalidation and bounded repair}{失效与有界修复}}
\bi{A failed condition invalidates the revision and records the reason. Repair is restricted to two cases: a failed fact-table grain, for which it searches equality filters on low-cardinality columns, and a revised join path, whose new filters it adopts. A grain filter must keep exactly one row per business key without losing keys, which rejects, for instance, an application-state filter that restores uniqueness by dropping returns that never had such a row. \system\ further requires the fix to be \emph{unique}: it enumerates every passing filter and repairs only if exactly one exists. Two complete copies of the data, such as a primary table and an appended backup, each satisfy the structural tests, and nothing structural tells which copy holds the business truth; without this rule, the first filter found would be published (Section~\ref{sec:repair-eval}). A unique fix must then pass G3--G5 and the regression test G8, which runs the replacement compiled for the learning question and the agent's learning SQL on the \emph{learning snapshot} and requires equal results. The agent's SQL was judged correct on that snapshot only; on current data it can itself be stale, counting the old versions after a restatement, so a comparison there would reject even the correct fix (Section~\ref{sec:repair-eval}). On the learning snapshot, a fix passes when it leaves the agent's learning answer unchanged. Warehouses keep that snapshot through time travel; our PostgreSQL prototype copies the tables at admission. Repair searches over the same table and key are shared across definitions. A failed repair leaves the definition unavailable until new evidence is learned.}
{条件失败会使修订失效并记录原因。修复只处理两种情况：事实表粒度失效时，搜索低基数列上的等值过滤；连接路径被修订时，采用新路径的过滤。粒度过滤必须使每个业务键恰好保留一行且不丢键，因此会排除诸如申请状态过滤这样的候选：它恢复了唯一性，却丢掉了从未有过申请状态行的退货。\system\ 进一步要求修复是\emph{唯一}的：列出全部通过检查的过滤，只有恰好一个时才修复。主表与追加的备份副本这样的两份完整数据，各自都能通过结构检查，而结构上无从判断哪一份承载了业务事实；没有这条规则，搜索到的第一个过滤就会被发布（第~\ref{sec:repair-eval} 节）。唯一的修复还要通过 G3--G5 与回归测试 G8：把替代修订按学习题编译，与智能体的学习 SQL 一起在\emph{学习时快照}上执行，要求结果相同。智能体的 SQL 只在那个快照上被判过对；在当前数据上它本身可能已经过期，例如多版本更正后会把旧版本也算进去，在那里比较连正确的修复也会被拒绝（第~\ref{sec:repair-eval} 节）。在学习时快照上，修复只要不改变智能体当时的学习答案就能通过。数仓通过 time travel 保留这个快照；我们的 PostgreSQL 原型在准入时复制相关表。同一张表、同一个键上的修复搜索在定义之间共享。修复失败的定义保持不可用，直到学到新的证据。}

\bi{The request that triggers maintenance performs the repair and receives the replacement revision. Other requests that arrive while the repair runs observe an invalidated revision; instead of rejecting them, \system\ coalesces them with the running maintenance and lets them read its outcome, so a successful repair serves them as well.}
{触发维护的请求执行修复并获得替代修订。修复期间到达的其他请求看到的是已失效的修订；\system\ 不拒绝它们，而是把它们与进行中的维护合并，读取其结果，因此修复成功时它们同样得到服务。}
