\section{\bt{Use-Time Enforcement}{使用时的强制保证}}
\label{sec:execution}
\subsection{\bt{Version checks}{版本校验}}
\bi{Agents declare the metric keys and revisions used by a query; the middleware checks those references at execution. It rejects absent, inaccessible, and invalidated revisions, including those that a repair replaced, naming the failed condition; it accepts a revision superseded by an optimization, with a notice that names its successor, after checking the revision's own conditions. SQL review checks the supported grain and join requirements. Explicit rechecking at use makes a definition's maintained state actionable, and invalidation notices reach agents on their next tool response. Canonical compilation supplies the calculation encoded by the recorded fields.}
{智能体声明查询所用的指标键和修订号，中间件在执行时核对这些引用。它拒绝不存在、不可访问和已失效的修订（包括被修复替代的修订），并指明失败的条件；对被优化取代的修订，它先核对该修订自身的条件，然后接受，并附上指明后继修订的通知。SQL 审查检查支持的粒度与连接要求。使用时的显式重查使定义的维护状态直接约束执行，失效通知通过智能体下一次工具响应传达。规范编译提供记录字段所表达的计算。}

\subsection{\bt{Same-snapshot validation}{同快照验证}}
\label{sec:snapshot}
\bi{Version checks ensure that a declared revision was valid when it was last maintained, not that its conditions hold on the data the query reads. Between the two, a writer may commit, and the default version source may not yet show the write. Same-snapshot validation closes this gap. For a \code{run\_sql} call that declares revisions, \system\ (1) opens a repeatable-read, read-only transaction and reads the transactional versions; (2) collects the conditions of the declared revisions; (3) for each condition, looks up a check result at its canonical form and the snapshot's versions of its tables, and otherwise runs $Q_c$ inside the transaction; (4) rejects the call if any condition fails, which also hands the definition to regular maintenance; and (5) otherwise executes the business SQL in the same transaction.}
{版本校验只能保证声明的修订在最近一次维护时有效，不能保证其条件在查询读取的数据上成立。两者之间可能有写入提交，而默认版本来源可能还没反映这次写入。同快照验证填补了这一空隙。对声明了修订的 \code{run\_sql} 调用，\system{}（1）开启一个可重复读的只读事务并读取事务性版本；（2）收集所声明修订的条件；（3）对每个条件，按其规范形式及快照中其依赖表的版本查找检查结果，没有就在该事务内执行 $Q_c$；（4）任一条件不成立即拒绝调用，并把定义交给常规维护；（5）否则在同一事务中执行业务 SQL。}

\bi{Reuse in step~(3) rests on the following property of transactional versions.}
{第（3）步的复用依据事务性版本的如下性质。}
\begin{lemma}[\bt{Check-result reuse}{检查结果复用}]
\label{lem:reuse}
\bi{Let $v_s(T)$ be the transactional version of $T$ visible in snapshot $s$. For two snapshots $s_1,s_2$ and a condition $c$, if $v_{s_1}(T)=v_{s_2}(T)$ for every $T\in\operatorname{dep}(c)$, then $c(D_{s_1})=c(D_{s_2})$.}
{令 $v_s(T)$ 为快照 $s$ 中可见的 $T$ 的事务性版本。对两个快照 $s_1,s_2$ 与条件 $c$，若对每个 $T\in\operatorname{dep}(c)$ 都有 $v_{s_1}(T)=v_{s_2}(T)$，则 $c(D_{s_1})=c(D_{s_2})$。}
\end{lemma}
\begin{proof}
\bi{PostgreSQL snapshots are nested: the sets of committed transactions they see are totally ordered by inclusion, say $s_1\subseteq s_2$. A transaction that writes $T$ increments a shard of $T$'s counter inside the same transaction, so a snapshot sees the write exactly when it sees the increment, and $v_{s_2}(T)-v_{s_1}(T)$ is at least the number of transactions in $s_2\setminus s_1$ that write $T$. Equal versions leave no such transaction, so both snapshots see the same committed state of every table that $Q_c$ reads.}
{PostgreSQL 的快照是嵌套的：各快照看到的已提交事务集合在包含关系下全序，不妨设 $s_1\subseteq s_2$。写 $T$ 的事务在同一事务内增加 $T$ 计数器的某个分片，因此快照看到该写入当且仅当看到这次增加，$v_{s_2}(T)-v_{s_1}(T)$ 不小于 $s_2\setminus s_1$ 中写 $T$ 的事务数。版本相等意味着没有这样的事务，于是两个快照看到的 $Q_c$ 所读每张表的已提交状态完全相同。}
\end{proof}
\bi{A check runs as one statement and therefore reads one snapshot $s_c$. Maintenance, which runs outside a same-snapshot transaction, reads the versions in a statement before and one after the check; by nesting, $s_{\mathrm{before}}\subseteq s_c\subseteq s_{\mathrm{after}}$, so equal versions key the check result at those versions by the lemma, and unequal versions discard it. The lemma needs transactional versions: the default source reports DML statistics asynchronously after commit, so equal values do not imply equal states, which is the gap Section~\ref{sec:enforce-eval} measures. Concurrent identical checks at the same versions run once and are shared. The cost is a counter update per writing statement, which Section~\ref{sec:enforce-eval} also measures.}
{一次检查作为一条语句执行，因而只读一个快照 $s_c$。维护在同快照验证的事务之外运行，它在检查前后各用一条语句读取版本；由嵌套性 $s_{\mathrm{before}}\subseteq s_c\subseteq s_{\mathrm{after}}$，版本相等时由引理可把检查结果按这些版本索引，不相等则丢弃。引理需要事务性版本：默认来源在提交后异步上报 DML 统计，取值相等并不蕴含状态相等，这正是第~\ref{sec:enforce-eval} 节测量的空隙。相同版本上的相同检查并发到达时只执行一次并共享结果。代价是每条写语句多一次计数更新，第~\ref{sec:enforce-eval} 节同样测量了它。}

\subsection{\bt{Scope of the guarantee}{保证的范围}}
\bi{The guarantee covers declared uses: a query that declares a revision runs only on data on which the revision's conditions hold. It does not make undeclared SQL follow a definition, and it does not certify that an agent's own SQL matches the canonical calculation; SQL review checks the supported grain and join requirements, and canonical compilation supplies the calculation for agents that use it. Section~\ref{sec:scenarios} reports how often agents declare definitions and follow them.}
{这一保证覆盖声明了修订的使用：声明某个修订的查询只在该修订条件成立的数据上执行。它不能使未声明的 SQL 遵循定义，也不能证明智能体自己写的 SQL 与规范计算一致；SQL 审查检查支持的粒度与连接要求，规范编译为使用它的智能体提供计算。第~\ref{sec:scenarios} 节报告智能体声明并遵循定义的频率。}
