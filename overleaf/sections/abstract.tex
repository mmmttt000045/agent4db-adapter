\begin{abstract}
\bi{Data agents learn how to compute business metrics by exploring a database, and what one agent learns in a task is increasingly kept as shared knowledge that later sessions reuse. A shared definition can stay meaningful indefinitely, but its SQL implementation is valid only while data properties that the SQL does not state still hold: a filtered key identifying one business record, joins not fanning out, and dates assigning facts to their period. Routine data-only updates break these properties without any schema change, and the agents that reuse the definition never saw its evidence and cannot tell from a successful execution that the shared SQL now returns wrong aggregates. The database therefore has to carry the validity of what agents learned about it. We present \system, a middleware that keeps the validity evidence of shared metric definitions as explicit, versioned state and binds every declared use to evidence that holds on the data the query reads. \system\ records the evidence as executable conditions derived from each definition, for grain, join multiplicity, time role, and date coverage, and proves that under the definition's business premises they suffice for the canonical SQL to count each business event once in its period, up to the omissions that the coverage condition bounds. It maintains the evidence by keying verdicts to dependency versions and sharing them across definitions and agents, rechecking only the conditions an update touches. It constrains use by running a query that declares a definition on a snapshot on which the conditions hold, reusing verdicts only when transactional versions match. When evidence fails, it publishes a replacement only if it is the unique structural fix and passes regression, and withdraws the definition otherwise. We evaluate \system\ on \RpLibs\ definition libraries learned by three LLMs, on a library derived from the TPC-DS query templates, and end to end with agents facing data changes. Under modeled breaking changes, agents with maintained definitions answer \DsCondModeled\% of questions correctly, against \DsTrajModeled\% with matched trajectory retrieval and \DsTrajVerifyModeled\% when those agents are told to verify validity themselves. Under concurrent writes, checking before execution answers on condition-violating data in up to \SnPreUnannMax\% of uses; snapshot-bound execution never does, at the same reader latency. \system\ also reduces client-agent effort: in a fixed-library session study, agents complete tasks in \SlCondMean\ instead of \SlNoneMean\,s with \SlCondInputSaveNone\% fewer input tokens than agents that explore without shared definitions, and at equal accuracy shared knowledge removes a quarter of the schema lookups and 70\% of the SQL probes per task. With 19 shared definitions, condition-level maintenance costs \CbStagCondSix\% of definition-level revalidation.}
{数据智能体通过探索数据库学会如何计算业务指标，一个智能体在一次任务中学到的内容，正越来越多地作为共享知识保存下来，供之后的会话复用。共享定义的业务含义可以长期不变，但它的 SQL 实现只在一些 SQL 本身没有写明的数据性质成立时才有效：过滤后的键对应一条业务记录，连接不放大行数，日期把事实归入其期间。日常的纯数据更新可以在不改任何表结构的情况下破坏这些性质，而复用该定义的智能体从未见过它的证据，也无法从一次成功的执行中看出共享 SQL 已经返回错误的汇总值。因此数据库必须替智能体记住它们学到的东西为什么成立。本文提出 \system，一个把共享指标定义的有效性证据作为显式、版本化状态来维护，并把每一次声明了定义的使用绑定到在查询所读数据上成立的证据的中间层。\system\ 把证据记录为从每个定义推出的可执行条件，涵盖粒度、连接多重性、时间角色和日期覆盖，并证明在定义的业务前提下，这些条件足以让规范 SQL 把每个业务事件在其期间内恰好计数一次，遗漏仅限于覆盖条件所约束的部分。它按依赖版本索引条件结论并在定义与智能体之间共享，更新后只重查被触及的条件，以此维护证据。它让声明了定义的查询在条件成立的快照上执行，且只在事务性版本一致时复用结论，以此约束使用。证据失效时，只有当替代修订是唯一的结构性修复并通过回归测试时才发布，否则撤下该定义。我们在 3 个大模型学到的 \RpLibs\ 个定义库、从 TPC-DS 查询模板导出的定义库，以及智能体面对数据变化的端到端任务上评估 \system。在已建模的破坏性变化下，使用维护后定义的智能体答对 \DsCondModeled\% 的问题，匹配的轨迹检索基线为 \DsTrajModeled\%，让这些智能体自行核验有效性后为 \DsTrajVerifyModeled\%。存在并发写入时，执行前检查会让最多 \SnPreUnannMax\% 的使用在违反条件的数据上作答，绑定快照的执行一次也没有，读者延迟不变。\system\ 还降低用户端智能体的任务开销：在固定定义库的会话实验中，相比没有共享定义、独立探索的智能体，任务完成时间从 \SlNoneMean\ 秒降至 \SlCondMean\ 秒，输入 token 少 \SlCondInputSaveNone\%；在正确率相同的情况下，共享知识省去每题四分之一的结构查找和 70\% 的 SQL 探查。19 个定义共享条件时，条件级维护耗时为定义级重验证的 \CbStagCondSix\%。}
\end{abstract}
