\begin{abstract}
\bi{Data agents that work on the same database rediscover the same knowledge in every session: which fact rows a business metric aggregates, which records count as one business event, and how tables join. A shared memory lets later agents skip this exploration, but one agent's success does not make its knowledge something others can depend on: the knowledge carries assumptions of the task that produced it, its SQL stays correct only while unstated data properties hold, and the agents that reuse it cannot tell from a successful execution that a routine update has broken it. We present \system, a maintainable shared memory layer between data agents and a SQL database. \system\ keeps metric definitions, with their grain and join paths, as versioned revisions that carry executable validity conditions derived from their structure, and takes over three responsibilities that no consumer should carry alone. It \emph{publishes} a revision only after admission checks that replay the SQL other agents will read; it lets a use \emph{rely} on a revision only on a snapshot on which the revision's conditions hold; and it \emph{maintains and improves} revisions once for all consumers, through condition-level revalidation, repair by the unique fix that reproduces the learned answer as of learning time, and cheaper rewrites whose added premises it maintains. We prove that the conditions suffice for the canonical SQL to count each business event once in its period, up to omissions that completeness bounds, and that the conditions a rewrite rule adds imply its equivalence. End to end, sharing raises accuracy on held-out questions from \DsNoShareHoldout\% to \DsCondHoldout\%, as retrieved examples also do, and makes these tasks \AmHoldSpeedup$\times$ faster; under the breaking changes that the conditions cover, maintained memory keeps \DsCondModeled\% of answers correct, against \DsTrajModeled\% for matched example retrieval and \DsTrajVerifyModeled\% when those agents verify validity themselves. Under concurrent writes, same-snapshot use never answers on condition-violating data, whereas check-then-execute does in up to \SnPreUnannMax\% of uses.}
{在同一数据库上工作的数据智能体，每个会话都在重新获取同样的知识：一个业务指标聚合哪些事实行，哪些记录算作一次业务事件，表之间如何连接。共享记忆让后来的智能体省去这些探索；但一个智能体的成功，并不使它的知识成为其他智能体可以依赖的知识：知识带有产生它的任务的假设，它的 SQL 只在一些未写明的数据性质成立时才正确，而复用它的智能体无法从一次成功的执行中看出一次日常更新已经破坏了它。本文提出 \system，一个位于数据智能体与 SQL 数据库之间的可维护共享记忆层。\system\ 把指标定义及其粒度与连接路径保存为版本化的修订，每个修订带有从其结构推出的可执行有效性条件，并承担不应由每个使用者各自承担的三项职责。它只在准入检查重放其他智能体将要读到的 SQL 之后才\emph{发布}修订；只允许一次使用在修订条件成立的快照上\emph{依赖}该修订；并为所有使用者一次性地\emph{维护和改进}修订：条件级重验证、只用按学习时刻复现所学答案的唯一修复来修复，以及采纳新增前提受到维护的更省改写。我们证明，这些条件足以让规范 SQL 把每个业务事件在其期间内计数一次，遗漏仅限于完整性所约束的部分，并证明改写规则新增的条件蕴含改写的等价。端到端实验中，共享把留出题正确率从 \DsNoShareHoldout\% 提高到 \DsCondHoldout\%（检索示例同样做到），并使这些任务快 \AmHoldSpeedup\ 倍；在条件覆盖的破坏性变化下，维护后的记忆保持 \DsCondModeled\% 的答案正确，匹配的示例检索为 \DsTrajModeled\%，让这些智能体自行核验有效性后为 \DsTrajVerifyModeled\%。存在并发写入时，同快照使用从不在违反条件的数据上作答，先检查后执行则在最多 \SnPreUnannMax\% 的使用中如此。}
\end{abstract}
