\begin{abstract}
\bi{Data agents that work on the same database rediscover the same knowledge in every session: which fact rows a business metric aggregates, which records count as one business event, and how tables join. A shared memory lets later agents skip this exploration, but knowledge that one agent learned stays correct only while unstated data properties hold, and the agents that reuse it cannot tell when a routine update has broken it. We present \system, a maintainable shared memory layer between data agents and a SQL database. \system\ keeps metric definitions as versioned revisions with executable validity conditions derived from their structure, which we prove sufficient for the canonical SQL to count each business event once in its period. It \emph{publishes} a revision only after admission checks replay the SQL that other agents will read, lets a use \emph{rely} on a revision only on a snapshot on which its conditions hold, and \emph{maintains and improves} revisions once for all consumers, through condition-level revalidation, repair by the unique fix that reproduces the learned answer as of learning time, and rewrites whose equivalence the maintained conditions imply. Replayed on fixed libraries over TPC-DS and three schemas not written for this paper, including a real bank database, maintained definitions serve no wrong answer under the changes their conditions cover. End to end, sharing raises accuracy on held-out questions from \DsNoShareHoldout\% to \DsCondHoldout\% and makes these tasks \AmHoldSpeedup$\times$ faster; under the breaking changes that the conditions cover, maintained memory keeps \DsCondModeled\% of answers correct, against \DsTrajModeled\% for matched example retrieval. Under concurrent writes, same-snapshot use never answers on condition-violating data, whereas check-then-execute does in up to \SnPreUnannMax\% of uses, and through a lifecycle of accumulating updates one library keeps \LcAccCond\% of answers correct, against \LcAccTraj\% for example retrieval and \LcAccNone\% without memory.}
{在同一数据库上工作的数据智能体，每个会话都在重新获取同样的知识：一个业务指标聚合哪些事实行，哪些记录算作一次业务事件，表之间如何连接。共享记忆让后来的智能体省去这些探索；但一个智能体学到的知识只在一些未写明的数据性质成立时才正确，复用它的智能体也无法察觉一次日常更新已经破坏了它。本文提出 \system，一个位于数据智能体与 SQL 数据库之间的可维护共享记忆层。\system\ 把指标定义保存为版本化的修订，每个修订带有从其结构推出的可执行有效性条件，我们证明这些条件足以让规范 SQL 把每个业务事件在其期间内只计数一次。它只在准入检查重放其他智能体将要读到的 SQL 之后才\emph{发布}修订；只允许一次使用在修订条件成立的快照上\emph{依赖}该修订；并为所有使用者一次性地\emph{维护和改进}修订：条件级重验证，只用按学习时刻复现所学答案的唯一修复来修复，只采纳受维护条件蕴含其等价的改写。在 TPC-DS 与另外三种不是为本文编写的模式（包括一家银行的真实数据库）上回放固定的定义库，维护后的定义在其条件覆盖的变化下不给出错误答案。端到端实验中，共享把留出题正确率从 \DsNoShareHoldout\% 提高到 \DsCondHoldout\%，并使这些任务快 \AmHoldSpeedup\ 倍；在条件覆盖的破坏性变化下，维护后的记忆保持 \DsCondModeled\% 的答案正确，匹配的示例检索为 \DsTrajModeled\%。存在并发写入时，同快照使用从不在违反条件的数据上作答，先检查后执行则在最多 \SnPreUnannMax\% 的使用中如此；在更新不断累积的生命周期中，一个定义库保持 \LcAccCond\% 的答案正确，示例检索为 \LcAccTraj\%，无记忆为 \LcAccNone\%。}
\end{abstract}
