\begin{abstract}
\bi{Data agents that work on the same database rediscover the same knowledge in every session: which fact rows a business metric aggregates, which records count as one business event, and how tables join. A shared memory that keeps what one agent learned lets later agents skip this exploration, but one agent's success does not make its knowledge something others can depend on: the knowledge may carry assumptions of the task that produced it, its SQL stays correct only while data properties that it does not state still hold, and the agents that reuse it never saw its evidence and cannot tell from a successful execution that a routine data update has broken it. We present \system, a maintainable shared memory layer between data agents and a SQL database. \system\ keeps database knowledge, centered on metric definitions with their grain and join paths, as versioned revisions that carry executable validity conditions derived from their implementation, and it takes over three responsibilities that consumers cannot carry. It \emph{publishes} a revision only after admission checks that separate the definition from the question and replay the SQL that other agents will read. It lets a use \emph{rely} on a revision only on a snapshot on which the revision's conditions hold, reusing check results only when transactional versions match. It \emph{maintains and improves} revisions once for all consumers: check results are shared across definitions and agents, a broken revision is replaced only by the unique structural fix that reproduces the learned answer as of learning time, and a valid revision is replaced by an equivalent, cheaper one whose added premises become maintained conditions. We prove that, under a definition's business premises, its conditions suffice for the canonical SQL to count each business event once in its period, up to the omissions that the completeness condition bounds. End to end, shared definitions raise agents' accuracy on held-out questions from \DsNoShareHoldout\% to \DsCondHoldout\%, in \ScenHoldTurnsCondModelA\ instead of \ScenHoldTurnsNoShareModelA\ turns. Under the breaking data changes that the conditions cover, maintained memory keeps \DsCondModeled\% of answers correct, against \DsTrajModeled\% for matched example retrieval and \DsTrajVerifyModeled\% when those agents verify validity themselves; under concurrent writes, same-snapshot use never answers on condition-violating data, whereas check-then-execute does in up to \SnPreUnannMax\% of uses. One optimization round published faster revisions for \OptPublished\ of \OptDefs\ learned definitions, \OptSaveMin--\OptSaveMax\% faster on one million rows and equivalent on \OptPeriods\ periods each, and later agents adopted them.}
{在同一数据库上工作的数据智能体，每个会话都在重新获取同样的知识：一个业务指标聚合哪些事实行，哪些记录算作一次业务事件，表之间如何连接。把一个智能体学到的东西保存在共享记忆中，后来的智能体就可以省去这些探索；但一个智能体的成功，并不使它的知识成为其他智能体可以依赖的知识：知识可能带有产生它的那个任务的假设，它的 SQL 只在一些未写明的数据性质成立时才正确，而复用它的智能体从未见过它的证据，也无法从一次成功的执行中看出一次日常的数据更新已经破坏了它。本文提出 \system，一个位于数据智能体与 SQL 数据库之间的可维护共享记忆层。\system\ 把以指标定义及其粒度与连接路径为核心的数据库知识保存为版本化的修订，每个修订带有从其实现推出的可执行有效性条件，并承担使用者自己无法承担的三项职责。它只在准入检查把定义与题目分开、并重放其他智能体将要读到的 SQL 之后才\emph{发布}修订。它只允许一次使用在修订条件成立的快照上\emph{依赖}该修订，且只在事务性版本一致时复用检查结果。它为所有使用者一次性地\emph{维护并改进}修订：检查结果在定义与智能体之间共享；被破坏的修订只由唯一的、按学习时刻复现所学答案的结构性修复替代；仍然有效的修订可由等价且更省的修订替代，后者新增的前提成为受维护的条件。我们证明，在定义的业务前提下，这些条件足以让规范 SQL 把每个业务事件在其期间内计数一次，遗漏仅限于完整性条件所约束的部分。端到端实验中，共享定义把智能体在留出题上的正确率从 \DsNoShareHoldout\% 提高到 \DsCondHoldout\%，每题轮数从 \ScenHoldTurnsNoShareModelA\ 降至 \ScenHoldTurnsCondModelA{}。在条件覆盖的破坏性数据变化下，维护后的记忆保持 \DsCondModeled\% 的答案正确，匹配的示例检索基线为 \DsTrajModeled\%，让这些智能体自行核验有效性后为 \DsTrajVerifyModeled\%；存在并发写入时，同快照使用从不在违反条件的数据上作答，先检查后执行则在最多 \SnPreUnannMax\% 的使用中如此。一轮优化为 \OptDefs\ 条学到的定义中的 \OptPublished\ 条发布了更快的修订：在 100 万行数据上快 \OptSaveMin\%--\OptSaveMax\%，每条在 \OptPeriods\ 个期间上结果一致，之后的智能体也采用了它们。}
\end{abstract}
