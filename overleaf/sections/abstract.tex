\begin{abstract}
\bi{LLM data agents learn what business metrics mean by exploring a database. Sharing the learned metric definitions across agents makes answers more accurate and consistent, but it turns each definition into long-lived state over a changing database. A definition's SQL is correct only while data properties that the SQL does not state still hold: a filtered key identifies one business record, joins do not fan out, and dates assign facts to the intended period. Data-only updates break these properties without any schema change; the shared query keeps running and silently returns wrong aggregates. We present \system, a middleware that maintains the validity of shared metric definitions and enforces it where they are used. \system\ derives typed executable conditions from each learned definition, keys their verdicts by dependency versions, and admits a query that declares a definition only if the definition's conditions hold on the snapshot on which the query runs. It repairs a broken definition only with a filter that is the unique structural fix and passes regression, and otherwise withdraws the definition. Replaying \RpLibs\ definition libraries learned by three LLMs under \RpChanges\ data changes, maintained definitions never serve a wrong answer under the modeled changes, whereas schema-only maintenance serves \RpSchemaWrongModeled. Under concurrent writers, checking before execution answers on condition-violating data in up to \SnPreUnannMax\% of uses; snapshot-bound execution does so in none of \SnSnapAnswered\ uses at the same reader latency. Repair is safe but depends on its reference: with the agent's own learning query as reference, \RpRefDiff\ points of answers become unavailable instead of repaired, and none becomes wrong. Maintenance follows the distinct conditions an update touches; with 19 shared definitions it costs \CbStagCondSix--\CbStagCacheSix\% of definition-level revalidation, whether verdicts are keyed by typed conditions or by check SQL in a generic version-keyed cache. End to end, maintained sharing raises agent accuracy from \ScenAccNoShare\% to \ScenAccCond\%.}
{大语言模型数据智能体通过探索数据库学到业务指标的含义。在智能体之间共享学到的指标定义，能让答案更准确、口径更一致，但也使每个定义成为变化数据库上的长期状态。定义的 SQL 只在一些 SQL 本身没有写明的数据性质成立时才正确：过滤后的键对应一条业务记录，连接不放大行数，日期把事实归入预期的期间。纯数据更新可以在不改任何表结构的情况下破坏这些性质；共享查询照常执行，却静默返回错误的汇总值。本文提出 \system，一个维护共享指标定义的有效性、并在使用处强制这种有效性的中间层。\system\ 从每个学到的定义推出类型化的可执行条件，按依赖版本索引条件结论；声明使用某个定义的查询，只有在该定义的条件于查询执行所在的快照上成立时才被放行。它只用“结构上唯一、且通过回归测试”的过滤修复失效定义，否则撤下该定义。把 3 个大模型学到的 \RpLibs\ 个定义库在 \RpChanges\ 种数据变化下回放：在已建模的变化下，维护后的定义从不给出错误答案，而只看结构的维护给出了 \RpSchemaWrongModeled\ 个错误答案。存在并发写入时，执行前检查会让最多 \SnPreUnannMax\% 的使用在违反条件的数据上作答；绑定快照的执行在 \SnSnapAnswered\ 次使用中一次也没有，读者延迟不变。修复是安全的，但取决于其参照：以智能体自己的学习查询为参照时，有 \RpRefDiff\ 个百分点的答案变为不可用而不是被修复，没有一个变为错误。维护工作沿更新触及的不同条件展开；19 个定义共享条件时，耗时为定义级重验证的 \CbStagCondSix--\CbStagCacheSix\%，无论结论按类型化条件还是按检查 SQL 在通用版本缓存中索引。端到端实验中，维护后的共享把智能体正确率从 \ScenAccNoShare\% 提高到 \ScenAccCond\%。}
\end{abstract}
