\subsection{\bt{Shared Maintenance and Optimization Overhead (Q4)}{共享维护与优化开销（Q4）}}
\label{sec:cost}
\label{sec:opt-eval}
\bi{Sharing validation and repair reduces maintenance work across agents and definitions, while one accepted optimization speeds up every consumer. We measure these benefits separately through the population restatement, controlled rechecking workloads, and query-optimization tests.}
{共享验证与修复减少了跨智能体、跨定义的维护工作，一次被采纳的优化也让所有使用者受益。下面分别通过群体更正实验、受控重查负载与查询优化测试测量这些收益。}
\bi{\emph{Shared repair.} The population restatement illustrates why repair belongs in the shared layer. Repairing each affected definition once takes \PpMavraMaintS\,s of database time per run, whereas repairing private copies takes \PpPrivateMaintS\,s. In the end-to-end study, maintenance takes \AmMaintBenignS\,s per non-breaking update and \AmMaintRepairS\,s per repaired change. Other strategies pay at different points: prompted verification adds \AmVerifyExtraS\,s and \AmVerifyExtraTokK\,k tokens to each question even on unchanged data, because each agent rechecks grain, joins, and dates; write-triggered relearning uses \ScenRelearnTok\,M tokens per run to rebuild revoked definitions.}
{\emph{共享修复。}群体更正实验说明了把修复放在共享层的收益。每个受影响定义只修复一次，每次运行需要 \PpMavraMaintS\ 秒数据库时间；逐个修复私有副本则需要 \PpPrivateMaintS\ 秒。端到端实验中，每次正常更新的维护需 \AmMaintBenignS\ 秒，每次修复变化需 \AmMaintRepairS\ 秒。其他策略在不同环节付出代价：提示核验让每个智能体重新检查粒度、连接与日期，即使数据不变也每题增加 \AmVerifyExtraS\ 秒和 \AmVerifyExtraTokK\,k token；写入即重学则每次运行花费 \ScenRelearnTok\,M token，重新建立被撤销的定义。}

\bi{\emph{Sharing checks across definitions.} Many definitions depend on the same structural facts. Grouping the aggregates of each SELECT block by fact table yields \TpDefs\ definitions from \TpQueries\ of the \TpTemplates\ TPC-DS templates. A write to \code{store\_sales} affects \TpSalesDefs\ definitions but only \TpSalesConds\ distinct conditions. We reproduce this overlap in a controlled workload with four definition families. After each of four updates, eight scripted agents use all definitions, with library size ranging from 4 to 19.}
{\emph{跨定义共享检查。}许多定义依赖相同的结构事实。将每个 SELECT 块的聚合按事实表归组，可以从 \TpTemplates\ 个 TPC-DS 模板中的 \TpQueries\ 个导出 \TpDefs\ 个定义。一次 \code{store\_sales} 写入会影响 \TpSalesDefs\ 个定义，却只涉及 \TpSalesConds\ 个不同条件。受控负载用四个定义族重现这种重叠：定义库规模从 4 增至 19，每次更新后，八个脚本智能体使用全部定义，共进行四次更新。}

\bi{As the library grows, Definition-Level Maintenance rises from \CbStagDefOne\ to \CbStagDefSix\,s, while \system\ remains within \CbCondStagMin--\CbCondStagMax\,s. At 19 definitions, it takes \CbStagCondSix\% of full-recheck time. Rechecking only changed tables without sharing still takes 83--94\%, showing that avoiding unchanged tables accounts for only part of the saving. When definitions share no conditions, all methods take \CbZeroMin--\CbZeroMax\% of full-recheck time. The benefit also persists at larger scales: the ratio is \CbFourStagCond\% with four million rows, \CbAgentsStagCond\% with 32 agents, and \EoneRatioSixteen--\EoneRatioFour\% in tests extending to sixteen million rows.}
{定义库增大时，整定义重查耗时从 \CbStagDefOne\ 增至 \CbStagDefSix\ 秒，\system\ 则保持在 \CbCondStagMin--\CbCondStagMax\ 秒。19 个定义时，它只需整定义重查耗时的 \CbStagCondSix\%。仅重查变化的表而不共享结果，仍需 83--94\%，说明跳过未变化的表只解释了部分节省。定义之间没有共享条件时，各方法均需整定义重查耗时的 \CbZeroMin--\CbZeroMax\%。扩大规模后仍有收益：四百万行时该比例为 \CbFourStagCond\%，32 个智能体时为 \CbAgentsStagCond\%，扩展至一千六百万行的测试中为 \EoneRatioSixteen--\EoneRatioFour\%。}

\bi{\emph{Sharing optimized queries.} On the one-million-row retail workload, \OptPublished\ of \OptDefs\ learned definitions receive a key-range revision. These revisions reduce query execution time by \OptSaveMin--\OptSaveMax\%, with a mean reduction of \OptSaveMean\%; every 95\% interval for the time difference lies below zero. Each revision returns the same results as its predecessor on \OptPeriods\ periods. Agents benefit through ordinary retrieval: \OptHoldAdopted\ of \OptHoldTasks\ held-out queries use the faster SQL.}
{\emph{共享优化后的查询。}在一百万行零售负载上，\OptDefs\ 个学得定义中的 \OptPublished\ 个获得了键区间版本。这些版本使查询耗时减少 \OptSaveMin--\OptSaveMax\%，平均减少 \OptSaveMean\%；耗时差的每个 95\% 区间都低于零。每个版本在 \OptPeriods\ 个期间上均与前一版本返回相同结果。智能体通过正常检索就能获得收益：\OptHoldTasks\ 条留出查询中有 \OptHoldAdopted\ 条使用了更快的 SQL。}

\bi{We also test what happens when an optimization's assumption stops holding. A separate system test optimizes \PbDefs\ definitions---store revenue, return amount, return rate, and electronics revenue---then re-keys one month of the date dimension so that only date-key contiguity fails. Maintenance withdraws all \PbDefs\ key-range revisions and restores their predecessors, with a maximum restoration time of \PbFallbackSMax\,s per definition. All \PbAnswers\ answers served afterwards are correct; continuing to use the optimized SQL would have produced errors of up to \PbStaleErrMax\%.}
{我们还检验优化前提失效后的行为。一项独立系统测试优化了 \PbDefs\ 个定义，分别为门店营业额、退货金额、退货率和电子品类营业额；随后对日期维度的一个月重新编键，使只有日期键连续性失效。维护撤下全部 \PbDefs\ 个键区间版本，恢复前一版本的单定义最长耗时为 \PbFallbackSMax\ 秒。之后提供的 \PbAnswers\ 个答案全部正确；若继续执行优化后的 SQL，误差会高达 \PbStaleErrMax\%。}
