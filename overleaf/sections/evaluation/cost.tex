\subsection{\bt{The cost of sharing, paid once}{共享的代价只付一次}}
\label{sec:cost}
\label{sec:opt-eval}
\bi{\emph{Maintenance once, not per agent (Q3).} Sharing would lose its saving if every agent had to keep its knowledge valid by itself. In the population study, the restatement breaks the definitions that read store sales; \system\ repairs each of them once for all agents, with \PpMavraMaintS\,s of database time per run, whereas single-agent memory repairs every agent's copy separately and spends \PpPrivateMaintS\,s. End to end, \system\ spends \AmMaintBenignS\,s of database time per non-breaking update and \AmMaintRepairS\,s per repaired change. The alternatives move this cost to the agents: an agent told to verify the grain, joins, and date keys of the shared SQL it reads spends \AmVerifyExtraS\,s and \AmVerifyExtraTokK\,k tokens more per question even on unchanged data, and dropping shared knowledge on every write costs \ScenRelearnTok\,M tokens of relearning per run.}
{\emph{维护只做一次，而不是每个智能体一次（Q3）。}如果每个智能体都得自己让知识保持有效，共享就会失去它省下的代价。在群体实验中，更正破坏了读取门店销售的定义；\system\ 为所有智能体对每个定义只修复一次，每次运行用 \PpMavraMaintS\ 秒数据库时间；单智能体记忆则要分别修复每个智能体手中的副本，用 \PpPrivateMaintS\ 秒。端到端实验中，\system\ 每次正常更新用 \AmMaintBenignS\ 秒数据库时间，每次需要修复的变化用 \AmMaintRepairS\ 秒。替代做法把这份代价转给智能体：被要求自己核对所读共享 SQL 的粒度、连接与日期键的智能体，即使数据不变，每题也多花 \AmVerifyExtraS\ 秒和 \AmVerifyExtraTokK\,k token；每次写入就丢弃共享知识，则每次运行要为重新学习花 \ScenRelearnTok\,M token。}

\bi{\emph{Shared check results.} Definitions share conditions, so the check results that \system\ keys by condition and table versions serve many definitions: an update of \code{store\_sales} touches \TpSalesDefs\ of the \TpDefs\ definitions derived from the TPC-DS templates but only \TpSalesConds\ distinct conditions. A controlled benchmark publishes 4 to 19 definitions in four families and lets eight scripted agents use all of them after each of four updates. Against a full recheck per definition, whose database time grows with the number of definitions (\CbStagDefOne\ to \CbStagDefSix\,s): \system\ stays at \CbCondStagMin--\CbCondStagMax\,s and needs \CbStagCondSix\% of the full recheck's time at 19 definitions, while rechecking changed tables only, without reuse, needs 83--94\%. Without shared conditions all methods cost \CbZeroMin--\CbZeroMax\% of the full recheck, so the saving comes from sharing alone, and it holds at 4 million rows (\CbFourStagCond\%), with 32 agents (\CbAgentsStagCond\%), and up to 16 million rows (\EoneRatioSixteen--\EoneRatioFour\%).}
{\emph{共享的检查结果。}定义之间共享条件，因此 \system\ 按条件与表版本索引的检查结果能服务多个定义：更新 \code{store\_sales} 会触及从 TPC-DS 模板导出的 \TpDefs\ 个定义中的 \TpSalesDefs\ 个，但不同的条件只有 \TpSalesConds\ 个。一个受控实验在四个族中发布 4 到 19 个定义，四次更新之后各让 8 个脚本智能体使用全部定义。与整定义重查相比（其耗时随定义数增长，\CbStagDefOne\ 到 \CbStagDefSix\ 秒），\system\ 保持在 \CbCondStagMin--\CbCondStagMax\ 秒，19 个定义时只需整定义重查的 \CbStagCondSix\%；只重查变化的表而不复用结果需要 83--94\%。没有共享条件时各方法都需要整定义重查的 \CbZeroMin--\CbZeroMax\%，因此节省只来自共享；这一比例在 400 万行（\CbFourStagCond\%）、32 个智能体（\CbAgentsStagCond\%）以及直到 1600 万行（\EoneRatioSixteen--\EoneRatioFour\%）时保持不变。}

\bi{\emph{One optimization speeds up every agent.} We evaluate an optimization pass over the \OptDefs\ learned definitions on the one-million-row retail workload. \OptPublished\ of the \OptDefs\ published definitions received a key-range revision that reduced query execution time by \OptSaveMin--\OptSaveMax\% relative to the previous revision (mean \OptSaveMean\%, every 95\% interval below zero), with equal results on \OptPeriods\ periods each, and \OptHoldAdopted\ of the \OptHoldTasks\ held-out queries ran the faster form because agents copy the SQL they retrieve. To break the added assumption, a system-level test re-keys one month of the date dimension so that only date-key contiguity fails: maintenance invalidated all \PbDefs\ key-range revisions and restored their previous revisions within \PbFallbackMsMax\,ms each, and all \PbAnswers\ answers served afterwards are correct, whereas the key-range SQL would have been wrong by up to \PbStaleErrMax\%.}
{\emph{一次优化让每个智能体都更快。}我们在 100 万行销售的零售负载上，针对学得的 \OptDefs\ 个定义评估一轮优化。已发布的 \OptDefs\ 个定义中有 \OptPublished\ 个得到键区间版本，相对前一版本使查询执行耗时减少 \OptSaveMin--\OptSaveMax\%（平均减少 \OptSaveMean\%，每个 95\% 区间都低于零），每个都在 \OptPeriods\ 个期间上结果相同；由于智能体照抄检索到的 SQL，\OptHoldTasks\ 条留出查询中有 \OptHoldAdopted\ 条用了更快的写法。为了破坏新增的前提，一个系统层测试给日期维度的一个月重新编键，使只有日期键连续性失败：维护使全部 \PbDefs\ 个键区间版本失效，并在每个 \PbFallbackMsMax\ 毫秒内恢复其前一版本，之后给出的 \PbAnswers\ 个答案全部正确，而键区间 SQL 的误差会高达 \PbStaleErrMax\%。}
