\subsection{\bt{Data-change scenarios with LLM agents}{大模型智能体的数据变化场景}}
\label{sec:scenarios}
\bi{\emph{Protocol (Q5).} Five metrics, store revenue, store return amount, store return rate, catalog revenue, and electronics store revenue, each have two learning questions and three scored questions: a new period, a period difference, and a monthly ranking. \system's built-in analysis optimizer answers the learning questions with explicit business definitions; the extractor turns judged-successful trajectories into candidates, which pass admission. A user agent that has never seen the metrics answers the scored questions given only metric names, first on unchanged data and then once per data-change scenario. Each scenario starts from the same initial snapshot and shared store, applies one update, re-asks the questions whose metric reads an updated table, and is rolled back. The reference answers reflect the update's business effect, computed before representation changes such as duplicate rows, status rows, backup copies, or old versions are applied; an agent must therefore filter those rows out to answer correctly. Figure~\ref{fig:scenarios} groups the eleven scenarios by the condition they target: the ten earlier scenarios plus the backup copy of Section~\ref{sec:repair-eval}, whose repair is ambiguous; the unit change is a control that no condition covers.}
{\emph{实验流程（Q5）。}5 个指标为门店营业额、门店退货金额、门店退货率、目录渠道营业额和电子品类门店营业额，各有 2 道学习题和 3 道计分题（新期间、跨期差值和按月排名）。\system\ 内置的分析优化器在给出显式业务定义的学习题上作答，提取器把判题成功的轨迹转成候选，经准入后发布。从未接触过这些指标的用户端智能体只拿到指标名，先在未变化的数据上回答计分题，再在每个数据变化场景下各答一次。每个场景都从相同的初始快照和共享知识库出发，施加一次更新，只重问读到被更新表的指标，结束后回滚。标准答案反映更新的业务效果，在施加重复行、状态行、备份副本或旧版本等表示变化之前计算，因此智能体必须过滤掉这些行才能答对。图~\ref{fig:scenarios} 按目标条件对 11 个场景分组：此前的 10 个，加上第~\ref{sec:repair-eval} 节修复有歧义的备份副本；单位变化是任何条件都不覆盖的对照。}

\bi{\emph{Methods and runs.} Besides the methods of Table~\ref{tab:baselines}, we evaluate a matched \emph{trajectory-retrieval} baseline in the spirit of AgentSM~\cite{biswal2026agentsm}: it receives the same learning tasks under the same admission precondition (judged success and a verifiable answer provenance), stores the question, the SQL that produced the answer, and its derivation, and lets the user agent retrieve up to three stored trajectories by question similarity, without validity maintenance. Agent and extractor use DeepSeek V4.1 Flash through the Cline gateway with high reasoning effort, a 20-turn limit, and a 60\,s SQL timeout; each of the nine methods of Table~\ref{tab:baselines} evaluated end to end runs three times, and every run learns its own library. Here \system's G8 compares on current data, as in the ablation of Section~\ref{sec:repair-eval}; the main runs used \system\ (gold SQL), and \system\ and the self-check baseline were added later, with their comparisons against trajectory retrieval and \system\ (gold SQL) fixed in advance. The middleware is the current one, with the uniqueness rule and request coalescing; updates are applied between phases, so same-snapshot validation is not exercised here. Following an analysis plan fixed before the runs, tasks that failed with provider errors are not scored (\ScenQuotaTasks), and the \ScenCellsDropped\ runs that met a provider failure while learning were rerun in full. We analyze \ScenCells\ runs with \ScenValidTasks\ scored tasks; intervals are 95\% bootstrap intervals that resample whole runs.}
{\emph{方法与运行。}除表~\ref{tab:baselines} 中的方法外，我们还评估一个仿照 AgentSM~\cite{biswal2026agentsm} 的匹配\emph{轨迹检索}基线：它获得同样的学习题，入库前提也相同（判题成功、答案溯源可复核），保存题面、产生答案的 SQL 与算式，用户端智能体按题面相似度检索最多 3 条，不做有效性维护。智能体与提取器使用 DeepSeek V4.1 Flash，经 Cline 网关调用，推理强度为 high，每题最多 20 轮，SQL 超时 60 秒；表~\ref{tab:baselines} 中端到端评估的 9 种方法各运行 3 次，每次各自学习自己的定义库。这里 \system\ 的 G8 在当前数据上比较，即第~\ref{sec:repair-eval} 节的消融设置；主实验运行的是 \system（标准答案 SQL），\system\ 与自检基线是之后增补的，它们与轨迹检索、与 \system（标准答案 SQL）的比较事先写定。中间件为当前版本，含唯一性规则与请求合并；更新在阶段之间施加，因此这里不涉及同快照验证。按运行前写定的分析方案，因服务错误失败的题不计分（\ScenQuotaTasks\ 道），学习阶段遇到服务失败的 \ScenCellsDropped\ 次运行整次重跑。我们分析 \ScenCells\ 次运行、\ScenValidTasks\ 道计分题；区间为按运行整体重抽样的 95\% 自助法区间。}

\bi{\emph{Sharing and benign updates.} Without shared knowledge, the user agent answers \DsNoShareAll\% of all questions. Every sharing method transfers what the analysis optimizer learned: on held-out questions, \system\ and trajectory retrieval both answer \DsCondHoldout\% (\DsNoShareHoldout\% without sharing), the outcome expected for unchanged data. After the four benign updates, \system\ keeps \DsCondBenign\%, whereas invalidate-on-write falls to \DsRevokeBenign\% because it discards valid definitions on every write and relearns them (\DsRevokeRevoked\ invalidations per run). Definition-level runs are less accurate on held-out and benign questions (\DsDefHoldout\% and \DsDefBenign\%) although their maintenance is identical to \system's on a fixed library (Section~\ref{sec:validity}); the difference comes from what those runs learned.}
{\emph{共享与正常更新。}没有共享知识时，用户端智能体全部题目答对 \DsNoShareAll\%。各共享方法都能迁移分析优化器学到的内容：留出题上，\system\ 与轨迹检索都答对 \DsCondHoldout\%（不共享为 \DsNoShareHoldout\%），这是数据不变时应有的结果。四种正常更新之后，\system\ 保持 \DsCondBenign\%，写入即失效则降到 \DsRevokeBenign\%，因为它每次写入都丢弃有效定义并重新学习（每次运行失效 \DsRevokeRevoked\ 次）。定义级各次运行在留出题与正常变化上较低（\DsDefHoldout\% 与 \DsDefBenign\%），而在固定的定义库上它的维护与 \system\ 完全相同（第~\ref{sec:validity} 节）；差别来自这些运行学到的内容。}

\bi{\emph{Covered breaking changes.} Here the methods separate (Figure~\ref{fig:groups}). Over the five breaking changes that the conditions cover, \system\ answers \DsCondModeled\% (\DsCondModeledLo--\DsCondModeledHi), trajectory retrieval \DsTrajModeled\%, and definition-level \DsDefModeled\%: \system\ is \DsCmpModeledTraj\ points ahead of trajectory retrieval (95\% interval \DsCmpModeledTrajLo--\DsCmpModeledTrajHi) and \DsCmpModeledDef\ points ahead of definition-level (\DsCmpModeledDefLo--\DsCmpModeledDefHi), the latter again reflecting learning rather than maintenance. Retrieved trajectories carry no validity state: under status-change rows they replay SQL that now counts some returns twice (\ScenAccTrajStatus\% versus \ScenAccCondStatus\% for \system), and under restatements and duplicate loads they reuse SQL written for the old grain (\ScenAccTrajRevision\% and \ScenAccTrajDupload\%, versus \ScenAccCondRevision\% and \ScenAccCondDupload\%). Sharing without validation and schema-change invalidation serve stale definitions in \DsNoguardStaleModeled\ and \DsSchemaStaleModeled\ tasks, while the revalidation methods serve none. \system\ publishes \DsCondRepaired\ repairs per run, every status-change repair among them; where G8 refuses a restatement or SCD Type 2 fix, the agent re-derives the filter after the invalidation and still answers every question. \system\ (gold SQL) publishes \DsCondGoldRepaired\ repairs and answers \DsCondGoldModeled\%, \DsCmpModeledGold\ point lower (interval \DsCmpModeledGoldLo--\DsCmpModeledGoldHi): the reference changes how much repair is automated, not accuracy.}
{\emph{条件覆盖的破坏性变化。}各方法在这里拉开差距（图~\ref{fig:groups}）。在条件覆盖的 5 种破坏性变化上，\system\ 答对 \DsCondModeled\%（\DsCondModeledLo--\DsCondModeledHi），轨迹检索 \DsTrajModeled\%，定义级 \DsDefModeled\%：\system\ 比轨迹检索高 \DsCmpModeledTraj\ 个百分点（95\% 区间 \DsCmpModeledTrajLo--\DsCmpModeledTrajHi），比定义级高 \DsCmpModeledDef\ 个百分点（\DsCmpModeledDefLo--\DsCmpModeledDefHi），后者同样反映学习而非维护。检索到的轨迹没有有效性状态：状态变更行下它重放的 SQL 会把部分退货算两次（\ScenAccTrajStatus\%，\system\ 为 \ScenAccCondStatus\%）；多版本更正与重复加载下它沿用为旧粒度写的 SQL（\ScenAccTrajRevision\% 与 \ScenAccTrajDupload\%，\system\ 为 \ScenAccCondRevision\% 与 \ScenAccCondDupload\%）。共享不验证与按模式变更失效分别在 \DsNoguardStaleModeled\ 和 \DsSchemaStaleModeled\ 道题中提供了过期定义，各重验证方法一道也没有。\system\ 每次运行发布 \DsCondRepaired\ 个修复，状态变更行的修复全部在内；G8 拒绝多版本更正或缓慢变化维（类型 2）的修复时，定义失效，智能体自己重新推出过滤，这些题仍全部答对。\system（标准答案 SQL）发布 \DsCondGoldRepaired\ 个修复，答对 \DsCondGoldModeled\%，低 \DsCmpModeledGold\ 个百分点（区间 \DsCmpModeledGoldLo--\DsCmpModeledGoldHi）：参照改变的是修复有多少能自动完成，而不是正确率。}

\bi{\emph{Self-check.} Telling the trajectory agent to verify grain, join keys, and date keys before reusing retrieved SQL, the properties \system\ checks for it, moves trajectory retrieval to \DsTrajVerifyModeled\% (\DsCmpModeledVerifyTraj\ points, \DsCmpModeledVerifyTrajLo--\DsCmpModeledVerifyTrajHi) at \DsTrajVerifyTurns\ instead of \DsTrajTurns\ turns per task, and \system\ remains \DsCmpModeledCondVerify\ points ahead (\DsCmpModeledCondVerifyLo--\DsCmpModeledCondVerifyHi): an agent that is told what to check still has to find the distinguishing column and the right filter in every session, whereas a maintained definition carries the check result and the repair.}
{\emph{自检。}让轨迹智能体在复用检索到的 SQL 之前核对粒度、连接键与日期键——正是 \system\ 替它检查的性质——使轨迹检索达到 \DsTrajVerifyModeled\%（\DsCmpModeledVerifyTraj\ 个百分点，\DsCmpModeledVerifyTrajLo--\DsCmpModeledVerifyTrajHi），每题轮数从 \DsTrajTurns\ 增至 \DsTrajVerifyTurns，\system\ 仍领先 \DsCmpModeledCondVerify\ 个百分点（\DsCmpModeledCondVerifyLo--\DsCmpModeledCondVerifyHi）：被告知要检查什么的智能体仍要在每次会话中自己找到区分列和正确的过滤，而维护后的定义带着检查结果和修复。}

\bi{\emph{Controls.} Duplicate loads and the date-key format change are detected and the definitions invalidated, since no filter restores the grain, and the unit change violates no condition and serves as the control (\ScenAccCondUnit\% for \system, \ScenAccTrajUnit\% for trajectory retrieval). Under the backup copy the uniqueness rule refuses an ambiguous repair and invalidates the returns definitions: for return amount the agent then finds the backup rows itself and answers 8 of 9 questions, whereas retrieved trajectories replay SQL that double counts (4 of 9); for return rate, which has no definition to fall back on, retrieval keeps its edge (\DsTrajMirror\% against \DsCondMirror\% over the backup-copy questions), the price of invalidating rather than guessing.}
{\emph{对照。}重复加载与日期键格式变化被检测到，定义失效，因为没有过滤能恢复粒度；单位变化不违反任何条件，是对照（\system\ 为 \ScenAccCondUnit\%，轨迹检索为 \ScenAccTrajUnit\%）。备份副本下唯一性规则拒绝有歧义的修复，退货定义失效：对退货金额，智能体自己发现了备份行，9 题答对 8 题，而检索到的轨迹重放会重复计算的 SQL（9 题对 4 题）；对没有定义可以回退的退货率，检索保持优势（备份副本题上 \DsTrajMirror\% 对 \DsCondMirror\%），这是使定义失效而不是猜测的代价。}

\bi{\emph{Cost and declared use.} End to end, maintenance database time is dominated by repair searches, which condition-level and definition-level maintenance both perform (\ScenMaintCond\ versus \ScenMaintDef\,s per run, \ScenMaintRatio\%). Invalidate-on-write spends no maintenance database time but relearns with \ScenRelearnTok\,M LLM tokens per run. Sharing shortens agent work on held-out questions from \ScenHoldTurnsNoShareModelA\ to \ScenHoldTurnsCondModelA\ turns per task and cuts input tokens by \ScenHoldTokSaveModelA\% (Table~\ref{tab:scen-cost}). A separate session study measures the same effect on complete tasks: \SlLibraries\ learned libraries are fixed, and \SlSessions\ fresh DeepSeek sessions answer named parameter questions on one million rows at first use, on warm reuse, after a benign append, and after the status-change rows, including six-request bursts. Agents without shared definitions answer \SlNoneCorrect\ of \SlNoneN\ questions in \SlNoneMean\,s on average with \SlNoneRounds\ LLM calls per task; with \system\ they answer \SlCondCorrect\ of \SlCondN\ in \SlCondMean\,s with \SlCondRounds\ calls and \SlCondInputSaveNone\% fewer input tokens, and after the status-change rows the gap widens to 28.4 against 73.6\,s, because the exploring agent must rediscover the broken grain and still answers wrongly. The saving comes from sharing rather than from the maintenance method: definition-level revalidation and the check-result cache complete in \SlDefMean\ and \SlCacheMean\,s. With identical business definitions in every question, so that only exploration differs, the profiles, join paths, and definitions accumulated by three producers cut schema lookups per task from 3.5 to 2.5, SQL probes from 0.20 to 0.06, and completion time from 13.4 to 9.5\,s over 216 fresh sessions, at equal accuracy. Execution-side checks apply only to declared uses: in our earlier runs, \DuUndeclPct\% of scored answers declared no definition, and \DuDevPct\% of the answers that declared a correct revision were still wrong because the agent's SQL deviated from it.}
{\emph{代价与声明使用。}端到端的维护数据库时间以修复搜索为主，条件级与定义级都要做（每次运行 \ScenMaintCond\ 秒对 \ScenMaintDef\ 秒，\ScenMaintRatio\%）。写入即失效不花维护数据库时间，但每次运行用 \ScenRelearnTok\ 百万个大模型 token 重新学习。共享缩短了智能体在留出题上的工作：每题轮数从 \ScenHoldTurnsNoShareModelA\ 降至 \ScenHoldTurnsCondModelA{}，输入 token 减少 \ScenHoldTokSaveModelA\%（表~\ref{tab:scen-cost}）。另一个会话实验在完整任务上测量同一效应：固定 \SlLibraries\ 个已学库，\SlSessions\ 个全新 DeepSeek 会话在 100 万行数据上回答按名称给出的参数题，覆盖首次使用、热复用、正常追加后和状态变更行之后，并包含六请求突发。没有共享定义的智能体答对 \SlNoneN\ 题中的 \SlNoneCorrect\ 题，平均 \SlNoneMean\ 秒、每题 \SlNoneRounds\ 次大模型调用；使用 \system\ 时答对 \SlCondN\ 题中的 \SlCondCorrect\ 题，平均 \SlCondMean\ 秒、\SlCondRounds\ 次调用，输入 token 少 \SlCondInputSaveNone\%；状态变更行之后差距扩大到 28.4 秒对 73.6 秒，因为探索的智能体必须重新发现被破坏的粒度，而且仍然答错。节省来自共享而不是维护方式：定义级重验证与检查结果缓存的完成时间为 \SlDefMean\ 秒和 \SlCacheMean\ 秒。当每道题都给出相同的业务定义、只有探索不同时，三个生产者积累的画像、连接路径和定义把每题结构查找从 3.5 次降到 2.5 次，SQL 探查从 0.20 次降到 0.06 次，完成时间从 13.4 秒降到 9.5 秒（216 个全新会话，正确率相同）。执行端检查只作用于声明了修订的使用：在此前的运行中，\DuUndeclPct\% 的计分答案没有声明任何定义；在声明了正确修订的答案中仍有 \DuDevPct\% 答错，原因是智能体的 SQL 偏离了定义。}

\bi{\emph{Other models.} An earlier run with the previous middleware, the gold SQL as \system's G8 reference, six methods, ten changes, and three LLMs shows the same pattern for each model: maintained sharing raised accuracy from \PrevScenAccNoShareModelA\% to \PrevScenAccCondModelA\% for DeepSeek V4.1 Flash, from \PrevScenAccNoShareModelB\% to \PrevScenAccCondModelB\% for GLM-5.3, and from \PrevScenAccNoShareModelC\% to \PrevScenAccCondModelC\% for GLM-5.3 Flash.}
{\emph{其他模型。}此前一轮使用旧版中间件、以标准答案 SQL 作 \system\ 的 G8 对照、6 种方法、10 种变化和 3 个大模型的运行，在每个模型上呈现相同的规律：维护后的共享使 DeepSeek V4.1 Flash 的正确率从 \PrevScenAccNoShareModelA\% 提高到 \PrevScenAccCondModelA\%，GLM-5.3 从 \PrevScenAccNoShareModelB\% 提高到 \PrevScenAccCondModelB\%，GLM-5.3 Flash 从 \PrevScenAccNoShareModelC\% 提高到 \PrevScenAccCondModelC\%。}
