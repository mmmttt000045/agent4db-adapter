\subsection{\bt{Data-change scenarios with LLM agents}{大模型智能体的数据变化场景}}
\label{sec:scenarios}
\bi{\emph{Protocol (Q5).} Five metrics, store revenue, store return amount, store return rate, catalog revenue, and electronics store revenue, each have two learning questions and three scored questions: a new period, a period difference, and a monthly ranking. \system's built-in analysis optimizer answers the learning questions with explicit business definitions; the extractor turns judged-successful trajectories into candidates, which pass admission. A user agent that has never seen the metrics answers the scored questions given only metric names, first on unchanged data and then once per data-change scenario. Each scenario starts from the same initial snapshot and shared store, applies one update, re-asks the questions whose metric reads an updated table, and is rolled back. The reference answers reflect the update's business effect, computed before representation changes such as duplicate rows, status rows, backup copies, or old versions are applied; an agent must therefore filter those rows out to answer correctly. Figure~\ref{fig:scenarios} groups the eleven scenarios by the condition they target: the ten earlier scenarios plus the backup copy of Section~\ref{sec:repair-eval}, whose repair is ambiguous; the unit change is a control that no condition covers.}
{\emph{实验流程（Q5）。}5 个指标为门店营业额、门店退货金额、门店退货率、目录渠道营业额和电子品类门店营业额，各有 2 道学习题和 3 道计分题（新期间、跨期差值和按月排名）。\system\ 内置的分析优化器在给出显式业务定义的学习题上作答，提取器把判题成功的轨迹转成候选，经准入后发布。从未接触过这些指标的用户端智能体只拿到指标名，先在未变化的数据上回答计分题，再在每个数据变化场景下各答一次。每个场景都从相同的初始快照和共享知识库出发，施加一次更新，只重问读到被更新表的指标，结束后回滚。标准答案反映更新的业务效果，在施加重复行、状态行、备份副本或旧版本等表示变化之前计算，因此智能体必须过滤掉这些行才能答对。图~\ref{fig:scenarios} 按目标条件对 11 个场景分组：此前的 10 个，加上第~\ref{sec:repair-eval} 节修复有歧义的备份副本；单位变化是任何条件都不覆盖的对照。}

\bi{\emph{Methods and runs.} Besides the strategies of Table~\ref{tab:ladder}, we evaluate a matched \emph{trajectory-retrieval} baseline in the spirit of AgentSM~\cite{biswal2026agentsm}: it receives the same learning tasks under the same admission precondition (judged success and a verifiable answer provenance), stores the question, the SQL that produced the answer, and its derivation, and lets the user agent retrieve up to three stored trajectories by question similarity, without validity maintenance. Agent and extractor use DeepSeek V4.1 Flash with high reasoning effort, a 20-turn limit, and a 60\,s SQL timeout. Each of the ten methods evaluated end to end runs three times, and every run learns its own library; updates are applied between phases, so same-snapshot validation is not exercised here. We analyze \ScenCells\ runs with \ScenValidTasks\ scored tasks (\ScenAgentTasks\ agent tasks in all, \ScenTokensM\,M tokens, \ScenAgentHours\ agent-hours; \ScenQuotaTasks\ tasks that failed with provider errors are not scored); intervals are 95\% bootstrap intervals that resample whole runs, and the comparison with trajectory retrieval was specified before the runs.}
{\emph{方法与运行。}除表~\ref{tab:ladder} 中的维护方式外，我们还评估一个仿照 AgentSM~\cite{biswal2026agentsm} 的匹配\emph{轨迹检索}基线：它获得同样的学习题，入库前提也相同（判题成功、答案溯源可复核），保存题面、产生答案的 SQL 与算式，用户端智能体按题面相似度检索最多 3 条，不做有效性维护。智能体与提取器使用 DeepSeek V4.1 Flash，推理强度为 high，每题最多 20 轮，SQL 超时 60 秒。端到端评估的 10 种方法各运行 3 次，每次各自学习自己的定义库；更新在阶段之间施加，因此这里不涉及同快照验证。我们分析 \ScenCells\ 次运行、\ScenValidTasks\ 道计分题（共 \ScenAgentTasks\ 个智能体任务、\ScenTokensM\,M token、\ScenAgentHours\ 智能体小时；因服务错误失败的 \ScenQuotaTasks\ 道题不计分）；区间为按运行整体重抽样的 95\% 自助法区间，与轨迹检索的比较在运行前确定。}

\bi{\emph{Sharing and benign updates.} Without shared knowledge, agent B answers \DsNoShareAll\% of all questions. Every sharing method transfers what agent A learned: on held-out questions, \system\ and trajectory retrieval both answer \DsCondHoldout\% (\DsNoShareHoldout\% without sharing), and after the four benign updates \system\ keeps \DsCondBenign\%. Invalidate-on-write keeps \DsRevokeBenign\% as well, but only by relearning after every write (\DsRevokeRevoked\ invalidations per run).}
{\emph{共享与正常更新。}没有共享知识时，智能体 B 全部题目答对 \DsNoShareAll\%。各共享方法都能迁移智能体 A 学到的内容：留出题上，\system\ 与轨迹检索都答对 \DsCondHoldout\%（不共享为 \DsNoShareHoldout\%），四种正常更新之后 \system\ 保持 \DsCondBenign\%。写入即失效同样保持 \DsRevokeBenign\%，但要靠每次写入后重新学习（每次运行失效 \DsRevokeRevoked\ 次）。}

\bi{\emph{Covered breaking changes.} Here the methods separate (Figure~\ref{fig:scenarios}, last row). Over the five breaking changes that the conditions cover, \system\ answers \DsCondModeled\% (\DsCondModeledLo--\DsCondModeledHi) and trajectory retrieval \DsTrajModeled\%, \DsCmpModeledTraj\ points apart (95\% interval \DsCmpModeledTrajLo--\DsCmpModeledTrajHi). Retrieved trajectories carry no validity state: under status-change rows they replay SQL that now counts some returns twice (\ScenAccTrajStatus\% versus \ScenAccCondStatus\% for \system), and under restatements and duplicate loads they reuse SQL written for the old grain (\ScenAccTrajRevision\% and \ScenAccTrajDupload\%, versus \ScenAccCondRevision\% and \ScenAccCondDupload\%). Sharing without validation and schema-change invalidation serve stale definitions in \DsNoguardStaleModeled\ and \DsSchemaStaleModeled\ tasks and answer \DsNoguardModeled\% and \DsSchemaModeled\%; the revalidation methods serve none. Among these, accuracy is the same within noise: definition-level revalidation answers \DsDefModeled\% (\DsCmpModeledDef\ points, \DsCmpModeledDefLo--\DsCmpModeledDefHi), as the replay predicts, and differs from \system\ in cost (Section~\ref{sec:cost}). The as-of comparison changes automation: \system\ publishes \DsCondRepaired\ repairs per run, against \DsCondCurRepaired\ with G8 on current data, where the agent re-derives the refused filters in its own session (\DsCondCurModeled\%; difference \DsCmpModeledCur\ points, \DsCmpModeledCurLo--\DsCmpModeledCurHi). \system\ (gold SQL) answers \DsCondGoldModeled\%.}
{\emph{条件覆盖的破坏性变化。}各方法在这里拉开差距（图~\ref{fig:scenarios} 末行）。在条件覆盖的 5 种破坏性变化上，\system\ 答对 \DsCondModeled\%（\DsCondModeledLo--\DsCondModeledHi），轨迹检索 \DsTrajModeled\%，相差 \DsCmpModeledTraj\ 个百分点（95\% 区间 \DsCmpModeledTrajLo--\DsCmpModeledTrajHi）。检索到的轨迹没有有效性状态：状态变更行下它重放的 SQL 会把部分退货算两次（\ScenAccTrajStatus\%，\system\ 为 \ScenAccCondStatus\%）；多版本更正与重复加载下它沿用为旧粒度写的 SQL（\ScenAccTrajRevision\% 与 \ScenAccTrajDupload\%，\system\ 为 \ScenAccCondRevision\% 与 \ScenAccCondDupload\%）。共享不验证与按模式变更失效分别在 \DsNoguardStaleModeled\ 和 \DsSchemaStaleModeled\ 道题中提供了过期定义，答对 \DsNoguardModeled\% 与 \DsSchemaModeled\%；各重验证方法一道也没有。重验证方法之间的正确率在误差范围内相同：定义级重验证答对 \DsDefModeled\%（相差 \DsCmpModeledDef\ 个百分点，\DsCmpModeledDefLo--\DsCmpModeledDefHi），与回放的结论一致，它与 \system\ 的差别在代价（第~\ref{sec:cost} 节）。按学习时刻比较改变的是自动化程度：\system\ 每次运行发布 \DsCondRepaired\ 个修复，G8 用当前数据时只有 \DsCondCurRepaired\ 个，被拒绝的过滤由智能体在自己的会话里重新推出（\DsCondCurModeled\%；相差 \DsCmpModeledCur\ 个百分点，\DsCmpModeledCurLo--\DsCmpModeledCurHi）。\system（标准答案 SQL）答对 \DsCondGoldModeled\%。}

\bi{\emph{Self-check.} Telling the trajectory agent to verify grain, join keys, and date keys before reusing retrieved SQL, the properties \system\ checks for it, moves trajectory retrieval to \DsTrajVerifyModeled\% (\DsCmpModeledVerifyTraj\ points, \DsCmpModeledVerifyTrajLo--\DsCmpModeledVerifyTrajHi) at \DsTrajVerifyTurns\ instead of \DsTrajTurns\ turns per task, and \system\ remains \DsCmpModeledCondVerify\ points ahead (\DsCmpModeledCondVerifyLo--\DsCmpModeledCondVerifyHi): an agent that is told what to check still has to find the distinguishing column and the right filter in every session, whereas a maintained definition carries the check result and the repair.}
{\emph{自检。}让轨迹智能体在复用检索到的 SQL 之前核对粒度、连接键与日期键——正是 \system\ 替它检查的性质——使轨迹检索达到 \DsTrajVerifyModeled\%（\DsCmpModeledVerifyTraj\ 个百分点，\DsCmpModeledVerifyTrajLo--\DsCmpModeledVerifyTrajHi），每题轮数从 \DsTrajTurns\ 增至 \DsTrajVerifyTurns，\system\ 仍领先 \DsCmpModeledCondVerify\ 个百分点（\DsCmpModeledCondVerifyLo--\DsCmpModeledCondVerifyHi）：被告知要检查什么的智能体仍要在每次会话中自己找到区分列和正确的过滤，而维护后的定义带着检查结果和修复。}

\bi{\emph{Controls.} Duplicate loads and the date-key format change are detected and the definitions invalidated, since no filter restores the grain, and the unit change violates no condition and serves as the control (\ScenAccCondUnit\% for \system, \ScenAccTrajUnit\% for trajectory retrieval). Under the backup copy the uniqueness rule refuses an ambiguous repair and invalidates the returns definitions: for return amount the agent then finds the backup rows itself and answers 7 of 9 questions, whereas retrieved trajectories replay SQL that double counts (4 of 9); for return rate, which has no definition to fall back on, retrieval keeps its edge (\DsTrajMirror\% against \DsCondMirror\% over the backup-copy questions), the price of invalidating rather than guessing.}
{\emph{对照。}重复加载与日期键格式变化被检测到，定义失效，因为没有过滤能恢复粒度；单位变化不违反任何条件，是对照（\system\ 为 \ScenAccCondUnit\%，轨迹检索为 \ScenAccTrajUnit\%）。备份副本下唯一性规则拒绝有歧义的修复，退货定义失效：对退货金额，智能体自己发现了备份行，9 题答对 7 题，而检索到的轨迹重放会重复计算的 SQL（9 题对 4 题）；对没有定义可以回退的退货率，检索保持优势（备份副本题上 \DsTrajMirror\% 对 \DsCondMirror\%），这是使定义失效而不是猜测的代价。}

\bi{\emph{Cost and declared use.} End to end, maintenance database time is dominated by repair searches, which condition-level and definition-level maintenance both perform (\ScenMaintCond\ versus \ScenMaintDef\,s per run, \ScenMaintRatio\%). Invalidate-on-write spends no maintenance database time but relearns with \ScenRelearnTok\,M LLM tokens per run. Sharing shortens agent work on held-out questions from \ScenHoldTurnsNoShareModelA\ to \ScenHoldTurnsCondModelA\ turns per task and cuts input tokens by \ScenHoldTokSaveModelA\% (Table~\ref{tab:scen-cost}). A separate session study measures the same effect on complete tasks: \SlLibraries\ learned libraries are fixed, and \SlSessions\ fresh DeepSeek sessions answer named parameter questions on one million rows at first use, on warm reuse, after a benign append, and after the status-change rows, including six-request bursts. Agents without shared definitions answer \SlNoneCorrect\ of \SlNoneN\ questions in \SlNoneMean\,s on average with \SlNoneRounds\ LLM calls per task; with \system\ they answer \SlCondCorrect\ of \SlCondN\ in \SlCondMean\,s with \SlCondRounds\ calls and \SlCondInputSaveNone\% fewer input tokens, and after the status-change rows the gap widens to 28.4 against 73.6\,s, because the exploring agent must rediscover the broken grain and still answers wrongly. The saving comes from sharing rather than from the maintenance method: definition-level revalidation and the check-result cache complete in \SlDefMean\ and \SlCacheMean\,s. With identical business definitions in every question, so that only exploration differs, the profiles, join paths, and definitions accumulated by three producers cut schema lookups per task from 3.5 to 2.5, SQL probes from 0.20 to 0.06, and completion time from 13.4 to 9.5\,s over 216 fresh sessions, at equal accuracy. Execution-side checks apply only to declared uses: in the three-LLM study, \DuUndeclPct\% of scored answers declared no definition, and \DuDevPct\% of the answers that declared a correct revision were still wrong because the agent's SQL deviated from it.}
{\emph{代价与声明使用。}端到端的维护数据库时间以修复搜索为主，条件级与定义级都要做（每次运行 \ScenMaintCond\ 秒对 \ScenMaintDef\ 秒，\ScenMaintRatio\%）。写入即失效不花维护数据库时间，但每次运行用 \ScenRelearnTok\ 百万个大模型 token 重新学习。共享缩短了智能体在留出题上的工作：每题轮数从 \ScenHoldTurnsNoShareModelA\ 降至 \ScenHoldTurnsCondModelA{}，输入 token 减少 \ScenHoldTokSaveModelA\%（表~\ref{tab:scen-cost}）。另一个会话实验在完整任务上测量同一效应：固定 \SlLibraries\ 个已学库，\SlSessions\ 个全新 DeepSeek 会话在 100 万行数据上回答按名称给出的参数题，覆盖首次使用、热复用、正常追加后和状态变更行之后，并包含六请求突发。没有共享定义的智能体答对 \SlNoneN\ 题中的 \SlNoneCorrect\ 题，平均 \SlNoneMean\ 秒、每题 \SlNoneRounds\ 次大模型调用；使用 \system\ 时答对 \SlCondN\ 题中的 \SlCondCorrect\ 题，平均 \SlCondMean\ 秒、\SlCondRounds\ 次调用，输入 token 少 \SlCondInputSaveNone\%；状态变更行之后差距扩大到 28.4 秒对 73.6 秒，因为探索的智能体必须重新发现被破坏的粒度，而且仍然答错。节省来自共享而不是维护方式：定义级重验证与检查结果缓存的完成时间为 \SlDefMean\ 秒和 \SlCacheMean\ 秒。当每道题都给出相同的业务定义、只有探索不同时，三个生产者积累的画像、连接路径和定义把每题结构查找从 3.5 次降到 2.5 次，SQL 探查从 0.20 次降到 0.06 次，完成时间从 13.4 秒降到 9.5 秒（216 个全新会话，正确率相同）。执行端检查只作用于声明了修订的使用：在三模型实验中，\DuUndeclPct\% 的计分答案没有声明任何定义；在声明了正确修订的答案中仍有 \DuDevPct\% 答错，原因是智能体的 SQL 偏离了定义。}

\bi{\emph{Other models.} A study with three LLMs on an earlier prototype (six methods, ten changes) shows the same pattern for each model: maintained sharing raised accuracy from \PrevScenAccNoShareModelA\% to \PrevScenAccCondModelA\% for DeepSeek V4.1 Flash, from \PrevScenAccNoShareModelB\% to \PrevScenAccCondModelB\% for GLM-5.3, and from \PrevScenAccNoShareModelC\% to \PrevScenAccCondModelC\% for GLM-5.3 Flash.}
{\emph{其他模型。}在较早的原型上用 3 个大模型（6 种方法、10 种变化）的实验，在每个模型上呈现相同的规律：维护后的共享使 DeepSeek V4.1 Flash 的正确率从 \PrevScenAccNoShareModelA\% 提高到 \PrevScenAccCondModelA\%，GLM-5.3 从 \PrevScenAccNoShareModelB\% 提高到 \PrevScenAccCondModelB\%，GLM-5.3 Flash 从 \PrevScenAccNoShareModelC\% 提高到 \PrevScenAccCondModelC\%。}
