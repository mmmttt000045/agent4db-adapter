\subsection{\bt{Data-change scenarios with LLM agents}{大模型智能体的数据变化场景}}
\label{sec:scenarios}
\bi{\emph{Protocol (Q5).} Five metrics, store revenue, store return amount, store return rate, catalog revenue, and electronics store revenue, each have two learning questions and three scored questions: a new period, a period difference, and a monthly ranking. Agent A answers the learning questions with explicit business definitions; the extractor turns judged-successful trajectories into candidates, which pass admission. Agent B, which has never seen the metrics, answers the scored questions given only metric names, first on unchanged data and then once per data-change scenario. Each scenario starts from the same initial snapshot and shared store, applies one update, re-asks the questions whose metric reads an updated table, and is rolled back. The reference answers reflect the update's business effect, computed before representation changes such as duplicate rows, status rows, or old versions are applied; an agent must therefore filter those rows out to answer correctly. Table~\ref{tab:scenarios} groups the ten scenarios by the condition they target; the unit change is a control that no condition models. These runs predate snapshot-bound execution, the uniqueness rule, and waiting for repairs, and their updates are applied between phases.}
{\emph{实验流程（Q5）。}5 个指标为门店营业额、门店退货金额、门店退货率、目录渠道营业额和电子品类门店营业额，各有 2 道学习题和 3 道计分题（新期间、跨期差值和按月排名）。智能体 A 在给出显式业务定义的学习题上作答，提炼器把判题成功的轨迹转成候选，经准入后发布。从未接触过这些指标的智能体 B 只拿到指标名，先在未变化的数据上回答计分题，再在每个数据变化场景下各答一次。每个场景都从相同的初始快照和共享知识库出发，施加一次更新，只重问读到被更新表的指标，结束后回滚。标准答案反映更新的业务效果，在施加重复行、状态行或旧版本等表示变化之前计算，因此智能体必须过滤掉这些行才能答对。表~\ref{tab:scenarios} 按目标条件对 10 个场景分组，其中单位变化是任何条件都没有刻画的对照。这些运行早于绑定快照执行、唯一性规则与修复等待的实现，更新在阶段之间施加。}

\bi{Agent and extractor use the same model: DeepSeek V4.1 Flash, GLM-5.3, or GLM-5.3 Flash, served through the Cline gateway with high reasoning effort, a 20-turn limit, and a 60\,s SQL timeout. Each model and method is planned for three repetitions, but the provider's usage cap interrupted part of the runs. We analyze \ScenCells\ cells. Tasks that failed with provider errors (\ScenQuotaTasks) are excluded, leaving \ScenValidTasks\ scored tasks; \ScenCellsDropped\ cells whose learning phase was interrupted are dropped because they never acquired the definitions. Accuracies are computed per model and then averaged, and summary rows weight each setting equally.}
{智能体与提炼器使用同一模型：DeepSeek V4.1 Flash、GLM-5.3 或 GLM-5.3 Flash，经 Cline 网关调用，推理强度为 high，每题最多 20 轮，SQL 超时 60 秒。每个模型与方法计划重复 3 次，但服务商的用量上限中断了部分运行。我们分析 \ScenCells\ 组：因服务错误失败的题（\ScenQuotaTasks\ 道）不计入，余下 \ScenValidTasks\ 道计分题；学习阶段被中断的 \ScenCellsDropped\ 组没有学到定义，整组剔除。正确率先在每个模型内计算再取平均，汇总行对各情形等权平均。}

\bi{\emph{Sharing and benign updates.} Shared definitions transfer across agents: on held-out questions, accuracy rises from \ScenHoldoutNoShare\% without shared definitions to \ScenHoldoutCond\% with condition-level maintenance. After the four benign updates, condition-level maintenance keeps \ScenBenignCond\% accuracy, compared with \ScenBenignNoShare\% without sharing. Revoke-on-write falls to \ScenBenignRevoke\% because it discards valid definitions on every write, and about a third of its relearning attempts (93 of 284) do not restore a valid definition.}
{\emph{共享与正常更新。}共享定义能在智能体之间迁移：在留出题上，正确率从不共享时的 \ScenHoldoutNoShare\% 提高到条件级维护的 \ScenHoldoutCond\%。四种正常更新之后，条件级维护保持 \ScenBenignCond\% 的正确率，不共享时为 \ScenBenignNoShare\%。写入即撤销降到 \ScenBenignRevoke\%，因为它每次写入都丢弃有效定义，而约三分之一的重新学习（284 次中的 93 次）没有恢复出有效定义。}

\bi{\emph{Modeled breaking changes.} Condition-level and definition-level maintenance and revoke-on-write never return or execute a stale revision under the five modeled breaking changes, whereas schema-only maintenance and unguarded sharing do so in \ScenStaleModeledSchema\ and \ScenStaleModeledNoguard\ tasks (Table~\ref{tab:scen-cost}). Where restricted repair succeeds, accuracy recovers: under the status history, condition-level maintenance answers \ScenAccCondStatus\% correctly, versus \ScenAccSchemaStatus\% for schema-only maintenance and \ScenAccNoShareStatus\% without sharing; under versioned corrections, \ScenAccCondRevision\% versus \ScenAccSchemaRevision\%. These repairs regress against judged learning queries that anticipate the status and current-version columns (Section~\ref{sec:repair-eval}). Under dimension history, every method that shares definitions answers correctly: execution-side SQL review rejects the item join that fans out, and agents add the current-version filter even when they declare a stale revision.}
{\emph{已建模的破坏性变化。}在 5 种已建模的破坏性变化下，条件级、定义级维护和写入即撤销从不返回或执行过期修订；只看结构的维护和无守护共享则分别在 \ScenStaleModeledSchema\ 和 \ScenStaleModeledNoguard\ 道题中这样做（表~\ref{tab:scen-cost}）。受限修复成功时，正确率得以恢复：状态流水下，条件级维护答对 \ScenAccCondStatus\%，只看结构为 \ScenAccSchemaStatus\%，不共享为 \ScenAccNoShareStatus\%；版本化更正下为 \ScenAccCondRevision\% 对 \ScenAccSchemaRevision\%。这些修复是以预先知道状态列与当前版本列的判题学习查询为参照回归的（第~\ref{sec:repair-eval} 节）。维表拉链下，所有共享定义的方法都能答对：执行端 SQL 审查拒绝放大行数的商品连接，即使智能体声明了过期修订，也会自行补上当前版本过滤。}

\bi{\emph{Where the model stops.} A duplicate load breaks the sales grain and is revoked (\ScenRevokedDupload\ revocations), but no filter can separate identical rows, so repair fails and accuracy falls to the level without sharing (\ScenAccCondDupload\% versus \ScenAccNoShareDupload\%). Re-keyed dates break the coverage of the date join and are likewise revoked without a repair candidate (\ScenAccCondLatekey\% versus \ScenAccNoShareLatekey\%). In both cases maintenance is safe but the definition becomes unavailable. The unit change violates no condition: \ScenUnitStaleTasks\ of \ScenUnitTasks\ condition-level tasks use the unchanged definition, and every method that shares definitions inherits the error. Validity conditions capture grain, multiplicity, and coverage, not the meaning of values.}
{\emph{模型的边界。}重复装载破坏销售粒度并被撤销（\ScenRevokedDupload\ 次撤销），但任何过滤都无法区分完全相同的行，修复失败，正确率降到不共享的水平（\ScenAccCondDupload\% 对 \ScenAccNoShareDupload\%）。日期键改写破坏日期连接的覆盖，同样被撤销且没有修复候选（\ScenAccCondLatekey\% 对 \ScenAccNoShareLatekey\%）。这两种情形下维护是安全的，但定义变得不可用。单位变化不违反任何条件：条件级的 \ScenUnitTasks\ 道题中有 \ScenUnitStaleTasks\ 道使用了未变化的定义，所有共享定义的方法都继承了这一错误。有效性条件刻画粒度、多重性与覆盖，而不刻画取值的含义。}

\bi{\emph{Across models.} The gain from sharing holds for every model (Figure~\ref{fig:models}): accuracy rises from \ScenAccNoShareModelA\% to \ScenAccCondModelA\% for DeepSeek V4.1 Flash, from \ScenAccNoShareModelB\% to \ScenAccCondModelB\% for GLM-5.3, and from \ScenAccNoShareModelC\% to \ScenAccCondModelC\% for GLM-5.3 Flash. Condition-level and definition-level cells answer equally well for the two stronger models (\ScenAccCondModelA\% vs.\ \ScenAccDefModelA\%, \ScenAccCondModelB\% vs.\ \ScenAccDefModelB\%), while for GLM-5.3 Flash the condition-level cells trail (\ScenAccCondModelC\% vs.\ \ScenAccDefModelC\%). The paired replay attributes this gap to learning, not maintenance: on the same library the two methods give identical answers, but GLM-5.3 Flash's condition-level cells promoted only three definitions each, against four to eight in its definition-level cells.}
{\emph{跨模型。}共享带来的提升对每个模型都成立（图~\ref{fig:models}）：DeepSeek V4.1 Flash 从 \ScenAccNoShareModelA\% 提高到 \ScenAccCondModelA\%，GLM-5.3 从 \ScenAccNoShareModelB\% 提高到 \ScenAccCondModelB\%，GLM-5.3 Flash 从 \ScenAccNoShareModelC\% 提高到 \ScenAccCondModelC\%。对两个较强模型，条件级与定义级各组的正确率相当（\ScenAccCondModelA\% 对 \ScenAccDefModelA\%，\ScenAccCondModelB\% 对 \ScenAccDefModelB\%）；GLM-5.3 Flash 的条件级各组则落后（\ScenAccCondModelC\% 对 \ScenAccDefModelC\%）。配对回放把这一差距归于学习而非维护：在同一个库上两种方法答案完全相同，但 GLM-5.3 Flash 的条件级各组每组只晋升了 3 个定义，其定义级各组为 4--8 个。}

\bi{\emph{Cost and declared use.} Condition-level maintenance needs \ScenMaintCond\,s of maintenance database time per cell, versus \ScenMaintDef\,s for definition-level revalidation (\ScenMaintRatio\%), while revoking and repairing about the same number of revisions (Table~\ref{tab:scen-cost}). Revoke-on-write spends no maintenance database time, but it revokes about 24 revisions per cell and relearns them with \ScenRelearnTok\,M LLM tokens per cell. Sharing also shortens agent work on held-out questions: turns per task fall from \ScenHoldTurnsNoShareModelA\ to \ScenHoldTurnsCondModelA\ for DeepSeek and from \ScenHoldTurnsNoShareModelB\ to \ScenHoldTurnsCondModelB\ for GLM-5.3, and input tokens by \ScenHoldTokSaveModelA\% and \ScenHoldTokSaveModelB\%. Execution-side checks apply only to declared uses: across the condition- and definition-level cells, \DuUndeclared\ of \DuRecords\ scored answers (\DuUndeclPct\%) declare no definition. Among answers that declare a revision whose canonical SQL is correct, \DuDeviate\ of \DuValid\ (\DuDevPct\%) are still wrong because the agent's SQL deviated from the definition.}
{\emph{代价与声明使用。}条件级维护每组需要 \ScenMaintCond\ 秒维护数据库时间，定义级重验证为 \ScenMaintDef\ 秒（\ScenMaintRatio\%），两者撤销和修复的修订数大致相同（表~\ref{tab:scen-cost}）。写入即撤销不花维护数据库时间，但每组撤销约 24 个修订，并用每组 \ScenRelearnTok\ 百万个大模型 token 重新学习。共享还缩短了智能体在留出题上的工作：DeepSeek 每题轮数从 \ScenHoldTurnsNoShareModelA\ 降至 \ScenHoldTurnsCondModelA{}，GLM-5.3 从 \ScenHoldTurnsNoShareModelB\ 降至 \ScenHoldTurnsCondModelB{}，输入 token 分别减少 \ScenHoldTokSaveModelA\% 和 \ScenHoldTokSaveModelB\%。执行端检查只作用于声明了修订的使用：在条件级与定义级各组中，\DuRecords\ 个计分答案里有 \DuUndeclared\ 个（\DuUndeclPct\%）没有声明任何定义。在声明了规范 SQL 正确的修订的答案中，仍有 \DuValid\ 个中的 \DuDeviate\ 个（\DuDevPct\%）答错，原因是智能体的 SQL 偏离了定义。}
