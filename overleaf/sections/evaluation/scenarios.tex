\subsection{\bt{Data-change scenarios with LLM agents}{大模型智能体的数据变化场景}}
\label{sec:scenarios}
\bi{\emph{Protocol (Q5).} Five metrics, store revenue, store return amount, store return rate, catalog revenue, and electronics store revenue, each have two learning questions and three scored questions: a new period, a period difference, and a monthly ranking. Agent A answers the learning questions with explicit business definitions; the extractor turns judged-successful trajectories into candidates, which pass admission. Agent B, which has never seen the metrics, answers the scored questions given only metric names, first on unchanged data and then once per data-change scenario. Each scenario starts from the same initial snapshot and shared store, applies one update, re-asks the questions whose metric reads an updated table, and is rolled back. The reference answers reflect the update's business effect, computed before representation changes such as duplicate rows, status rows, backup copies, or old versions are applied; an agent must therefore filter those rows out to answer correctly. Table~\ref{tab:scenarios} groups the eleven scenarios by the condition they target: the ten earlier scenarios plus the backup copy of Section~\ref{sec:repair-eval}, whose repair is ambiguous; the unit change is a control that no condition models.}
{\emph{实验流程（Q5）。}5 个指标为门店营业额、门店退货金额、门店退货率、目录渠道营业额和电子品类门店营业额，各有 2 道学习题和 3 道计分题（新期间、跨期差值和按月排名）。智能体 A 在给出显式业务定义的学习题上作答，提炼器把判题成功的轨迹转成候选，经准入后发布。从未接触过这些指标的智能体 B 只拿到指标名，先在未变化的数据上回答计分题，再在每个数据变化场景下各答一次。每个场景都从相同的初始快照和共享知识库出发，施加一次更新，只重问读到被更新表的指标，结束后回滚。标准答案反映更新的业务效果，在施加重复行、状态行、备份副本或旧版本等表示变化之前计算，因此智能体必须过滤掉这些行才能答对。表~\ref{tab:scenarios} 按目标条件对 11 个场景分组：此前的 10 个，加上第~\ref{sec:repair-eval} 节修复有歧义的备份副本；单位变化是任何条件都没有刻画的对照。}

\bi{\emph{Methods and runs.} Besides the methods of Table~\ref{tab:baselines}, we evaluate a matched \emph{trajectory-retrieval} baseline in the spirit of AgentSM~\cite{biswal2026agentsm}: it receives the same learning tasks under the same admission precondition (judged success and a verifiable calculation chain), stores the question, the SQL that produced the answer, and its derivation, and lets agent B retrieve up to three stored trajectories by question similarity, without validity maintenance. Agent and extractor use DeepSeek V4.1 Flash through the Cline gateway with high reasoning effort, a 20-turn limit, and a 60\,s SQL timeout; each of the seven methods runs three times, and every run learns its own library. The middleware is the current one, with the uniqueness rule and waiting for repairs; updates are applied between phases, so snapshot binding is not exercised here. Following an analysis plan fixed before the runs, tasks that failed with provider errors are not scored (\ScenQuotaTasks), and the \ScenCellsDropped\ runs that met a provider failure while learning were rerun in full. We analyze \ScenCells\ runs with \ScenValidTasks\ scored tasks; intervals are 95\% bootstrap intervals that resample whole runs.}
{\emph{方法与运行。}除表~\ref{tab:baselines} 中的方法外，我们还评估一个仿照 AgentSM~\cite{biswal2026agentsm} 的匹配\emph{轨迹检索}基线：它获得同样的学习题，入库前提也相同（判题成功、计算链可复核），保存题面、产生答案的 SQL 与算式，智能体 B 按题面相似度检索最多 3 条，不做有效性维护。智能体与提炼器使用 DeepSeek V4.1 Flash，经 Cline 网关调用，推理强度为 high，每题最多 20 轮，SQL 超时 60 秒；7 种方法各运行 3 次，每次各自学习自己的定义库。中间层为当前版本，含唯一性规则与修复等待；更新在阶段之间施加，因此这里不涉及绑定快照执行。按运行前写定的分析方案，因服务错误失败的题不计分（\ScenQuotaTasks\ 道），学习阶段遇到服务失败的 \ScenCellsDropped\ 次运行整次重跑。我们分析 \ScenCells\ 次运行、\ScenValidTasks\ 道计分题；区间为按运行整体重抽样的 95\% 自助法区间。}

\bi{\emph{Sharing and benign updates.} Without shared knowledge, agent B answers \DsNoShareAll\% of all questions. Every sharing method transfers what agent A learned: on held-out questions, \system\ and trajectory retrieval both answer \DsCondHoldout\% (\DsNoShareHoldout\% without sharing), the outcome expected for unchanged data. After the four benign updates, \system\ keeps \DsCondBenign\%, whereas revoke-on-write falls to \DsRevokeBenign\% because it discards valid definitions on every write and relearns them (\DsRevokeRevoked\ revocations per run). Definition-level runs are less accurate on held-out and benign questions (\DsDefHoldout\% and \DsDefBenign\%) although their maintenance is identical to \system's on a fixed library (Section~\ref{sec:validity}); the difference comes from what those runs learned.}
{\emph{共享与正常更新。}没有共享知识时，智能体 B 全部题目答对 \DsNoShareAll\%。各共享方法都能迁移智能体 A 学到的内容：留出题上，\system\ 与轨迹检索都答对 \DsCondHoldout\%（不共享为 \DsNoShareHoldout\%），这是数据不变时应有的结果。四种正常更新之后，\system\ 保持 \DsCondBenign\%，写入即撤销则降到 \DsRevokeBenign\%，因为它每次写入都丢弃有效定义并重新学习（每次运行撤销 \DsRevokeRevoked\ 次）。定义级各次运行在留出题与正常变化上较低（\DsDefHoldout\% 与 \DsDefBenign\%），而在固定的定义库上它的维护与 \system\ 完全相同（第~\ref{sec:validity} 节）；差别来自这些运行学到的内容。}

\bi{\emph{Modeled breaking changes.} Here the methods separate (Table~\ref{tab:scenarios}). Over the five modeled breaking changes, \system\ answers \DsCondModeled\% (\DsCondModeledLo--\DsCondModeledHi), trajectory retrieval \DsTrajModeled\%, and definition-level \DsDefModeled\%. The two comparisons fixed in our analysis plan give \system\ an advantage of \DsCmpModeledTraj\ points over trajectory retrieval (95\% interval \DsCmpModeledTrajLo--\DsCmpModeledTrajHi) and of \DsCmpModeledDef\ points over definition-level (\DsCmpModeledDefLo--\DsCmpModeledDefHi), the latter again reflecting learning rather than maintenance. Retrieved trajectories carry no validity state: under the status history they replay SQL that now counts some returns twice (\ScenAccTrajStatus\% versus \ScenAccCondStatus\% for \system), and under versioned corrections and duplicate loads they reuse SQL written for the old grain (\ScenAccTrajRevision\% and \ScenAccTrajDupload\%, versus \ScenAccCondRevision\% and \ScenAccCondDupload\%). Unguarded and schema-only sharing serve stale definitions in \DsNoguardStaleModeled\ and \DsSchemaStaleModeled\ tasks, while the revalidation methods serve none. Where repair succeeds, as for the status history and versioned corrections, it relies on judged learning queries that anticipate the distinguishing columns (Section~\ref{sec:repair-eval}).}
{\emph{已建模的破坏性变化。}各方法在这里拉开差距（表~\ref{tab:scenarios}）。在 5 种已建模的破坏性变化上，\system\ 答对 \DsCondModeled\%（\DsCondModeledLo--\DsCondModeledHi），轨迹检索 \DsTrajModeled\%，定义级 \DsDefModeled\%。分析方案中预先确定的两个比较给出：\system\ 比轨迹检索高 \DsCmpModeledTraj\ 个百分点（95\% 区间 \DsCmpModeledTrajLo--\DsCmpModeledTrajHi），比定义级高 \DsCmpModeledDef\ 个百分点（\DsCmpModeledDefLo--\DsCmpModeledDefHi），后者同样反映学习而非维护。检索到的轨迹没有有效性状态：状态流水下它重放的 SQL 会把部分退货算两次（\ScenAccTrajStatus\%，\system\ 为 \ScenAccCondStatus\%）；版本化更正与重复装载下它沿用为旧粒度写的 SQL（\ScenAccTrajRevision\% 与 \ScenAccTrajDupload\%，\system\ 为 \ScenAccCondRevision\% 与 \ScenAccCondDupload\%）。无守护与只看结构的共享分别在 \DsNoguardStaleModeled\ 和 \DsSchemaStaleModeled\ 道题中提供了过期定义，各重验证方法一道也没有。修复成功之处（状态流水与版本化更正）依赖于预先知道区分列的判题学习查询（第~\ref{sec:repair-eval} 节）。}

\bi{\emph{Two further methods.} Two methods added after the main runs, with their comparisons fixed before they ran, test the two caveats of this result. First, with the agent's extracted learning query as the regression reference instead of the judged one, \system\ answers \DsCondExrefModeled\% under the modeled changes (\DsCondExrefModeledLo--\DsCondExrefModeledHi), \DsCmpModeledExrefTraj\ points over trajectory retrieval (\DsCmpModeledExrefTrajLo--\DsCmpModeledExrefTrajHi) and \DsCmpModeledExrefCond\ points from \system\ with the judged reference (\DsCmpModeledExrefCondLo--\DsCmpModeledExrefCondHi): the reference changes which repairs are published, and the replay of Section~\ref{sec:repair-eval} shows that what it refuses becomes unavailable, not wrong. Second, telling the trajectory agent to verify grain, join keys, and date keys before reusing retrieved SQL, the four properties \system\ checks for it, moves trajectory retrieval to \DsTrajVerifyModeled\% (\DsCmpModeledVerifyTraj\ points, \DsCmpModeledVerifyTrajLo--\DsCmpModeledVerifyTrajHi), and \system\ remains \DsCmpModeledCondVerify\ points ahead (\DsCmpModeledCondVerifyLo--\DsCmpModeledCondVerifyHi): an agent that is told what to check still has to find the distinguishing column and the right filter in every session, whereas a maintained definition carries the verdict and the repair.}
{\emph{两种增补方法。}主实验之后增补、比较在运行前预先写定的两种方法，检验这一结果的两个前提。其一，把回归参照从判题查询换成从智能体轨迹提炼的学习查询，\system\ 在已建模变化下答对 \DsCondExrefModeled\%（\DsCondExrefModeledLo--\DsCondExrefModeledHi），比轨迹检索高 \DsCmpModeledExrefTraj\ 个百分点（\DsCmpModeledExrefTrajLo--\DsCmpModeledExrefTrajHi），与判题参照下的 \system\ 相差 \DsCmpModeledExrefCond\ 个百分点（\DsCmpModeledExrefCondLo--\DsCmpModeledExrefCondHi）：参照改变的是哪些修复被发布，第~\ref{sec:repair-eval} 节的回放表明被拒绝的修复变为不可用而不是答错。其二，让轨迹智能体在复用检索到的 SQL 之前核对粒度、关联键与日期键——正是 \system\ 替它检查的四类性质——使轨迹检索达到 \DsTrajVerifyModeled\%（\DsCmpModeledVerifyTraj\ 个百分点，\DsCmpModeledVerifyTrajLo--\DsCmpModeledVerifyTrajHi），\system\ 仍领先 \DsCmpModeledCondVerify\ 个百分点（\DsCmpModeledCondVerifyLo--\DsCmpModeledCondVerifyHi）：被告知要检查什么的智能体仍要在每次会话中自己找到区分列和正确的过滤，而维护后的定义带着结论和修复。}

\bi{\emph{Where the model stops.} A duplicate load is revoked but cannot be repaired by a filter, and re-keyed dates break the coverage of the date join without a repair candidate; under re-keyed dates every method stays low (\ScenAccCondLatekey\% for \system, \ScenAccTrajLatekey\% for trajectory retrieval, \ScenAccNoShareLatekey\% without sharing). The unit change violates no condition, so all sharing methods inherit it (\ScenAccCondUnit\% for \system). The backup copy shows the price of withdrawing a definition. Two filters restore the returns grain equally well, so \system\ withdraws the return-amount definitions, and the return-rate definitions, which lose the unique side of their join to returns, with them. For return amount this helps: the agent finds the backup rows itself and answers 8 of 9 questions, whereas retrieved trajectories replay SQL that double counts (4 of 9). For return rate it hurts: the retrieved SQL happens to survive the duplication (6 of 6), but without a definition the agent fails as it does without sharing (0 of 6). Overall, trajectory retrieval answers \DsTrajMirror\% and \system\ \DsCondMirror\% of the backup-copy questions: withdrawal is safe but forgoes knowledge that was still correct for some questions, the conservative unavailability also seen in the replay.}
{\emph{模型的边界。}重复装载被撤销但无法用过滤修复；日期键改写破坏日期连接的覆盖且没有修复候选，各方法在这里都很低（\system\ \ScenAccCondLatekey\%，轨迹检索 \ScenAccTrajLatekey\%，不共享 \ScenAccNoShareLatekey\%）。单位变化不违反任何条件，所有共享方法都继承这一错误（\system\ 为 \ScenAccCondUnit\%）。备份副本体现了撤下定义的代价。两个过滤都能同样恢复退货粒度，因此 \system\ 撤下退货金额定义，与退货表的连接失去唯一一侧的退货率定义也随之撤下。对退货金额这有帮助：智能体自己发现了备份行，9 题答对 8 题，而检索到的轨迹重放会重复计算的 SQL（9 题对 4 题）。对退货率这有损失：检索到的 SQL 碰巧不受重复影响（6 题全对），而没有定义的智能体与不共享时一样答错（6 题全错）。总体上，轨迹检索答对备份副本题的 \DsTrajMirror\%，\system\ 为 \DsCondMirror\%；撤下定义是安全的，但放弃了对部分题目仍然正确的知识，这正是回放中看到的保守不可用。}

\bi{\emph{Cost and declared use.} End to end, maintenance database time is dominated by repair searches, which condition-level and definition-level maintenance both perform (\ScenMaintCond\ versus \ScenMaintDef\,s per run, \ScenMaintRatio\%). Revoke-on-write spends no maintenance database time but relearns with \ScenRelearnTok\,M LLM tokens per run. Sharing shortens agent work on held-out questions from \ScenHoldTurnsNoShareModelA\ to \ScenHoldTurnsCondModelA\ turns per task and cuts input tokens by \ScenHoldTokSaveModelA\%. Execution-side checks apply only to declared uses: in our earlier runs, \DuUndeclPct\% of scored answers declared no definition, and \DuDevPct\% of the answers that declared a correct revision were still wrong because the agent's SQL deviated from it.}
{\emph{代价与声明使用。}端到端的维护数据库时间以修复搜索为主，条件级与定义级都要做（每次运行 \ScenMaintCond\ 秒对 \ScenMaintDef\ 秒，\ScenMaintRatio\%）。写入即撤销不花维护数据库时间，但每次运行用 \ScenRelearnTok\ 百万个大模型 token 重新学习。共享缩短了智能体在留出题上的工作：每题轮数从 \ScenHoldTurnsNoShareModelA\ 降至 \ScenHoldTurnsCondModelA{}，输入 token 减少 \ScenHoldTokSaveModelA\%。执行端检查只作用于声明了修订的使用：在此前的运行中，\DuUndeclPct\% 的计分答案没有声明任何定义；在声明了正确修订的答案中仍有 \DuDevPct\% 答错，原因是智能体的 SQL 偏离了定义。}

\bi{\emph{Other models.} An earlier run with the previous middleware, six methods, ten changes, and three LLMs shows the same pattern for each model: maintained sharing raised accuracy from \PrevScenAccNoShareModelA\% to \PrevScenAccCondModelA\% for DeepSeek V4.1 Flash, from \PrevScenAccNoShareModelB\% to \PrevScenAccCondModelB\% for GLM-5.3, and from \PrevScenAccNoShareModelC\% to \PrevScenAccCondModelC\% for GLM-5.3 Flash.}
{\emph{其他模型。}此前一轮使用旧版中间层、6 种方法、10 种变化和 3 个大模型的运行，在每个模型上呈现相同的规律：维护后的共享使 DeepSeek V4.1 Flash 的正确率从 \PrevScenAccNoShareModelA\% 提高到 \PrevScenAccCondModelA\%，GLM-5.3 从 \PrevScenAccNoShareModelB\% 提高到 \PrevScenAccCondModelB\%，GLM-5.3 Flash 从 \PrevScenAccNoShareModelC\% 提高到 \PrevScenAccCondModelC\%。}
