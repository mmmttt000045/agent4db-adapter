\subsection{\bt{Publication and consumer performance}{发布与使用者性能}}
\label{sec:sharing-eval}
\bi{\emph{What the publication checks reject (Q6).} In the runs of Section~\ref{sec:scenarios}, \PubJudged\ learning sessions produced an answer that matched the reference; the publication checks published \PubPromoted\ of them as new entries, \PubCorroborated\ confirmed an existing entry, and \PubRefused\ were rejected. Over these runs and the three-LLM round of Section~\ref{sec:validity} (\PubAllJudged\ sessions with a verified answer), the replay of the generated SQL rejected \PubReplayRefused\ candidates into which extraction had introduced an error, and the calculation check rejected \PubChainRefused\ whose recorded calculation does not reproduce the answer. Each rejection is an extraction error that would otherwise have reached every consumer. In the worst case, the extractor dropped the category filter of electronics store revenue: the agent had answered \PubExAnswer, and the generated SQL that later agents would have received returns \PubExCanon, \PubExRatio\ times as much. The producer's own SQL was correct; only checking what consumers will read catches the error.}
{\emph{发布前检查拒绝了什么（Q6）。}在第~\ref{sec:scenarios} 节的运行中，\PubJudged\ 条学习会话的答案与参考答案一致；发布前检查把其中 \PubPromoted\ 条发布为新条目，\PubCorroborated\ 条与已有条目一致，拒绝了 \PubRefused\ 条。在这些运行与第~\ref{sec:validity} 节的三模型一轮中（共 \PubAllJudged\ 条答案核对正确的会话），生成的 SQL 重放拒绝了 \PubReplayRefused\ 个在提取时被引入错误的候选，算式检查拒绝了 \PubChainRefused\ 个记录的算式无法复现答案的候选。每一次拒绝都是提取中真实出现的错误，放行就会传到每个使用者。最严重的一例中，提取器丢掉了电子品类门店营业额的类别过滤：智能体答的是 \PubExAnswer，而之后的智能体将拿到的生成的 SQL 返回 \PubExCanon，是它的 \PubExRatio\ 倍。生产者自己的 SQL 是对的；只有检查使用者将要读到的内容，才能发现这个错误。}

\bi{\emph{What consumers gain.} Building the memory costs \AmProdTokK\,k tokens and \AmProdS\,s per library for the ten learning sessions, extraction, and the publication checks, once. On held-out questions, timed per agent session from the first tool call to the final answer, a consumer with \system\ is \AmHoldSpeedup$\times$ faster than one exploring alone on the synthetic dataset and \GeHoldSpeedup$\times$ on TPC-H (\GsHoldSpeedupMin$\times$--\GsHoldSpeedupMax$\times$ and \GeHoldSpeedupMin$\times$--\GeHoldSpeedupMax$\times$ per run) and uses \AmHoldTokSave\% and \GeHoldTokSave\% fewer tokens per question (Figure~\ref{fig:consumer}), \AmCorrectTokSave\% fewer per correct answer on the synthetic dataset. Maintenance is paid once per change for all consumers, \AmMaintBenignS\,s of database time per non-breaking change and \AmMaintRepairS\,s per repaired one, whereas the self-verifying retrieval agent pays \AmVerifyExtraS\,s and \AmVerifyExtraTokK\,k tokens more in every task on unchanged data and non-breaking updates and is still less accurate under breaking changes.}
{\emph{使用者得到了什么。}每个定义库的建立代价是 \AmProdTokK\,k token、\AmProdS\ 秒（10 个学习会话、提取与发布前检查），只付一次。在留出题上（每个智能体会话从第一次工具调用计到给出最终答案），使用 \system\ 的使用者比独自探索快：合成数据上 \AmHoldSpeedup\ 倍，TPC-H 上 \GeHoldSpeedup\ 倍（每次运行分别为 \GsHoldSpeedupMin--\GsHoldSpeedupMax\ 倍与 \GeHoldSpeedupMin--\GeHoldSpeedupMax\ 倍），每题 token 分别少 \AmHoldTokSave\% 与 \GeHoldTokSave\%（图~\ref{fig:consumer}），合成数据上每个正确答案的 token 少 \AmCorrectTokSave\%。维护每次变化只为所有使用者付一次：每次正常变化 \AmMaintBenignS\ 秒数据库时间，每次需要修复的变化 \AmMaintRepairS\ 秒；而自行核验的检索智能体在数据不变和正常更新时每题都多花 \AmVerifyExtraS\ 秒和 \AmVerifyExtraTokK\,k token，在破坏性变化下仍然不如维护准确。}
