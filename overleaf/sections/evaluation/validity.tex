\bi{\emph{Library replay (Q3).} End-to-end results mix maintenance with what agents happened to learn. To isolate maintenance, we replay fixed libraries under every method on the same data: each of the eleven changes is applied from the same initial snapshot, and every affected scored question is answered with the generated SQL of the revision the method serves. The first set consists of \RpLibs\ libraries of 3--8 published definitions, \RpDefs\ in all, learned end to end by three LLMs (DeepSeek V4.1 Flash, GLM-5.3, and GLM-5.3 Flash), with \RpCondN\ questions per method. A question is \emph{correct}, \emph{wrong}, or \emph{invalidated}; an invalidation is \emph{correct} if the unmaintained definition would also have answered wrongly, and \emph{false} otherwise. Every method that rechecks conditions serves wrong answers only under the unit change, which no condition covers, whereas invalidation on schema change serves \RpSchemaWrongModeled\ wrong answers under the covered changes (Figure~\ref{fig:replay}). \system, the full recheck per definition, and a query cache over the check queries give the same outcome on every question (\RpSameCondDef\%), so their end-to-end differences come from what agents learned. dbt-style table tests (key uniqueness per table and referential tests on date and item keys, with every definition on a failing table invalidated) serve no wrong answer under the covered changes but cannot repair: they answer \RpTableCorrect\ questions against \RpCondCorrect, and acting on tables rather than definitions gives \RpTableUnneeded\ false invalidations against \RpCondUnneeded.}
{\emph{定义库回放（Q3）。}端到端结果把维护与智能体碰巧学到的内容混在一起。为了把维护单独拿出来，我们在同一份数据上用每种方法回放固定的定义库：十一种变化都从同一初始快照施加，每道受影响的计分题用该方法提供的版本的生成的 SQL 作答。第一组是三个大模型（DeepSeek V4.1 Flash、GLM-5.3、GLM-5.3 Flash）端到端学到的 \RpLibs\ 个定义库，各含 3--8 个已发布定义，共 \RpDefs\ 个，每种方法 \RpCondN\ 道题。每道题的结果为\emph{答对}、\emph{答错}或\emph{失效}；若未经维护的定义同样会答错，则该失效为\emph{正确失效}，否则为\emph{误失效}。凡重查条件的方法都只在任何条件都不覆盖的单位变化下给出错误答案，而只在模式变更时失效在条件覆盖的变化下给出 \RpSchemaWrongModeled\ 个错误答案（图~\ref{fig:replay}）。\system、整定义重查与缓存检查查询的查询缓存在每道题上的结果都相同（\RpSameCondDef\%），因此它们在端到端上的差别来自智能体学到的内容。dbt 式表级测试（每张表的键唯一性、日期键与商品键的引用测试，测试失败的表上的定义全部失效）在条件覆盖的变化下不给出错误答案，但不能修复：它答对 \RpTableCorrect\ 题，\system\ 答对 \RpCondCorrect\ 题；按表而不是按定义行动带来 \RpTableUnneeded\ 次误失效，\system\ 为 \RpCondUnneeded\ 次。}

\bi{\emph{Libraries not written for this paper.} The same replay runs on TPC-DS SF1 with the \TrDefs\ definitions that can be derived from the benchmark's 99 query templates and expressed by the structured implementation, of which \TrSeeded\ pass the publication checks; each definition's generated SQL plays the agent's learning SQL. The middle panel of Figure~\ref{fig:replay} matches the learned libraries: \system\ serves no wrong answer under the covered changes, repairs every affected definition under status-change rows, restatements, and SCD Type 2 (\TrCondRepairedTasks\ questions answered through a repair), and invalidates under duplicate loads, the date-key format change, and the backup copy; invalidation on schema change serves \TrSchemaWrongModeled\ wrong answers, and table tests repair nothing. Generated from a short schema description instead of written by hand, the eleven changes give all \GnDsGenQuestions\ TPC-DS questions the same outcome. On TPC-H, SSB, and BIRD financial, all \GnKept\ definitions derived from the benchmarks' queries with a nonzero learning answer pass the publication checks (bottom panel). The pattern is that of TPC-DS: \system\ answers \GnFiCondRepairedTasks--\GnSbCondRepairedTasks\ questions per schema through a repair, while invalidation on schema change serves \GnFiSchemaWrongModeled--\GnSbSchemaWrongModeled\ wrong answers per schema; \system's only such wrong answers, \GnCondWrongModeled\ of \GnCondN, come from a filter on a column that no condition reads. SSB's yyyymmdd keys skip numbers between months, so date-key contiguity fails in \GnSsbContigBad\ of \GnSsbMonths\ months and the key-range rule is refused there.}
{\emph{不是为本文编写的定义库。}同一回放也在 TPC-DS SF1 上运行，定义库取自该基准 99 个查询模板中能够导出、且结构化实现能够表达的 \TrDefs\ 个定义，其中 \TrSeeded\ 个通过发布前检查；每个定义的生成的 SQL 充当智能体的学习 SQL。图~\ref{fig:replay} 中间的面板与学到的定义库一致：\system\ 在条件覆盖的变化下不给出错误答案，在状态流水、更正保留旧行与缓慢变化维（类型 2）下修复了每一个受影响的定义（\TrCondRepairedTasks\ 道题经修复后作答），在重复加载、日期键格式变化与备份副本下使定义失效；只在模式变更时失效给出 \TrSchemaWrongModeled\ 个错误答案，表级测试一个也不能修复。改由简短的模式描述生成而不是手写这十一种变化，TPC-DS 的全部 \GnDsGenQuestions\ 道题结果都相同。在 TPC-H、SSB 与 BIRD financial 上，从基准查询导出、学习题答案非零的 \GnKept\ 个定义全部通过发布前检查（最下面的面板）。结果与 TPC-DS 相同：\system\ 每种模式经修复作答 \GnFiCondRepairedTasks--\GnSbCondRepairedTasks\ 题，只在模式变更时失效每种模式给出 \GnFiSchemaWrongModeled--\GnSbSchemaWrongModeled\ 个错误答案；\system\ 在这些变化下仅有的 \GnCondWrongModeled\ 个错误答案（共 \GnCondN\ 题）来自一个过滤，其读取的列没有条件检查。SSB 的 yyyymmdd 日期键在月与月之间跳号，\GnSsbMonths\ 个月中有 \GnSsbContigBad\ 个月不满足日期键连续，键范围改写因此在 SSB 上被拒绝。}

\bi{\emph{Repair and its limits.}\label{sec:repair-eval} Because the agent's learning SQL was verified only on the data of learning time, \system\ runs it and the replacement as of that time. With this test \system\ repairs every affected definition under status-change rows (\RpCurStatusCond\ of \RpCurStatusN\ questions correct) and restatements (\RpCurRevisionCond\ of \RpCurRevisionN) and answers \RpCurDimhistCond\ of \RpCurDimhistN\ SCD Type 2 questions. Run on current data (the last bar of each panel), the test refuses correct fixes wherever a restatement or SCD Type 2 change touches the learning period, because the agent's SQL is itself stale there: \RpCurPairOther\ instead of \RpCurPairCond\ of the \RpCurPairN\ questions are answered (\RpCurDiff\ points fewer, 95\% cluster-bootstrap interval \RpCurDiffLo--\RpCurDiffHi). The uniqueness rule matters under the backup copy, which appends a full copy of the returns table, marked by a source column, that keeps the old amounts of corrected returns. Filters on either source restore one row per return; without the rule, repair takes the first filter it finds, the backup, and the published revision answers two of four new questions wrongly for both return metrics. With the rule, repair finds both filters and invalidates, and the rule changes none of the \RpCondN\ other outcomes, because the status-change, restatement, and SCD Type 2 fixes are unique.}
{\emph{修复及其限度。}由于智能体的学习 SQL 只在学习时刻的数据上被判过对，\system\ 以学习时刻为基准，把它与替代版本一起执行。用这个测试，\system\ 在状态流水（\RpCurStatusN\ 道题中答对 \RpCurStatusCond\ 道）与更正保留旧行（\RpCurRevisionN\ 道中 \RpCurRevisionCond\ 道）下修复了每一个受影响的定义，缓慢变化维（类型 2）的 \RpCurDimhistN\ 道题答对 \RpCurDimhistCond\ 道。在当前数据上比较时（每个面板的最后一条），凡更正保留旧行或缓慢变化维（类型 2）触及学习期之处，智能体的 SQL 本身已经过期，测试便拒绝正确的修复：\RpCurPairN\ 道题中只答对 \RpCurPairOther\ 道而不是 \RpCurPairCond\ 道（少 \RpCurDiff\ 个百分点，按库整群自助 95\% 区间 \RpCurDiffLo--\RpCurDiffHi）。唯一性规则在备份副本下起作用：这一变化追加一整份退货表的副本（以来源列标记），副本保留被更正退货的旧金额。按任一来源过滤都能使每笔退货恰好一行；没有这条规则时，修复取搜索到的第一个过滤，即备份，发布的版本在两个退货指标的 4 道新题中都答错 2 道。有了这条规则，修复会找到两个过滤并使定义失效，而 \RpCondN\ 道其他题的结果没有任何变化，因为状态流水、更正保留旧行与缓慢变化维（类型 2）的修复都是唯一的。}

\bi{\emph{Setup (Q3).} We compare \emph{check-then-execute}, which checks the declared revision and then runs the query, with same-snapshot validation for store revenue at 200,000 rows. The violating write reloads four months of sales, duplicating their keys. Each probe query returns the definition's answer for one month together with the number of duplicated keys in that month, computed in the same statement and therefore on the same snapshot; an answer is a \emph{violation} if that count is positive. When the write commits between the check and the execution, check-then-execute answers on violating data in \SnPausePre\ of \SnTrials\ trials and same-snapshot validation in none, answering from the pre-write snapshot; when the write commits just before an unannounced call, check-then-execute still answers on violating data in \SnBeforePre\ trials because its version source has not yet observed the write, and same-snapshot validation rejects all \SnBeforeSnapRej.}
{\emph{设置（Q3）。}我们在 20 万行数据上比较\emph{先检查后执行}（先核对所声明的版本，再执行查询）与同快照验证，指标为门店营业额。违反条件的写入把四个月的销售重新装载一次，使其键重复。每条探针查询返回某个月的定义的答案，同时在同一条语句、因而在同一快照上算出该月重复键的个数；该数大于零即为\emph{违规}。写入在检查与执行之间提交时，先检查后执行在 \SnTrials\ 次中有 \SnPausePre\ 次在违规数据上作答，同快照验证一次也没有，它在写入前的快照上作答；写入刚提交、未经通知就调用时，先检查后执行仍有 \SnBeforePre\ 次违规，因为其版本来源尚未观察到这次写入，同快照验证 \SnBeforeSnapRej\ 次全部拒绝。}

\bi{\emph{Random concurrency.} Table~\ref{tab:stress} randomizes the interleaving. Without announcement, check-then-execute answers on violating data in \SnPreUnannMin--\SnPreUnannMax\% of answered queries, in at least \SnPreUnannTrials\ of \SnStressTrials\ trials, starting up to \SnUnannLagMax\,ms after the commit, the lag of its version source. Announcing the write immediately after commit narrows but does not close the window: \SnPreAnnViol\ violations remain, all from queries checked before the commit and executed after it. Same-snapshot validation has no violation in \SnSnapAnswered\ answered queries (95\% upper bound \SnSnapUpper\% per row), at the same median latency (\SnStressPFiftyLo--\SnStressPFiftyHi\,ms); the first query after a write takes \SnFirstSnap\ against \SnFirstPre\,ms, because the snapshot reuses the check results that maintenance recorded under unchanged versions.}
{\emph{随机并发。}表~\ref{tab:stress} 把交错随机化。不通知时，先检查后执行有 \SnPreUnannMin--\SnPreUnannMax\% 的作答落在违规数据上，\SnStressTrials\ 次试验中至少 \SnPreUnannTrials\ 次出现，违规始于提交后最多 \SnUnannLagMax\ 毫秒内，即其版本来源的滞后。写入提交后立即通知能缩小但不能关闭这个窗口：仍有 \SnPreAnnViol\ 次违规，全部来自提交前已通过核对、提交后才执行的查询。同快照验证在 \SnSnapAnswered\ 次作答中没有违规（每行 95\% 上界 \SnSnapUpper\%），中位延迟相同（\SnStressPFiftyLo--\SnStressPFiftyHi\ 毫秒）；写入后的第一条查询为 \SnFirstSnap\ 对 \SnFirstPre\ 毫秒，因为快照复用了维护在版本未变时记录的检查结果。}
